# 01_要件定義

## 背景

`backend/pyproject.toml` には mypy が dev dependency として導入済みで、`[tool.mypy]` に `pydantic.mypy` プラグインを指定した最小設定が存在する。しかし CI（`backend-tests.yml`）には mypy 実行ステップがなく、`ruff format` / `ruff check` / `pytest` のみが必須ゲートになっている。

型エラーを未調査のまま mypy を CI 必須化すると、エラー件数次第で後続作業（#140〜#142）の見積もりが立てられない。そのため、まず現状の型エラーを実行・分類し、段階導入の方針を固める必要がある。

## 機能要件

- `uv run mypy app tests` を backend ディレクトリで実行し、結果を記録する
- 検出されたエラーを mypy のエラーコード（`arg-type` / `attr-defined` / `union-attr` / `call-overload` 等）およびディレクトリ単位（`app/models` / `app/schemas` / `app/routers` / `app/services` / `app/repositories` / `app/core`）で集計する
- エラーの根本原因を調査し、以下の観点で分類する
  - import / missing stubs に起因するもの
  - SQLModel / SQLAlchemy の型推論の限界に起因するもの
  - Pydantic / FastAPI の型推論に起因するもの
  - Optional / None 安全性に起因する実バグの疑いがあるもの
  - test mock / AsyncMock 周辺に起因するもの
- 「今すぐ修正すべきエラー」と「設定（per-module override 等）で当面許容し段階的に扱うべきエラー」を分離して整理する
- 後続 Issue（#140 設定整備 / #141 エラー修正 / #142 CI 組み込み）それぞれが着手すべき対象範囲・順序を明確にする

## 非機能要件

- 調査結果は `docs/issue-139/` 配下に文書として残し、後続 Issue から参照できる状態にする
- 調査に用いた mypy 生ログは再現性のため保存する
- 本 Issue ではソースコードの型エラー修正は行わない（受け入れ条件が満たされていることを確認する調査タスクのため）

## スコープ外

- 大量の型エラー修正
- CI への mypy 必須化（ワークフローファイルの変更）
- strict mode の全面適用

## 移植方針

本 Issue は移植作業ではなく、backend 自体の型チェック運用整備に向けた現状調査。

- `uv run mypy app tests` を実行し、エラーをエラーコード別・ディレクトリ別に集計する
- 集計結果から、エラーの大半（423/435件）が `app/repositories` に集中していることを確認し、原因を特定する
  - SQLModel のモデルフィールドは mypy 上では宣言した Python 型（`str` / `datetime` / `UUID` / `bool` 等）としてしか認識されず、`Model.field == value` のような SQLAlchemy 的なカラム比較や `.where()` / `.join()` / `.in_()` / `.desc()` / `.asc()` / `.is_()` / `.label()` 呼び出しが「plain な Python 値に対する操作」として型エラーになる（SQLModel 側に InstrumentedAttribute を返す mypy プラグインが存在しないための構造的な限界）
  - このパターンで `arg-type`（249件）/ `attr-defined`（95件のうち89件）/ `union-attr`（48件）/ `call-overload`（27件）/ `dict-item`（4件）/ `operator`（1件）の大部分（実測: 234件が `incompatible type "bool"` に起因）を説明できる
- 上記構造的エラーとは別に、Optional/None 安全性に関する実バグ疑いのエラーが2件、`app/services` 配下で検出された
  - `app/services/index_service.py:594`（`str | None` を `str` 引数へ渡している）
  - `app/services/message_service.py:1028`（`None` を `MessageContentResponse` 型変数へ代入している）
- `app/models` / `app/schemas` / `app/routers` / `main.py` は現時点でエラー 0 件であり、CI への mypy 導入の第一段階として対象にしやすい
- 詳細な集計・分類結果は `03_詳細設計.md` に記載する

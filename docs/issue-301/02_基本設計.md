# 02_基本設計

## 変更対象

| 対象 | 内容 |
|---|---|
| 社内側の Compose（新設） | server-local・Waha! エミュレーター・ベクトルDB を 1 つの Compose で起動する。プロジェクト名は既存と別にする |
| ベクトルDB のイメージ（新設） | 移植元の検証環境と同じく、pgvector の PostgreSQL 16 に PGroonga と Apache AGE を入れる。初回起動時に拡張と AGE のグラフを作る |
| ファイルサーバーの代わり（新設） | サンプル文書を置くディレクトリ。エミュレーターに読み取り専用で見せる |
| クラウド側の seed（新設） | backend の動作確認用テナントに、SECURE アシスタント・LOCAL_SERVER エンドポイントと紐付けを登録する |
| README（新設・追記） | 社内側の README を新設し、ルートの README から案内する |

## 画面 / API 変更概要

API・画面の変更はない。

### サービスと接続

| サービス | 表すもの | 公開ポート（ホスト） |
|---|---|---|
| server-local | 社内の SECURE の窓口 | 18090 |
| waha-emulator | Waha!（とアダプタ）の代わり | 18091 |
| vector-db | アダプタが使うベクトルDB | 15432 |

- server-local → エミュレーター: Compose のネットワーク内のサービス名で呼ぶ。認証キーは両方に同じ既定値を渡す
- ストリームファイル: 名前付きボリュームを、両方のコンテナの同じパス（server-local がファイルを作るディレクトリ）にマウントする。同じパスで見えるため、パスの読み替えは不要。名前付きボリュームは初回にイメージ側のディレクトリ（uid 1000 所有）で初期化されるため、事前のディレクトリ作成も不要
- server-local → クラウド側 backend: ホストの backend の公開ポート（ルートの compose の 8001）を、コンテナからホストを指す名前で呼ぶ。Linux でもホストを解決できるよう、ホストの名前を明示的に足す
- ブラウザ → server-local: ブラウザはホストで動くため、LOCAL_SERVER エンドポイントの URL は `http://localhost:18090/`、API キーは server-local の認証キー

### 既定値

| 項目 | 既定値 | 変える方法 |
|---|---|---|
| server-local の認証キー（LOCAL_SERVER の API キー） | ローカル用の固定値 | `.env` |
| エミュレーターの認証キー | ローカル用の固定値 | `.env` |
| クラウド側 backend の URL | ホストの 8001 | `.env` |
| LLM | echo（キー不要） | `.env`（Azure OpenAI） |
| ベクトルDB の DB 名・ユーザー・パスワード | ローカル用の固定値 | なし（ローカル検証専用） |

## 影響範囲

- 既存のコード・Dockerfile・Compose は変更しない
- ルートの compose・server-local / エミュレーター単体の compose とは、プロジェクト名・コンテナ名・ポート・ボリューム名が異なるため同時に動かせる（server-local 単体 8090・エミュレーター単体 8091 とも衝突しない）
- backend の seed は別ファイルにし、既存の `seed.sql` の後に流す。既存の seed は変更しない

## 移植方針

- ベクトルDB は、移植元 `generative-ai-adapter` の Waha! 手動検証環境（`docker/waha-embedding-graph/`）と、そこがビルドするイメージ（`embedding-adapter/src/test/docker/graph-db/Dockerfile`）に合わせる
  - 基底イメージ・PGroonga と AGE の版は移植元と同じ
  - 拡張は vector・pgroonga・age の 3 つ。手動検証環境の初期化 SQL は vector と age だけだが、イメージには PGroonga が入っており、移植元のアダプタ本体（検索のハイブリッド検索・Graph RAG の初期化）が PGroonga を使うため、統合テスト用の初期化 SQL と同じく 3 つとも作る
  - グラフ名は移植元の手動検証環境と同じ `embedding_graph`
  - 移植元の手動検証環境は Waha!（Windows）から `localhost:5432` 固定で接続するため 5432 を使うが、こちらはエミュレーターから Compose のネットワーク内で接続し、ホストの公開は確認用の 15432 にする
  - 移植元の GraphRAG のマイグレーション（アダプタ側の `migrations/`）は、アダプタを取り込む Issue で扱う
- 移植元の vector-only の DB（AGE なしの失敗系の検証用）は、統合テスト用のため含めない
- クラウド側の seed を `backend/seed.sql` に追記せず社内側のディレクトリに置くのは、LOCAL_SERVER の URL・API キーが社内側の Compose の公開ポート・既定の認証キーに依存し、一緒に変える必要があるため。並行する Issue の seed 追記とも衝突しない

# 02_基本設計

## 変更対象

- `backend/app/routers/indexes.py`（エンドポイント追加）
- `backend/app/services/index_service.py`（ビジネスロジック追加）
- `backend/app/services/file_service.py`（ファイル作成の共通ロジックをcore層へ抽出するリファクタ）
- `backend/app/repositories/message_feedback_repository.py`（ID単体取得メソッド追加）
- `backend/app/schemas/index.py`（追加学習用フォームスキーマ追加）
- `backend/app/core/`（ファイル作成共通ロジックの新規モジュール追加）

## 画面 / API 変更概要

- `POST /api/admin/indexes/{id}/sync`
  - 常に400エラー（「ファイル一括同期機能はローカルAPIサーバしか対応していません。」）を返すスタブ。
- `POST /api/admin/indexes/{id}/additionalLearning`
  - `multipart/form-data`（`feedbackId`・`roomId`・`content`）を受け取り、インデックス配下にファイルを新規作成する。
  - 成功時は204 No Contentを返す。
  - `feedbackId`/`roomId`の相関バリデーション、インデックス存在確認・`LOCAL`タイプ拒否・クレジット上限チェックを行う。
  - `feedbackId`指定時は、対象`MessageFeedback`の`index_id`を更新する。

## 影響範囲

- `routers/indexes.py`は既存同様`IndexService`のみに依存させる（router:service 1対1規約を維持するため、`FileService`は直接呼ばない）。
- `FileService.create_file`が内部で行っている「ストレージへの保存＋`File`エンティティ作成」処理（`_save_to_storage_and_create`）は、`IndexService`側の追加学習でも必要になる。サービス間呼び出し（`xxx_service.py`が別の`yyy_service.py`を呼ぶ構造）は規約で禁止されているため、この処理を`core/file_creation.py`という新規モジュールに切り出し、`FileService`・`IndexService`の双方から呼び出す（`core/credit_quota.py`が複数サービスで共有される既存パターンと同様）。
- この抽出により`FileService`のプライベートメソッド`_save_to_storage_and_create`・`_ensure_not_local`は削除し、呼び出し元を`core.file_creation`経由に置き換える（外部から見た`FileService`の公開APIの挙動に変更はない）。
- `MessageFeedbackRepository`にテナントIDを条件に含めたID単体取得メソッドを追加する（既存メソッドは複数ID・複数条件の一覧取得のみで、単体取得が無かったため）。

## 移植方針

- 移植元Javaの`FileService.syncFiles`・`FileService.additionalLearning`のロジックをそのまま踏襲する。
  - バリデーションメッセージ・ファイル名/reference文字列の組み立てルールは移植元の文字列をそのまま使用する（reference文字列がroomId指定時も「フィードバック_」接頭辞のままである点を含め、意図的なバグ修正はスコープ外として行わない）。
- 例外は移植元の`BadRequestException`・`EntityNotFoundException`をFastAPI版の`HTTPException`（400/404/429）にマッピングする（Issue #87の`create_file`と同じマッピング方針を踏襲）。
- `feedbackId`指定時の`MessageFeedback.index_id`更新は、既存の`MessageFeedbackRepository.save`を再利用する。

# 02_基本設計

## 構成（移植元に合わせる）

```
サーバーのコンテナ（1 つ）
├─ uvicorn（FastAPI）  ──HTTP（127.0.0.1:9998）──▶  Tika サーバー（java -jar、子プロセス）
└─ /opt/tika-server.jar（ビルドのときに取得・検証）
```

- 移植元（Java）は、Tika をサーバーのプロセスの中で使う。Python は、Java のライブラリを直接は呼べないため、同じコンテナの中で、子プロセスとして起動し、`localhost` で呼ぶ。コンテナ（デプロイの単位）は、1 つのまま
- 別のサービス・サイドカーは、作らない

## 変更対象

- サーバーのコンテナのイメージ（`Dockerfile`・`Dockerfile.dev`）: JRE と jar を追加
- アプリの設定: Tika の設定を追加
- Tika を呼ぶ部品（新規）: 遅延起動・HTTP の呼び出し・終了
- 学習データ登録の取り出し: Tika が使えるときは Tika、そうでなければ従来
- アプリの起動・終了（`lifespan`）: 終了時に子プロセスを止める

## 流れ

1. 学習データのファイルを登録する
2. 取り出しの設定を確かめる（`TIKA_URL` → `TIKA_SERVER_JAR` → なし）
3. Tika を使う場合: 起動していなければ起動して待つ → `PUT /tika`（ファイル名・Content-Type・本文）→ テキストを受け取る
4. 以降は #462 と同じ（分割・埋め込み・保存）

## 影響範囲

- コンテナのサイズが、JRE と jar の分、増える。本番のメモリが、Tika の JVM の分、増える（ヒープの上限 256MB。遅延起動なので、取り出しを使うまでは、増えない）
- Tika の設定がない環境（CI の単体テストなど）は、今のまま

## 移植方針

- 移植元と同じ Tika 3.1.0。取り出しの結果の形（本文のテキスト）は、同じ
- 移植元は、jar をビルドの依存として持つ。移植先は、ビルドのときに取得して、チェックサムで検証する

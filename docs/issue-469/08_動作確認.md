- macOS、`feature/issue-469`、Docker（ローカルの compose）
- テストは `server/` の `uv run pytest`（Tika への HTTP と子プロセスはモック）
- 実機: 開発用イメージ（`Dockerfile.dev`）と本番用イメージ（`Dockerfile`）をビルドし、コンテナの中の実際の Tika 3.1.0 で確認した。Bedrock の埋め込み・回答は本物

## 確認手順

1. Tika の jar を公式から取得し、公式の `.sha512` と一致する SHA-512 を確かめて、Dockerfile に固定する
2. 開発用・本番用のイメージをビルドする（ビルドの中で、チェックサムの検証が通る）
3. コンテナの中で、Java・jar の存在と、チェックサム・環境変数を確かめる
4. PDF・Word・Excel・PowerPoint を作り、API で登録して、取り出し・保存・質問を確かめる
5. Java のプロセス・ヒープの上限・メモリを確かめる

### JVM のヒープとメモリ

- Tika は、**親（監視役）と子（実際に処理する側）の 2 つの JVM** で動く。最初は、`-Xmx256m` が親にだけ効き、**子にヒープの上限がついていない**ことを、実機で見つけた（`java -Xmx256m -jar …` の子の起動の引数に `-Xmx` がなかった）
- Tika 3.1 の `-J` は未対応で、子の JVM の引数は、設定ファイル（`-c`）の `forkedJvmArgs` で渡す仕組み。**実行時に設定ファイルを作り**、子に `-Xmx{TIKA_HEAP}`（既定 256m）、親に `-Xmx64m` を付ける形に直した
- 修正後（実機）: 親 `-Xmx64m`（メモリ使用 約 100MB）、子 `-Xmx256m`（約 220MB）。Tika 全体で約 320MB。開発用コンテナ全体で約 590MB（`--reload` など込み）

### 文字コードとファイル名（実際の Tika）

- UTF-8・UTF-8 の BOM つき・Shift_JIS の日本語のテキスト（短い 1 行も含む）を、Tika で取り出し、いずれも**文字化けなく**、元の文章と一致した
- ファイル名の渡し方（`Content-Disposition: attachment; filename*=UTF-8''…`、RFC 5987）を、Tika が正しく読み、`resourceName` に日本語のファイル名（`報告.csv`）が復元された。`filename=` との併記も同じ結果

### 複数の worker・再読み込み・終了

- すでに応答する Tika があるとき（別の worker が起動済み、コードの再読み込みで前のプロセスが残った場合など）は、起動せずに借りる。借りた先が落ちたときは、その呼び出しが 503、次の呼び出しで自分で起動する（単体テストで確認）
- 開発用の `--reload` でコードを再読み込みすると、古い Tika が止まり、新しく起動し直される（プロセス番号が変わることを実機で確認）。終了処理は、リスナーの停止のあと、`finally` で行う

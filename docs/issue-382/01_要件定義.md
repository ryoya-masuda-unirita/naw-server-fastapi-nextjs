# 01_要件定義

## 背景

- インフラ定義が 1 つのディレクトリにフラットに並んでおり、ネットワーク・データストア・実行基盤・配信・CI 用の権限が混在している。親 Issue（#380）では、移植元と同じ「モジュール + 環境」の構成に揃えて、以降の設定値の変更（Fargate 化、Secrets Manager、CloudFront など）を、関心ごとに分けて進められるようにしたい
- 以降の Issue（変数化、Fargate 化、設定値の変更）は、モジュールが分かれていることを前提にする。ここで構成だけを先に変えておけば、後の差分が「構成の変更」と「設定値の変更」に混ざらず、レビューしやすい
- 移植先は、別の AWS アカウントに新規構築する。既存の state やリソースは引き継がないので、リソースの移動を state に反映する作業は要らない

## 機能要件

1. インフラ定義を、再利用できる単位（モジュール）と、それらを組み合わせる環境（dev）に分けること
   - ネットワーク（VPC・サブネット・ルート・セキュリティグループ）
   - データベース、キャッシュ、コンテナレジストリ
   - ロードバランサ
   - コンテナ実行基盤（クラスタ・タスク・サービス・関連する権限）
   - 画面の配信（静的ファイルのバケット・CDN・配信用の関数）
   - CI から使う権限（OIDC プロバイダとロール）
   - 踏み台サーバー
   - ユーザー一括取込用のバケットとキュー
2. 環境（dev）の構成が、モジュールの入出力だけで組み立てられていること。モジュール同士が互いのリソースを直接参照しないこと
3. 分けた前後で、作られるリソースの種類・名前・設定値・タグが変わらないこと（差分は、モジュールをまたぐための入出力に限る）
4. 変数の名前・既定値、環境から外に出す出力の名前は、現状のまま維持すること（CI や手順書が使っているため）
5. CI・手順書・ローカルの作業手順が、新しいディレクトリ構成で動くこと
   - インフラのデプロイのワークフローの作業ディレクトリ
   - 配信用の関数の単体テストの実行場所
   - state の接続設定ファイルの置き場所

## 非機能要件

- フォーマットと構文の検証が、各モジュールと環境で通ること
- 移植元の分け方に揃えるが、循環参照が起きる場合は、循環を避ける分け方を優先する（理由を文書に残す）
- AWS のプロファイルは設定ファイルに固定しない（#381 の方針を維持）

## スコープ外

- 設定値の変更（#384〜#387）、アカウント ID・プロジェクト名の変数化と `default_tags`（#383）、CI ロールの権限の見直し（#388）
- state の移行（`moved` ブロックを含む）。同じアカウントの既存リソースへ適用することは想定しない
- 別 state のホストゾーン用ディレクトリの削除（#383）
- ECS の Fargate 化、NAT の追加、Secrets Manager の導入

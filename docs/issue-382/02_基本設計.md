# 02_基本設計

## 変更対象

### 環境（dev）とモジュールの分け方

| 単位 | 含めるもの |
|---|---|
| network | VPC、サブネット（public / private）、インターネットゲートウェイ、ルートテーブル、セキュリティグループとそのルール（ALB・ECS・RDS・キャッシュ・踏み台） |
| rds | DB サブネットグループ、PostgreSQL |
| elasticache | キャッシュのサブネットグループ、Redis |
| ecr | backend のコンテナレジストリ |
| alb | ロードバランサ、ターゲットグループ、HTTP リスナー |
| ecs | クラスタ、起動テンプレート・Auto Scaling グループ・キャパシティプロバイダ、ログ、タスク定義（backend・マイグレーション）、サービス、実行ロール・インスタンスロール・タスクロール |
| frontend | 静的ファイルのバケット、OAC、バケットポリシー、CloudFront ディストリビューション、配信用の関数 2 本（SPA フォールバック・認証 API の prefix 除去）と、その単体テスト |
| github-actions | OIDC プロバイダ、ロール、ポリシー |
| bastion | AMI の検索、踏み台のインスタンス |
| user-import | ユーザー一括取込用のバケットと SQS（DLQ 付き） |
| 環境（dev） | state の接続設定、provider、変数、各モジュールの呼び出し、出力 |

### 移植元との分け方の違い

- ロードバランサを、コンテナ実行基盤から独立させる。移植元は同じモジュールにあるが、このリポジトリでは「ECS のタスクが CDN のドメイン（CORS 設定）を使い、CDN が ALB のドメインをオリジンに使う」ため、ALB が ECS と同じモジュールにあるとモジュール同士が循環する。独立させれば、ALB → CDN → ECS の一方向になる
- セキュリティグループは移植元と同じく network にまとめる（踏み台の分も含む）
- 移植元の secrets・dns・data-aws-existing に当たるモジュールは作らない（secrets は #386、dns はサブドメイン廃止、既存参照は不要）。踏み台・user-import・github-actions は、このリポジトリ独自の要素として独立したモジュールにする

## 画面 / API 変更概要

なし（インフラ・CI のみ）。

## 影響範囲

- **作業ディレクトリ**: インフラの操作は、環境（dev）のディレクトリで行う。手元の変数ファイル・初期化済みの作業ファイル・state 接続設定ファイルは、新しい場所に置き直す必要がある
- **CI**: インフラのワークフローの作業ディレクトリ、配信用の関数のテストの実行パスを直す。push で動く判定は、インフラのディレクトリ配下の変更を見ているので変わらない
- **手順書**: 構築手順、state 用バケットの出力から接続設定ファイルを作る手順を直す
- **出力**: 環境から外に出す出力は名前を維持する。ワークフローや手順書が参照している
- **リソースの名前**: 変えない。新アカウントに新規構築する前提なので、分割による再作成は問題にならない
- **後続の Issue**: #383 以降は、この構成の上で進める

## 移植方針

- 移植元の「モジュール + 環境」の構成に揃え、モジュールは入力・出力・本体（変数、リソース、出力）に分ける
- リソース本体の内容は、元のファイルからそのまま移す。別のモジュールのリソースを参照していた箇所だけを、変数（入力）に置き換える
- 移すリソースの網羅性は、元の定義と新しい定義のリソースの対応表と、内容の差分（入出力に置き換えた行のみが違うこと）で確認する

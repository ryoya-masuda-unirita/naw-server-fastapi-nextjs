## Terraformコードの実装ミス（apply〜動作確認で判明したもの）

初回の`terraform apply`自体は成功したが、以下は**applyのエラーにはならず、デプロイ・動作確認の段階で初めて顕在化した**実装ミス。いずれも修正してコミット済み。

### 1. ACM検証レコードの重複作成エラー

- **症状**: `terraform apply`時に`InvalidChangeBatch: ... but it already exists`でRoute53レコード作成が失敗
- **原因**: `acm.tf`の`aws_route53_record.cert_validation`が`domain_validation_options`を`for_each`で回す際、ベースドメインとワイルドカードドメインの検証用CNAMEが**同一名・同一値**になる。素朴な実装だとRoute53側で重複作成エラーになる
- **修正**: `allow_overwrite = true`を追加し、同一レコードをUPSERT（冪等）させる（HashiCorp公式の定番パターン）
- **教訓**: `for_each`のキーを検証レコード名（`resource_record_name`）に変えて重複を1エントリに集約する対処も試したが、これは`for`式内でキー重複エラーになり逆効果だった。`allow_overwrite`のみが正しい解

### 2. ECSのEC2がインターネットに出られない（public IP未付与）

- **症状**: ECSタスクが`PROVISIONING`のまま進まず、`registeredContainerInstancesCount`が0のまま
- **原因**: `ecs.tf`の`aws_launch_template`が`vpc_security_group_ids`のみでネットワークインターフェースの設定がなく、publicサブネットに配置していても**public IPが付与されていなかった**。そのためECSエージェントがECS API・ECRに到達できず、クラスタに登録すらできていなかった
- **修正**: `vpc_security_group_ids`を`network_interfaces { associate_public_ip_address = true, security_groups = [...] }`に置き換え

### 3. 全セキュリティグループにegressルールが1つもなかった

- **症状**: 上記2を修正してpublic IPを付与した後も、まだECSがクラスタに登録できなかった。また、bastion経由でRDSにSSHトンネル接続しても`psql`がハングして応答が返らなかった
- **原因**: `security_groups.tf`で定義した5つのSG（bastion, alb, ecs, rds, elasticache）すべてに**egress（アウトバウンド）ルールが1つも定義されていなかった**。Terraformで`aws_security_group_rule`を使う場合、AWSのデフォルトである「egress全許可」は適用されず、明示的に書かないと**egressが完全に塞がれる**。ingressだけ書いて満足し、egressを書き忘れていたのが根本原因
- **修正**: 各SGにegressルールを追加（詳細は次項）
- **教訓（誤った判断も含む）**:
  - 当初「RDS/ElastiCacheはingressのみで自発的な発信は不要なはずなのでegress不要」と判断したが、**実際にはRDSへのbastion経由接続がegress不足でハングしており、この判断は誤りだった**。動いた事実（`select 1`成功）でしか正しさは確認できない
  - その後、逆にセキュリティを意識してALB/bastion/ECS/RDS/ElastiCache全てのegressをポート単位（443番のみ等）に絞る修正を行ったが、**RDS/ElastiCacheについては「絞って何が壊れるか」を実際に検証しないまま進めるのはリスクが高いと判断**し、最終的に以下の方針に落ち着いた

### 最終的なegress設計方針

| SG | egress | 理由 |
|---|---|---|
| bastion | RDSへの5432番（SG参照）+ 443番 | 用途が明確（DB接続・OS更新）で確実に絞れる |
| ALB | ECSへの8000番のみ（SG参照） | ALBはbackendへの転送以外の通信をしない |
| ECS | 全許可（`0.0.0.0/0`, 全ポート） | ECR/ECS API/CloudWatch Logs等、広範囲かつ変わりうるAWS管理IPに依存するため、狭めると壊れるリスクの方が大きいと判断 |
| RDS | 全許可（`0.0.0.0/0`, 全ポート） | 一度「不要」と誤判断してハマった経緯があり、追加の検証コストをかけずリスクを避ける方針とした |
| ElastiCache | 全許可（`0.0.0.0/0`, 全ポート） | 同上 |

ingress（インバウンド）は当初から一貫してIPまたはSG参照で厳密に絞ってあり、変更していない。今回の一連の問題・修正はすべてegress（アウトバウンド）側の設計・実装漏れに起因する。

## destroy時にハマったポイント

- `force_destroy`/`force_delete`をS3・ECRに追加したコードは、**一度applyしないとstateに反映されない**。追加した直後にdestroyだけを実行すると、`BucketNotEmpty`/`RepositoryNotEmptyException`で失敗する。応急処置として`aws s3 rm --recursive`・`aws ecr batch-delete-image`で直接中身を空にしてから`destroy`を再実行した
- ASGのインスタンスが`Terminating:Wait`のまま進まなくなり、`aws_autoscaling_group`のdestroyがタイムアウトすることがあった。EC2実体は`terminated`済みなのにASG側のライフサイクル状態が更新されない状態で、`aws autoscaling delete-auto-scaling-group --force-delete`で強制削除して解消した
  - 教訓: ASG配下のEC2を手動terminateする際は、**先にASGの`desired_capacity`が0になっていることを確認してから**行う。そうしないとASGが「補充が必要」と判断し、新しいEC2を自動で作り直してしまう（今回実際に発生した）

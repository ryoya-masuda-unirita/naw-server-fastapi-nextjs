# 02_基本設計

## 変更対象

- 新規ディレクトリ`infra/`（Terraformコード一式）
- リポジトリの`.gitignore`（`*.tfstate`・`*.tfvars`・`.terraform/`等を追加）
- 既存のAWSリソース・アプリケーションコードへの変更はなし

## ディレクトリ構成（案）

```
infra/
├── main.tf              # providerブロック、rootモジュール呼び出し
├── variables.tf          # ルート変数（region、プロジェクト名、DBパスワード等）
├── outputs.tf             # ALB DNS名、CloudFrontドメイン名等の出力
├── terraform.tfvars.example  # 変数の記入例（実値は各自のterraform.tfvarsに、gitignore対象）
└── modules/
    ├── network/          # VPC・サブネット・IGW・ルートテーブル・SG
    ├── ecr/               # ECRリポジトリ
    ├── frontend/          # S3・CloudFront・OAC
    ├── database/          # RDS・DBサブネットグループ
    ├── cache/             # ElastiCache・サブネットグループ
    ├── bastion/           # 踏み台EC2・キーペア
    ├── ecs/               # ECSクラスタ・ASG・タスク定義・サービス
    ├── alb/               # ALB・ターゲットグループ
    └── acm/               # ACM証明書（us-east-1プロバイダエイリアス使用）
```

- モジュール分割は学習教材としての見通しの良さを優先する（Issue #158で「リソース種別ごとにセクションを分けて構築した」経験と対応させやすくするため）
- 初回はモジュール化せず単一の`.tf`ファイル群からスタートし、慣れてきたら`modules/`に切り出す、という段階的な進め方も選択肢にする（詳細設計時に相談）

## tfstateの管理方針

- **今回はローカルのtfstateファイル運用とする**（`infra/terraform.tfstate`、`.gitignore`で除外）
- 理由: S3バックエンド化は「バックエンド自体を最初に手動 or 別のterraformで作る」という鶏卵問題があり、初学者にとって最初の一歩としては複雑。まずローカルで一通り`plan`/`apply`/`destroy`のサイクルを体験することを優先する
- 将来的にS3バックエンド化する場合は、別チケットで対応する

## 認証情報の方針

- Terraform実行時のAWS認証は、Issue #158で作成済みの作業用IAMユーザー（プロファイル`naw-fastapi-issue158`）をそのまま使う（`AWS_PROFILE`環境変数、またはproviderブロックの`profile`引数で指定）
- RDSマスターパスワード等の秘匿情報は`variables.tf`で`sensitive = true`の変数として宣言し、実値は`terraform.tfvars`（gitignore対象）に記載する

## 移植方針（Issue #158からの変換ルール）

`docs/issue-158/構築済みリソース一覧.md`の実際の設定値を、対応するTerraformリソースにそのまま変換する。主な対応関係:

| Issue #158（実績値） | Terraformリソース |
|---|---|
| VPC `10.0.0.0/16` | `aws_vpc` |
| サブネット2つ（`10.0.1.0/24`・`10.0.2.0/24`） | `aws_subnet`（`for_each`または個別リソース） |
| セキュリティグループ5つ | `aws_security_group` + `aws_security_group_rule`（相互参照の順序に注意。Issue #158でも一部SGが依存関係エラーで即削除できなかった経験あり） |
| ECR `naw-fastapi-issue158-backend` | `aws_ecr_repository` |
| RDS `db.t4g.micro` | `aws_db_instance`（`skip_final_snapshot = true`、`publicly_accessible = false`） |
| ElastiCache `cache.t4g.micro` | `aws_elasticache_replication_group`（Issue #158の削除時、`cluster`ではなく`replication_group`として管理されていたことが判明済み） |
| ECS クラスタ・ASG・タスク定義・サービス | `aws_ecs_cluster`/`aws_autoscaling_group`/`aws_ecs_task_definition`/`aws_ecs_service` |
| ALB・ターゲットグループ | `aws_lb`/`aws_lb_target_group`/`aws_lb_listener` |
| ACM証明書 | `aws_acm_certificate`（`provider = aws.us_east_1`のエイリアス使用） |

## 影響範囲

- 既存のアプリケーションコード（`backend/`・`frontend/`・`frontend-angular/`）には影響しない
- 既存のGitHub Actions（`backend-tests.yml`・`project-status-sync.yml`）には影響しない
- 新規にAWS利用料が発生するが、Issue #158と同様「動作確認後は`terraform destroy`で全削除」する運用のため、恒久的な固定費用は発生しない

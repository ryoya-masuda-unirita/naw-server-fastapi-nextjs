# 03_詳細設計

## ファイル構成（確定版・段階的にモジュール化する前提の単一ファイル群）

```
infra/
├── main.tf                    # terraformブロック・providerブロック（ap-northeast-1 + us-east-1エイリアス）
├── variables.tf                # 変数定義（region、プロジェクト名、DBパスワード、allowed_ssh_cidrs、allowed_admin_cidrs、key_pair_name、domain_name等）
├── outputs.tf                  # ALB DNS名・CloudFrontドメイン名・RDSエンドポイント・Route53 NS等の出力
├── network.tf                  # VPC・publicサブネット2つ・privateサブネット2つ（RDS/ElastiCache用）・IGW・public/private双方のルートテーブル
├── security_groups.tf          # セキュリティグループ5つ
├── ecr.tf                       # ECRリポジトリ
├── s3_cloudfront.tf             # S3バケット・CloudFront・OAC・ALBオリジン/ビヘイビア
├── rds.tf                       # RDSインスタンス・DBサブネットグループ（privateサブネット使用）
├── elasticache.tf               # ElastiCache（replication_group）・サブネットグループ（privateサブネット使用）
├── bastion.tf                   # 踏み台EC2（AMIはdata "aws_ami"で最新のAmazon Linux 2023 arm64を取得、キーペアはコンソールで事前作成しkey_pair_name変数で参照）
├── iam.tf                       # ECSタスク実行ロール・EC2インスタンスロール・インスタンスプロファイル
├── ecs.tf                       # ECSクラスタ・Launch Template・ASG・Capacity Provider・ロググループ・タスク定義・サービス
├── alb.tf                       # ALB・ターゲットグループ・リスナー
├── route53.tf                   # Route53ホストゾーン（secuaigent-ryoyamasuda.tech）。ムームードメイン側のネームサーバー変更のみ手動
├── acm.tf                       # ACM証明書（`provider = aws.us_east_1`）、DNS検証はaws_route53_recordで自動化
├── terraform.tfvars.example    # 変数の記入例（実値は各自のterraform.tfvarsへ）
└── .gitignore                  # *.tfstate*・*.tfvars（.exampleを除く）・.terraform/
```

- 依存関係はTerraformが`resource`間の参照から自動解決するため、ファイルを分けても実行順序の問題は起きない
- 学習しやすさのため、ファイル名はIssue #158の作業フェーズ（0: ネットワーク・SG・ECR、1: RDS・ElastiCache・踏み台、2: ECS、3: ALB・CloudFront・ACM・Route53）とおおよそ対応させている
- 設計時点からの主な変更点（実装を進める中で判明・決定した内容）
  - RDS/ElastiCacheをpublicサブネットではなくprivateサブネットに配置する方針に変更（bastion/ECSからはVPC内`local`ルートで到達可能なためNAT Gatewayは不要）
  - ALBのSGを`0.0.0.0/0`許可から、CloudFrontマネージドプレフィックスリスト（`pl-58a04531`）＋`allowed_admin_cidrs`（動作確認用の作業者IP）の2ルールに変更
  - bastionのキーペアはTerraform管理（`aws_key_pair`）ではなく、コンソールで事前作成したキーペアを`key_pair_name`変数で参照する方式に変更（秘密鍵をTerraform管理下に置かないため）
  - ムームードメインで取得したドメイン`secuaigent-ryoyamasuda.tech`のDNS管理をRoute53に委任し、ACM証明書のDNS検証・CloudFrontのAレコードをTerraformで自動化する方針を追加（ムームードメイン側のネームサーバー変更のみ手動操作が必要）

## 主要リソースの設計詳細（Issue #158実績値からの変換）

### network.tf

- `aws_vpc`: CIDR `10.0.0.0/16`
- `aws_subnet` × 2: `10.0.1.0/24`（ap-northeast-1a）・`10.0.2.0/24`（ap-northeast-1c）、`map_public_ip_on_launch = true`（Issue #158でデフォルト無効な点にハマったため、Terraformでは明示指定して事故を防ぐ）
- `aws_internet_gateway`・`aws_route_table`（`0.0.0.0/0` → IGW）・`aws_route_table_association` × 2

### security_groups.tf

- `sg-bastion`/`sg-alb`/`sg-ecs`/`sg-rds`/`sg-elasticache`の5つ
- Issue #158と同じルール（bastion: 22番を作業者IP、alb: 80番を`0.0.0.0/0`、ecs: albからのみ、rds: bastion+ecsから、elasticache: ecsから）
- SG同士の相互参照は`aws_security_group_rule`（別リソース）で表現し、循環参照によるcreate/destroy順序の問題を避ける

### rds.tf / elasticache.tf

- RDS: `db.t4g.micro`、`engine = "postgres"`、`allocated_storage = 20`、`storage_type = "gp3"`、`publicly_accessible = false`、`multi_az = false`、`skip_final_snapshot = true`（destroyを一発で通すため。Issue #158で自動スナップショットが個別削除不可だった教訓を活かし、最初から残さない設定にする）、`aws_db_subnet_group`はprivateサブネット2つを束ねる
- ElastiCache: `aws_elasticache_replication_group`（Issue #158の削除時、単純な`cluster`ではなく`replication_group`として管理されていたことが判明済みのため）、`cache.t4g.micro`、`num_cache_clusters = 1`、`aws_elasticache_subnet_group`はprivateサブネット2つを束ねる

### ecs.tf

- `aws_ecs_cluster` + Capacity Provider（EC2）
- `aws_autoscaling_group`: `min_size = max_size = desired_capacity = 1`
- `aws_ecs_task_definition`: `network_mode = "bridge"`、`requires_compatibilities = ["EC2"]`、コンテナ定義でメモリソフト制限128MB（Issue #158の実測値=利用可能メモリ418MBに基づく）
- `aws_ecs_service`: `deployment_minimum_healthy_percent = 0`（Issue #158で1台構成・ホストポート固定によるデプロイのデッドロックを経験したため。Terraformでも同じ制約が残る点を学習ポイントとして解説する）
- IAMロール2つ（`aws_iam_role` + `aws_iam_role_policy_attachment`）

### alb.tf / route53.tf / acm.tf / s3_cloudfront.tf

- ALB: `internet_facing = true`、リスナーはHTTP:80のみ
- Route53: `aws_route53_zone`でホストゾーン（`secuaigent-ryoyamasuda.tech`）を作成。発行されたNSレコードをムームードメインの管理画面に手動登録し、DNS管理をRoute53に委任する（ここのみ手動操作、Terraform管理外）
- ACM証明書: `us-east-1`固定（`provider = aws.us_east_1`のエイリアス。CloudFront用証明書の既知の制約）。DNS検証は`aws_route53_record`（検証用CNAME）＋`aws_acm_certificate_validation`でTerraform内で自動化する
- CloudFront: オリジン2つ（S3 + ALB）、`/api/*`・`/auth/*`のビヘイビアをALBへ、デフォルトビヘイビアをS3へ

## Terraform学習ポイント（実装時に解説する項目）

- `terraform init`/`plan`/`apply`/`destroy`の役割の違い
- `resource`ブロックの基本構文（type/name/引数）
- `variable`/`output`の使い方、`sensitive = true`
- `depends_on`が必要になる場面（暗黙の依存関係だけでは順序が保証されないケース）
- `for_each`/`count`によるリソースの繰り返し定義（サブネット2つ、SGルール等）
- プロバイダエイリアス（`provider = aws.us_east_1`）
- tfstateの役割（「今何が存在すると認識しているか」の記録）、`terraform state list`/`terraform show`

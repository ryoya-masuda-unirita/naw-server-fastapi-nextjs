# 02_基本設計

## 変更対象

- LLM チャット API のストリーム配信の終了処理（トークン使用量・ライブラリの保存）
- メッセージ送信 API のストリーム配信の終了処理（回答・ライブラリ・トークン使用量の保存）
- 上記が共通で使う、「呼び出し元がキャンセルされても最後まで動くタスク」の実行ヘルパー（新規）

## 画面 / API 変更概要

API の仕様（リクエスト・レスポンス・SSE のイベント）は変えない。変わるのは、切断された場合に保存が完了するようになる点のみ。

## 原因の確認結果

Issue 起票時は未検証だった見立て（切断のキャンセルで終了処理内のコミットが中断される）を、修正前に確かめた。

- 切断を再現するテストを書き、修正前に 2 つとも失敗することを確認した（LLM チャット: 使用量 0 件、メッセージ送信: 回答・使用量とも 0 件）
- 再現には、実機と同じ ASGI の spec_version（2.3）で、`message_stop` 送出直後に切断を返す。保存側のコミットは、実物の DB ドライバと同じく一度イベントループへ制御を渡す
- 既存の切断テスト（ジェネレータを `aclose()` するもの）は、切断のキャンセルではなく `GeneratorExit` だけを再現していたため、この不具合を検出できなかった

## 影響範囲

- メッセージ送信 API も同じ構造で、同じ不具合があった（回答の保存・使用量とも漏れる）。同一 PR で直す
- 他の SSE 配信（`StreamingResponse`）で、終了処理に `await` を持つ箇所は、着手時点でこの 2 か所のみ

## 移植方針

移植元は別スレッドで保存する。FastAPI では、保存を別の `asyncio` タスクとして切り離し、呼び出し元をキャンセルから守る（`asyncio.shield`）形に揃える。切り離したタスクは参照を保持して回収を防ぐ。

DB 接続への影響は、保存がキャンセルされなくなることで、コミットの途中中断がなくなる。切断後の `connection is closed` の 500 は、中断された接続がプールに戻ったことが原因と考えられ、同じ修正で出なくなる想定（実 DB での確認は未実施。`08_動作確認.md` 参照）。

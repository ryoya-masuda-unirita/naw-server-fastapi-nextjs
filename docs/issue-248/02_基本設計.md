# 02_基本設計

## 変更対象

- パスワード再設定のリクエストの入力チェック
- パスワード再設定の業務処理（ロック判定・失敗記録・成功時の記録削除）
- 失敗記録の保存（新設）
- 設定（回数・ロック時間）

## 画面 / API 変更概要

`POST /auth/password/reset`

| 条件 | 変更前 | 変更後 |
|---|---|---|
| ログインID・旧パスワード・新パスワードのいずれかが未指定・空・空白のみ | 400 `Field required`、または 403 `User not found` など | 400 と移植元の必須メッセージ |
| ユーザーが存在しない | 403 `User not found` | 403「ログインIDまたは旧パスワードが正しくありません。」（失敗は記録しない） |
| パスワード履歴がない | 403 `Invalid old password` | 403「ログインIDまたは旧パスワードが正しくありません。」（失敗は記録しない） |
| 旧パスワード誤り（上限未満） | 403 `Invalid old password` | 403「ログインIDまたは旧パスワードが正しくありません。」（失敗を記録する） |
| 旧パスワード誤りでロック時間内の失敗が上限に達した | 403 | 429 とロックメッセージ |
| ロック中に再設定 | 正しければ成功 | 429 とロックメッセージ |
| 成功 | 200 | 200（失敗記録を消す） |

## 影響範囲

- パスワード再設定 API のみ。ログイン API には影響しない
- フロントエンドは移植元と同じ応答になるため、変更不要

## 移植方針

### 失敗記録の保存先

移植元は失敗記録を DB のテーブル（パスワード不一致履歴）に保存している。backend にはこのテーブルがなく、ログイン失敗のロック（`LoginAttemptService` 相当）も未実装のため、「揃える既存の仕組み」は存在しない。

次の理由から、DB ではなく Redis に保存する。

- backend は認証まわりの一時的な状態（ログインセッション）を既に Redis に置いている。失敗記録もロック時間内のものだけが意味を持つ一時的な状態である
- テーブルを追加するとマイグレーションが必要になり、他の未マージ PR とのマージ順の調整が発生する
- 移植元は失敗記録を別トランザクション（REQUIRES_NEW）で確定させている。Redis は DB トランザクションと独立しているため、何もしなくても同じ性質になる
- ロック時間を過ぎた記録は数えないため、ロック時間を有効期限にして自動で消せる

Redis の記録が失われた場合（再起動など）はロックが解除されるが、ロックは総当たり対策であり、失われても安全側（ログインできなくなる方向）の問題は起きないため許容する。

### ログイン失敗ロックとの関係

移植元はログイン失敗とパスワード再設定の失敗を同じテーブルに記録している（片方の失敗がもう片方の回数にも数わる）。ログイン失敗ロックは backend 未実装のため本 Issue では移植しないが、将来移植するときに同じ記録を共有できるよう、記録の置き場所は「パスワード不一致の記録」として汎用的な名前にする。ログイン側は記録の数え方（期間を区切らず全件を数える）が異なるため、移植時に保持期間を見直す必要がある。

### 必須チェック

対象スキーマ（パスワード再設定のリクエスト）だけに、未指定も含めて移植元のメッセージを返すチェックを追加する。他のスキーマには触れない（#239 と競合させないため）。

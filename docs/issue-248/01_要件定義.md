# 01_要件定義

## 背景

パスワード再設定 API は未認証で呼べるが、旧パスワードの誤りに回数制限がないため、総当たりで旧パスワードを推測できる。移植元は失敗回数によるロックと、リクエストの必須チェックを持っている。

## 移植元の仕様（調査結果）

### 失敗回数ロック

| 項目 | 移植元の仕様 |
|---|---|
| 失敗とみなす条件 | 対象ユーザーが存在し、旧パスワードが最新のパスワードと一致しないとき。ユーザーが存在しない・パスワード履歴がない場合は失敗として数えない |
| 回数 | 設定 `password-reset.max-failure-attempts`（既定 5） |
| ロック時間 | 設定 `password-reset.lockout-minutes`（既定 15 分） |
| 判定方法 | 直近ロック時間（15 分）以内の失敗が回数（5 回）以上ならロック中。ロック時間を過ぎた失敗は数えない（スライディングウィンドウ） |
| ロック判定のタイミング | ユーザーの存在確認の直後、旧パスワード照合の前。ロック中は正しい旧パスワードでも再設定できない |
| ロックに達した失敗 | 失敗を記録した結果ロック条件を満たしたら、その回の応答もロック中の応答にする（5 回目の失敗で 429） |
| 失敗記録の独立性 | 呼び出し元の処理が失敗しても、失敗の記録は残る |
| 解除の条件 | ロック時間の経過、または再設定の成功（成功時にそのユーザーの失敗記録をすべて消す） |
| 単位 | テナント + ユーザーごと |
| ロック中の応答 | 429、メッセージ「連続でパスワード更新に失敗したため、一定期間更新はできません。しばらく時間を空けて再度お試しください」 |

### 認証失敗時の応答

移植元はユーザーが存在しない場合・パスワード履歴がない場合・旧パスワードが一致しない場合のいずれも、403 と同じメッセージ「ログインIDまたは旧パスワードが正しくありません。」を返す（`INVALID_CREDENTIALS_MESSAGE`）。backend は `User not found` / `Invalid old password` と出し分けており、メッセージの違いからログインIDの有無が分かってしまう（Issue へのコメントで追加された指摘）。

### 必須チェック

| 項目 | メッセージ |
|---|---|
| ログインID（`loginId`、別名 `username`） | ログインIDの入力は必須です。 |
| 旧パスワード | 旧パスワードの入力は必須です。 |
| 新パスワード | 新パスワードの入力は必須です。 |

- 未指定・null・空文字・空白のみをエラーにする（`@NotBlank`）
- 入力チェックはサービス処理の前に行うため、必須エラーは失敗回数に数えない
- 応答は 400（既存の入力チェックエラーの形式どおり、最初の 1 件のメッセージ）

## 機能要件

1. パスワード再設定で旧パスワードを誤ると失敗を記録し、ロック時間内の失敗が上限に達したら 429 とロックメッセージを返す
2. ロック中は旧パスワードの正誤によらず 429 を返す
3. 再設定に成功したら、そのユーザーの失敗記録を消す
4. 回数とロック時間は設定で変更できる（既定 5 回・15 分）
5. ログインID・旧パスワード・新パスワードが未指定・空・空白のみなら 400 と移植元のメッセージを返す
6. ユーザーが存在しない・パスワード履歴がない・旧パスワードが一致しない場合は、いずれも 403 と「ログインIDまたは旧パスワードが正しくありません。」を返す。失敗回数として数えるのは移植元どおり旧パスワード不一致の場合だけ（存在しないユーザーは数えない）

## 非機能要件

- DB のマイグレーションを追加しない
- 失敗記録は再設定処理の DB トランザクションと独立して残る

## スコープ外

- ログイン失敗のロック（移植元 `LoginAttemptService`）。backend には未実装のため、本 Issue では移植しない（後述の基本設計を参照）
- テナントが存在しない場合の応答。移植元は処理の最初にテナントを確認して 404「テナントが存在しません。」を返すが、backend はユーザーをテナントで絞って検索するため、存在しないテナントは「ユーザーが存在しない」と同じ 403 になる。ログインIDの有無が分かる問題とは別のため、本 Issue では変えない
- パスワード再設定以外のスキーマのメッセージ（#239 で対応）

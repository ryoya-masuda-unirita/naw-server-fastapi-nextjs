# 02_基本設計

## 変更対象

- リポジトリのルートに、ローカルサーバー用の独立したプロジェクトを新設する（バックエンドとは別の依存定義・テスト・コンテナ定義を持つ）
- ローカルサーバー用のコンテナイメージ定義と、単体で起動するための Compose 定義
- ローカルサーバーの README（起動手順・環境変数・Waha! との連携方法）
- 本 Issue の設計・動作確認ドキュメント

既存のバックエンド・フロントエンド・インフラには変更を加えない。

## 画面 / API 変更概要

### 移植元のエンドポイント一覧と移植先の対応

| No | メソッド | パス | 移植元の役割 | 認証 | 移植先の対応 |
|---|---|---|---|---|---|
| 1 | GET | `/api/hello` | 稼働確認（固定文言） | 不要 | 移植済み |
| 2 | POST | `/api/messages/content` | 質問を受け付け、NAW 互換 SSE で回答を返す（multipart: `textData` / `attachmentFiles` / `historyAttachmentFiles`） | 要 | 移植済み |
| 3 | POST | `/api/messages/content/sync` | 旧形式。Waha! 実行を待って回答を JSON で返す（非推奨） | 要 | 移植済み |
| 4 | POST | `/api/messages/content/stream` | 旧形式。ストリームファイルの内容をそのまま SSE で中継し、`X-Message-Content-Id`・`X-Message-Id` ヘッダーを返す（非推奨） | 要 | 移植済み |
| 5 | POST | `/api/messages/contents` | メッセージ ID 一覧を指定してメッセージ内容を一括取得 | 要 | 移植済み |
| 6 | DELETE | `/api/messages/{messageId}` | メッセージ内容を削除（添付ファイルも削除） | 要 | 移植済み |
| 7 | GET | `/api/libraries/{libraryId}/content` | ライブラリ本文を `{"data": 本文}` で返す | 要 | 移植済み |
| 8 | DELETE | `/api/libraries/{libraryId}` | ライブラリ本文を削除 | 要 | 移植済み |
| 9 | GET | `/api/admin/indexes/{indexId}/files` | 学習ファイル一覧（絞り込み・ページング、Page 形式） | 要 | 移植済み |
| 10 | POST | `/api/admin/indexes/{indexId}/files` | 学習ファイルを Waha! で登録（multipart） | 要 | 移植済み |
| 11 | PATCH | `/api/admin/indexes/{indexId}/files/{fileId}` | 学習ファイルの更新（ファイル添付時は削除→再登録、multipart） | 要 | 移植済み |
| 12 | DELETE | `/api/admin/indexes/{indexId}/files/{fileId}` | 学習ファイルの削除（JSON ボディで物理/論理を指定） | 要 | 移植済み |
| 13 | GET | `/api/admin/indexes/{indexId}/files/{fileId}` | 学習ファイルのダウンロード（移植元は未実装で常に例外） | 要 | 移植済み（移植元どおり常に 500） |
| 14 | POST | `/api/admin/indexes/{indexId}/sync` | Waha! の取得ジョブ結果から学習ファイルを同期 | 要 | 移植済み |
| 15 | POST | `/api/admin/indexes/{indexId}/additionalLeaning` | フィードバック／ルームの内容を追加学習（multipart。パス名の綴りも移植元のまま） | 要 | 移植済み |
| - | （任意） | `/h2-console` | H2 データベースの Web コンソール（Spring Boot 標準機能） | 不要 | 対象外（DB を SQLite に置き換えるため） |

→ 業務エンドポイント 15 本をすべて移植する。

### 認証・CORS・エラー形式

| 項目 | 移植元 | 移植先 |
|---|---|---|
| 認証ヘッダー | `X-SERVER-AUTH-KEY` が設定値と一致しなければ 401 | 同じ |
| 認証の除外 | OPTIONS、`/secuaigent/api/hello`、`/secuaigent/h2-console`（Tomcat の war 配置時のコンテキストパス前提でハードコード） | OPTIONS と「コンテキストパス + `/api/hello`」。コンテキストパスは設定値（既定は空） |
| CORS | 全オリジン（パターン `*`）・全ヘッダー・全メソッド、資格情報あり | 同じ |
| 業務エラー | `{"timestamp": UNIX秒, "message": "..."}`（400 / 404 / 500） | 同じ |
| フレームワーク既定のエラー（必須パラメーター欠落・型不一致・認証失敗・想定外例外） | Spring Boot 既定の `{"timestamp", "status", "error", "path"}` | 同じ形式で返す（FastAPI 既定の 422 は使わず 400 にする） |

### SSE の形式

- 1 イベント = `data:{JSON}` + 空行（`data:` の後ろに空白を入れない。Spring の SseEmitter と同じ）
- NAW 互換（No.2）のイベント種別: `library_id` / `reasoning_delta` / `library_title_delta` / `library_content_delta` / `text_delta` / `message_stop` / `message_content` / `error`
- 旧形式（No.4）はストリームファイルの `data:` 行をそのまま中継し、エラー時のみ `error` イベントを送る

## 影響範囲

- 新規プロジェクトの追加のみで、既存のバックエンド・フロントエンド・インフラ・CI の動作には影響しない
- リポジトリルートの pre-commit 設定に、ローカルサーバー向けの lint/format を追加する（既存の対象範囲は変えない）
- Docker で動かす場合、Waha! とストリームファイルの出力先ディレクトリを共有する必要がある（Waha! はローカルサーバーが指定したパスへ書き込むため）。README に共有方法とパス変換の設定を記載する

## 移植方針

- 技術スタックはバックエンドに揃える（FastAPI / SQLModel（SQLAlchemy 非同期）/ pydantic-settings / Alembic / uv / ruff / pytest）
- DB は SQLite を採用する
  - 理由: 移植元の H2 は組み込み・ファイル 1 つで動く用途であり、SQLite は Python 標準でサポートされ追加のサーバー不要、ファイル 1 つで永続化できるため用途が一致する
  - テーブル定義（テーブル名・列名・制約・インデックス）は移植元の Liquibase 定義に揃え、Alembic の初期マイグレーション 1 本にまとめる
  - 学習ファイルの状態列は、移植元と同じく序数（ENABLE=0 / DISABLE=1 / DELETED=2）で保存し、API では名前で返す
- 外部連携（Waha!、NAW 本体）は非同期 HTTP クライアントで呼び出し、URL・認証キーは環境変数で設定する。Waha! の呼び出しパス・クエリパラメーター・アップロードのスロット名は移植元のまま
- SSE は、移植元のスレッドプール + スケジューラー構成を、非同期タスク（ジョブ実行・ストリームファイルの追従読み取り・結果ポーリング）と送信キューに置き換える。クライアント切断後も処理は最後まで続け、DB には結果を保存する（移植元と同じ）
- ストリームファイルの追従読み取り（空行区切りのイベントと、`data:` で始まる 1 行イベントの両方を扱う）・終端判定（`completed` / `error`）は移植元のロジックをそのまま移植する
- 移植元の動作上の不具合・曖昧な点は、互換性を優先しつつ以下のとおり扱う
  - 移植元で Tomcat の `BadRequestException` を投げている箇所（質問の対象未指定、追加学習の指定不備）は、ハンドラー未定義で 500 になり得るが、意図どおり 400 の業務エラーで返す
  - 稼働確認 API の認証除外は、移植元がコンテキストパス `/secuaigent` をハードコードしていたものを、設定したコンテキストパスに追従させる
- 定期処理（古いストリームファイルの削除）はアプリ起動中に動く非同期タスクとして実装する
- Windows 固有の処理（バックスラッシュ区切りのパス）は行わない。Waha! に渡すストリームファイルのパスは、必要に応じて Waha! 側から見えるパスへ置き換えられるよう設定を用意する

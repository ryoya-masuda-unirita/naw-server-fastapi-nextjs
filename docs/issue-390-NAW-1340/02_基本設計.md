# 02_基本設計

## 変更対象

- ローカル用サーバーと通信する処理（新規）: 接続先の取得、URL の組み立て、一覧・追加・更新・削除・同期の送信
- 学習データ詳細のデータ取得・更新の処理（フォルダの種類で、クラウドとローカルに振り分ける）
- 学習データ詳細の画面（振り分けに必要な情報の受け渡し）
- フォルダの情報の変換（接続先の ID を取り出す）
- 型・API のパスの定義
- テスト（変換・振り分け・失敗時の動作）と、画面テスト用のモック

## 画面 / API 変更概要

- 画面: 見た目は変えない。ローカルのフォルダでも、同じ操作で一覧・追加・編集・削除・同期ができるようになる
- API（クラウド側）: 変更しない。接続先の取得（既存）だけを使う
- API（ローカル用サーバー側）: 既存の受け口へ、接続先の URL に対して、次のとおり送る
  - 一覧: GET。検索の語・期間（日付）・ページ
  - 追加: POST。ファイルと、名前・表示名・参照資料のリンク・チャンクサイズ・更新者・追加のサービス名
  - 更新: PATCH。上記に加え削除のサービス名。ファイルを付けると作り直し、付けないと表示名とリンクだけ変わる
  - 削除: DELETE。削除のサービス名と物理削除を JSON で送る
  - 同期: POST。更新者と取得のサービス名
- 認証: ローカル用サーバーの認証キーのヘッダーと、テナント ID のヘッダーを付ける

## 影響範囲

- ローカルのフォルダの学習データ詳細（一覧・追加・編集・削除・同期）
- クラウドのフォルダは、呼び先を変えない（振り分けの条件だけが増える）
- デモ環境: ローカルのフォルダに接続先が登録されていないと、一覧を含めて失敗する。今は DB の行が表示できているため、見え方が変わる
- 呼び出し元の関数の引数が増える（フォルダの情報を渡す）

## 移植方針

- 移植元と同じく、フォルダの種類がローカルのときだけ、ローカル用サーバーへ振り分ける
- 接続先はキャッシュせず、操作のたびに取得する
- 一覧の期間の日付変換と、接続先の URL の結合は、移植元と同じ規則にする（月末・年末の繰り上げに注意）
- 更新から学習の ON/OFF を送らない（ローカル用サーバーが受け取らないため。編集ダイアログの扱いは #375 で対応済みか確認する）

## 不明点・要確認

1. 更新者名の解決: ローカル用サーバーは更新者名を持たない。移植元は `loginIds`（#372、PR #378 でマージ済み）で、表示ページの更新者のログイン ID だけを引く。こちらの画面側は未対応なので、ローカルのときはこの方式にする（クラウドの更新者の扱いは変えない）
2. デモ環境: ローカルのフォルダの接続先をデモデータに登録するか。登録しないと、変更後はデモでローカルのフォルダが開けなくなる
3. 同期: 移植元は同期もローカル用サーバーへ送る。今回に含めてよいか（含める想定）
4. ブラウザから直接ローカル用サーバーを呼ぶため、CORS や、https の画面から http の接続先を呼べない制約が出る。移植先の server-local では CORS は通る見込みだが、実環境では未確認

# 02_基本設計

## 変更対象

1. **`IndexService.delete_index`**: 引数に `storage: FileStorage` を足す。フォルダが LOCAL 型でなければ、中の学習データのうち `DELETED` でないものを 1 件ずつ `FileService.delete_file(physical_delete=True)` で消してから、フォルダを消す
2. **`FileRepository`**: インデックス ID とテナント ID で、学習データを全件取る関数を足す（既存は、ページング用の `find_page` のみ）
3. **`routers/indexes.py`**: `delete_index` に `Depends(get_file_storage)` を足し、サービスへ渡す
4. **テスト**: 物理削除が呼ばれる・途中失敗でフォルダが残る・LOCAL 型と `DELETED` の扱い・可視性・冪等

## 画面 / API 変更概要

- API の入出力は変えない。フォルダの削除で、ストレージの実体が消える。ストレージの削除に失敗すると、これまで 204 だったものが、エラー（500）になる
- `client/` の変更はない

## 「1 件ずつ確定する」の移し方（要確認だった点）

- 移植元は、`REQUIRES_NEW` で、1 件ずつ別のトランザクションにしている
- こちらは、`FileRepository.delete` が、1 件ごとに `session.commit()` する。`FileService.delete_file` を 1 件ずつ呼べば、**追加の仕組みなしで、1 件ずつ確定する**。ストレージの削除が先で、行の削除が後、という順番も、`delete_file` がそのまま満たす
- 失敗したときは、例外がそのまま上に出て、`IndexRepository.delete` に進まない。フォルダは残り、消せた分は確定済み
- ストレージの実体の削除が成功し、行の削除が失敗する場合、行だけが残る（もう一度削除すれば、`LocalFileStorage.delete` は存在しなくても何もしないので、続きが消える）。逆（行だけ消えて、実体が残る）は起きない

## 影響範囲

- フォルダの削除の動作のみ。ほかの API は変わらない
- フォルダ内の学習データの件数に比例して、削除に時間がかかる（1 件ずつ順に。移植元と同じ）
- ストレージの実体が消えるのは、不可逆。テストでは、一時ディレクトリの `LocalFileStorage` を使う
- **デプロイ**: `server/` を変更するので、マージすると `Deploy` の `backend` ジョブが動く
- 費用・インフラ: なし

## 移植方針

- 移植元の判定（LOCAL 型は対象外、`DELETED` はスキップ、失敗したらフォルダを消さない）をそのまま移す
- ベクトルの削除は、こちらに仕組みがないので、移さない（`02` に明記）

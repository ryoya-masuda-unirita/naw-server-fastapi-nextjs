## 詳細

### 1. 件数が多いときの時間・途中失敗（対応しない）
移植元と同じ 1 件ずつの順次処理で、`01_要件定義.md` のスコープ外に明記している。途中で失敗しても、消せた分は確定していて、もう一度削除すれば続きが消える（テスト No.4 で確認）。一括削除・並行化は、1 件ずつ確定する設計（失敗時に行と実体がずれない）を崩すため、移植元と合わせて、別の Issue で検討する。API・テストに、中途半端な状態の説明を足すかは、必要になったときに決める。

### 2. 一覧の取得後に別の管理者が消した場合（対応しない）
同じフォルダを同時に消す操作と、そのファイルを同時に消す操作が重なったときだけ。失敗は 404 として見え、もう一度削除すれば成功する。移植元も、同じ作りで、同じ状況になる。404 を握りつぶすと、本当にファイルが無いことと区別できなくなるため、変えない。

### 3. 種別の判定（対応しない）
移植元が `!= LOCAL`。`IndexType` は 2 値（`SAAS_GLOBAL`・`LOCAL`）のみ。種別が増えたときに、判定を見直す。

### 4. `DELETED` のスキップ（対応しない）
移植元の仕様（コミット c6bb9b852）で、画面からの削除（論理削除）が、ストレージの実体を先に消してから `DELETED` にするため。もう一度消しに行くと、外部の都合で、消せていたフォルダが失敗するようになる、というのが移植元の理由。こちらの `LocalFileStorage` は、なくても失敗しないが、S3 などを足したときの挙動が分からない。実体が残る `DELETED` 行が実在するかは、確認していない。

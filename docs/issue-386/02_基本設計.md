# 02_基本設計

## 変更対象

1. **新しい「secrets」モジュール**: シークレットの入れ物（Secrets Manager のシークレットと、その値）と、アプリの秘密鍵の自動生成。入力は、DB のホスト・ユーザー・DB 名・パスワード。出力は、シークレットの ARN と名前
2. **rds モジュール**: マスターパスワードを自動生成する。パスワードは、出力として（機密扱いで）外に出し、secrets モジュールが接続文字列を組み立てるのに使う。外から渡す入力（`db_password`）は削除する
3. **ecs モジュール**
   - タスク定義（backend・マイグレーション）の環境変数から、接続文字列と秘密鍵を削除し、`secrets` で注入する
   - 実行ロールに、このシークレットだけを読む権限を足す
   - 入力: `db_password`・`secret_key`・DB のホスト・ユーザー・DB 名を削除し、シークレットの ARN を足す
4. **環境（dev）**: 変数 `db_password`・`secret_key` を削除し、モジュールの接続を組み替える（rds → secrets → ecs）。出力にシークレット名を足す。プロバイダに、乱数用のものを足し、ロックファイルを更新する
5. **CI**: インフラのデプロイから、`TF_VAR_db_password`・`TF_VAR_secret_key` を削除する
6. **踏み台のシード投入スクリプト**: DB のパスワードを、環境変数がなければ、Secrets Manager から取得する
7. **手順書**: GitHub Secret の登録手順から `DB_PASSWORD`・`SECRET_KEY` を削除し、シークレットの扱い（取得、変更、注意）を書く。変数の例（`terraform.tfvars.example`）からも削除する

## 画面 / API 変更概要

なし（インフラ・CI・スクリプトのみ。アプリのコードは変えない）。

## 影響範囲

- **アプリ**: 環境変数の名前と形式は同じ。値の出どころが、タスク定義の平文から、Secrets Manager に変わる
- **タスクの起動**: タスクの起動時に、実行ロールがシークレットを読む。シークレットが読めないと、タスクが起動しない（権限・名前を間違えると、原因が分かりにくいため、設計で明確にする）
- **CI のデプロイ**: タスク定義を登録し直すとき、稼働中の定義の `secrets` の指定が、そのまま引き継がれる。イメージの差し替えだけを行うので、影響しない
- **Terraform によるコンテナ定義の変更**: タスク定義の `container_definitions` は、CI との共存のため、Terraform が変更を無視する設定になっている。既存の環境に適用しても、タスク定義は書き換わらない（新アカウントへの新規構築なら、最初から `secrets` 付きで作られる）
- **変数の削除**: `db_password`・`secret_key` を削除するので、手元の `terraform.tfvars` にこれらがあっても、使われない（警告が出るだけ）。GitHub の Secret `DB_PASSWORD`・`SECRET_KEY` も不要になる（削除は、利用者の判断）
- **tfstate**: パスワード・秘密鍵・接続文字列の値は、Terraform が生成・保存するため、これまでどおり state に残る。state は、非公開で暗号化されたバケットにある。タスク定義・コンソール・API から見えなくなることが、今回の改善
- **既存の環境**: RDS のパスワードが変わる（再作成になる変更は #385 で入った）ので、新アカウントへの新規構築が前提
- **費用**: シークレット 1 つの保管料と、API 呼び出しの料金（単価は未確認）。`apply` はしないので、今は発生しない

## 移植方針

- 移植元の構成（シークレットを JSON で持ち、ECS の `secrets` で、キーごとに注入する。実行ロールに `GetSecretValue`。開発環境は削除待ちなし）に揃える
- 移植元との違い
  - 移植元は、値をプレースホルダにしておき、`apply` 後に手動で差し替える。このリポジトリは、**Terraform が生成して保存する**（DB のパスワードは、RDS の作成時に必要なため、先に決まっていなければならない）
  - キーは、移植元の Java サーバー用（`DB_USER`・`LIQUIBASE_*`・`JWT_SECRET`）ではなく、このアプリが使う `DATABASE_URL`・`SECRET_KEY`、それに人が DB に接続するための `DB_PASSWORD`
  - シークレットの値は、アプリが期待する形（接続文字列 1 本）で保存する。移植元のように、アプリ側でキーを組み立てる処理は、このアプリにはない
  - シークレットの名前は、移植元の `secuaigent/dev/naw-server` ではなく、`<プロジェクト名>/backend`
- サブドメイン関連は関係しない

# 01_要件定義

## 背景

- ECS のタスク定義の環境変数に、DB のパスワードを含む接続文字列と、アプリの秘密鍵が、平文で入っている。タスク定義は、AWS のコンソールや API で、読み取りの権限があれば誰でも見られる。デプロイのたびに登録される新しいリビジョンにも、同じ値が残り続ける
- DB のパスワードと秘密鍵は、利用者が決めた値を、変数（CI では GitHub の Secret）として渡している。値を人が決めて管理する手間と、漏れる経路（設定ファイル、CI の設定）が増えている
- 移植元は、シークレットを Secrets Manager に置き、ECS のタスクが起動するときに注入する構成で、DB のパスワードは自動生成している。同じ構成に揃える方針（#380）
- アプリは、接続文字列 1 本と秘密鍵を、環境変数で受け取る。値の受け取り方（環境変数）は変えずに、渡し方だけを変えたい

## 機能要件

1. Secrets Manager にシークレットを 1 つ作り、次の値を JSON のキーとして持つこと
   - アプリが使う接続文字列（`DATABASE_URL`）
   - アプリの秘密鍵（`SECRET_KEY`）
   - DB のパスワード（`DB_PASSWORD`。踏み台からのシード投入など、人が DB に接続するときの取得元として）
2. DB のマスターパスワードと、アプリの秘密鍵を、Terraform が自動生成すること（人が決めない）。パスワードは、接続文字列に埋め込んでも壊れない文字だけを使う
3. 接続文字列は、Terraform が、DB のホスト・ユーザー・DB 名と、生成したパスワードから組み立てて、シークレットに保存すること
4. ECS のタスク定義（backend とマイグレーション用の両方）から、接続文字列と秘密鍵を、平文の環境変数として持たないこと。代わりに、ECS が起動時にシークレットから取り出して環境変数として注入する形にすること
5. タスクの実行ロールに、このシークレットだけを読める権限を付けること（シークレットの値を読めるのは、タスク起動時の実行ロールのみ。アプリのタスクロールには付けない）
6. 変数 `db_password`・`secret_key` を削除し、CI の対応する設定（`TF_VAR_db_password`・`TF_VAR_secret_key`）と、手順書の GitHub Secret の登録手順（`DB_PASSWORD`・`SECRET_KEY`）を削除すること
7. 踏み台経由のシード投入が、DB のパスワードを、Secrets Manager から自動で取得できること（呼び出し側が環境変数で渡す方法も、後方互換として残す）
8. 環境の出力に、シークレットの名前を足すこと（シード投入や手順書から使うため）
9. CI のデプロイ（タスク定義の登録し直し）と共存すること。登録し直したタスク定義に、シークレットの注入の指定が残ること
10. 手順書に、シークレットの取得方法、値を変える方法、tfstate に値が残ることの注意を書くこと

## 非機能要件

- アプリのコード（`server/`）は変えない。受け取る環境変数の名前と形式は、現状のまま
- 命名・タグの規則は、これまでの方針（`<プロジェクト名>-...`、`Project` タグは既定タグ）に従う
- 開発用の環境なので、シークレットの削除は即時とする（削除待ちの期間を設けない。`destroy` 後に、同じ名前で作り直せるようにする）
- `fmt`・`validate` が通ること。`plan` で、追加・変更されるリソースが想定どおりであること
- 費用: シークレット 1 つの保管料と、API 呼び出しの料金がかかる。単価は未確認のため、金額は書かない。`apply` はしない

## スコープ外

- シークレットの自動ローテーション、顧客管理の KMS キー
- 接続文字列・秘密鍵以外の環境変数（CORS の許可元、S3・SQS の名前など。機密ではない）
- DB の接続ユーザーの分離（アプリ用ロールの作成、マイグレーション用との分離）。移植元の `scripts/db-init` と同じ領域で、別の変更で扱う
- 既存の環境からの移行（新アカウントへの新規構築が前提）
- tfstate に値が残らないようにすること（Terraform で値を生成する限り、state に入る。state は暗号化された非公開のバケットにある）

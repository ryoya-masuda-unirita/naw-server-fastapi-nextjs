# 01_要件定義

## 背景

Issue #48でメッセージ送受信APIの同期系（メッセージ作成、一覧取得、内容取得、削除、フィードバック）は移植済みだが、実際にAIアシスタントの応答を生成する `POST /api/messages/content`（SSEストリーミング）はスコープ外としていた。本Issueでこれを移植する。

移植元（Spring Boot）の `MessageService#resolveStreamContext` は、アシスタント種別（`SAAS_CHAT` / `SAAS_RAG` / `SECURE`）により処理を分岐する。うち `SAAS_RAG`（ベクトル検索付き）は、移植先リポジトリに以下が未整備であることを確認した。

- ベクトルDB（Azure AI Search）への接続クライアント（移植元 `VectorStoreFactory` 相当）
- 類似検索（`similaritySearch`）ロジック、Embeddingトークン計測ラッパー（`EmbeddingUsageCountingModel` 相当）

`Index` / `IndexEndpoint` / `tenant_endpoints.VDB` 等のDBスキーマ自体は既に存在するが、上記クライアント層が丸ごと新規実装になり、本Issue単体でこなすには実装規模・調査コストが大きい。また `SECURE`（オンプレローカルLLM）分岐は移植元でもテナントのローカルサーバー呼び出しであり、Azure OpenAI前提の現状のLLM呼び出し基盤（`llm_client.py`）とは別軸の実装が必要。

Issueチケット本文にも「まず基本チャット（RAG・添付ファイル・tools・ライブラリ生成・response_format除外）から着手し、RAG対応等は別issueに切り出す」という段階分けの検討が明記されているため、本Issueでは **SAAS_CHATアシスタントによる基本チャット応答生成のみ** をスコープとし、それ以外は次項の「スコープ外」として本Issueでは対応しない。

## 機能要件

- `POST /api/messages/content` エンドポイントを新設する。
- リクエストは既存 `POST /api/messages`（Issue #48）で作成済みの `Message`（質問スレッド）の `messageId` を指定し、ユーザー発話本文（`userInput`）・会話履歴（`historyMessages`）・追加プロンプト（`additionalPrompt`, 任意）を渡す。
- 対象メッセージが属するルームの所有者であることを確認する（`require_owned_room`を再利用）。
- 対象メッセージの `assistant_id` からアシスタントを解決し、種別が `SAAS_CHAT` であることを確認する（`SAAS_RAG`・`SECURE`・アシスタント未解決時は400）。
- テナント月次クレジット上限チェック（`enforce_within_quota`, Issue #88で実装済み）を行い、超過時は429を返す。
- アシスタントに紐づくAzure OpenAI Chatエンドポイント（`AssistantEndpoint` + `TenantEndpoint`）とAIモデル定義（`AIModel`）を解決する。解決できない場合は400。
- 会話履歴＋ユーザー発話からメッセージ列を組み立てる。`additionalPrompt` が指定されている場合、末尾から見て最後の `user`（大文字小文字を区別しない）ロール発話に「追加プロンプト + `\n\n` + 元の発話」の形で前置する（Issue #88の `LlmChatService._apply_additional_prompt` と同じ規約に統一する）。
- Azure OpenAI Chat Completions APIをストリーミング呼び出しし（`AzureLlmChatClient.stream_chat`, Issue #88で実装済み）、テキスト差分をSSE `text_delta` イベントとして順次配信する。
- ストリーム完了後、入出力トークン数を `message_stop` イベントで送出する。
- ストリーム完了後、回答内容（質問・回答・ステータス）を `MessageContent` として永続化し、ルームの `updated_at` を更新する。永続化結果を `complete` イベントとして送出する。
- ストリーミング中に例外が発生した場合、`error` イベントを送出したうえで、ステータス `ERROR` の `MessageContent` を永続化し、`complete` イベントを送出する（クライアントがエラー後も応答IDを認識できるようにするため）。
- トークン使用量（`TokenUsage`）を永続化する（Issue #88の `_persist_token_usage` と同等のロジックを再利用する）。

## 非機能要件

- Azure OpenAI SDKへの実際の接続は行わず、自動テストでは全てモック化する。
- SSEストリーミングのレスポンスボディ生成処理は、リクエストのDBセッション（DIスコープ）のライフサイクルに依存しないよう、Issue #88の実装パターン（ストリーミング完了後の永続化は新規セッションで行う）を踏襲する。
- 既存の `messages.py` ルーター・`message_service.py` サービスの1対1規約を維持し、新規サービスファイルを作らない。

## スコープ外（フォローアップIssueで対応）

- `SAAS_RAG`（ベクトル検索付きアシスタント）対応。ベクトルDB接続クライアント・類似検索ロジックの新規実装が必要なため、別Issueとして切り出す。
- `SECURE`（オンプレローカルLLM）アシスタント対応。
- 添付ファイル（`attachmentFiles` / `historyAttachmentFiles`）の送受信。
- tools（Function Calling, web_search / mcp）。
- ライブラリ生成（`createLibrary`, `library_title_delta` / `library_content_delta` イベント）。
- `responseFormat`（構造化出力）。
- メッセージ再生成（`messageContentId` 指定による既存回答の上書き）。本Issueでは新規回答生成（`messageId` 指定のみ）のみを対象とする。

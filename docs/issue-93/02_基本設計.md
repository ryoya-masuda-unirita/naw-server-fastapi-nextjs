# 02_基本設計

## 変更対象

- `backend/app/routers/messages.py`（既存ファイルへエンドポイント追加）
- `backend/app/services/message_service.py`（既存ファイルへメソッド追加）
- `backend/app/schemas/message.py`（リクエスト/レスポンス/イベントペイロード用スキーマ追加）
- `backend/app/repositories/message_content_repository.py`（`save`メソッド追加）
- `backend/app/repositories/assistant_endpoint_repository.py`（単一アシスタントのチャットエンドポイント解決メソッド追加）

## 画面 / API 変更概要

- `POST /api/messages/content` を新設する。
  - リクエスト（JSON）: `messageId`, `userInput`, `additionalPrompt`(任意), `historyMessages`(任意、既定空配列)
  - レスポンス: `text/event-stream`（SSE）
    - `text_delta` イベント: `{ "text": string }` を回答生成中に複数回配信
    - `message_stop` イベント: `{ "inputTokens": number, "outputTokens": number }` をストリーム完了時に1回配信
    - `complete` イベント: `{ "id", "messageId", "status", "question", "answer", "context": null, "attachmentFiles": [], "referencePaths": [], "isRated": false }`（永続化した `MessageContent` の内容）
    - `error` イベント: `{ "message": string }`（例外発生時のみ、`complete` の前に配信）
- 既存の `POST /api/messages`（メッセージ作成）・`POST /api/messages/contents`（内容一覧取得）とは別エンドポイントであり、フロントエンドは「メッセージ作成→本APIで応答生成→（必要なら）内容一覧取得」の順で呼び出す想定（移植元と同様）。

## 影響範囲

- 新規追加のみで、既存の `create_message` / `get_messages_and_assistants` / `get_message_contents` / `delete_message` / `feedback_message` の挙動には影響しない。
- Issue #88（PR #91）で実装済みの `app/core/llm_client.py`・`app/core/credit_quota.py`・`app/core/token_usage_credit.py`・`app/models/token_usage.py` を再利用する（重複実装しない）。
- `MessageContentRepository` に `save` を追加するのみで、既存メソッドの挙動は変更しない。

## 移植方針

- 移植元 `resolveStreamContext` のうち、`SAAS_CHAT`分岐（`buildChatContext`相当）のみを移植し、`SAAS_RAG`（`buildRagContext`）・`SECURE`分岐は非対応（400エラー）として扱う。
- 移植元は `SseEmitter` + 別スレッド（`TaskExecutor`）による非同期配信だが、FastAPI側はIssue #88の `LlmChatService.stream_chat` と同じ `StreamingResponse` + 非同期ジェネレータのパターンに統一する。
- 移植元の `messageId` / `messageContentId` の両対応（新規生成・再生成の分岐）のうち、本Issueでは `messageId` 指定（新規回答生成）のみをスポートし、`messageContentId`（既存回答の再生成）は非対応とする（スコープ外）。
- 移植元の `additionalPrompt` 前置ロジックは、Issue #88で実装済みの `LlmChatService._apply_additional_prompt`（末尾から最後の`user`ロール発話に前置、区切りは`\n\n`）とロジックを統一する（本Issueでも同等の関数を実装する）。
- SSEイベント名は移植元の命名（`text_delta`, `message_stop`, `error`）をIssue #88の実装に合わせて踏襲しつつ、最終確定イベントは移植元の「`CreateMessageContentResponse`をラップしたイベント」に相当するものとして `complete` を新設する（移植元にはこの名前の直接対応はないため、本ポートで定めた名称であることをここに明記する）。

# 02_基本設計

## 変更対象

- backend の共通の例外ハンドラ（新規）とアプリへの登録
- multipart の `textData` 解釈の説明（422 → 400）など、ステータスに触れている説明
- 既存テスト（422 / `detail` の確認）
- 共通の例外ハンドラのテスト（新規）
- backend の規約

## 画面 / API 変更概要

全 API のエラー応答が次のとおり変わる。正常系の応答は変わらない。

| エラーの種類 | 変更前 | 変更後 | 移植元 |
|---|---|---|---|
| 業務エラー（ステータス・メッセージ指定） | 指定ステータス `{"detail": "..."}` | 指定ステータス `{"timestamp", "message": "..."}` | `ResponseStatusException` ほか: 同じ |
| 存在しない URL・許可されていないメソッド | 404 / 405 `{"detail": "Not Found"}` 等 | 404 / 405 `{"timestamp", "message": "Not Found"}` 等 | Spring Boot 既定の応答（下記） |
| 入力チェックのエラー | **422** `{"detail": [{...}, ...]}` | **400** `{"timestamp", "message": "最初の1件"}` | `MethodArgumentNotValidException` ほか: 400 `{"timestamp", "message"}` |
| multipart の `textData` の解釈エラー | **422** `{"detail": [{...}]}` | **400** `{"timestamp", "message": "最初の1件"}` | 同上 |
| 予期しない例外 | 500（変更なし） | 500（変更なし） | Spring Boot 既定の応答 |
| SSE 内のエラーイベント | 変更なし | 変更なし | - |

### 移植元と完全には一致しない点

- 移植元では、JSON として読めないボディ・必須のクエリパラメータの欠落・型変換の失敗・存在しない URL などは `APIControllerAdvice` を通らず、Spring Boot 既定のエラー応答（`timestamp`・`status`・`error`・`path`。`message` は含まない）になる
- backend ではこれらも `{"timestamp", "message"}` にそろえる。クライアントは `message` だけを見ればよく、エラーの種類によって本文の形が変わらないほうが扱いやすいため（ユーザー指示「`RequestValidationError` はすべて移植元と同じ形・同じステータス（入力チェックは 400）にする」に従う）
- ステータスは移植元と同じ（入力エラーは 400、存在しない URL は 404）

## 影響範囲

- 全 API のエラー応答の本文（`detail` → `message`）
- 入力チェックのエラーのステータス（422 → 400）。テンプレート名の 32 文字超（#171）、テナント名の上限超過・null、ページ番号の負数などを含む
- 業務エラーで 400 を返していた API は、ステータスは変わらず本文だけが変わる
- 既存の業務エラーの呼び出し側は変更しない

## 移植方針

- 例外ハンドラを 1 か所にまとめ、アプリ起動時に登録する。移植元 `APIControllerAdvice` に相当
- 業務エラーは既存の FastAPI 標準の例外（`detail` にメッセージを入れる）をそのまま使い、ハンドラで `message` に変換する
- 入力チェックのエラーは、フレームワークが返すエラーの一覧から最初の 1 件のメッセージを取り出して返す。独自チェックのメッセージに付く接頭辞は外す
- server-local（#210）の例外ハンドラの構成を参考にする（コードは共有しない）

## 実装内容

### `app/core/errors.py`

```python
DEFAULT_VALIDATION_MESSAGE = "リクエストが不正です"
_VALUE_ERROR_PREFIX = "Value error, "

def error_response_body(message: str | None) -> dict[str, Any]:
    """移植元 ErrorResponse 相当（timestamp は UNIX 秒）"""
    return {"timestamp": int(time.time()), "message": message}

def validation_error_message(errors: Sequence[Any]) -> str: ...

def register_exception_handlers(app: FastAPI) -> None: ...
```

- `error_response_body`: 移植元 `ErrorResponse` は `timestamp = new Date().getTime() / 1000`（UNIX 秒の整数）と `message` を持つ。同じ 2 項目を返す
- `validation_error_message`: 入力チェックのエラー一覧の**最初の 1 件**の `msg` を返す（移植元 `getAllErrors().get(0).getDefaultMessage()` / `findFirst()` と同じく連結しない）
  - `type == "value_error"`（`field_validator` / `model_validator` で `ValueError` を送出した場合）は Pydantic が `msg` に `Value error, ` を付けるため外す。独自チェックの日本語メッセージ（例:「タグ名は必須です」）がそのまま `message` になる
  - 一覧が空なら「リクエストが不正です」（移植元 `ConstraintViolationException` の `orElse` と同じ）
- `register_exception_handlers`:
  - `starlette.exceptions.HTTPException`（FastAPI の `HTTPException` と、存在しない URL の 404・許可されていないメソッドの 405 を含む）
    - ステータスはそのまま。本文を持てないステータス（204・304 等）は FastAPI 既定と同じく本文なしで返す
    - `detail` が文字列ならそのまま `message` に。文字列以外は `str()` で文字列にする（後述の洗い出しのとおり現状は無い）
    - 例外の `headers` はそのまま返す（405 の `Allow` など）
  - `RequestValidationError`（ボディ・クエリ・パス・ヘッダーの検証エラー、`parse_text_data_form` が送出するもの）
    - 400 で `validation_error_message(exc.errors())` を返す
    - 応答には最初の 1 件しか出ないため、全件の `loc`・`type` を WARNING でログに出す（入力値はパスワードや添付ファイルを含み得るため出さない）

### `detail` の型の洗い出し

- `app/` 配下の `HTTPException(...)` 約 140 か所を確認し、`detail` はすべて文字列（リテラル・f-string・文字列定数・文字列を返す関数の戻り値）。dict / list を渡している箇所は無い
- dict / list になっていたのは FastAPI 既定の入力チェックのエラー応答（`[{"loc", "msg", "type", ...}]`）だけで、これは `RequestValidationError` のハンドラで最初の 1 件の `msg` に置き換わる
- 今後 dict / list を渡した場合も 500 にせず `str()` で文字列化して返す（クライアントが `message` を文字列として扱えるように）。規約で「`detail` には文字列を渡す」と明記する

### `app/main.py`

- `app = FastAPI(...)` の直後で `register_exception_handlers(app)` を呼ぶ

### `app/schemas/multipart_form.py`

- `_to_request_validation_error` の処理はそのまま（`loc` を `("body", "textData", ...)` に揃え、`input` を含めない）。応答に `loc` は出なくなるが、ログで原因箇所を特定するのに使う
- 「422」と書いている説明を「400」に直す。`input` を含めない理由を「添付ファイルを含むリクエスト全体を例外に保持しない」に改める

### `backend/.claude/CLAUDE.md`

- 「エラー応答」の節を追加し、`{"timestamp", "message"}`・入力チェックは 400・業務エラーは `HTTPException(detail=文字列)` で投げる、の 3 点を書く

## テストの書き換え方針

- `status_code == 422` → `== 400`、テスト名の `_returns_422` → `_returns_400`、docstring の 422 → 400
- `response.json()["detail"]` → `response.json()["message"]`（業務エラー。値の確認はそのまま）
- `response.json() == {"detail": ...}` は `response.json()["message"] == ...` に直す（`timestamp` は実行時刻のため完全一致では比べない）
- `response.json()["detail"][0]["loc"] == [...]` のように入力エラーの項目を確かめていたテストは、`message` が該当項目のエラーメッセージであることを確かめる形に直す
- 業務エラーで既に 400 を返していたテスト（#226 の削除済みファイル等）は、ステータスはそのまま、本文の確認だけを直す

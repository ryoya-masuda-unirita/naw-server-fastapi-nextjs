# 02_基本設計

## 変更対象

- インデックス（`indexes`テーブル）に関するモデル・リポジトリ・サービス・ルーター・スキーマの新規追加
- インデックスとテナントエンドポイントの中間テーブル（`indexes_endpoints`）
- インデックスとグループの中間テーブル（`indexes_groups`）
- Alembicマイグレーションの追加

## 画面 / API 変更概要

| メソッド | パス | 概要 |
|---|---|---|
| GET | `/api/admin/indexes` | 一覧取得（ページング・グループフィルタ・検索フィルタ） |
| GET | `/api/admin/indexes/{id}` | 詳細取得 |
| POST | `/api/admin/indexes` | 作成 |
| PATCH | `/api/admin/indexes/{id}` | 更新（全フィールド置換） |
| DELETE | `/api/admin/indexes/{id}` | 削除 |

いずれも `require_admin_or_group_admin`（テナント管理者 or グループ管理者）でアクセス制御する。

## 影響範囲

- 新規追加のみで既存エンドポイントへの変更なし
- `main.py` へのrouter登録が必要
- 既存の `assistants`・`groups`・`tenant_endpoints` ドメインは読み取り専用で参照するのみ（サービス間呼び出しは行わず、リポジトリ経由で取得する）

## 移植方針

- レイヤー構成・命名は既存の `assistants`/`prompt_templates` ドメインの実装パターンに合わせる（Router 1対1 Service、Repositoryにクエリを集約）
- 一覧のページング・ソート・検索はDBクエリで実施する（既存パターンに合わせる。移植元のメモリ上処理は踏襲しない）
- グループ管理者向けの可視性ロジック（自グループの直接紐付け ∪ 自グループのアシスタントが使用中のインデックス）は移植元のロジックをそのまま再現する
- バリデーションのうち単純な文字数制限はPydanticの宣言的制約、日本語エラーメッセージが必要なもの・複数フィールドにまたがるものは`@field_validator`/`@model_validator`で実装する
- テナントエンドポイント・グループの実在チェックなど、セッションが必要なビジネスロジックはサービス層に実装する
- 中間テーブル（`indexes_endpoints`・`indexes_groups`）はSQLModelの明示的なモデルクラスとして定義する

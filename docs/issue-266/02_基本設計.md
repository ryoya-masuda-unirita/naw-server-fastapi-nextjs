# 02_基本設計

## 変更対象

- 結合テスト 5 本（クレジット利用量・ファイル・テナント・ユーザー・グループ）のサブスクリプション作成箇所
- アプリ（本番コード）は変更しない

## 画面 / API 変更概要

なし（テストのみの変更）。

## 影響範囲

- 結合テストのみ。CI（UTC で実行）の結果は変わらない
- ユーザー・グループの結合テストは契約開始日が「2 日前」から「UTC の今日」に変わる。請求期間の開始が UTC の今日 0 時になり、テスト内で作るトークン使用量（作成日時 = 現在の UTC 時刻）は引き続き当期間に含まれるため、期待値は変わらない

## 移植方針

### アプリ側の日付の扱い（調査結果）

移植元は請求期間の判定に UTC の日付（`BillingPeriodService`・`SubscriptionBillingCycle` で現在時刻を UTC の日付に変換）を使っており、UTC の日付が正である。backend も同じく UTC で判定しているため、アプリ側は正しく、テスト側をアプリに合わせる。

backend のアプリ側で、ローカル日付・ローカル時刻を使う箇所がないかを grep で確認した。

| 確認したもの | 結果 |
|---|---|
| 今日の日付の取得・タイムゾーンなしの現在時刻の取得・UTC の naive な現在時刻の取得 | アプリ側には無し |
| 現在時刻の取得 | すべてタイムゾーン付きの UTC |
| 現在時刻からの日付の取り出し | 請求期間の判定・テナント情報の使用量集計とも UTC の日付 |
| DB の現在日付関数 | 使っていない。作成日時・更新日時の既定値はタイムゾーン付きの現在時刻 |
| ローカル時刻への変換 | 無し |

アプリ側に同じ問題は無いため、本 Issue ではアプリを変更しない。

### テストでの日付の作り方

- 各箇所で「UTC の今日」を、アプリと同じ書き方（現在の UTC 時刻から日付を取り出す）で作る
- 共通のヘルパーは作らない。結合テストの共通設定は fixture だけで構成されており、テストから共通の関数を import する前例が無い。また対象の各ファイルは日時の型・UTC をすでに読み込んでおり、その場で書き換える方が差分が小さく、アプリ側の書き方と同じで読みやすい

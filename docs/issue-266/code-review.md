## 詳細

### 1. 再混入を防ぐ仕組みが無い（🔵 提案）→ 対応しない（別 Issue の候補）

ruff の flake8-datetimez（DTZ）を有効にした場合の既存違反を数えた結果は 2 件だけだった。

```text
$ uv run ruff check --select DTZ --statistics app tests
1	DTZ003	call-datetime-utcnow
1	DTZ007	call-datetime-strptime-without-zone
Found 2 errors.
```

有効にするには lint 設定の変更に加えて、アプリ側（Azure のコスト API 応答の日付文字列の解析）の修正も必要になり、本 Issue（テストの日付を UTC にそろえる）の範囲を超える。導入の手間は小さいため、別 Issue での対応を提案する。

### 2. `datetime.utcnow()` が残っている（🟡 注意）→ 対応しない

値は UTC の日時であり、本 Issue の原因である「ローカル日付と UTC の混在」ではない（`01_要件定義.md` のスコープ外に記載済み）。タイムゾーン付きに変えると、SQLite に保存される値の形と、パスワード有効期限の比較の挙動が変わりうるため、確認を伴う別の変更とする。指摘 1 の DTZ ルール導入時に合わせて直すのが適切。

### 3. 補助関数の重複（🔵 提案）→ 対応しない

各テストファイルが自前の補助関数を持つのは既存の作りで、共通 fixture への集約はテスト構成のリファクタリングになり範囲外。今回の重複箇所は日付の作り方を 1 行ずつそろえただけで、開始日の差（2 日前と今日）は本 PR で解消した。

### 4. 期限切れテストの日数（🔵 提案）→ 対応しない

`60`・`3`・`1` は「契約が過去に終わっている」状態を作るためのテストデータで、本 PR 以前からの値。`3` は回避策のマージンではなく（回避策は有効な契約の開始日側だけ）、期限切れであれば何日でもよい。本 PR では基準日を UTC にそろえるだけにとどめ、値は変えない。

### 5. 共有の時計ヘルパー（🔵 提案）→ 対応しない

アプリ側に新しい仕組みを入れる変更で、本 Issue の範囲（テスト側をアプリに合わせる）を超える。移植元も各所で UTC の日付をその場で求めており、アプリ側の書き方は移植元と一致している。

### 6. JST での実行に users・groups を含めていない（🟡 注意）→ 対応済み

回避策を取り除いたユーザー・グループのテストを、手元の既定の JST（2026-11-13 00:15、失敗時間帯）で実行し、125 件成功した。結果を `08_動作確認.md` に追記した。

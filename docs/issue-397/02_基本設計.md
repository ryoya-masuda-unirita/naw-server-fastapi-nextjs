# 02_基本設計

## 変更対象

- e2e-spec の並列数の既定値と、その説明
- vitest の非同期待ち（`findBy`・`waitFor`）の待ち時間の上限
- 通し実行で落ちた項目のうち、待ち時間の見直しが必要なテスト
- 原因が backend にあった場合は、該当する API（ルームの作成・削除）

## 画面 / API 変更概要

画面と API の仕様は変えない。テストの設定を変える。backend に原因があった場合だけ、そこを直す。

## 影響範囲

- e2e-spec の通し実行にかかる時間（並列数を下げると延びる）
- vitest の全体実行にかかる時間（待ち上限を伸ばしても、通常は延びない。タイムアウトまで待つのは失敗時だけ）
- 製品コードへの影響はない（backend に原因があった場合を除く）

## 進め方

1. 現状の再現: 通し実行・全体実行を、変更前の設定で回して、落ちる項目を確かめる
2. 切り分け: 落ちた項目を、要素待ちのタイムアウト、API の 500、切断に分類する。500 は backend のログで原因を確かめる
3. 対策: 並列数の既定を 2 に下げる、vitest の待ち上限を伸ばす、個別のテストの待ちを見直す。原因が backend にあった場合は、直すか別チケットにする
4. 検証: 通し実行を 2 回、vitest の全体実行を 2 回続けて回し、結果を記録する

## 現状（着手時点）

前の作業で、次の 3 つがコミットされずに残っている。検証はまだしていない。

- e2e-spec の並列数の既定を 4 から 2 に変更
- vitest の非同期待ちの上限を 5 秒に変更
- 上記に合わせた README の更新

## 確認したいこと

1. backend の 500 が負荷によるものと分かった場合、並列数を下げるだけで済ませてよいか。それとも、backend 側で同時操作に耐えるよう直す必要があるか
2. 並列数を 2 にして、通し実行の時間が許容できないほど延びた場合の扱い

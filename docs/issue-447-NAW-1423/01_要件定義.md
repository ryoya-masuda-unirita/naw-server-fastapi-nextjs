# 01_要件定義

## 機能要件

1. 共通関数 `fetchAllPages(fetchPage, pageSize = 1000)` を作ること。0 ページ目から順に取り、`total` に届くか、空のページが来たら止める。途中のページで失敗したら、そのまま失敗にする（一部だけの候補を作らない）。テストで確かめること
2. 次の 10 か所に適用し、21 件目（箇所により 51 件目、1,001 件目）以降も、候補・対応表に出ること
   - テンプレートメニュー、チーム候補、学習先フォルダ候補（アシスタント管理は変えない。下記）、フィードバックのアシスタント候補・学習先フォルダ候補、チーム詳細の追加候補 3 種、チーム管理一覧の名前の対応表、チャット履歴の利用者の絞り込み
3. チーム候補（`/admin/all-groups`）は、server の上限（100）に合わせて、1 ページ 100 件で取ること
4. 既存の挙動（失敗時に候補なしにする・ID のまま表示するなど）は、各所の今の扱いを変えないこと
5. 既存の `useUsageFilterUsers`（#426）の取得を、共通関数に置き換えて、重複した処理をなくすこと（挙動は変えない）

## 要判断

| # | 内容 | 推奨 |
|---|---|---|
| A | アシスタント管理の学習先フォルダ候補（`use-assistant-list.ts`、`size: 1000`）を、全ページ取得にするか | **変えない**。移植元も、`size: '1000'` の 1 ページのまま（`fetchAllPages` に変えていない）。1,000 件を超える学習先フォルダは、現実的でない |
| B | チーム管理一覧の「対応表の取得を待たずに一覧を出す」変更を、含めるか | 現状のこちらの依存を、詳細設計で確認する。**一覧が対応表の完了を待っているなら、含める**。待っていなければ、不要 |

## 非機能要件

- `vitest`・`tsc`・`eslint`・`vite build` が通ること
- 取得件数が多いと、通信が増える（1,000 件ごとに 1 回）。移植元と同じ
- 費用: なし

## スコープ外

- server の変更
- 利用状況タブの利用者絞り込み（#426・#432 で対応済み）

# GitHub Actionsによるバックエンドテストの導入

## 概要

バックエンドのテストをGitHub Actionsで自動実行する。プッシュ時は単体テストのみ、`develop`へのマージ時は単体・結合テスト両方を実行する。

## 説明

### 背景

現状、テストはローカルで手動実行するのみで、CIによる自動検証が存在しない。プッシュのたびに軽量な単体テストで素早くフィードバックを得つつ、`develop`へのマージ時（＝リリース相当のタイミング）には結合テストも含めて厳密に検証したい。

### 事前調査で判明したこと

- `backend/tests/unit/`・`backend/tests/integration/`とも、実際のPostgreSQLへの接続を必要としない（結合テストはSQLite in-memoryを使用し、`get_session`依存をオーバーライドしているため）。よってCI上でPostgresコンテナを起動する必要はない
- `backend/.env`（ローカル専用、gitignore対象）が存在しない環境でテストを実行すると、以下の8件が失敗することを確認した
  - `tests/unit/test_cors.py`の2件（`CORS_ALLOWED_ORIGINS`未設定のため許可オリジンが空になる）
  - `tests/unit/test_security.py`の1件・`tests/integration/test_auth.py`の5件（`Settings`の`DATABASE_URL`・`SECRET_KEY`が未設定でCookie発行時の`get_settings()`が失敗する）
- `backend/.env.example`を`.env`としてコピーするだけで全160件が成功することを確認済み。CI上でも同様の対応で解決できる

### やること

- `.github/workflows/backend-tests.yml`を新規作成する
- **プッシュ時**（`develop`・`main`以外のブランチへのプッシュ）：`backend/tests/unit`のみ実行
- **`develop`へのプッシュ時**（PRマージ後）：`backend/tests/unit`・`backend/tests/integration`の両方を実行
- 依存関係のインストールは`uv sync`を使用する（`backend/pyproject.toml`・`uv.lock`が既に存在する）
- テスト実行前に`backend/.env.example`を`backend/.env`としてコピーするステップを含める
- `backend/`配下の変更があった場合のみワークフローが走るよう`paths`フィルタを設定する

### 動作確認方法

- 実際にfeature branchへプッシュし、単体テストのみが実行されることをGitHub Actions上で確認する
- `develop`へのマージ（テスト用にdevelopへの軽微な変更をマージするか、既存の動作を確認できる形で）で単体・結合テスト両方が実行されることを確認する

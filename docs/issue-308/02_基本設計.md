# 02_基本設計

## 変更対象

- アシスタントカテゴリのサービス（作成・更新）
- アシスタントカテゴリのリポジトリ（同名判定の処理を削除）
- 単体テスト・結合テスト

## 画面 / API 変更概要

| API | 条件 | 変更前 | 変更後（移植元どおり） |
|---|---|---|---|
| カテゴリ更新 | 説明を省略・null・空白 | 説明を null・空白で上書き | 元の説明を残す |
| カテゴリ更新 | 別カテゴリと同名 | 400（独自メッセージ） | 500（DB の一意制約違反） |
| カテゴリ作成 | 既存カテゴリと同名 | 400（独自メッセージ） | 500（DB の一意制約違反） |

## 影響範囲

- 移植元クライアント（Angular）のカテゴリタブは、作成・更新の失敗を状態コードに関係なく汎用のエラートーストで表示する。400 から 500 に変わっても表示は同じ
- React 版の画面は同名エラーの文言に依存していない

## 移植方針

- 移植元の調査結果
  - カテゴリのサービスの更新処理: 名前・説明とも「空白でない」ときだけ上書きする。同名の事前チェックはない
  - カテゴリのサービスの作成処理: 同名の事前チェックはない
  - Liquibase のカテゴリテーブル定義: テナント ID・名前の組の一意制約がある
  - 共通の例外ハンドラ: DB 制約違反のハンドラがないため、Spring Boot 既定のエラー処理で 500 になる（既定のエラー画面のパスはセキュリティ設定で誰でも到達できる）
- 作成もそろえる判断: Issue は更新の 2 点を対象にしているが、作成の事前チェックも移植元に根拠がない同じ差分で、作成だけ 400・更新は 500 だと API 間で挙動がずれる。目標が移植元の完璧なクローンのため、作成もあわせて外す
- backend では一意制約違反を捕捉してロールバックし、500 の業務エラーとして共通のエラー形式で返す。捕捉せずに送出すると、FastAPI の最外周のエラー処理で応答が作られ、共通のエラー形式にならず CORS ヘッダーも付かない（ブラウザから状態コードを読めない）ため（code-review の指摘 1）

# 08_動作確認

## 確認環境
- ローカル（macOS）。性能の確認は、使い捨ての PostgreSQL 18（Docker、`tmpfs`、確認後に破棄）で行った。他のセッションの PostgreSQL（e2e-spec）には触れていない。AWS・インフラには触れていない（費用なし）
- データ: 3 テナント × 7,500 ルーム × 20 メッセージ = **450,000 メッセージ**、本文 450,010 件（質問・回答は日本語の繰り返し文）、フィードバック 22,500 件。外部キーの検査を切って、`generate_series` で作った

## 確認結果

| No | 確認内容 | 結果 |
|---|---|---|
| 1 | **実装前の失敗** | 新規テスト 4 件がすべて失敗 |
| 2 | 実装後 | 4 件すべて成功。サーバー全体 **1467 件すべて成功**。`ruff format --check`・`ruff check`・`mypy app` エラーなし |
| 3 | PostgreSQL でマイグレーション | `alembic upgrade head`（`issue309` → `issue433`）で索引ができ、`downgrade -1` で消え、`upgrade head` でもう一度できる |
| 4 | 実行計画（`EXPLAIN ANALYZE`） | 下の表 |

| クエリ | 索引なし | マイグレーションの索引 |
|---|---|---|
| ルームのメッセージ一覧（結合） | 168.9 ms（`message_contents` を Parallel Seq Scan） | 12.3 ms（Index Scan） |
| メッセージ ID 一覧から本文 | 200.8 ms（同上） | 10.2 ms（Index Scan） |
| メッセージ 1 件の削除（CASCADE） | 83.9 ms | 13.3 ms |

- 索引のサイズ: 14 MB（`message_contents` 全体は 367 MB）
- 参考: `messages (tenant_id, room_id)` の索引を足すと、ルームの一覧は 12 ms → 0.2 ms（この PR では足さない。別の Issue）

## 確認の途中で分かったこと
- `alembic check` は、このリポジトリの `env.py` では、無関係な差分（テーブルの追加・削除）が大量に出て、検査として使えない。モデルとマイグレーションの一致は、テスト（No.4）で確かめた
- 移植元（Liquibase）には、`message_contents.message_id` の索引も、`messages.room_id` の索引もない（`created_at`・`tenant_id` の索引だけ）

## 未確認事項
- **実データの規模・分布では確認していない**。上の数値は、ルームごとに 20 メッセージの均一なデータでの計測で、実際の傾向とは違う可能性がある。ルーム・メッセージの数が少ない環境では、効果は小さい
- **本番の `CREATE INDEX` の所要時間・書き込みの待ち時間は、計測していない**（`CONCURRENTLY` を使わないため、適用中、`message_contents` への書き込みが待たされる）
- **書き込み（INSERT・UPDATE）への影響は、計測していない**
- **実環境へは適用していない**。Deploy は旧環境向けで、動かない見込み（直近の `backend`・`frontend` ジョブは、AWS の OIDC ログインで失敗した）

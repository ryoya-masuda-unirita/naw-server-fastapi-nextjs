# message_contents に message_id の索引を足す

## 概要

Issue #433。`message_contents.message_id` で引ける索引を、マイグレーションで足す。**移植元にはない、こちら独自の改善**（移植元の Liquibase にも `message_id` の索引はない。`created_at`・`tenant_id` の索引だけ）。

## 背景

- `message_contents.message_id` は、`messages.id` への外部キー（`ON DELETE CASCADE`）。PostgreSQL は、外部キーの列に索引を自動では作らない。既存の `message_contents_created_at_idx` は `(id, created_at)` で、`message_id` には効かない
- `message_id` を使うクエリ: ルームのメッセージ一覧（`message_repository` の結合）、メッセージ ID 一覧からの本文の取得、フィードバック一覧の結合。さらに、**メッセージを削除したときの外部キーの `CASCADE`** が、`message_contents` を `message_id` で探す
- 性能への影響は、Issue 起票時は未計測だった。今回、使い捨ての PostgreSQL で計測した（`08_動作確認.md`）

## 計測結果（450,000 メッセージ・本文 450,010 件、`EXPLAIN ANALYZE`）

| クエリ | 索引なし | `message_contents(message_id)` | さらに `messages(tenant_id, room_id)` |
|---|---|---|---|
| ルームのメッセージ一覧（結合） | 168.9 ms | 12.4 ms | 0.2 ms |
| メッセージ ID 一覧から本文 | 200.8 ms | 10.2 ms | 0.2 ms |
| メッセージ 1 件の削除（CASCADE） | 83.9 ms | 13.5 ms | （未測定） |

- 索引なしでは、`message_contents` 全体を走査（Parallel Seq Scan）。索引ありでは、Index Scan
- **`messages` にも `room_id` の索引がない**（移植元にもない）。これを足すと、さらに 12 ms → 0.2 ms
- 索引のサイズ: `message_contents(message_id)` が 14 MB（テーブル全体 367 MB）

# 02_基本設計

## 変更対象

- `GroupListItemResponse`（グループ一覧レスポンススキーマ）
- `GroupService`（グループ一覧取得ロジック）
- `GroupAssistantRepository`（グループに紐づくアシスタントのIN句一括取得メソッドを追加）
- `GroupPromptTemplateRepository`（グループに紐づくプロンプトテンプレートのIN句一括取得メソッドを追加）

## 画面 / API 変更概要

- `GET /api/groups` / `GET /api/admin/groups` / `GET /api/admin/all-groups` のレスポンスにある `assistants`/`assistantIds`/`promptTemplates`/`promptTemplateIds` が、これまで常に空配列だったのが実データ（グループに紐づくアシスタント・プロンプトテンプレートのID一覧・名前一覧）を返すようになる
- レスポンスの型・フィールド構成自体は変更しない（値の中身のみ変更）

## 影響範囲

- グループ一覧を参照するフロントエンド画面（表示上フィールドが埋まるようになる。本Issueではフロントエンド側の実装変更は行わない）
- グループ一覧取得の内部処理（クエリ発行数が増える点に留意。IN句一括取得でグループ数に対して定数回のクエリに抑える）

## 移植方針

- 移植元 `GroupListResponse.from(Group group)` は、JPAのlazy loading経由で`group.getGroupAssistants()`等のコレクションを辿って組み立てているが、これは1グループ分の変換処理であり、一覧全体としてはN+1が発生する構造（Spring側の実装をそのまま踏襲すると非効率）。
- FastAPI側では、バックエンド規約（`N+1問題を発生させない`）に従い、一覧取得時にグループID一覧をまとめてIN句で1クエリ取得し、Python側でグループIDをキーに集約してから各グループのレスポンスを組み立てる方式に変更する（移植元のロジックそのものではなく、既存の`find_groups_grouped_by_template_ids`と同じ設計パターンを踏襲）。
- 具体的には、`GroupAssistantRepository`/`GroupPromptTemplateRepository`に、グループID一覧を受け取り `dict[group_id, list[tuple[id, name]]]` を返す新規メソッドを追加し、`GroupService.get_groups`/`list_groups`側で一覧取得後に1回ずつ呼び出して結果を`_to_list_item`に渡す。

## 設定の書き方

```json
"services": {
  "kb-learn-*": {
    "adapter": "embedding", "operation": "learn", "defaultSplitLength": 1000,
    "properties": { "...": "...", "VDB_TABLE_NAME": "docs_{name}" }
  },
  "bedrock-rag-*": {
    "outputType": 1, "properties": { "...": "..." },
    "retrieval": { "properties": { "...": "...", "VDB_TABLE_NAME": "docs_{name}" } }
  }
}
```

- キーが `*` で終わるものがひな形。`*` の前が「前の部分」（例: `kb-learn-`）。前の部分は空にできない
- ひな形の値の文字列にある `{name}` が、接尾辞に置き換わる（辞書・配列の中の文字列も対象）。`{name}` が 1 つもないひな形は、全フォルダが同じ保存先になるため、読み込み時に分かる失敗にする

## 処理の流れ

### 読み込み時（`parse_workflow_config`）

1. `services` のキーを、ひな形（`*` で終わる）と個別に分ける
2. ひな形は、検証用の接尾辞（`x`）で `{name}` を置き換えて、既存の `_definition` で読み、構造の誤りを起動時に見つける
3. 前の部分が同じひな形が 2 つあるとき、`*` の前が別のひな形の前の部分に含まれる（例: `kb-*` と `kb-learn-*`）ときは、長い前の部分を優先する（最長一致）。同じキーの重複は、JSON の仕様上、後勝ち

### 呼び出し時（`WorkflowRegistry.resolve`）

1. 個別に登録されたサービス ID があれば、それを返す（従来どおり）
2. 前の部分で始まり、接尾辞が 1 文字以上のひな形があれば、その接尾辞を検証する
   - 検証は、英小文字・数字・アンダースコアで 1〜40 文字（`^[a-z0-9_]{1,40}$`）
   - 不正なら、`EmulatorError(400, "...")`。保存先は作らない
3. 検証を通ったら、接尾辞を入れた定義からワークフローを作り、サービス ID に結びつけて使い回す
4. ひな形に当てはまらないときは、従来どおり（学習・同期の判別 → 既定）

### 接尾辞の検証

- テーブル名は SQL に埋め込まれるため、既存のテーブル名の検証（`TABLE_NAME_PATTERN`）に加えて、接尾辞そのものを先に厳しく検証する
- 大文字を許さないのは、PostgreSQL のテーブル名が引用符なしでは小文字になり、`HR` と `hr` が同じ保存先になるのを避けるため

## 4 つの名前をそろえる運用

| 用途 | サービス ID の例（フォルダ `hr`） |
|---|---|
| 学習 | `kb-learn-hr` |
| 取得（同期） | `kb-sync-hr` |
| 削除 | `kb-delete-hr` |
| 質問（アシスタント） | `bedrock-rag-hr` |

そろえ間違い（例: 学習 `hr`、質問 `hrr`）は、検知しない。質問側が空の保存先を探すだけで、失敗にはならない。README に注意として書く。

## 不要コードの確認

- 既存の設定の読み込み・解決の処理は変えない（ひな形がなければ、従来と同じ）
- 他に孤立するコードはない

# 02_基本設計

## 変更対象

- ワークフローの設定の読み込み（ひな形を書けるようにする）
- サービス ID からワークフローを選ぶ処理（ひな形に一致するサービス ID から、その接尾辞で作ったワークフローを返す）
- 例の設定（Bedrock）と、waha-emulator・onprem の README

## 画面 / API 変更概要

- 画面・外部 API の変更はない（サービス ID を受け取る口は、そのまま）
- 設定ファイルの `services` に、ひな形のキー（末尾が `*`）を書ける（例: `kb-learn-*`）。ひな形の設定の中の `{name}` が、接尾辞に置き換わる

### 使い方（イメージ）

学習先フォルダ「hr」を作るとき、画面で次を入れる。

| 画面の入力 | 入れる値 |
|---|---|
| 学習データ学習用サービス ID | `kb-learn-hr` |
| 学習データ取得用サービス ID | `kb-sync-hr` |
| 学習データ削除用サービス ID | `kb-delete-hr` |
| アシスタント（セキュア）のサービス ID | `bedrock-rag-hr` |

保存先は `docs_hr` になる。別のフォルダ「expense」には、`kb-learn-expense` などを入れる。設定の追記と再起動は要らない。

## 影響範囲

- ひな形を使わない既存の設定は、動作が変わらない
- 例の設定に、ひな形の項目を足す（`onprem/config/workflows.bedrock.example.json`）。ユーザーの手元の設定（`workflows.json`）は変わらない
- 接尾辞を付けないサービス ID（`kb-learn` など）は、従来どおり 1 つの保存先（`docs`）を使う

## 移植方針

- 移植元にない、エミュレーター（検証用）だけの拡張。移植元の設計（サービス ID の先が保存先を決める）は変えず、ジョブを用意する手間だけを減らす
- ひな形の判定は、設定の読み込み時に行い、サービス ID が実際に呼ばれたときに、接尾辞を入れた設定からワークフローを作る。同じサービス ID は、作ったものを使い回す
- 接尾辞の検証（英小文字・数字・アンダースコア、長さ）は、ワークフローを作る前に行い、不正なときは、既存のサービス ID の失敗と同じ形で返す
- 優先順位は、個別に書いたサービス ID → ひな形 → 学習・同期の判別 → 既定の順

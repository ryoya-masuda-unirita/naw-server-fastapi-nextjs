# 01_要件定義

## 背景

- #228 で、入力チェックのエラーは 400・`{timestamp, message}`・最初の 1 件のメッセージ、という移植元の形に揃えた
- ただし、文字数の上限・必須・数値の範囲など、フレームワーク組み込みの制約で弾いたエラーのメッセージは Pydantic の英語の既定文言（例: `String should have at most 32 characters`、`Field required`）のまま
- 移植元は Request クラスの Bean Validation の注釈ごとに日本語のメッセージを指定しており、クライアントはそのメッセージを画面に出す。backend でも同じ文言を返す

## 移植元のメッセージの決まり方（参照実装を読んだ結果）

- 入力チェックのエラーは、共通の例外ハンドラが「最初の 1 件の違反のメッセージ」を返す（#228 で確認済み）。メッセージは注釈の `message` 属性で、指定が無ければ Bean Validation 実装（Hibernate Validator）の既定文言になる
- 移植元には独自の `messages.properties`・`ValidationMessages.properties` が無く、ロケールの設定（`LocaleResolver`・`MessageSource`・`spring.web.locale`・JVM の `user.language`）もしていない。コンテナの起動コマンドにもロケールの指定は無い
- そのため既定文言は、Spring Boot の既定どおりリクエストの `Accept-Language` のロケールで補間される（Spring の Validator は要求ごとのロケールで文言を組み立てる）。`Accept-Language` が無いときは JVM の既定ロケールになる
- 移植元が使う Hibernate Validator（Spring Boot 3.5.10 の既定の 8.0.3.Final）の日本語の既定文言を jar から確認した（下表）
- クライアント（Angular）は日本語の画面で、`Accept-Language` を上書きしていない。日本語のブラウザが自動で付ける `Accept-Language: ja` により、移植元は日本語の既定文言を返す。これを移植元の実際の応答として揃える

| 注釈 | 日本語の既定文言（8.0.3.Final） | 英語の既定文言（参考） |
|---|---|---|
| `@NotBlank` | 空白は許可されていません | must not be blank |
| `@NotNull` | null は許可されていません | must not be null |
| `@NotEmpty` | 空要素は許可されていません | must not be empty |
| `@AssertTrue` | true にしてください | must be true |

## 移植元の Request の制約とメッセージ（全件）

移植元の Request クラス（リクエストを受けてサービスで検証するモデルを含む）にある Bean Validation の制約をすべて洗い出し、backend の対応と突き合わせた。「対応」の意味は次のとおり。

- **揃える**: 本 Issue で backend のメッセージを移植元と同じにする
- **一致済み**: 既に同じ文言を返している
- **対象外**: 理由を備考に書く（backend 独自の制約・API が未移植・利用者が値を指定できない項目など）

「既定」は注釈に `message` の指定が無く、上表の日本語の既定文言になるもの。

### Request クラス以外の検証（対象外）

- 移植元のエンティティ（プロンプトテンプレート・テナントエンドポイント・ユーザー）にも Bean Validation の注釈があるが、コントローラーでは検証しておらず Request クラスではないため対象外とする
- テナント名の 32 文字以内（テナント管理の更新）・tenantName の null 不可、テンプレート名の 32 文字以内（#171）は backend 独自の制約のため変えない

## 機能要件

1. 上表で「揃える」とした制約に違反したとき、400 の `message` に移植元と同じ文言を返す
2. 必須の制約（空白不可・null 不可・空不可）は、項目の欠落・null の両方で移植元の文言を返す。空白不可・空不可は、空文字（空配列）で弾いた場合も同じ文言にする
3. 移植元にメッセージ指定が無い制約は、上記の日本語の既定文言を返す
4. 独自チェックの文言で、移植元と違うもの（フィードバックの並び替え、トークン使用量の期間・並び替え、埋め込みの input、アシスタント更新の名前）は移植元の文言に揃える
5. 型が違う値（数値の項目に文字列を送るなど）・列挙外の値・JSON として読めないボディなど、移植元では Bean Validation に届かないエラーは、これまでどおり英語の既定文言のままとする
6. 複数のエラーがあるときに最初の 1 件だけを返すこと、応答の形・ステータスは #228 から変えない

## 非機能要件

- 文言は項目の定義のそばに書き、移植元の注釈と見比べやすくする（新しい項目を移植するときに同じ書き方で足せること）
- 受け付ける値・弾く値（制約そのもの）は変えない。OpenAPI のスキーマ（最大長・範囲など）も変えない

## スコープ外

- **制約の差分**: 移植元にあって backend に無い制約（パスワードリセット・ユーザー作成・アシスタントのエンドポイントの空白のみの拒否、ユーザー作成・更新の loginKey の拒否など）は追加しない。本 Issue は文言を揃えるもので、受け付ける値を変えると別の影響があるため。必要なら別 Issue で扱う
- **未移植の API**（ライブラリ作成・タイトル更新）
- **移植元で Bean Validation を通らないエラー**（型変換・JSON の読み込み・必須のクエリパラメータの欠落など。Spring の既定の応答で `message` が無い）の文言
- **`Accept-Language` による言語の切り替え**: 移植元は `Accept-Language` が日本語以外（または無し）だと英語の既定文言を返すが、backend は常に日本語の文言を返す（クライアントは日本語の画面のみのため）
- frontend（React）は変更しない

# 02_基本設計

## 変更対象

- backend の入力チェックの文言を項目ごとに指定する共通の仕組み（新規）
- 01 の表で「揃える」とした項目を持つリクエストのスキーマ（アシスタントカテゴリ・アシスタント・メッセージ・ツール設定・フィードバック一覧・ライブラリ・ライブラリタグ・LLM・パスワードリセット・ユーザー作成・テナント管理の更新・トークン使用量）
- ライブラリ一覧 API のクエリパラメータ（ページ番号・件数）
- テスト（共通の仕組みの単体テスト、項目ごとの文言のテスト）
- backend の規約（バリデーションの書き方）

## 画面 / API 変更概要

400 の `message` の文言だけが変わる。ステータス・応答の形・受け付ける値は変わらない。

| 例 | 変更前 | 変更後 |
|---|---|---|
| カテゴリ名が 17 文字 | String should have at most 16 characters | カテゴリ名は16文字以内で入力してください |
| タグ作成で name が無い | Field required | タグ名は必須です |
| ユーザー作成で role が null | Input should be 'ADMIN', ... | null は許可されていません |
| ライブラリ一覧で size=0 | Input should be greater than or equal to 1 | ページサイズは1以上である必要があります |
| トークン使用量で from が日時でない | Input should be a valid datetime ... | 開始日時は YYYY-MM-DDTHH:mm:ssZ 形式で指定してください |
| フィードバック一覧で sortOrder=x | sortOrder は asc または desc です | ソート順は asc または desc を指定してください |

### 移植元と完全には一致しない点

- **複数の違反があるときの 1 件目**: 移植元は違反の集合の並びが決まらず、どれが 1 件目になるかは不定。backend は項目の定義順で最初のエラーを返す（#228 と同じ）
- **必須のクエリパラメータの欠落**（トークン使用量の from・to）: 移植元は Bean Validation に届く前に Spring の既定の応答（`message` なし）になる。backend は #228 で全入力エラーを `{timestamp, message}` に揃えたため、同じ項目の必須の文言（「開始日時は必須です」）を返す
- **トークン使用量の合計 API の from・to の形式**: 移植元の合計 API は from・to に形式・必須の制約を持たない（形式が不正だとサービスで解析に失敗する）。backend は一覧と合計で同じ期間の検証を共有しているため、一覧と同じ文言を返す
- **`Accept-Language`**: 移植元は日本語以外のロケールだと英語の既定文言になるが、backend は常に日本語（01 のスコープ外）

## 実装方式

### 選択肢

| 方式 | 内容 | 評価 |
|---|---|---|
| A. 各項目に独自チェックを書く | 文字数・必須などを Pydantic の宣言ではなく、項目ごとの独自チェック（例外に日本語を入れる）で書き直す | 項目の欠落はモデルの独自チェックでしか拾えず、1 項目で複数の独自チェックが要る。制約を宣言から手続きに書き換えるため OpenAPI のスキーマ（最大長など）が消える。項目数（約 40）ぶんの重複が増える |
| B. 共通のマッピングを 1 か所に置く | エラー応答の組み立て時に「位置とエラーの種類 → 文言」の表を引く | エラーの位置（`body.name` など）からはどのモデルの項目か分からず、同じ名前の項目（name・page・size など）で文言が違うものを区別できない。項目の定義と文言が離れ、移植時に表の更新を忘れやすい |
| **C. 項目に文言を添え、共通の仕組みで置き換える（採用）** | 項目の型注釈に「制約の種類 → 文言」を添える。共通の仕組みが、その項目で起きた組み込みの制約のエラーだけを指定の文言に置き換える | 制約の宣言（最大長など）はそのままなので受け付ける値・OpenAPI は変わらない。文言が項目の定義のすぐ横に並び、移植元の注釈（`@Size(message=...)` など）と一対一で見比べられる。置き換えの規則は 1 か所 |

### 採用理由（保守性）

- 移植元は「項目の注釈に文言を書く」作りで、新しい API の移植は Request クラスを見ながら項目を書く作業になる。方式 C なら注釈の種類（`@NotBlank`・`@Size`・`@Min` など）と同じ名前の引数に文言を書けばよく、移植時の書き漏れ・取り違えが起きにくい
- 制約は今までどおり宣言的に書けるため、既存の書き方（`Field(max_length=...)` 等）を壊さず、変更は文言の追加だけで済む
- 置き換えの規則（Pydantic のどのエラーをどの注釈に対応させるか）を 1 か所にまとめられ、Pydantic の更新でエラーの種類が変わっても直す場所が 1 つ

### 仕組みの概要

- 項目に添える文言の指定は、移植元の注釈に合わせて「空白不可」「null 不可」「空不可」「文字数」「最小値」「最大値」「ISO-8601 の日時」の 7 種類
- Pydantic のエラーの種類との対応

| 文言の種類（移植元の注釈） | 置き換えるエラー |
|---|---|
| 空白不可（`@NotBlank`） | 項目の欠落、null、空文字、空白のみの文字列での型・形式のエラー |
| null 不可（`@NotNull`） | 項目の欠落、null |
| 空不可（`@NotEmpty`） | 項目の欠落、null、空文字、空配列 |
| 文字数（`@Size`） | 文字数・件数の上限超過 |
| 最小値（`@Min`・`@DecimalMin`・`@PositiveOrZero`） | 下限未満 |
| 最大値（`@Max`・`@DecimalMax`） | 上限超過 |
| ISO-8601 の日時（`@ISO8601Instant`） | 日時として解釈できない |

- 独自チェック（例外に文言を入れて送出するもの）のエラーは置き換えない。既に移植元の文言を返している、または backend 独自の検証のため
- 項目の値の検証で起きるエラーは項目単位で置き換える。項目の欠落は項目の検証が呼ばれないため、リクエストのモデルの共通の基底で置き換える。文言を指定した必須項目を持つモデルは、この基底を継承する
- クエリパラメータ（ライブラリ一覧のページ番号・件数）も、同じ文言の指定を型注釈に添えるだけで置き換わる
- 移植元の既定文言（「空白は許可されていません」など）は定数として 1 か所に置き、各項目から参照する

## 影響範囲

- 上記の API の 400 の `message` の文言。ステータス・応答の形・正常系の応答は変わらない
- 受け付ける値・弾く値は変わらない（制約は変更しない）
- OpenAPI のスキーマ（最大長・範囲・必須）は変わらない
- 既存テストのうち、変わる文言を確かめているものは新しい文言に直す

## 移植方針

- 文言は移植元の Request クラスの注釈の `message` をそのまま写す（句点の有無・全角/半角も同じ）。指定が無いものは Hibernate Validator 8.0.3.Final の日本語の既定文言にする
- backend 独自の制約・独自チェックの文言は変えない
- 新しい API を移植するときも同じ書き方で文言を添えるよう、backend の規約に書き方を追記する

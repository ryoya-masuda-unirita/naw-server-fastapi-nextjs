# 02_基本設計

## 変更対象

- `backend/app/schemas/llm.py`（`LlmChatRequest`）
- `backend/app/schemas/message.py`（`MessageContentCreateRequest`）
- `backend/app/schemas/response_format.py`（新規、共有スキーマ）
- `backend/app/core/llm_client.py`（`AzureLlmChatClient.stream_chat`）
- `backend/app/services/llm_chat_service.py`（`LlmChatService.stream_chat`）
- `backend/app/services/message_service.py`（`MessageService.stream_message_content`）

## API 変更概要

- `POST /api/llm/chat`・`POST /api/messages/content` のリクエストボディに、任意項目 `responseFormat: { type: "json_object" | "json_schema" }` を追加する
- レスポンス（SSEイベント）の形式・イベント種別は変更しない
- `responseFormat` を指定した場合、LLM応答がJSON形式で返るよう促す。何が返るか自体はLLM依存であり、サーバー側でJSONとしてのパース・検証は行わない（移植元同様）

## 影響範囲

- `llm_chat_service.py`・`message_service.py`は「serviceが別serviceを呼ばない」規約により、`responseFormat`をLLM呼び出しパラメータへ変換するロジック（JSON指示文の前置・`response_format`辞書の組み立て）はそれぞれのファイルに複製する（既存の`_apply_additional_prompt`・`_sse`と同様の方針）
- `AzureLlmChatClient.stream_chat`のシグネチャに`response_format`引数が増えるため、2つの呼び出し元・既存テスト（`tests/unit/test_llm_client.py`）に影響する

## 移植方針

- 移植元のDTO構造（`type`/`json_schema`）はそのまま踏襲しつつ、バリデーション実装は移植元の`record`内`validate()`メソッド方式ではなく、backend規約（Pydantic v2の`@field_validator`）に従う
- 移植元のResponses API固有の型（`ResponseFormatJsonObject`等）は使わず、Chat Completions APIの`response_format={"type": "json_object"}`辞書へ変換する薄いアダプタとして実装する
- `json_schema`の中身は移植元同様に未使用のまま（受け取っても無視する）。将来対応する場合の設計は本Issueでは行わない

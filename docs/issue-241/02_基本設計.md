# 02_基本設計

## 変更対象

- GitHub Actions のワークフローを 1 本新設する（フロントエンドテスト）
- デプロイワークフロー（フロントエンド）のコメントのうち、「フロントエンドのテストを実行する CI は他にない」という記述を実態に合わせて直す（処理は変えない）

## 画面 / API 変更概要

- 画面・API の変更なし

## 影響範囲

- フロントエンドに変更がある PR の画面に、新しいチェック「lint・型チェック・テスト・ビルド」が表示される
- develop へのマージ時は、既存のデプロイワークフローとは別に、このワークフローも並行して走る（相互に依存しない）
- アプリケーションコードへの影響はない

## 設計方針

| 項目 | 方針 | 理由 |
|---|---|---|
| トリガー（PR） | 向き先が develop / main の PR で、フロントエンド配下かワークフロー自身に変更がある場合 | Issue の要件どおり。フィーチャーブランチ同士の PR では走らせない |
| トリガー（push） | develop への push で、同じパス条件 | マージ後の develop の状態も検証する。作業ブランチへの push は PR 側で検証されるため重複させない |
| ジョブ構成 | 1 ジョブにまとめ、各チェックをステップに分ける | ジョブを分けるとジョブごとに依存のインストールが走り時間がかかる。ステップを分けるので失敗箇所は特定できる |
| Node バージョン | 24（デプロイワークフローと同じ） | 実行環境を揃える。ビルドツールの要件も満たす |
| 依存インストール | lockfile どおりにインストールし、ズレがあれば失敗させるコマンド | lockfile が npm のもの。バックエンドの「lock ずれ検出」と同じ考え方 |
| キャッシュ | Node セットアップの npm キャッシュを、フロントエンドの lockfile をキーにして使う | デプロイワークフローと同じ指定 |
| 各チェックのコマンド | パッケージ定義の既存スクリプト（lint / type-check / test / build）を使う | 手元でも同じコマンドで再現できる。type-check スクリプトは既にあるため追加不要 |
| テスト | test スクリプトに 1 回だけ実行するオプションを渡す | test スクリプトはウォッチモードのため |
| 権限 | contents: read | コード取得のみで十分 |

## 移植方針

- 移植作業ではない（移植元に対応するものはない）

# 01_要件定義

## 目的

RAG チャットを、本物の Waha! のジョブと同じ「検索アダプタ → 生成AIアダプタ」の 2 段で動かす。#298 では検索アダプタがなかったため、RAG の入力は固定の RAG Context JSON ファイルだった。それを、ベクトルDB を実際に検索した結果に置き換える。

## 要件

| # | 要件 | 根拠 |
|---|---|---|
| R1 | 移植元 `retrieval-adapter` の App（プロパティの保存時検証・設定・出力モード 0/1・列の定義）を Python に移す | Issue 本文 |
| R2 | 出力形式 `LEGACY_TSV`（`"id"` をタブ区切り + 改行）と `RAG_CONTEXT_JSON_V1`（最大 20 件、本文 8000 文字まで、安全な出典パスだけ、Graph 根拠のパス）を移植元どおりに出す | `docs/rag-context-json-contract.md`、`RetrievalOutputFormat` |
| R3 | core の retrieval（ベクトル検索・ハイブリッド（PGroonga + RRF + リランク）・Graph RAG（AGE））と Azure AI Search / PostgreSQL(pgvector) のプロバイダ、クエリ埋め込みを移植元の構造のまま移す | Issue 本文 |
| R4 | GraphRAG・ハイブリッドで AGE・graph・PGroonga・スキーマが足りないときは、ベクトルだけの成功にせず分類付きの失敗にする | `retrieval-adapter/AGENTS.md` |
| R5 | エミュレーターのサービス定義に `retrieval` を足し、RAG の前に検索アダプタを動かして、出力を生成AIアダプタの列 index 6 に渡す | Issue 本文、#298 の設定の持ち方 |
| R6 | チャット 1 回の流れ（検索 → 生成AI）を INFO ログで追える。秘密（パスワード・API キー）はログに出さない | Issue 本文 |
| R7 | DB・Azure・LLM に接続しない自動テスト。実 DB は手元の Docker で確認し、結果を 08 に貼る | 依頼 |
| R8 | #300 と衝突しにくいよう、core の共通部分は #298 のものを使い、retrieval 固有を足す | 依頼 |

## 範囲外

- ベクトルの保存・更新・削除、文書の分割（embedding-adapter。#300）
- 移植元の評価・リリース判定用のコード（`retrieval.releasegate` の評価系、`retrieval.graph` の証拠モデル）。実行時の検索から呼ばれないため移植しない（03 に詳細）
- 本物の Waha! の管理コンソール、ライブラリ生成・学習の API

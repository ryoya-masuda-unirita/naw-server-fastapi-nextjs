## 検索 → 生成AI の流れ

```
質問 ─► 検索アダプタ App（出力モード 1）
          └ RetrievalController ─► core CoreRetrievalRuntime
                 ├ RuntimeQueryClassifier / StrategySelector（クエリ分類 → 戦略）
                 ├ PostgreSQL: ベクトル検索 ┬ ハイブリッド（PGroonga + RRF + LLM リランク）
                 │                           └ Graph RAG（readiness 確認 + AGE で近傍を広げる）
                 └ Azure AI Search: ベクトル検索
        ─► RAG Context JSON（ジョブのディレクトリ /rag-context.json）
        ─► 生成AIアダプタ App（出力モード 1。列 index 6 = そのパス、許可ルート = ジョブのディレクトリ）
        ─► RetrievalAnswer JSON（outputfile）
```

Waha! の呼び方（`set_property` → `connect` → `set_column_information` → `set_view_name` → `before_execute` → `write`）は 2 つのアダプタで同じ。

## サービス ID → ワークフローの持ち方（#298 に合わせる）

`WAHA_WORKFLOWS_FILE` の `services.<サービスID>` に `retrieval.properties` を足す。

- 検索アダプタのプロパティは `RetrievalPropertyIds` の名前で書く（番号は生成AIアダプタと別。例: 42 は VDB パスワード）。`VENDOR`・`VDB_VENDOR` は名前でも ID でもよい。値は `${環境変数}` で参照できる
- `OUTPUT_DIR`・`TEXT_DATA_JSON_FILE_PATH` はエミュレーターがジョブごとに決める（textData は生成AIアダプタと同じファイルを検索アダプタにも渡す）
- `retrieval` は出力モード 1 のときだけ。`ragContextJson`（固定入力）・`RAG_CONTEXT_JSON_ALLOW_ROOT` とは同時に書けない（検索の出力をエミュレーターが渡すため）
- 不正な設定は起動時に失敗させる（検索アダプタの保存時チェック `validate_property` を通す）。`ragContextJson` は検索アダプタを使わない確認用に残す

## 入力スロットと検索アダプタの対応

| 入力 | 検索アダプタへの渡し方 |
|---|---|
| 質問 | 検索文字列の列（index 0、文字）。移植元の列定義は FILE だが、`CHAR` も受け付ける（`data.s`）ので質問をそのまま渡す |
| textData | プロパティ 52（SecuAiGent の URL・トークン・テナント・deployName の上書き） |
| 定義の `retrieval.properties` | そのままのプロパティ |

## 影響範囲

- `ragContextJson` だけを書いた既存のサービス定義・`LLM_PROVIDER` による既定の定義は、これまでどおり動く
- エミュレーターの依存に `psycopg` が加わる（core の検索が PostgreSQL に接続するため）
- 検索を使うサービスは、検索の失敗（DB に届かない・スキーマ不足など）が `/result` の失敗理由（「検索アダプタの実行に失敗しました: …」）になる

## 移植方針

- 移植元のクラス・メソッドの構造と挙動をそのまま移す（命名は Python に合わせる）。迷ったら移植元のコードを正とする
- Spring `JdbcTemplate`・PG JDBC・Spring `RestClient`・Gson は、同じ入出力になるよう `psycopg`・`httpx`・`json` で書き換え、再現できなかった差は 03 に列挙する
- core の共通部分（provider・network・chat・media・failure）は #298 のものを使う。#300 の担当（embedding・前処理・ベクトルの保存）は、検索側で必要な最小限だけを retrieval 内に置く（03）

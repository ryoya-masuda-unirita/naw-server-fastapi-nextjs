## #300 との境界（衝突を減らすための判断）

| 移植元 | 扱い | 理由 |
|---|---|---|
| core `embedding`（CoreEmbeddingRuntime ほか）と `CoreProviderRuntimeFactory.createEmbeddingRuntime` | **移植しない**。検索の中の `retrieval/query_embedding.py` に、クエリ 1 件を埋め込むだけの最小の呼び出し（`embed_text`）を置く。`QueryEmbeddingGenerator` のインターフェースは同じなので、#300 の embedding が入ったら `embed_text` を置き換えるだけで済む | embedding パッケージ・factory は #300 が触る |
| `graphrag.bootstrap` | VERIFY_ONLY（読み取りで確認）だけを `retrieval/graph_readiness.py` に移す。CREATE_IF_MISSING（canonical SQL の実行）・`graphrag.ingestion` は移植しない | 作る側は embedding-adapter の担当 |
| `vector`（`CoreVectorDbTarget`・AGE セッション・PGroonga インデックス名） | 検索が使う部分だけ `vector/target.py` に移す。保存・更新・削除（`CoreVectorDbRuntime`・`PgVectorCoreVectorDbProvider` ほか）は移植しない | 同上 |
| `resource` | 全部移す（小さい） | 検索の graph 名・インデックス名の導出に要る |

core の既存ファイル（provider・network・chat・media・failure）は変更していない。core の `pyproject.toml` に `psycopg[binary]` を足しただけ。

**マージ時に重なりうるファイル**: `generative-ai-adapter/pyproject.toml`（members・testpaths・mypy_path）、`generative-ai-core/pyproject.toml`（依存）、`vector/`・`resource/` の `__init__.py`、emulator の `Dockerfile`・`Dockerfile.dockerignore`・`pyproject.toml`・`uv.lock`。内容は足すだけ。

## 移植元から省いたもの

| 省いたもの | 理由 |
|---|---|
| core `retrieval.releasegate` の評価系（MetricCatalog・各 Evaluator・Evidence 類） | 合成データだけで動くリリース判定。実行時の検索から呼ばれない。実行時に要る `QueryType`・`RetrievalStrategy`・`RouterEvaluator.expectedStrategies` だけ移した |
| core `retrieval.graph`（BusinessImpactPath* ほか） | 実行時の検索（`CoreRetrievalRuntime` 以下）から呼ばれない |
| adapter `graph.GraphRagSearchException`・`GraphRagSearchErrorSanitizer`・`GraphRagSearchStatus`、`domain.*`（`PromptTemplate`・`RequestChatSchema`・`RequestEmbeddingSchema`） | main のどこからも使われない |
| `RetrievalController.testConnect`・`requestEmbeddingApi`・`formatIdsForOutput`・`resolveOutputIds`、`App.createSampleData`・`readColumnData` | 検索の実行に使われない（`App.testConnect` はプロキシ設定の確認だけで、移植済み） |
| `NonGoalExecutionProbe` のカウンタ類 | 実行時は常に 0。ID だけ持つ |
| Lombok / Gson / Spring の型 | Python の標準的な書き方で同じ入出力にした |

## 移植元と同じにした挙動（気づきにくいもの）

- `RAG_CONTEXT_JSON_V1`: 最大 20 件、本文 8000 文字、`sourceFilePath` は URL・JDBC・秘密らしい語を含むと出さない、Graph 根拠は `A --型(ラベル)--> B` を検証し深さ 1〜3・パス 7 要素まで。`graphOnly.<id>` かつ根拠不正のコンテキストは除く
- VDB プロバイダ 0（`Azure AI Search`）: 移植元のマッパーは `AzureOpenAI` という名前のときだけ Azure の接続先・プロバイダ ID を作るため、`Azure AI Search` は検索プロバイダが未対応（`UNSUPPORTED_PROVIDER`）になる。**移植元と同じにした**（報告に記載）。Azure AI Search の検索そのものは core のテスト（`AzureOpenAI` を渡す）で確かめた
- プロパティ 30 のベンダー表は検索アダプタ専用（`2`=VertexAI Gemini・`3`=Anthropic。生成AIアダプタと番号が違う）。Python 版だけ `99`=Echo
- ハイブリッドで FTS の候補が先に入ったチャンクは、ベクトル検索の出典（`sourceRef`・`sourceFilePath`）ではなく FTS 候補の出典（`postgresql-pgroonga`）が使われる（移植元の `Accumulator` が最初の候補を残すため）。**移植元と同じ**で、実 DB の確認（08）でも `filepaths` に `postgresql-pgroonga` が出る
- ハイブリッドの候補の本文・出典は `CoreFailureSanitizer.sanitize` を通る（URL や `token=…` が伏せ字になる）。ベクトルだけの経路は通らない
- `CoreFailureSanitizer` は `postgres://user:pass@host` 形式の URL を伏せない（jdbc: と http(s) だけ）。移植元と同じ

## Python 版で変えた点（再現できなかった差）

| 項目 | 内容 |
|---|---|
| DB 接続 | PG JDBC + `JdbcTemplate` → `psycopg`（検索ごとに接続し、プールなし。移植元の `PGSimpleDataSource` と同じ）。SQL は同じで、パラメータは `?` → `%s` |
| AGE の Cypher | 第 3 引数の agtype は、`TypeInfo.fetch(conn, "agtype")` で OID を取って `AgtypeParameter` として送る（実 DB で確認） |
| クエリの埋め込み HTTP | Spring AI / Azure SDK が作る HTTP を `httpx` で直接作った。OpenAI は `POST {URL}/v1/embeddings`（本文 `input`・`model`・`encoding_format=float`）、Azure は `POST {URL}/openai/deployments/{モデル}/embeddings?api-version=2025-01-01-preview`（`api-key`、#298 の chat と同じ版）、SecuAiGent は移植元の `SecuAiGentEmbeddingClient` と同じ。Spring AI の埋め込みの本文は jar を読んで確かめていない（chat と違い推定）。実際の埋め込み API には接続していない |
| Echo の埋め込み（Python 版だけ） | 文字 2-gram のハッシュによる擬似ベクトル。キーなしで通しの確認をするため |
| Gson の JSON | `json.dumps(ensure_ascii=False, separators=(",", ":"))` + U+2028/2029 のエスケープ |
| `generatedAt` | `OffsetDateTime.now(UTC).toString()` → `datetime.isoformat()` の `Z` 表記（生成AIアダプタの読み取りで受理されることをテストで確認） |
| `IllegalArgumentException` | `ValueError`、`RuntimeException` → `RuntimeError` |

## エミュレーター

- `workflow_config.py`: `RetrievalDefinition`、`retrieval` の読み込みと検証（上の 02）。`_properties` を汎用化（ID 表・予約名・名前→ID の変換・検証関数を引数で差し替え）
- `workflows/generative_ai.py`: `RetrievalJob`、`_build_retrieval_job`、`_run_retrieval_step`（検索 → 出力の存在確認 → 生成AI）。検索アダプタの失敗は `WorkflowError("検索アダプタの実行に失敗しました: …")`
- ログ: `workflow step 1/2 retrieval: …`（列・プロパティ名。値は出さない）→ `retrieval: …` → `core retrieval: provider=…, queryType=…, strategies=…` → `postgresql retrieval: route=vector|hybrid` → `query embedding: …` → `core retrieval finished: ids=N` → `retrieval output written` → `step 1/2 … finished: contexts=N` → `step 2/2 generative-ai`

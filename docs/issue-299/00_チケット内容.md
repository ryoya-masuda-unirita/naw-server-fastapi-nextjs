# 検索アダプタとcoreの検索部分をPythonに移植しWaha!エミュレーターに差し込む

Issue: #299（依存: #298）

## 概要

移植元 `generative-ai-adapter/retrieval-adapter` と `generative-ai-core` の retrieval 部分（vector・hybrid（PGroonga）・Graph RAG（PostgreSQL + AGE）、Azure AI Search・PostgreSQL/PGVector のプロバイダ）を移植し、エミュレーターの RAG チャットのワークフロー（検索 → 生成AI）に差し込む。出力は `LEGACY_TSV`（outMode=0）と `RAG_CONTEXT_JSON_V1`（outMode=1）。

## 方針（Issue 本文）

- 移植元（Java）の 4 プロジェクトと同じ分け方のまま Python に移植する（完璧なクローン）。置き場所はルートの `generative-ai-adapter/` 配下の Python パッケージ
- アダプタはサーバーではなくライブラリ。`waha-emulator/` のワークフローから import して呼ぶ。Waha! 固有の受け口は、エミュレーター側の設定・入出力に置き換える
- 本物の Waha! のワークフロー定義はどちらのリポジトリにもないため、移植元のコード・テスト・docs から読み取って決め、根拠を docs に書く
- チャット 1 回でどのアダプタがどの順に何を受け取り何を返したかを、エミュレーターのログ（INFO）で追えるようにする

## 依頼時の追加条件

- #298（生成AIアダプタ。マージ済み）の作り方に揃える（`generative-ai-adapter/README.md`、`docs/issue-298/`、`waha-emulator/`）
- 実際の DB・Azure には接続しない自動テスト（DB・HTTP はモック）。可能なら `onprem/` の vector-db の Docker で PostgreSQL + pgvector の実接続を手元で確認し、結果を 08 に貼る。確認後はコンテナを片付ける
- 別のエージェントが #300（埋め込みアダプタ・core の embedding と前処理）を並行で進める。core の共通部分（プロバイダ・ネットワーク）は #298 のものを使い、retrieval 固有の部分だけを足して衝突を減らす
- docstring は NumPy 形式（日本語。`Parameters`・`Returns`・`Raises`）。追加・変更したすべての関数・メソッド・クラスに書く

# 04_テスト設計

## テスト方針

- ストリーミング応答を、フロントエンドと同じ規則（`data:` 行の JSON を読み、`type` で種別を判定する）で解釈して検証する。
- Issue の再現シナリオ（送信済みメッセージを編集し、同じ親で新しいメッセージを作成して再送信する）を API レベルで再現し、最後に編集後の質問文を持つメッセージ内容イベントが届くこと、編集前後のメッセージが同じ親の兄弟（バージョン）になることを確認する。
- 既存の送信 API テスト（単体・結合）のイベント検証を新しい形式に置き換え、従来の観点（エラー時・再生成・ライブラリ生成・添付保存失敗時）が維持されていることを確認する。

| No | 観点 | 条件 | 期待結果 |
|---|---|---|---|
| 1 | イベント形式 | 通常の送信 | すべてのイベントが `data:` 行の JSON で `type` を持ち、イベント名の行がない |
| 2 | 回答の差分 | 通常の送信 | `text_delta` の `text` が回答の差分になる |
| 3 | トークン数 | 通常の送信 | `message_stop` に入力・出力トークン数が入る |
| 4 | 最後のメッセージ内容 | 通常の送信 | 最後のイベントが `message_content` で、`data` にメッセージ内容（質問・回答・ID）が入る |
| 5 | エラー時 | LLM 呼び出しが失敗 | `error` イベントの後に、`status` が `ERROR` の `message_content` が届く |
| 6 | 回答再生成 | 既存の回答を再生成 | `message_content` に元の質問文と新しい回答が入る |
| 7 | ライブラリ生成 | ライブラリ生成モード | `library_title_delta`・`library_content_delta`・`text_delta`・`message_stop` が `type` 付きで届く |
| 8 | 添付保存失敗時 | 添付ファイルの保存に失敗 | `message_content` まで届く |
| 9 | 編集・再送信シナリオ | 同じ親で新しいメッセージを作成し、編集後の質問文で送信 | `message_content` の `question` が編集後の質問文になり、編集前後のメッセージが同じ親を持つ |

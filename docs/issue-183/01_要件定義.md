# 01_要件定義

## 背景

### 原因の切り分け結果

編集・再送信は、フロントエンド（移植元クライアントのコピー）で次の順に処理される。

1. 編集前のメッセージと同じ親を指定して、新しいメッセージを作成する（メッセージ作成 API）
2. 作成したメッセージに対して、編集後のテキストでメッセージ送信（アシスタント応答生成）API を呼び、ストリーミング応答（SSE）を受け取る
3. ストリーミング応答の途中経過（回答の差分）を画面に反映し、最後に届く「メッセージ内容」イベントを受け取って完了とする
4. 1〜3 のどこかで例外が発生した場合は、**画面の状態を編集前のスナップショットに戻す**

Issue の症状（ユーザーメッセージが編集前の元テキストのまま／回答がエラー表示）は、4 のスナップショット復元が起きたときの画面と一致する（編集前の回答も同じ原因でエラーになっていたため、復元後もエラー表示が残る）。

例外の原因はバックエンド側にあり、次の 2 点で移植元のメッセージ送信 API と形式が異なっていた。

| # | 差異 | 移植元 | 本ポート（修正前） | 影響 |
|---|---|---|---|---|
| A | リクエスト形式 | `multipart/form-data`（`textData` JSON パート＋添付ファイルパート） | JSON ボディ | フロントエンドの送信が常に 422 になる |
| B | ストリーミング応答の形式 | イベント名なしの `data:` 行に `{"type": "<種別>", ...}` の JSON。最後に `{"type": "message_content", "data": {メッセージ内容}}` | `event: <種別>` 行＋`data:` 行（JSON に `type` なし）。最後は `event: complete` でメッセージ内容をそのまま送る | フロントエンドは `type` のないイベントをすべて無視するため、回答の差分が表示されず、「メッセージ内容」イベントも受け取れずに「メッセージ内容イベントなしでストリームが終了した」例外になる |

- A は Issue #182 で修正済み（PR #207。develop にマージ後、本 Issue のブランチに取り込む）。
- **本 Issue では B を修正する。** A だけを直した状態では、送信自体は受け付けられ本文も保存されるが、B によりフロントエンドで例外となり、編集・再送信では依然としてスナップショットに戻ってしまう。

メッセージ作成 API（同じ親での新規メッセージ作成）と、編集時のメッセージ送信（新しいメッセージに対する新規生成）のサーバー側の処理は、通常送信と同じで移植元と挙動差はない。

### 対応しない項目（フロントエンド側の問題）

- 編集テキストエリアを空にしても「再送信」ボタンが非活性にならない件は、フロントエンドのボタン活性制御の問題でありバックエンドでは直せない。なお、フロントエンドの編集処理は空白のみの入力では API を呼ばずに終了し、バックエンドも質問文が空の送信は 422 で拒否するため、空の内容で保存されることはない。

## 機能要件

1. メッセージ送信（アシスタント応答生成）API のストリーミング応答を、移植元と同じ形式にする。
   - 各イベントは `data: <JSON>` の 1 行（イベント名の行は付けない）とし、JSON に種別 `type` を含める。
   - 回答の差分: `{"type": "text_delta", "text": ...}`
   - ライブラリのタイトル・本文の差分: `{"type": "library_title_delta", "text": ...}` / `{"type": "library_content_delta", "text": ...}`
   - トークン数: `{"type": "message_stop", "inputTokens": ..., "outputTokens": ...}`
   - エラー: `{"type": "error", "message": ...}`
   - 最後のメッセージ内容: `{"type": "message_content", "data": {id, messageId, status, question, answer, context, attachmentFiles, referencePaths, isRated}}`
2. 送信成功時・LLM 呼び出し失敗時ともに、最後に `message_content` イベントを送る（失敗時は `status` が `ERROR`）。これにより、フロントエンドは例外を出さずに処理を完了でき、編集・再送信では新しいメッセージ（編集後の質問文）と新しい回答が表示される。

## 非機能要件

- イベントの送出順序・永続化の内容とタイミングは変更しない。
- マイグレーションは発生させない。

## スコープ外

- リクエスト形式（Issue #182 で対応済み）
- 編集テキストエリアが空のときの「再送信」ボタン活性制御（フロントエンドの問題）
- LLM Chat API（汎用チャット API）の SSE 形式。フロントエンドからは呼ばれておらず本 Issue の症状に関係しない（形式差異は会話内で報告し、対応要否はユーザー判断とする）
- フロントエンド（`frontend-angular/`・`frontend/`）の変更

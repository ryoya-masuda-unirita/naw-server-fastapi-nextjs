# 02_基本設計

## 全体像

```
保存形式 版 2（ノード + 線 + 設定）
   │ 読み込み時に検証し、実行の計画（コンパイル済みのグラフ）にする
   ▼
グラフの実行エンジン（新規）
   開始から線をたどる → ノードを動かす → 出力を「変数の置き場」に入れる → 次のノードへ
   ├─ 生成AI ──▶ 今の生成AIアダプターの呼び出し（プロンプトを埋めて 1 回）
   ├─ 検索   ──▶ 今の検索アダプターの呼び出し
   ├─ 条件分岐・テンプレート ──▶ エンジンの中で完結（外部を呼ばない）
   └─ 終了   ──▶ 出力文字列を作り、回答の JSON にする
```

## 設計の方針

1. **servicerun の層に触れない。** 今と同じ `Workflow`（`run`）として動く
2. **アダプターの呼び出しは使い回す。** 生成AI・検索を動かす処理（プロパティの検証・ジョブのディレクトリ・ストリーム・秘密の伏せ字）は、今のものを部品にして、ノードごとに呼ぶ
3. **版 1 は、PR 2 で、読み込み時に版 2 へ変換する**（PR 1 では、版 1 は今のまま動かし、版 2 と共存させる。検索ノードが版 2 に入るまで、変換できないため）。** 版 1 の `start →（retrieval →）generative-ai → end` は、版 2 の同じ形のグラフ（生成AI のプロンプトは「{{question}}」）になる。実行は、1 つのエンジンだけ。変換のテストで、今と同じ回答になることを確かめる
4. **PR を分け、各 PR で、使える状態にする。**

## PR の分け方

| PR | 内容 | 動くようになるもの |
|---|---|---|
| 1 | 版 2 の保存形式・検証・変数・実行エンジン。ノードは、開始・生成AI（プロンプトつき）・テンプレート・終了。**版 1 は、今のまま別に動かす**（共存） | 例 1（推敲）を、API（curl）で保存して動かせる |
| 2 | 検索の出力を変数に（`contexts`・`contexts_text`）、生成AI が検索の引用資料を使う、条件分岐、複数の終了。**版 1 を版 2 へ変換して、版 1 の実行経路を外す** | 例 3（根拠チェック付きの RAG）を API で動かせる |
| 3 | 画面: パレット・自由なつなぎ方・種類ごとの設定・変数の挿入・使い方の案内 | 画面で、例 1・3 を組める |
| （別の Issue） | 試し実行（API と画面） | 画面で、その場で動かして確かめられる |

## 保存形式 版 2（概念）

- ノード: `id`・`type`（`start`・`llm`・`retrieval`・`branch`・`template`・`end`）・`name`・`position`・`config`（種類ごとの設定）
  - `llm`: `prompt`（テンプレート）・`properties`（接続）・`retrieval`（引用資料に使う検索ノードの ID。なければ使わない）
  - `branch`: `variable`・`operator`（`contains`・`equals`・`empty`）・`value`
  - `template`: `text`
  - `end`: `output`（テンプレート）
  - `retrieval`: `properties`
- 線: `source`・`target`・`sourceHandle`（条件分岐だけ、`true`／`false`）
- 値の書き方（`properties`・`${環境変数}`・秘密の伏せ字）は、今と同じ

## 変数と実行

- 変数の置き場: 実行ごとの辞書（`ノードID.変数名` → 文字列）。開始が `question`・`history` を入れる
- テンプレート: `{{...}}` を、置き場から引いて埋める。保存の時点で、参照が、上流の（そのノードより前に実行される）ノードの変数であることを確かめる
- 実行順: 開始から、線をたどる。分岐のないところは 1 本道、条件分岐では、条件に合う側の線だけをたどる。合流（複数の線が 1 つのノードに入る）は、片方の道を通った結果だけが使える（もう片方の変数は、参照できない）ことを、保存の時点で確かめる
- 生成AI ノードの動き:
  - プロンプトを埋めて、生成AI アダプターの質問として渡す（検索の引用資料を使うときは、RAG の出力モードで、検索ノードの RAG Context JSON を、引用資料にする）
  - 回答（`text`）を変数に入れる。引用元（`references`）は、最後の回答に使う
- 条件分岐: 変数を、`contains`（含む）・`equals`（等しい）・`empty`（空）で調べる。大文字小文字は区別しない（判定の LLM が「ok」「OK」と答えても通るよう）
- 終了: 出力のテンプレートを埋めて、回答の JSON にする。最後に動いた、引用資料つきの生成AI の `references` を付ける

## 検証（保存時）

- 開始は 1 つ。終了は 1 つ以上。ノード数の上限は 50
- 輪がない。すべてのノードが、開始から到達でき、どこからか終了に到達できる
- 条件分岐の出口は `true`・`false` の 2 つで、どちらにも線がある
- 変数の参照が、上流のノードのものである。使えない変数・存在しないノードは、どのノードのどこかを示して弾く
- 生成AI・検索のプロパティは、今と同じ検証

## 失敗の扱い

- ノードの実行が失敗したら止め、ノード名つきの理由を返す（今と同じ）
- 条件分岐が、変数を持たない（上流で動かなかった）場合は、保存で弾く。実行時に起きたら、ノード名つきの失敗にする

## 確認したい点（ユーザーへ）

1. 変数の書き方は `{{ノードID.変数名}}`（例: `{{draft.text}}`）。画面では、変数の一覧から挿入できるので、手で書かなくてもよい
2. 根拠チェックの判定は、「生成AI が OK／NG と答え、条件分岐が『OK』を含むかで分ける」方式でよい（点数や JSON で返させる方式は、スコープ外）
3. 並列の枝分かれ（同じ質問を複数の LLM に同時に投げる）は、今回は作らない
4. 実装の担当: エンジンと画面（PR 1〜3）は私、試し実行（別の Issue）はご自身

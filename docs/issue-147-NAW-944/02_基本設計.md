# 02_基本設計

## 変更対象

- 認証情報の生成・検証・Cookie発行を担う認証まわりの共通処理
- ログイン・ログインキー認証・パスワードリセット・認証トークン再取得・ログアウトの各エンドポイント
- ローカル開発用のRedis起動構成（docker-compose）

## 画面 / API変更概要

- 各認証系APIのレスポンスボディの形式（`id`・`name`・`role`・`token`・`groups`・`loginStatus`等）
  は変更しない
- Cookieの中身が「JWT文字列そのもの」から「セッションID」に変わる。Cookie名は現行の
  `access_token`から、意味に合わせて`session_id`に変更する（HttpOnly属性のためブラウザJS・
  frontend側のコードから値を直接参照している箇所はなく、名称変更による表側の影響はない）
- Authorizationヘッダーによるbearer認証は現行同様に維持し、セッション認証が成立しない場合の
  フォールバック経路として使う
- ログアウトAPIは、Cookie削除に加えてサーバー側セッションの削除処理を行う
- Cookieの `same-site` 属性を環境変数から設定可能にする（現状 `lax` 固定になっている点を、
  既存の `secure` 属性と同様に環境ごとの切り替えに対応させる）

## 影響範囲

- 認証を要求する全APIエンドポイント（現在Cookieまたはbearerトークンで認証しているすべての
  エンドポイント）
- ローカル開発環境のセットアップ手順（Redis起動が新たに必要になる）
- 既存の認証系テスト（unit/integration）は、セッションベースの認証確立・検証に合わせて
  更新が必要

## 移植方針

- Spring Session相当の仕組みは既製のセッションライブラリに頼らず、Redisクライアントを直接
  使って自作する（セッションキー生成・シリアライズ・TTL管理を実装する）
- 認証優先順位は移植元をそのまま踏襲する: セッションCookieが有効ならそれを優先し、無効・
  未送信の場合のみbearer JWTにフォールバックする
- ローカル環境も含めて常にRedisを使う構成にする。移植元はローカルのみインメモリ代替だが、
  このモノレポではdocker-composeでRedisを容易に用意できるため、あえて別実装（インメモリ
  代替）は持たず、ローカル・dev/staging共通でRedisバックエンドを使う

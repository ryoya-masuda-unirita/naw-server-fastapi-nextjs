# 01_要件定義

## 背景

issue-93で移植した `POST /api/messages/content`（メッセージ送信・SSEストリーミング）は、常に新規の`MessageContent`を作成する実装のみに対応しており、既存回答の再生成（regenerate）はスコープ外としていた。

移植元（Spring Boot）の`MessageController.createMessageContent` / `MessageService.resolveStreamContext` / `MessageService.persistMessageContent`を調査した結果、以下のことが判明した。

- 再生成専用の新規エンドポイントは存在しない。既存の`POST /api/messages/content`が、リクエストの`messageContentId`（回答再生成用）と`messageId`（新規生成・質問再生成用）のどちらか一方を受け取り、サービス層で分岐する設計になっている。
- `messageContentId`が指定された場合、対応する既存`MessageContentEntity`を検索し、それが属する`MessageEntity`・ルームを解決したうえで、通常のストリーミング処理を実行する。
- ストリーミング完了後の永続化時、`messageContentId`指定時は既存レコードの`status`・`answer`・`context`・`referenceFilePaths`を上書きし、`question`（元の質問文）は変更しない。
- トークン使用量（`TokenUsageEntity`）は再生成のたびに常に新規追加され、既存レコードを上書きしない（積み増し）。
- 添付ファイルは新規生成時のみ保存され、再生成時は既存の添付ファイルに変更を加えない。

## 機能要件

- `MessageContentCreateRequest`（`POST /api/messages/content`のリクエストボディ）に`messageContentId`（任意）フィールドを追加する。
- `messageId`と`messageContentId`はどちらか一方が必須。両方nullの場合は400を返す（移植元と同様）。
- `messageContentId`が指定された場合:
  - 対応する`MessageContent`をテナントスコープで検索し、存在しなければ404を返す。
  - 検索した`MessageContent`から紐づく`Message`を解決し、以降のルームアクセス権チェック・アシスタント解決・SAAS_CHAT/SAAS_RAG分岐・SSEストリーミングは既存フローをそのまま利用する。
  - LLMへの入力（ユーザー発話）は、既存の質問文ではなくリクエストの`userInput`を使う（移植元の`buildChatContext`/`buildRagContext`が`vm.userInput()`を使う挙動に合わせる）。
  - ストリーミング完了後の永続化時、既存`MessageContent`の`status`・`answer`・`context`・`referencePaths`を上書き更新し、`question`は変更しない。
- `messageId`が指定された場合（既存動作）は、これまで通り新規`MessageContent`を作成する。
- トークン使用量は再生成時も常に新規レコードとして追加する（既存動作の`_persist_token_usage`をそのまま利用すればよく、変更不要）。

## 非機能要件

- 移植元にはない改善として、`messageContentId`の検索は必ずテナントIDでスコープする（移植元の`messageContentRepository.findById`単体呼び出しにはテナントスコープがないが、本プロジェクトのRLS・テナント分離方針に従い、FastAPI側では明示的にテナントIDでの絞り込みを行う）。

## スコープ外

- 添付ファイルの再生成時の引き継ぎ・再アップロード対応（移植元も非対応のため踏襲しない）
- RAG・tools・ライブラリ生成・response_format対応（Issue #97〜#100で別途対応中、本Issueでは既存実装のインターフェースをそのまま維持する）
- フロントエンド（`frontend/`・`frontend-angular/`）側の再生成ボタンUI対応（本Issueはバックエンドのみ）

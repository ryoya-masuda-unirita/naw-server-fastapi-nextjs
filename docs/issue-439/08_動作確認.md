### 確認で分かったこと

- 既存のテストは 1 件も書き換えていない。#436 で `97` を選んだことが、ここでも効いた（既存のテストが「未知の ID」に使う値と重ならない）
- 質問用の失敗は、既存の `embed_text` の仕組みで `QueryEmbeddingError` に包まれる。そのため、専用の例外の変換を、既存のファイルに足さずに済んだ
- 学習で保存するベクトルと、検索で作る質問のベクトルの次元数が合うことは、モックの応答でテストした（`04` の No 15）。ワークフロー全体（PostgreSQL つき）の通しは、ベクトル DB を使うテストが既存にないため、行っていない

## 未確認事項

次は、本物の Bedrock API キーと、ベクトル DB（`onprem/` の vector-db）が要るため、**まだ確認していない。** ユーザーが次の手順で確認する。

1. Bedrock Runtime の `/model/amazon.titan-embed-text-v1/invoke` が、**Bedrock API キーの Bearer** で呼べること（AWS の案内では、Bedrock API キーは Bedrock Runtime に使える。IAM の `bedrock:InvokeModel` と、第三者の案内の `bedrock:CallWithBearerToken` が要る）
2. Titan G1 が返すベクトルが、**1536 次元**であること（AWS の公式ページ 2 つには、次元数の記載がなかった。AWS の別の資料と複数の記事は 1536。違えば `DIMENSION_MISMATCH` で失敗するので、原因はすぐ分かる）
3. Bedrock のコンソールで、Titan のモデルの利用が有効になっていること
4. 学習 → 検索 → 回答が、Bedrock だけで通ること

手順:

```bash
# 1. #436 の手順で、クラウド側と onprem を起動する（onprem/README.md の「Bedrock で動かす」）
cd onprem
cp config/workflows.bedrock.example.json config/workflows.json   # URL のリージョンを必要なら直す
# .env に WAHA_WORKFLOWS_FILE=/app/onprem-config/workflows.json と BEDROCK_API_KEY=... を書く
docker compose up -d --build

# 2. 学習（server-local から、学習のサービス ID を kb-learn にして、文書を登録する）
# 3. 質問する（アシスタントのサービス ID を bedrock-rag にする）
# 4. 失敗したとき
docker compose logs waha-emulator    # "provider embedding response: status=" の行を見る
```

- 401・403 のとき: キーの種類（Bedrock API キーか）、IAM の権限、リージョン、Titan の有効化を確認する
- 400 のとき: `MODEL_NAME` が Titan のモデル ID か確認する
- `DIMENSION_MISMATCH` のとき: モデルが 1536 次元でない（V2 を指定していないか確認する）
- 接続先が回答の生成（Mantle）と、埋め込み（Runtime）で別のホストであることに注意する
- ヘッダーなどの形式が原因と分かったときは、`embedding/bedrock.py` の `request_target` だけを直せばよい

**注意（品質）:** Titan G1 は英語に最適化されており、日本語の社内文書の検索の質は低い可能性がある。質を求めるなら、V2 を、次元数の設定化と一緒に、別の Issue で行う。

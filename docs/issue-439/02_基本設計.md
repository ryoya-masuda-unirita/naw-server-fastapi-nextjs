# 02_基本設計

## 変更対象

| 対象 | 変更内容 |
|---|---|
| generative-ai-core（埋め込み） | Bedrock の埋め込みを呼ぶ実行器を、**新しい専用のファイル 1 つ**として追加する。既存の OpenAI・Azure の実行器と同じ作りにする |
| generative-ai-core（埋め込みの工場・質問の埋め込み） | プロバイダが Bedrock のときに、新しい実行器を選ぶ分岐を足す（学習用と、検索の質問用の 2 か所） |
| 埋め込みアダプタ・検索アダプタ（ベンダー ID の表） | #436 で決めた Python 版だけの ID（97）で、Bedrock を、それぞれの表と、実行できるプロバイダの一覧に足す |
| onprem | 学習・検索の例（ワークフロー定義）と、手順を足す |

#436 で、プロバイダの識別子（`Bedrock`、ID 97）は、すでにある。この Issue では、その識別子に、埋め込みの実行器を足す。

## 画面 / API 変更概要

画面と HTTP の API の変更はない。変わるのは、埋め込み・検索のワークフロー定義で、`VENDOR` に `Bedrock` を指定できること。

通信の流れ（追加される部分）:

```
アダプタ → Bedrock Runtime の InvokeModel（/model/{モデル ID}/invoke）→ Titan 埋め込み
```

- #436 の回答の生成は、Bedrock Mantle の入口を呼ぶ。埋め込みは Mantle にないため、**別の入口（Bedrock Runtime）を呼ぶ**。接続先の URL は、回答の生成とは別の値になる（リージョンのホストが違う）
- 送るもの: 入力のテキスト（と、モデルによっては次元数・正規化の指定）
- 認証: Bedrock の API キー（Bearer 方式）。#436 のように 2 種類のヘッダーを送る必要はない（これは Mantle の Anthropic 形式の入口の事情で、AWS の標準の入口は Bearer が公式に案内されている）
- 受け取るもの: ベクトル（float の配列）

## 影響範囲

- 既存の埋め込み・検索の実行器: 変更しない。工場に分岐が 1 つ増えるだけ
- ベクトルの次元数: 「決めること 1」の案による。案 A は、既存のテーブルとの互換に影響する
- ベンダー ID の表: 埋め込み・検索アダプタの表に、Python 版だけの ID を足す。既存のテストが「未知の ID」に使っている値と、重ならないことを確かめる
- 既存のテスト: 影響しない想定
- 取り外し: #436 と同じく、専用ファイルと目印の行を消せば、元の状態に戻る

## 移植方針

移植元に実装がないため、次の方針で作る。

1. 実行器の構成、設定の項目、失敗の分類は、移植元と既存の Python 版（OpenAI・Azure）に揃える
2. 呼び出しの形式は、AWS の公式ドキュメント（Titan の InvokeModel）に合わせる
3. 接続先ごとの違い（URL・認証のヘッダー）は、1 つの関数に集める（#436 と同じ）
4. 移植元が将来 Bedrock の埋め込みに対応したら、専用ファイルを置き換えられるようにする

## 決めること（第1承認の前に確認したい）

### 決めること 1: どのモデルを使うか（次元数との関係）

今のベクトル DB のテーブルは 1536 次元で固定されている。Bedrock の Titan は、モデルによって次元数が違う。

| 案 | モデル | 次元数 | 長所 | 短所 |
|---|---|---|---|---|
| **A** | Titan Text Embeddings V2 | 1024・512・256 から選ぶ（1536 は選べない） | 日本語を含む 100 以上の言語に対応。新しいモデル | 次元数が合わず、**テーブルの次元数を設定にする変更**が要る（既存の 1536 のテーブルと別の次元数は混ぜられない）。変更が既存の核の部分に及び、後から消しにくい |
| **B（推奨）** | Titan Embeddings G1 - Text（V1） | 1536（AWS の資料と記事は 1536。公式ページには明記なし） | 今の固定の次元数と合い、**既存のコードを変えずに済む**。専用ファイルだけで足せるので、消せる | 英語に最適化されており、**日本語の検索の質は落ちる**。次元数・形式を、実機でも確かめる必要がある。提供終了の予定は、確認したページにはなかった |
| C | V2 を 1024 次元で出して 0 で埋め、1536 にする | 1536 | コードの変更が少ない | 検索の質も保証できず、不自然な作りになる。推奨しない |

推奨は B。理由は、(1) 目的が「Azure なしで RAG の流れを通す」ことで、(2) あなたの方針（後から消せる、既存のファイルに手を入れない）に合うため。ただし、**日本語の社内文書の検索の質が低くなる可能性が高い。** 質を求めるなら、A を別の Issue として、次元数を設定にする変更（既存のテーブルとの互換を含む）と一緒に行うのがよい。

### 決めること 2: 接続先

Mantle には埋め込みの入口がないため、Bedrock Runtime（`https://bedrock-runtime.<リージョン>.amazonaws.com`）を呼ぶ。`workflows.json` の `URL` には、このホストを書く（回答の生成の `URL` とは別）。このまま進めてよいか。

### 決めること 3: 実機の確認

本物の Bedrock API キーでの接続は、私は行えない。手順を `08_動作確認.md` と `onprem/README.md` に残し、あなたが確認する。IAM の権限（`bedrock:InvokeModel`、`bedrock:CallWithBearerToken`）と、モデルのアクセス許可（Titan の有効化）が、実機で問題にならないかが、主な未確認点。

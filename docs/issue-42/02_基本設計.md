# 02_基本設計

## 変更対象

- `assistant_category_mappings`テーブル・モデルを新規作成する（マイグレーション追加）
- `ai_models`テーブル・モデルを新規作成する（マイグレーション追加、`token_weight`列まで含めて移植元の最終スキーマに準拠）
- Assistant管理者向けCRUD・一覧・エンドポイント一覧・AIモデル一覧のスキーマ・サービス・ルーターを追加する
- 既存の`assistants`・`groups_assistants`・`assistants_endpoints`テーブル自体への変更はない
- 既存の一般ユーザー向け`GET /api/assistants`（issue-26実装分）は変更しない。ただしレスポンスの`category`/`categories`フィールドは常に空だった状態から、実データを返すよう修正する（カテゴリ紐付けが実装されるため）

## 画面 / API 変更概要

| メソッド | パス | 概要 |
|---|---|---|
| POST | `/api/admin/assistants` | 作成（テナント管理者専用） |
| PATCH | `/api/admin/assistants/{id}` | 更新（テナント管理者専用） |
| DELETE | `/api/admin/assistants/{id}` | 削除（テナント管理者専用。404: 自テナント外） |
| GET | `/api/admin/assistants` | 管理者向け一覧。ページネーション・検索・種別/カテゴリ/グループ絞り込み |
| GET | `/api/admin/assistants/endpoints/{type}` | 種別ごとの選択可能テナントエンドポイント一覧 |
| GET | `/api/admin/assistants/AIModels` | AIモデル一覧 |

### 一覧取得のルーティング方針

Group管理APIが`/api/admin/groups`（グループ管理者絞り込みあり）と`/api/admin/all-groups`（テナント管理者専用・全件）の2パスに分かれているのは、移植元`GroupController`自体がもともと`@GetMapping("/api/admin/groups")`・`@GetMapping("/api/admin/all-groups")`の2エンドポイントを持っていたため（1対1移植の結果であり、本プロジェクト独自の設計判断ではない）。

Assistantの移植元`AssistantController`は`GET /api/admin/assistants`の1エンドポイントのみで、その中で「テナント管理者は全件」「グループ管理者（テナント管理者でない）は自分の管理グループのみ」を条件分岐している。パスが最初から1本のため、Assistantも移植元通り`GET /api/admin/assistants`の1本のみとする。

**方針**: パスは`GET /api/admin/assistants`の1本のみ。依存関係は`get_current_user`とし、テナント管理者判定・グループ管理者絞り込みはサービス層内部で行う（Groupのような`restrict_to_managed`引数によるルーター分割は行わない）。

## バリデーション設計

`AssistantCreateRequest`・`AssistantUpdateRequest`相当の共通基底クラスをPydanticで用意し、以下を宣言的制約 + `@field_validator`で実装する。

| 項目 | 制約 |
|---|---|
| `type` | 必須（Enum: SECURE/SAAS_CHAT/SAAS_RAG） |
| `endpoints` | 必須・1件以上（`Field(min_length=1)`） |
| `name` | 作成: 必須・非空白・32文字以内。更新: 任意。送信時のみ非空白・32文字以内を検証（`@field_validator`で「値がNoneでない場合のみ検証」） |
| `description` | 任意・1000文字以内（`Field(max_length=1000)`） |
| `iconColor`/`indexId`/`groups`/`categoryIds` | 任意 |

エンドポイント種別の相関チェック（`SECURE`はLOCAL_SERVERのみ等）は、複数フィールド（`type`と`endpoints`）にまたがるため、サービス層で実施する（移植元`AssistantCreateRequestValidator`相当。テナントエンドポイントのDB参照を伴うため、Pydanticモデル内では完結できない）。

## 影響範囲

- 一般ユーザー向け`GET /api/assistants`のレスポンスの`category`/`categories`が空固定でなくなる（テストの期待値更新が必要）
- `AssistantGetResponse`（backend側スキーマ）に`category`/`categories`の実データ設定ロジックを追加する
- N+1回避のため、一覧取得時は対象アシスタントID一覧に対して`assistant_category_mappings`・`groups_assistants`・`assistants_endpoints`をそれぞれ1回のIN句で取得し、Python側で集約する（`group_prompt_template_repository.find_groups_grouped_by_template_ids`と同じパターン）
- フロントエンド（`frontend-angular`/`frontend`）側の画面追加は本チケットの対象外

## 移植方針

- レイヤー構成（router / service / repository / model / schema）は既存ドメイン（Group・PromptTemplate・AssistantCategory）と同じ構成に揃える
- ページネーションは既存の`GroupListPageResponse`と同様に、クエリパラメータ`q`・`page`・`size`・`sort`（`"フィールド名,asc/desc"`形式）を受け取る方式を踏襲する。移植元`PageableSortUtil.remapSort`のフロントエンド向けエイリアス（`serverType`/`server`→`type`、`category`→カテゴリ名）は、許可ソートキーのマッピングテーブルとしてサービス層に実装する
- `assistant_category_mappings`は複合PK（`assistant_id`, `category_id`）の中間テーブルとして、`assistant_categories`同様に`SQLModel(table=True)`で明示的にモデル化する
- `ai_models`は独立したマスタテーブル。`endpoint_type`はテナントエンドポイントの`EndpointType`と値集合が重なるが、移植元同様に別Enumとして定義する（`AIModelEndpointType`）
- カテゴリ・グループ・エンドポイントの更新時差分計算（削除対象／追加対象の算出）は、移植元のPythonへの直訳（`clear()`+`addAll()`によるHibernateの制約回避策）ではなく、SQLAlchemyのセット操作として素直に「削除対象IDをDELETE」「追加対象のみINSERT」を1回ずつのバルク操作で行う
- 削除時のRoom参照409判定は、room未移植のため実装しない（コメントで理由を明記し、room移植時に追う）
- AIモデル一覧・エンドポイント種別一覧は読み取り専用のシンプルな一覧のため、専用サービスメソッド（`AssistantService`内、他serviceを呼ばない既存ルールに従う）として実装する

## 詳細

### 1. テナント条件がない（🟡 注意）→ 対応済み

`GroupUser.tenant_id == tenant_id` を条件に加えた。移植元のサブクエリにはテナント条件がないが、`groups_users` には所属行のテナントとユーザーのテナントの一致を保証する制約がないため、不整合な行があると他テナントのグループ ID で自テナントのユーザーが消え得る。通常のデータでは結果は移植元と同じ（存在しない・他テナントのグループ ID は 200 で何も除外しない）で、テナント境界を越えて結果が変わらないことを優先した。同じリポジトリのアシスタント・プロンプトテンプレートの除外とも揃う。

### 2. 他テナントのテストが何も検証していない（🔵 提案）→ 対応済み

他テナントのグループの所属行（`tenant_id` は他テナント）に自テナントのユーザーを結ぶ行を入れ、そのユーザーが除外されないことを確かめるテストに直した。テナント条件を一時的に外すとこのテストが失敗することを確認した（`08_動作確認.md`）。

### 3. Service にクエリを書いている（🔵 提案）→ 対応しない

既存の `UserService.get_users` は一覧のクエリ全体（検索・ロール・並べ替え・利用クレジット）を Service で組み立てている。除外条件だけを Repository に移すと 1 つのクエリが 2 か所に分かれて読みにくくなり、全体を Repository に移すのはこの Issue の範囲を超えるため、既存の構造に合わせた。

### 4. 空白だけの値の判定（🔵 提案）→ 対応済み

`if exclude_group_id and exclude_group_id.strip():` にして、移植元の `!excludeGroupId.isBlank()` と同じく空白だけの値は指定なしとして扱うようにした。空文字・空白だけの両方をテストに入れた。

### 5. テストヘルパーの型ヒント（🔵 提案）→ 対応済み

`session: AsyncSession`、`members: list[User]` にした。

# 02_基本設計

## 変更対象

- `backend/app/routers/tenant_endpoints.py`: 新規 `APIRouter`（`/api/tenants/endpoints` プレフィックス）を追加し、`GET /local/{endpoint_id}` を実装する
- `backend/app/schemas/tenant_endpoint.py`: `apiKey` を含む `LocalServerEndpointResponse` を新規追加する
- `backend/app/services/tenant_endpoint_service.py`: `get_local_server_endpoint` メソッドを追加する
- `backend/app/main.py`: 新規 router を `include_router` する
- `backend/tests/integration/test_tenant_endpoints.py`: 新規エンドポイントのテストケースを追加する

## API変更概要

| メソッド | パス | 認可 | レスポンス |
|---|---|---|---|
| GET | `/api/tenants/endpoints/local/{endpointId}` | 管理者（ADMIN/SYSTEM） | `id`, `tenantId`, `type`, `endpoint`, `apiKey` |

- 存在しない/自テナント外/`LOCAL_SERVER`以外のタイプの場合は `404 Not Found`
- 一般ユーザーがアクセスした場合は `403 Forbidden`（既存の `require_admin` の挙動を踏襲）

## 影響範囲

- 既存の一覧・作成・更新・削除・タイプ別一覧エンドポイントには変更を加えない（レスポンス形状・挙動とも既存のまま）
- `TenantEndpointRepository.find_by_id_and_tenant_id` は既存メソッドをそのまま流用するため、リポジトリ層の変更は不要
- `TenantEndpointService` にメソッドを1件追加するのみで、既存メソッドには影響しない

## 移植方針

- 移植元 Java の `getLocalServerEndpoint`（Controller）→ `getLocalServerEndpointById`（Service）→ `findByIdAndTenantId`（Repository）の3層構成を、FastAPI側でも router → service → repository の対応関係で移植する
- パスが独立している（`/api/admin/tenants` 配下ではなく `/api/tenants/endpoints` 配下）ため、既存 `router`（prefix: `/api/admin/tenants`）とは別の新規 `APIRouter` インスタンスを同一ファイル内に追加する（`groups.py` が複数 router を1ファイルで定義している既存パターンを踏襲）
- 認可は、移植元 Java コードが `X-Tenant-ID` ヘッダーのみに依存し明示的なロールチェックがない一方、`apiKey` という機密情報を返すエンドポイントであること、および既存の類似エンドポイント（タイプ別一覧）が `require_admin` を使っていることを踏まえ、`require_admin`（ADMIN/SYSTEMロール必須）+ JWTの`tenant_id`を採用する
- レスポンスは新規スキーマ `LocalServerEndpointResponse`（`endpointName` を含まない点が既存 `EndpointResponse` と異なる）を追加する

## 項目ごとの設計

### 1. リクエスト全体のサイズ上限

純粋な ASGI ミドルウェア `MultipartSizeLimitMiddleware(max_bytes=MAX_REQUEST_SIZE_BYTES)`。

- `content-type` を小文字にして `multipart/` で始まらなければ何もしない（移植元の上限は multipart の設定。メディアタイプは大文字小文字を区別しない。Starlette も小文字にして解析するため、区別すると上限をすり抜けられる）
- `Content-Length` が数値で上限を超えていれば、アプリを呼ばずに 413（`spring_default_error_body`）を返す
- それ以外は `receive` を包み、受け取った `http.request` の本文の合計が上限を超えた時点で `starlette.exceptions.HTTPException(413)` を送出する。FastAPI は本文の解析中の例外を 400 に変えるが、`HTTPException` はそのまま再送出する（`fastapi/routing.py` で確認）。例外ハンドラーが Spring 既定の形の 413 にする
- 追加の順番: `UnhandledErrorMiddleware` → `MultipartSizeLimitMiddleware` → `ServerAuthKeyMiddleware` → `CORSMiddleware`（後に追加したものが外側）。認証（401）を先に確かめ、413 にも CORS ヘッダーを付ける

413 の `error` は Spring の `HttpStatus.PAYLOAD_TOO_LARGE` の理由句（`Payload Too Large`）にする。Python の `HTTPStatus` は `Request Entity Too Large` のため、`SPRING_REASON_PHRASES` で置き換える。

### 2. 500 の CORS ヘッダー

`UnhandledErrorMiddleware`: アプリを呼び、`Exception` が出たら、応答をまだ送り始めていなければ `unexpected_error_response(path)`（`logger.exception` + Spring 既定の形の 500）を返す。送り始めていれば（SSE の途中など）そのまま外に投げる。CORS の内側にあるため 500 にも CORS ヘッダーが付く。既存の `@app.exception_handler(Exception)` は、このミドルウェアより外側（認証ミドルウェア・サイズ上限ミドルウェアなど）の例外のために残し、同じ `unexpected_error_response()` を使う。

### 3. `status=` の空文字

`if status_ is not None:` を `if status_:` にし、空文字は未指定と同じにする。

### 5. multipart の空文字

`form_text(name)` は `Depends` を返す。依存の中で `await request.form()`（FastAPI が解析済みのフォームを Starlette がキャッシュしているため再解析しない）から値を取り、文字列ならそのまま、なければ None を返す。`CreationServiceNameForm = Annotated[str | None, form_text("creationServiceName")]` のように項目ごとに型エイリアスを作り、`POST/PATCH /files`・`POST /additionalLeaning` の `Form()` を置き換える。

### 12. `name` / `userId` の必須

- `_require_name(name)`（ルーター）: None なら `BadRequestError("name が指定されていません")`
- `POST /files`: `name` を確かめてからサービスを呼ぶ
- `PATCH /files/{fileId}`: アップロードがあり空でないとき（差し替え）だけ `name` を確かめる。サービスと同じ判定（`upload is None or upload.is_empty()` なら表示名・参照先の更新だけ）。サービスの `create_file` / `update_file` の本体は #251 の PR（同じ関数の本体を書き換えている）と衝突するため、ルーターで確かめる
- `_save()`（サービス）: 既存のファイルがなく新しく作るとき、`user_id is None` なら `BadRequestError("userId が指定されていません")`。登録・差し替え・追加学習の共通の保存処理のため、どの経路でも移植元と同じ条件になる。`_save()` はコミット前に失敗するため、差し替えの旧ファイルの削除もロールバックされる
- 同期（サービス）: 既存 ID を読んだ後、`user_id is None` かつ新しく登録するファイルがあれば同じ `BadRequestError`（同期は `_save()` を使わないため）
- メッセージは定数 `USER_ID_NOT_SPECIFIED_MESSAGE`・`NAME_NOT_SPECIFIED_MESSAGE`

### 7・8. 質問 API の入力

- Content-Type を小文字にして `multipart/form-data` で始まらなければ `HTTPException(415)`（例外ハンドラーで Spring 既定の形）
- textData のファイルパートを UTF-8 で読めなければ `_bad_request(...)`（`RequestValidationError` → Spring 既定の形の 400）

### 9. 履歴の `type`

`type: HistoryMessageContentType | None = None`。`histories.json` は `{"role": m.type.value if m.type is not None else None, "content": ...}`。

### 4. 空の data

`_handle_stream_chunk` で、旧形式（そのまま中継）の分岐の後に `if not payload: return` を入れる。旧形式は移植元もイベントブロックをそのまま中継するため変えない。

### 10. tail の読み取り

`StreamRuntime` に `tail_read_lock: asyncio.Lock` を追加し、`async with runtime.tail_read_lock: result = await asyncio.to_thread(runtime.tail_reader.read_new, path)`。ストリームの監視タスクと、結果ポーリング側の確定前の読み残し処理（`_drain_pending_stream_events`）が同じ `StreamFileTailReader` を使うため、スレッドで同時に読んで読み取り位置が競合しないよう直列化する。

読み取りの待ちが入ったことで、ストリームの監視タスクと結果のポーリングタスクの両方が `_try_finalize` の最初の確認（`finalized` が False）を通り、読み残し処理と「終端なしで確定する」警告が二重に走りうる（code-review の指摘）。`StreamRuntime.finalize_started` を追加し、`_try_finalize` は SUCCESS の確認の直後（await の前）にこれを確かめて立てる。後から入った方はすぐ戻る。

### 11. 定期掃除

`run_cleanup_loop` のループ内で `cleanup_orphan_stream_files` の呼び出しを `try/except Exception` で囲み、`logger.exception` を出して次の回へ進む。タスクが例外で終わらなくなるため、アプリ終了時の `await cleanup_task` で例外が出て後続の終了処理（SSE の停止・HTTP クライアント・DB の後始末）が飛ばされることもなくなる。

### 13. インデックス

- モデル: `FilePart.__table_args__` に `Index("file_parts_file_id_idx", "file_id")`
- マイグレーション: revision `issue253`、down_revision `0001`。`op.create_index` / `op.drop_index`
- revision ID は他の未マージ PR と衝突しないよう Issue 番号にする。他の PR が server-local のマイグレーションを追加した場合、マージ順によって down_revision の付け替えが必要

### 14. alembic の DB

`DatabaseSettings(BaseSettings)` に `model_config`（`.env`、`extra="ignore"`）と `database_url` を置き、`Settings` はこれを継承する（`database_url` と `model_config` を `Settings` から移す）。`alembic/env.py` の `_database_url()` は、Config の `sqlalchemy.url`（テスト用）がなければ `DatabaseSettings().database_url` を返す。`os.environ` の直接参照と `import os` は削除する。

### 15. LOG_LEVEL

- entrypoint: `log_level` を小文字にした後、`warn` は `warning`、`fatal`・`off` は `critical` にしてから `uvicorn --log-level` に渡す（uvicorn は `critical|error|warning|info|debug|trace` だけを受け付ける）
- アプリ: `Settings.log_level` の `field_validator` で大文字にし、`SPRING_LOG_LEVEL_ALIASES`（`TRACE`→`DEBUG`、`WARN`→`WARNING`、`FATAL`・`OFF`→`CRITICAL`）で Python の logging のレベル名に読み替える。Python は `TRACE`・`FATAL`・`OFF` を知らず、`logging.basicConfig` が失敗するため（code-review 対応で追加）

# 02_基本設計

## 変更対象

- アプリの組み立て（ミドルウェアの追加: リクエストサイズの上限、想定外のエラー）
- エラー応答の共通処理（Spring の理由句）
- 学習ファイル API（入力値の受け取り方・必須項目）と同期の処理
- 質問 API（Content-Type・textData の解析）と履歴の Waha! への渡し方
- SSE の処理（空の data・ストリームファイルの読み取り）
- ストリームファイルの定期掃除
- モデル・マイグレーション（インデックス）・マイグレーションの設定の読み込み
- コンテナの起動スクリプト
- README（環境変数・移植元との違い）

## 画面 / API 変更概要

| No | API / 場面 | 修正前 | 修正後 | 移植元との関係 |
|---|---|---|---|---|
| 1 | multipart の API 全般 | 全体の上限なし | 215MB 超は 413（`{"timestamp","status","error":"Payload Too Large","path"}`） | 同じ |
| 2 | 想定外のエラー | 500（CORS ヘッダーなし） | 500（CORS ヘッダーあり） | 同じ |
| 3 | `GET /files?status=` | 400 | 未指定として 200 | 同じ |
| 4 | `POST /content`（NAW 互換 SSE） | 空の `data:` でエラー終了 | 無視して続ける | 同じ |
| 5 | `POST/PATCH /files`・`POST /additionalLeaning` | 空文字は None（PATCH で空にできない） | 空文字のまま（PATCH で空にできる） | 同じ |
| 6 | SSE の確定失敗 | 変更なし（テストを追加） | 同左 | 同じ |
| 7 | `POST /content`・`/content/sync`・`/content/stream` に multipart 以外 | 400 | 415（Spring 既定のエラー本文） | 同じ |
| 8 | textData が不正な UTF-8 | 500 | 400（Spring 既定のエラー本文） | 同じ |
| 9 | 履歴の `type` 省略 | 400 | 受け付け、`role: null` で Waha! に渡す | 同じ |
| 10 | SSE の途中経過の読み取り | イベントループ上で読む | スレッドで読む | 内部のみ |
| 11 | 定期掃除の例外 | ループが止まり、終了処理で例外が出る | ログに出して次の回も実行 | 同じ |
| 12 | 登録・差し替え・追加学習・同期で `name`/`userId` が未指定 | 空文字で登録 | 400（`{"timestamp","message"}`）。登録・差し替え・追加学習は Waha! を呼ぶ前に返す。同期は新しく登録するファイルがあるときだけ | **意図的に変える**（下記） |
| 13 | DB | `file_parts.file_id` にインデックスなし | あり | 同じ（H2 の自動インデックス相当） |
| 14 | `uv run alembic upgrade head` | 環境変数だけを読む | 環境変数と `.env` を読む | アプリと同じ DB にする |
| 15 | コンテナの起動 | `LOG_LEVEL=WARN` で起動失敗 | 起動する（uvicorn には `warning` で渡す） | 同じ |

### 意図的に変える点

- **No.12**: 移植元は `name`/`userId` が null のまま保存しようとして DB の NOT NULL 制約で失敗し、Spring 既定の 500 になる。しかも Waha! への登録（学習ジョブ）が終わった後に失敗するため、Waha! にだけデータが残る。server-local では既に「移植元でハンドラー未定義のため 500 になり得た入力不備は 400 で返す」方針（README）をとっているため、それに合わせて 400 にし、Waha! を呼ぶ前に返す。同期は、移植元と同じく新しく登録するファイルがあるときだけ失敗させる（既存のファイルだけなら成功する）
- **No.14**: 移植元は Liquibase をアプリの起動時に実行するため、マイグレーション先は常にアプリと同じ DB。server-local は alembic を別コマンドで実行するため、アプリと同じ設定（環境変数・`.env`）を読むようにして揃える

### 移植元の挙動を確認した結果（要確認とされていた項目）

- **No.4**: `handleStreamChunk` は `extractDataPayload`（`data:` 以降を trim）の結果を `objectMapper.readTree` に渡す。Jackson 2.10 以降の `readTree("")` は例外ではなく MissingNode を返し、`path("type").asText()` は空文字になる。空文字は無視する種類にも転送する種類にも当たらないため、何もせずに次へ進む。なお、空行で区切られた 1 つのブロックに複数の `data:` 行があるときは最初の行だけを見る（移植元と同じ）
- **No.5**: `@ModelAttribute` は multipart の空文字をそのまま `""` として束縛する（`StringTrimmerEditor` などの設定はない）。`updateFile` は `if (fileDisplayName != null) file.setDisplayName(fileDisplayName)` のため、`displayName=` で表示名は空文字になる
- **No.2**: CORS は `SecurityConfig` で Spring Security のフィルターとして設定している。フィルターは処理の前に応答ヘッダーへ CORS を付けるため、コントローラーで例外が起きた 500（エラーページへのフォワード）にも CORS ヘッダーが残る

## 影響範囲

- ブラウザ・NAW 本体から見たエラー応答（413・415・400 の条件と、500 の CORS ヘッダー）
- 学習ファイル API で空文字を送った場合の保存値（None ではなく空文字）
- 学習ファイル API で `name`/`userId` を送らない呼び出し（400 になる）
- DB のマイグレーションが 1 本増える（`file_parts_file_id_idx` の追加。既存のデータはそのまま）
- 413 の `error` を Spring の語（`Payload Too Large`）にする。既存のファイルサイズ超過（200MB）の 413 も同じ語になる

## 移植方針

- 各項目は移植元のコード・設定を根拠にし、02 の表に根拠と結果を残す
- 移植元と同じ挙動にするのが原則。変える点は理由を書き、README の「移植元との違い」に載せる

# 01_要件定義

## 背景

フロントエンドの棚卸し（移植元 client の API パス定義から作成）で、backend に無い API として 3 件が挙がった。移植元 server（Spring Boot、2026-11-12 時点の develop）と client を突き合わせた結果は次のとおり。

| 対象 | 移植元 server | 移植元 client の実コードからの呼び出し | 結論 |
|---|---|---|---|
| `GET /api/libraries/{libraryId}/content` | 有る（`LibraryController#getLibraryContent`） | 有る。チャットのビューア（library-content-api.service）が呼び、応答の `data` だけを使う | 移植する |
| `PUT /api/rooms/pin`（一括） | 無い（全ブランチの履歴にも無い）。1 件ずつの `POST`・`DELETE /api/rooms/{roomId}/pin` だけ | 有る。チャットの並び替えダイアログが呼ぶ。本文 `{"rooms": [{"roomId", "isPinned"}]}`、応答 `{"data": ChatRoom[]}`。移植元の本番（モック無効）では server に無いため失敗する | 移植元に根拠が無いため、このチケットでは実装しない。どう扱うかは判断を仰ぐ |
| `PUT /api/rooms/reorder` | 無い（全ブランチの履歴にも無い）。ルームに並び順の列も無く、一覧はピン留め→更新日時の降順で固定 | 無い。`saveRoomOrder` は定義されているが呼び出し元が無い | 移植しない |

## 機能要件

1. `GET /api/libraries/{libraryId}/content` で、閲覧できるライブラリの本文を `{"data": "<本文>"}` で返す
2. 閲覧できるかの判定はライブラリの取得（`GET /api/libraries/{libraryId}`）と同じにする
   - 紐づくメッセージのルームを閲覧できる、またはライブラリが見える（所有者・共有先グループの所属）
3. 次の場合は 404 を返す
   - ライブラリが無い・他テナント・閲覧できない・id が UUID の形でない: `Library not found`
   - ライブラリはあるが本文が無い: `Library content not found`

## 非機能要件

- マイグレーションは追加しない
- 認証が必要（一般ユーザーで利用できる）

## スコープ外

- `PUT /api/rooms/pin`（一括）: 移植元 server に存在しない。backend には `pinned` 列があるので作ることはできるが、移植元に無い API を新設することになるため、扱いは判断待ちとし Issue に記録する
- `PUT /api/rooms/reorder`: 移植元 server に存在せず、client の実コードからも呼ばれない。並び順を保存する列も無いため実装しない
- 移植元の「ライブラリ本文の別テーブル（`library_contents`）への分離」とそれに伴う変更（`libraries.title` の NULL 許可、`GET /api/libraries/{id}` の応答の変化、ライブラリのスタブ作成 API など）。backend はまだ本文を `libraries.content` 列に持つため、このチケットでは列から読む。分離の移植は別チケットとする

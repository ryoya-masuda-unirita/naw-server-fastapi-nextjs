# 01_要件定義

## 背景

- 本モノレポは現在ローカル（`docker compose`）でのみ動作しており、AWS上で稼働させる仕組みが一切ない
- `.claude/CLAUDE.md`にクラウドインフラの選定（ECS/RDS/CloudFront+S3/ECR/Terraform/GitHub Actions+OIDC）は記載済みだが、実体（AWSリソース・Terraformコード・デプロイ手順）はまだ存在しない
- 移植元（`naw-server`/`secuaigent-client`）はAWS上で稼働しているが、いずれも`develop`ブランチのみでの利用であり、IaCは使わずAWSマネジメントコンソールでリソースを手動構築していると推測される（`docs/調査結果/AWS使用リソース.md`参照）
- 今回はまず「AWS上で実際に動く状態を作る」ことを優先し、IaC化・CI/CD自動化は後続チケットに切り出す
- **運用方針: 動作確認が終わったら、作成したAWSリソースを（RDS/踏み台の「停止」ではなく）全て完全削除し、課金をゼロに戻す「使い捨て」運用とする**。ECS（backend）・S3・CloudFront・ECRも含め、常時稼働させ続けるリソースは作らない。次回検証時は、構築手順（`03_詳細設計.md`）に従ってゼロから再構築する

## 機能要件

- AWSマネジメントコンソールから以下のリソースをdev環境として手動構築する
  - Amazon ECR: `backend`のコンテナイメージを保管するリポジトリ
  - Amazon ECS（EC2起動タイプ、t4g.nano）: `backend`（FastAPI）を稼働させるクラスタ・サービス・タスク定義
  - Amazon ElastiCache for Redis（`cache.t4g.micro`）: Issue #147で導入したセッションCookie認証が依存するRedis。`backend`（ECS）からのみアクセス可能にする
  - Amazon RDS PostgreSQL（db.t4g.micro）: アプリケーションDB。パブリックサブネットに配置しつつ「パブリックアクセス可能」設定はNoにし、セキュリティグループで踏み台・ECSからのみアクセス可能にする（プライベートサブネットは作らず、NAT Gatewayを不要にする）
  - 踏み台サーバー（EC2）: RDSへの接続用。パブリックサブネットに配置し、SSH（キーペア）でアクセスする。セキュリティグループの22番ポートは作業者の自宅/オフィスIPのみに限定する
  - ALB（Application Load Balancer）: backend（ECS）の前段でHTTPS終端を行い、CloudFront（frontend-angular）とのクロスオリジン構成でセッションCookie（`SameSite=None`+`Secure=true`、Issue #147）が正しく機能するかを検証する。証明書はsslip.io + Let's Encrypt（HTTP-01検証）で取得しACMへインポートする（ドメイン登録・Route53ホストゾーンは作らない）。**検証後はALB・証明書を削除し、恒久稼働はさせない**
  - Amazon S3 + CloudFront: `frontend-angular`のビルド成果物を配信する静的ホスティング。CloudFrontはPrice Class 100（北米・欧州エッジのみ、最安）を採用する
- `backend`のDockerイメージをビルドし、ECRへ手動push、ECSサービスへ手動デプロイする
- `frontend-angular`のビルド成果物を手動でS3にアップロードし、CloudFrontで配信できる状態にする
- RDSを起動し、Alembicマイグレーション適用・seed投入まで行い、`backend`から実際に接続できることを確認する
- 踏み台サーバー経由で、ローカルのpgAdmin4等からRDSにSSHトンネル接続できることを確認する
- ALB経由のHTTPSで、CloudFront（frontend-angular）からのクロスオリジンセッションCookie認証が正しく機能することを確認する
- **動作確認が完了したら、作成した全リソース（ECS/RDS/踏み台EC2/ALB/ACM証明書/S3のオブジェクト/CloudFrontディストリビューション/ECRのイメージ/VPC関連一式）を完全に削除し、課金がゼロに戻ることを確認する**
- すべてのリソースに共通タグ（例: `Project=issue-158`）を付与し、削除後に`aws resourcegroupstaggingapi get-resources`で該当タグのリソースが0件であることを確認する
- 上記の一連の作業手順（構築手順・削除手順の両方）を本チケットのドキュメント（`03_詳細設計.md`等）に手順化して残す

## 非機能要件

- リージョンは`ap-northeast-1`固定（`.claude/CLAUDE.md`のクラウドインフラ方針に準拠）
- **各リソースは可能な限り最安のスペック・構成を選定する**
  - ECS: EC2起動タイプ、`t4g.nano`（メモリ不足時のみ`t4g.micro`に変更、`.claude/CLAUDE.md`記載の方針通り）
  - RDS: `db.t4g.micro`、Single-AZ（Multi-AZ無効）、ストレージは最小構成（gp3 20GiB）
  - ElastiCache for Redis: `cache.t4g.micro`、レプリカなし（1ノード構成）
  - 踏み台サーバー: EC2 `t4g.nano`
  - CloudFront: Price Class 100（日本からのアクセスは遠方エッジ経由になりレイテンシが上がり得るが、dev環境の動作確認用途と割り切り最安構成を優先する）
  - NAT Gateway（時間課金が高額）は使わない。プライベートサブネットを作らず、ECS・踏み台・RDSともにパブリックサブネットに配置し、RDSは「パブリックアクセス可能=No」＋セキュリティグループ制限のみでインターネットから遮断する（詳細は`02_基本設計.md`参照）
- **「停止」ではなく「完全削除」でコストゼロにする方針**
  - RDS・ElastiCache・踏み台は「作業時のみ起動→終了後は停止」ではなく、検証終了後は**削除**する（RDSは`--skip-final-snapshot`を付けて最終スナップショットを残さない。ElastiCacheにはRDSのような「停止」機能自体が存在しないため、必ず削除で対応する）
  - ECS（backend）・S3のオブジェクト・CloudFrontディストリビューション・ECRのイメージも、常時稼働・常時保持はせず、検証終了後は削除する。CloudFrontは固定月額費用がなく無効化のみでも$0にできるが、S3・ECRはオブジェクト/イメージが残っている限りごく僅かでもストレージ課金が発生し続けるため、完全にゼロにするには削除が必要
  - ALB・ACM証明書（sslip.io + Let's Encrypt経由でインポート）も検証完了後に削除する
  - VPC・サブネット・IGW・ルートテーブル・セキュリティグループも、他に利用予定がなければ削除する
- IAMユーザー・ロールは必要最小権限で作成する（各サービスへの操作に必要な権限のみ付与）
- 認証情報（DBパスワード・SSH秘密鍵等）をリポジトリ・ドキュメントに平文で残さない

## スコープ外

- GitHub Actions経由の自動デプロイ（CI/CD）
- TerraformによるIaC化
- `frontend`（React版）のデプロイ
- 本番環境の構築
- EventBridge SchedulerによるRDS自動起動・停止スケジュール設定（今回は「停止」ではなく検証後に完全削除する運用のため対象外）
- SSM Session Manager等、SSH以外の踏み台接続方式の導入（今回は従来のSSHキーペア方式を採用）
- ALBの恒久稼働・独自ドメイン取得・Route53ホストゾーンの新規作成（今回はsslip.io + Let's Encryptによる一時的な検証のみ。恒久的なHTTPS化を行うかは検証結果を踏まえて別チケットで判断）

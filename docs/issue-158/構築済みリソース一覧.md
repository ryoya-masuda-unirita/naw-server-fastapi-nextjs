### 発見・修正: `backend/Dockerfile`が実行時に依存を再インストールしていた

初回デプロイ時のログ冒頭に `Downloading ruff` `Downloading mypy` `Installed 27 packages` が出ていた。原因は`backend/Dockerfile`の2点の不備。

1. `COPY pyproject.toml .` のみで**`uv.lock`をコピーしていない** → `uv sync`がその場で依存を解決し直し、ロックファイルによるバージョン固定が効かない
2. `CMD ["uv", "run", ...]` に`--no-sync`がない → `uv run`が起動時に環境とロックの整合性を検証して再同期し、ビルド時に`--no-dev`で除外したはずの開発用パッケージ（ruff/mypy等）まで実行時に取得する

実害: 起動のたびに余計なダウンロード（インターネット必須）、不要パッケージによるメモリ・ディスク消費（`t4g.nano`の418MBでは効く）、イメージの再現性が保証されない。

**修正内容**（本Issueで実施）:

```dockerfile
COPY pyproject.toml uv.lock ./
RUN uv sync --no-dev --frozen
...
CMD ["uv", "run", "--no-sync", "uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

**修正の検証**: 再ビルド・ECRへpush・ECSサービスを「新しいデプロイの強制」で更新した結果、新タスク（`c2cd87e7...`）のログから`Downloading`が消え、以下のみになった。

```
INFO:     Started server process [10]
INFO:     Waiting for application startup.
INFO:     Application startup complete.
INFO:     Uvicorn running on http://0.0.0.0:8000 (Press CTRL+C to quit)
```

### ハマりどころ: 1台構成＋ホストポート固定でデプロイがデッドロックする

「新しいデプロイの強制」を実行したが、新タスクが起動せず自動ロールバックされた。ECSサービスイベントのメッセージ:

```
was unable to place a task because no container instance met all of its requirements.
The closest matching (container-instance ...) is already using a port required by your task.
```

原因: ECSのデフォルト`minimumHealthyPercent=100`は「新タスクを起動して健全になってから旧タスクを落とす」という無停止デプロイ前提の設定。しかし本構成はEC2 1台のみ＋タスク定義のホストポートを8000固定にしているため、旧タスクがポート8000を占有していて新タスクを配置できず、デッドロックする。

対処: サービスのデプロイ設定で**最小実行タスク率を`100` → `0`** に変更（旧タスクを先に停止してから新タスクを起動する動作になる）。1台構成の検証環境ではダウンタイムが許容できるため問題ない。

**本来の設計**: ALBを前提にするなら、タスク定義のホストポートは`0`（動的割り当て）にすべきだった。そうすればECSが空きポートを自動割り当てし、同一ホストに新旧タスクが共存できるためこの問題自体が起きず、ALBの動的ポートマッピングとも整合する。ホストポートを8000固定にしたのは「ALBなしでECSホストのIP:8000に直接アクセスして疎通確認する」ためだったが、`sg-ecs`がALBからのアクセスしか許可していないため**結局その確認はできず、固定にした意味がなかった**。

### 発見・対応: tenantサブドメイン運用のため独自ドメインを追加

`frontend-angular`がテナントIDを`window.location.hostname`の先頭ラベルから読む実装になっているため、CloudFrontの素の`*.cloudfront.net`ドメインでは正しいログイン運用ができないことが判明。急遽、以下を追加で行った（Issue #158のスコープ内として継続）。

1. **独自ドメイン取得**: ムームードメインで`secuaigent-ryoyamasuda.tech`を取得
2. **ACM証明書発行**（us-east-1、CloudFront利用には同リージョン必須）: `*.secuaigent-ryoyamasuda.tech`のワイルドカード証明書をDNS検証で発行（ARN: `62e57d29-e2b1-41b2-a7e1-924e2ca9654b`）
   - ルートドメイン（`secuaigent-ryoyamasuda.tech`単体）は証明書のSANに含めなかったため、当初「両方を代替ドメインに追加」しようとした際にCloudFrontが証明書を見つけられずエラーになった。ワイルドカードのみに絞ることで解決
3. **CloudFrontに代替ドメイン名`*.secuaigent-ryoyamasuda.tech`を追加**、上記証明書を割り当て
4. **ムームーDNSにワイルドカードCNAMEを追加**: サブドメイン`*` → `di4rwgutpepar.cloudfront.net`（tenantが増えても追加設定不要）
5. **動作確認**: `https://test-tenant.secuaigent-ryoyamasuda.tech/`からログイン成功（Cookie認証も含めて機能）

**ハマりどころ**: 動作確認時、`dig`が`google.com`ですらタイムアウトする状態だった。原因は作業者のMacの既定DNSサーバー（Wi-Fi等から配布されたもの）が応答しなかっただけで、AWS/ドメイン設定とは無関係。`dig @8.8.8.8 ...`で正常に解決できることを確認し、MacのDNS設定を`8.8.8.8`に切り替えることで解消した（ムームーDNSの設定自体は最初から正しかった）。

不要になった証明書（自動生成された`e2fedaea-...`等）は、全削除フェーズでまとめて削除する。

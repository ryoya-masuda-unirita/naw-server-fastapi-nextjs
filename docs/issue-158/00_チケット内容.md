# AWS環境（dev）を手動構築し、backend/frontend-angular/RDSを手動デプロイする

## 概要

本モノレポにはAWSデプロイ関連の実装・IaC（Terraform等）が一切存在しない。今回のチケットでは、AWSマネジメントコンソールから手動でリソースを構築し、現行の`backend`（FastAPI）・`frontend-angular`（Angular、動作確認用フロントエンド）・RDS（PostgreSQL）を手動デプロイして、実際にAWS上で動作する状態を作る。

## 説明

- 対象: バックエンド（ECS）＋フロントエンド（`frontend-angular`、CloudFront+S3）＋DB（RDS）＋キャッシュ（ElastiCache for Redis）＋踏み台サーバー＋ALB（検証用・一時）＋コンテナレジストリ（ECR）を一式
- IaC（Terraform）は使わず、マネジメントコンソールでの手動構築とする
- CI/CD（GitHub Actions経由の自動デプロイ）は今回のスコープに含めない。手動デプロイの確立までを本チケットのゴールとする（自動デプロイ化は別チケットで対応）
- 環境は`dev`のみ（本番環境なし、`.claude/CLAUDE.md`のクラウドインフラ方針に準拠）
- `frontend`（React版、移植中）は対象外。現在の開発方針（バックエンド優先、動作確認は`frontend-angular`を使用）に合わせる
- 各リソースは可能な限り最安のスペック・構成を選定する（`t4g.nano`/`db.t4g.micro`/`cache.t4g.micro`、CloudFront Price Class 100等）
- **運用方針: 動作確認が終わったら、作成したAWSリソースを（「停止」ではなく）全て完全削除し、課金をゼロに戻す「使い捨て」運用とする**。ECS（backend）・S3・CloudFront・ECRも含め、常時稼働させ続けるリソースは作らない
- 作業用のIAMユーザー（`AdministratorAccess`、`naw-fastapi-issue158-operator`）を作成済み。以降のAWS操作（コンソール・CLIとも）はrootではなくこのIAMユーザーで行う
- Issue #147で導入したセッションCookie認証（`SameSite=None`+`Secure=true`）が、CloudFront（frontend-angular）とECS（backend）の別オリジン構成で正しく機能するかを、ALB＋sslip.io+Let's Encrypt証明書で一時的にHTTPS化して検証する

## その他

- 移植元（`naw-server`/`secuaigent-client`）のAWS利用状況は事前調査済み: `docs/調査結果/AWS使用リソース.md`
  - 移植元はいずれもAWSリソースを`develop`ブランチでのみ利用しており、`main`/`master`には未マージ
  - 移植元にもIaCは存在せず、GitHub ActionsからVariables/Secrets経由でリソース名を参照するのみ（リソース自体は手動構築と推測される）
- 本チケットは「移植元コードのポート」ではなく「新規インフラ構築」のため、通常のIssue対応（参照実装の読み込み→実装）とは進め方が異なる。実作業の多くはAWSマネジメントコンソールでの手動操作（ユーザー側の操作）になる想定
- このAWSアカウントは無料利用枠（12ヶ月無料枠）の対象外であることを確認済み。EC2は`t4g.nano`が素直に最安
- 詳細な要件・設計・構築手順・費用概算はIssue本文および`01_要件定義.md`〜`06_タスクリスト.md`を参照

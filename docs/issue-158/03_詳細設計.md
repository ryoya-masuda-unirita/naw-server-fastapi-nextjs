# 03_詳細設計

## 構築順序の方針（コスト最小化）

時間課金される（＝ネットワーク・ストレージ系より高くつく）リソースは **EC2（ECSホスト・踏み台）・RDS・ElastiCache・ALB** の4種類。これらを稼働させる時間を最短にするため、以下の順序で構築する。

- **フェーズ0**: 無料・低コストな準備作業を先に全て終わらせる（時間制限なし、何度でもやり直せる）
- **フェーズ1**: RDS・ElastiCache・踏み台を起動し、DBの初期化（マイグレーション・seed投入）を済ませる
- **フェーズ2**: ECS（backend）を起動する
- **フェーズ3**: ALB＋HTTPS化を最後に、最短時間だけ行う（sslip.io + Let's Encrypt検証はALBのIPが変わらないうちに一気に終わらせる）
- **フェーズ4**: 動作確認
- **フェーズ5**: 全リソース削除（フェーズ3→2→1→0の逆順）

### リスクと対策: ALBには固定IPがない

ALBはAWSの仕様上、Elastic IPのような静的パブリックIPを持てない（DNS名での利用が前提）。sslip.io方式（`<IP>.sslip.io`）はIPが変わらないことを前提にしているため、**ALB作成直後に確認した現在のIPを使い、その場でLet's Encrypt検証→証明書取得→ACMインポート→HTTPSリスナー設定まで一気に完了させる**（フェーズ3を中断・長時間放置しない）。

## フェーズ0: 準備（コストなし・低コスト）

### 0-1. 共通事項

- 全リソースに共通タグ `Project=issue-158` を付与する
- リージョン: `ap-northeast-1`（CloudFrontのみグローバルサービスのためリージョン概念なし）

### 0-1.5. 作業用IAMユーザー（root運用の廃止）

以降のAWS CLI操作をrootではなくIAMユーザーで行うため、最初に作成する。

```bash
aws iam create-user --user-name naw-fastapi-issue158-operator --tags Key=Project,Value=issue-158
aws iam attach-user-policy --user-name naw-fastapi-issue158-operator \
  --policy-arn arn:aws:iam::aws:policy/AdministratorAccess

aws iam create-access-key --user-name naw-fastapi-issue158-operator --output json > /tmp/issue158-operator-key.json
aws configure set aws_access_key_id "$(jq -r .AccessKey.AccessKeyId /tmp/issue158-operator-key.json)" --profile naw-fastapi-issue158
aws configure set aws_secret_access_key "$(jq -r .AccessKey.SecretAccessKey /tmp/issue158-operator-key.json)" --profile naw-fastapi-issue158
aws configure set region ap-northeast-1 --profile naw-fastapi-issue158
rm -f /tmp/issue158-operator-key.json

aws sts get-caller-identity --profile naw-fastapi-issue158   # IAMユーザーとして認証できることを確認
```

- ローカルの`~/.aws/config`にプロファイル`naw-fastapi-issue158`として登録される
- `granted`（`assume`コマンド）でこのプロファイルへ切り替えて以降の作業を行う
- 権限は`AdministratorAccess`とする（個人単一アカウントのdev検証用途のため。詳細は`01_要件定義.md`参照）
- このIAMユーザーは検証用の使い捨てリソースではなく、次回以降のAWS作業でも再利用する想定のため、フェーズ5（全削除）の対象には含めない

### 0-2. IAM（ECS用ロール）

- ECSタスク実行ロール（`AmazonECSTaskExecutionRolePolicy`相当。ECRからのイメージpull・CloudWatch Logsへの書き込みに必要）
- ECSコンテナインスタンス用IAMロール（`AmazonEC2ContainerServiceforEC2Role`相当）

### 0-3. キーペア

- 踏み台SSH用のキーペアを作成し、秘密鍵をローカルに保存（`chmod 400`）

### 0-4. ネットワーク

- VPC作成（例: `10.0.0.0/16`）
- パブリックサブネット2つ（例: `10.0.1.0/24` in ap-northeast-1a、`10.0.2.0/24` in ap-northeast-1c）
- インターネットゲートウェイ作成・VPCにアタッチ
- ルートテーブル作成（`0.0.0.0/0` → IGW）、両サブネットに関連付け
- セキュリティグループ5つ
  - `sg-bastion`: 22番を作業者IPのみ許可
  - `sg-alb`: 80/443番を`0.0.0.0/0`許可
  - `sg-ecs`: `sg-alb`からのアプリケーションポート（例: 8000）のみ許可
  - `sg-rds`: `sg-bastion`・`sg-ecs`からの5432番のみ許可
  - `sg-elasticache`: `sg-ecs`からの6379番のみ許可

### 0-5. ECR + backendイメージ

```bash
aws ecr create-repository --repository-name naw-fastapi-backend-dev --tags Key=Project,Value=issue-158
aws ecr get-login-password --region ap-northeast-1 | docker login --username AWS --password-stdin <account-id>.dkr.ecr.ap-northeast-1.amazonaws.com

docker build -t naw-fastapi-backend-dev:latest -f backend/Dockerfile backend
docker tag naw-fastapi-backend-dev:latest <account-id>.dkr.ecr.ap-northeast-1.amazonaws.com/naw-fastapi-backend-dev:latest
docker push <account-id>.dkr.ecr.ap-northeast-1.amazonaws.com/naw-fastapi-backend-dev:latest
```

### 0-6. S3 + frontend-angularビルド成果物

```bash
cd frontend-angular
npm ci
npm run build -- --configuration dev   # 実際のビルドコマンドは package.json を確認

aws s3api create-bucket --bucket naw-fastapi-frontend-dev-<suffix> --region ap-northeast-1 \
  --create-bucket-configuration LocationConstraint=ap-northeast-1
aws s3 sync dist/example/browser/ s3://naw-fastapi-frontend-dev-<suffix>/ --delete
```

### 0-7. CloudFrontディストリビューション

- オリジン: 上記S3バケット（OAC/OAIでS3への直接アクセスを禁止し、CloudFront経由のみ許可）
- Price Class: **Price Class 100**
- デフォルトルートオブジェクト: `index.html`
- 作成後、デプロイ完了（Status: Deployed）まで15〜20分程度かかるため、フェーズ0の中で最初に着手し、他の作業と並行して待つ

## フェーズ1: DB・キャッシュ・踏み台

### 1-1. RDS

```bash
aws rds create-db-subnet-group --db-subnet-group-name naw-fastapi-dev-subnet-group \
  --subnet-ids <subnet-1> <subnet-2> --tags Key=Project,Value=issue-158

aws rds create-db-instance \
  --db-instance-identifier naw-fastapi-dev \
  --db-instance-class db.t4g.micro \
  --engine postgres \
  --allocated-storage 20 --storage-type gp3 \
  --master-username root --master-user-password <password> \
  --vpc-security-group-ids <sg-rds> \
  --db-subnet-group-name naw-fastapi-dev-subnet-group \
  --no-publicly-accessible \
  --no-multi-az \
  --tags Key=Project,Value=issue-158
```

### 1-2. ElastiCache for Redis

```bash
aws elasticache create-cache-subnet-group --cache-subnet-group-name naw-fastapi-dev-subnet-group \
  --subnet-ids <subnet-1> <subnet-2>

aws elasticache create-cache-cluster \
  --cache-cluster-id naw-fastapi-dev-redis \
  --engine redis \
  --cache-node-type cache.t4g.micro \
  --num-cache-nodes 1 \
  --cache-subnet-group-name naw-fastapi-dev-subnet-group \
  --security-group-ids <sg-elasticache> \
  --tags Key=Project,Value=issue-158
```

### 1-3. 踏み台EC2

- AMI: Amazon Linux 2023、インスタンスタイプ: `t4g.nano`、`sg-bastion`、パブリックサブネット、パブリックIP自動割当
- 起動後、SSH接続を確認

### 1-4. RDS初期化（踏み台経由）

- ローカルから踏み台へSSHトンネル（`ssh -L 5433:<RDSエンドポイント>:5432 ec2-user@<踏み台IP>`）
- `alembic upgrade head` をローカルから`DATABASE_URL=postgresql://root:***@localhost:5433/postgres`で実行
- `backend/seed.sql`を投入

## フェーズ2: ECS（backend）

### 2-1. ECSクラスタ・EC2インスタンス

- ECSクラスタ作成（EC2起動タイプ）
- ECS最適化AMI、`t4g.nano`、`sg-ecs`、パブリックサブネット、パブリックIP自動割当、IAMインスタンスプロファイルに0-2で作成したロールを指定
- 起動したインスタンスがECSクラスタに`ACTIVE`として登録されることを確認

### 2-2. タスク定義

- イメージ: 0-5でpushしたECRイメージ
- 環境変数: `DATABASE_URL`（RDSエンドポイント）・`REDIS_URL`（ElastiCacheエンドポイント）・`COOKIE_SECURE=true`・`COOKIE_SAME_SITE=none`等
- ポートマッピング: コンテナ8000番 → ホスト8000番

### 2-3. ECSサービス

- Desired count: 1
- 起動後、ECSインスタンスのパブリックIP:8000へ直接アクセスし、ヘルスチェック相当のエンドポイントが200を返すことを確認（ALB経由の前に、まずECS単体での疎通を確認する）

## フェーズ3: ALB + HTTPS化（最短時間で完了させる）

以下は**中断せず一気に実施する**（ALBの固定IPが保証されないため）。

1. ALB作成、リスナー: HTTP(80)、ターゲットグループにECSタスクを登録
2. ALBに割り当てられた現在のパブリックIPを確認（`nslookup <ALBのDNS名>`等）
3. `<ip>.sslip.io`が正しくそのIPに解決されることを確認
4. certbotで`<ip>.sslip.io`に対しHTTP-01チャレンジを実行し証明書を取得（ALBのHTTPリスナーがcertbotのチャレンジパスをECS/一時的な検証用サーバーに転送できるようにしておく）
5. 取得した証明書をACMへインポート
   ```bash
   aws acm import-certificate --certificate fileb://cert.pem --private-key fileb://privkey.pem \
     --certificate-chain fileb://chain.pem --tags Key=Project,Value=issue-158
   ```
6. ALBにHTTPS(443)リスナーを追加し、5でインポートした証明書をアタッチ、ターゲットグループへ転送
7. `https://<ip>.sslip.io/`でbackendに疎通できることを確認

## フェーズ4: 動作確認

- CloudFront配信URL（frontend-angular）からログインし、ALB経由（`https://<ip>.sslip.io`）のbackend APIにクロスオリジンでリクエストが飛ぶことを確認
- セッションCookie（`SameSite=None; Secure`）が正しく発行・送信され、ログイン状態が維持されることを確認
- 踏み台経由でpgAdmin4等からRDSに接続できることを確認
- 詳細な確認観点は`04_テスト設計.md`・`05_テスト詳細設計.md`を参照

## フェーズ5: 全リソース削除

フェーズ3→2→1→0の逆順で削除する。詳細な削除コマンド・確認方法は`02_基本設計.md`「運用方針」章、および以下の順序に従う。

1. ALBのHTTPSリスナー削除→ALB削除→ターゲットグループ削除→ACM証明書削除
2. ECSサービス削除→タスク定義の登録解除→ECSクラスタ削除→ECSホストEC2をterminate
3. 踏み台EC2をterminate
4. ElastiCacheクラスタ削除→キャッシュサブネットグループ削除
5. RDSインスタンスを`--skip-final-snapshot`で削除→DBサブネットグループ削除
6. CloudFrontディストリビューションを無効化→（15〜20分待機）→削除
7. S3バケットを空にしてから削除
8. ECRのイメージを削除（リポジトリごと削除でも可）
9. セキュリティグループ削除（相互参照があれば先にルール削除）
10. IGWをVPCからデタッチして削除→サブネット削除→ルートテーブル削除→VPC削除
11. キーペア削除、ECS用IAMロール削除
12. `aws resourcegroupstaggingapi get-resources --tag-filters Key=Project,Values=issue-158` で0件になっていることを確認（**作業用IAMユーザー`naw-fastapi-issue158-operator`は削除対象に含めない**。次回以降のAWS作業でも再利用するため）

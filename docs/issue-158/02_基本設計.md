# 02_基本設計

## 変更対象

- AWSアカウント上のリソース（作業用IAMユーザー/ECR/ECS/RDS/ElastiCache for Redis/踏み台EC2/ALB/ACM/S3/CloudFront、関連VPC・サブネット・セキュリティグループ・IAMロール）
- ローカル環境（`~/.aws/config`へのプロファイル追加、`granted`による切り替え設定）
- `backend`のDockerイメージ（本番相当のビルド用`backend/Dockerfile`が既に存在するため、コード変更は不要）
- `frontend-angular`のビルド成果物（`ng build`の出力）
- ドキュメント（本チケットの構築手順・接続情報の記録）

コード変更は不要（既存の`backend/Dockerfile`をそのまま使う）。主な作業はAWS側のリソース構築とデプロイ操作になる。

### ネットワーク構成の方針（最安構成優先）

- NAT Gateway（時間課金＋データ処理料金が高額）を避けるため、**プライベートサブネットは作らない**。以下の構成を基本方針とする
  - VPC: 1つ（新規、または`ap-northeast-1`のデフォルトVPC流用）
  - サブネット: **パブリックサブネットのみ、2AZ分（2つ）**。RDSのDBサブネットグループがAWSの制約で最低2AZ分のサブネット登録を要求するための対応であり、実際にRDSが稼働するのはSingle-AZの1つのみ
  - インターネットゲートウェイ: 1つ（無料）、ルートテーブル: パブリックサブネット用に1つ（IGWへのデフォルトルート、無料）
  - ECSのEC2インスタンス（`t4g.nano`）・踏み台EC2（`t4g.nano`）・ALBは、上記パブリックサブネットに配置しパブリックIPを付与
  - RDS（`db.t4g.micro`、Single-AZ）・ElastiCache for Redis（`cache.t4g.micro`）も同じパブリックサブネットのサブネットグループに配置するが、**RDSの「パブリックアクセス可能」設定はNo**、**ElastiCacheもパブリックアクセス不可（デフォルト）**とし、セキュリティグループで踏み台・ECSからのみアクセス可能にすることで、実質的にインターネットから遮断する
- セキュリティグループ
  - 踏み台EC2: 22番ポートを作業者IPのみに限定
  - ALB: 80/443番ポートを`0.0.0.0/0`に開放（dev環境の動作確認用）
  - ECS（backend）: ALBのセキュリティグループからのアプリケーションポートのみ許可
  - RDS: 踏み台EC2・ECSのセキュリティグループからの5432番ポートのみ許可
  - ElastiCache: ECSのセキュリティグループからの6379番ポートのみ許可

### ALB + HTTPS化の方針

Issue #147で導入したセッションCookie（`SameSite=None`は`Secure=true`必須というバリデーション）が、CloudFront（frontend-angular）とECS（backend）の別オリジン構成で正しく機能するかを検証するため、ALBによるHTTPS終端を**一時的に**構築する。

- ALB（Application Load Balancer）: ECS（backend）の前段に配置し、HTTPS（443）でリッスンしてECSへ転送する
- 証明書取得: **sslip.io**（`<パブリックIP>.sslip.io`が自動的にそのIPに解決されるワイルドカードDNSサービス、ドメイン登録・Route53ホストゾームともに不要）を使い、Let's EncryptのHTTP-01チャレンジで証明書を取得し、AWS Certificate Manager（ACM）へ「証明書のインポート」機能で登録してALBにアタッチする
  - ACMの標準的なDNS検証（Route53連携）は、第三者が保有するドメイン（sslip.io）に自分でCNAMEを追加できないため利用不可。そのためLet's Encrypt発行＋ACMインポートという手順を取る
  - Route53ホストゾーンの新規作成は行わない（ドメイン登録費・ホストゾーン費とも発生させない）
- **検証後、ALB・取得した証明書（ACMへのインポート分）は削除する**

## 運用方針: 「停止」ではなく「完全削除」でコストゼロに戻す（使い捨て運用）

動作確認が終わったら、作成した全リソース（ECS/RDS/ElastiCache/踏み台EC2/ALB/ACM証明書/S3のオブジェクト/CloudFrontディストリビューション/ECRのイメージ/VPC・サブネット・IGW・ルートテーブル・セキュリティグループ）を**完全に削除**し、月額の固定費用が一切残らない状態に戻す。次回動作確認が必要になった時点で、`03_詳細設計.md`の構築手順に従いゼロから再構築する。

- 全リソースに共通タグ（例: `Project=issue-158`）を付与し、削除後に以下のコマンドで対象タグのリソースが0件であることを確認する
  ```bash
  aws resourcegroupstaggingapi get-resources --tag-filters Key=Project,Values=issue-158
  ```
- 削除順序・注意点（詳細は`03_詳細設計.md`で手順化する）
  - CloudFront: 先に無効化し、反映（15〜20分程度）を待ってから削除
  - S3: バケット内のオブジェクトを空にしてから削除
  - RDS: `--skip-final-snapshot`を付けて削除（最終スナップショットを残さない。手動スナップショットがあれば別途削除）
  - ElastiCache: クラスタを削除（RDSと異なり最終スナップショット等の概念はなく、削除のみでよい）
  - ALB→リスナー→ターゲットグループ→ACM証明書の順に削除（証明書はリスナーから参照されている間は削除不可）
  - EC2（ECSホスト・踏み台）: stopではなくterminate（EBSは delete-on-termination で道連れ削除）
  - Elastic IPを割り当てていた場合はrelease
  - セキュリティグループ: 相互参照がある場合は先にルールを削除してから削除
  - IGWはVPCからデタッチしてから削除、最後にVPC本体を削除
  - ECR: イメージを削除（リポジトリごと削除でも可）

## 画面 / API変更概要

- 画面・API仕様の変更はなし（既存の`backend`/`frontend-angular`をそのままAWS上にデプロイする）

## 影響範囲

- ローカル開発環境（`docker compose`）には影響しない
- 既存のGitHub Actions（`backend-tests.yml`・`project-status-sync.yml`）には影響しない（CI/CDのデプロイ自動化は本チケットのスコープ外）
- 検証中のみAWS利用料が発生する（ECS/RDS/踏み台EC2/ALB/S3/CloudFront/ECR）。動作確認完了後は全リソースを完全削除するため、月次の固定費用は発生しない（「運用方針」章参照）
- CloudFrontをPrice Class 100にするため、日本からのアクセス時にレイテンシが上がる可能性がある（dev環境の動作確認用途と割り切る）

## 移植方針

- 本チケットは移植元コードのポートではないため、Spring Boot/Angular側の実装参照は不要
- ただし移植元（`naw-server`/`secuaigent-client`）が実際にAWS上でどう構成されているか（ECRリポジトリ名の命名規則、ECSのタスク定義の構成、S3+CloudFrontのキャッシュ戦略等）は`docs/調査結果/AWS使用リソース.md`の調査結果を参考にする
  - 移植元はIaCなしでコンソール手動構築＋GitHub ActionsからのVariables/Secrets参照という構成であり、今回も同様の考え方（まずコンソールで手動構築）を踏襲する

## 将来のTerraform化を見据えた補足

- 本チケットで洗い出す「構築すべきリソース一覧」「削除すべきリソースと順序」は、将来Terraformでコード化する際にそのままリソース定義・`depends_on`の設計根拠として流用できる
- Terraform移行後は、`terraform destroy`/`terraform apply`により「全削除」「ゼロから再構築」がそれぞれ1コマンドで実行可能になる（Terraformが依存関係グラフを自動計算するため、手動でのCLI実行順序の管理が不要になる）
- ただし以下はTerraform移行後も残る制約
  - S3バケットは`force_destroy = true`を設定しないと、非空バケットの`destroy`が失敗する
  - RDSは`skip_final_snapshot = true`（＋`deletion_protection = false`）を設定しないと、削除時に最終スナップショットが残る
  - CloudFrontの無効化→反映待ち（15〜20分）はAWS側の仕様であり、Terraformを使っても`destroy`の所要時間自体は短縮されない
  - Let's Encrypt発行証明書のACMインポートは、証明書取得自体（certbot実行）をTerraformの外（`local-exec`等）で行う必要がある

# 01_要件定義

## 背景

ログイン自体は成功するが、ログイン後のAPI呼び出しおよびページリロード時に認証が失われ、未認証状態（401）に戻ってしまう。

原因は、バックエンド（FastAPI）がJWTをレスポンスボディで返し `Authorization: Bearer <token>` ヘッダーでの認証のみをサポートしているのに対し、動作確認用フロントエンド（`frontend-angular`）は移植元のSpring Boot実装（Cookieセッション認証）に合わせて `withCredentials: true` でCookie送信を前提とした実装になっており、Authorizationヘッダーを付与する仕組みを持たないこと。

移植元のSpring Boot実装では、ログイン成功時にHTTPセッションを確立しSpring SessionによるCookie（`Set-Cookie`）を発行することで、ブラウザからの後続リクエストが自動的に認証される設計になっている。レスポンスボディのJWTはあくまで付随情報であり、ブラウザ経由の認証には使われていない。

## 方針

バックエンドの認証方式を、移植元の設計に合わせて**Cookieセッション方式に寄せる**。

- ログイン成功時、JWTをHttpOnly Cookieとして発行する（`Set-Cookie`）
- 認証が必要なAPIは、Cookieに含まれるJWTを検証して認証する
- `frontend-angular`（Angular）は既に `withCredentials: true` を全リクエストに付与済みのため、フロントエンド側の変更は不要
- `frontend`（React）は当面不問方針のため対象外
- 既存のBearerトークン方式（`Authorization: Bearer <token>`）による認証も、API直叩き・テストコードでの利用実績があるため、後方互換のため引き続きサポートする（Cookie優先、Cookieがない場合はAuthorizationヘッダーにフォールバック）

## 機能要件

- `POST /auth/login` 成功時、レスポンスボディに加えて `Set-Cookie` でJWTを含むHttpOnly Cookieを発行する
- `POST /auth/logout` で該当Cookieを削除する（`Set-Cookie` で無効化）
- 認証が必要なエンドポイント（`GET /api/auth`, `GET /api/users/profile`, `GET /api/admin/users` 等）は、Cookieに含まれるJWTを検証して認証する
- Cookieが存在しない場合は、従来どおり `Authorization: Bearer <token>` ヘッダーでの認証にフォールバックする（既存テスト・API直叩きとの後方互換のため）
- `GET /api/auth`（トークン再発行エンドポイント）で新たに発行するトークンも、レスポンスボディに加えてCookieとして再設定する

## 非機能要件

- Cookieは `HttpOnly` 属性を付与し、JavaScriptからのアクセスを防ぐ（XSS対策）
- ローカル開発環境（HTTP）でも動作するよう、`Secure` 属性は環境設定に応じて切り替え可能にする
- `SameSite` 属性は、フロントエンドとバックエンドが別オリジン（別ポート）で動作する構成を考慮し、クロスサイトリクエストでもCookieが送信される設定にする
- Cookieの有効期限は既存のJWT有効期限（5時間）に合わせる

## スコープ外

- `frontend`（React）側の対応（不問方針のため）
- JWTの署名鍵（`SECRET_KEY`）のハードコード解消（別Issueで対応する事項であり、今回のスコープ外）
- Spring SessionのようなサーバーサイドセッションストアやRedis等の導入（JWTをCookieに載せる方式のみとし、セッションストアは導入しない）

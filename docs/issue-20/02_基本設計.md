# 02_基本設計

## 変更対象レイヤー

- `core`（JWT検証・Cookie読み書きの共通処理）
- `routers`（ログイン・ログアウト・トークン再発行エンドポイントのレスポンス処理）

サービス層・リポジトリ層・モデル層の変更はない。

## API変更概要

### ログイン API

- 成功時、従来どおりレスポンスボディにJWTを含めつつ、`Set-Cookie` でJWTを含むHttpOnly Cookieを追加で発行する
- レスポンスボディの形式（フィールド構成）は変更しない

### ログアウト API

- Cookieを無効化する `Set-Cookie`（有効期限切れ）を返すよう変更する
- レスポンスボディの形式は変更しない

### トークン再発行 API（`GET /api/auth`）

- 認証済みユーザーに対して新しいJWTを発行する際、レスポンスボディに加えてCookieも再設定する

### 認証が必要なAPI全般

- 認証の検証方法を「Cookie優先、なければAuthorizationヘッダーにフォールバック」に変更する
- Cookie・Authorizationヘッダーいずれの場合もJWTの検証ロジック（署名検証・有効期限チェック・ユーザー存在チェック）は変更しない
- 401を返す条件（トークンなし・不正・期限切れ・ユーザー不在）は現状維持

## 影響範囲

- 認証が必要な全エンドポイント（`users`ルーター配下含む）が、認証依存関数を経由するため間接的に影響を受けるが、呼び出し側のインターフェース（依存関数の型・戻り値）は変更しない
- 既存の統合テスト（`Authorization: Bearer <token>` ヘッダーを使うテスト）は、フォールバック方式を維持するため修正不要な想定
- `frontend-angular`・`frontend`（React）のコード変更は不要
- CORS設定（`allow_credentials=True`）は対応済みのため変更不要

## Cookie設計

| 項目 | 値 | 理由 |
|---|---|---|
| Cookie名 | `access_token` | 用途が明確な名称 |
| 属性 | `HttpOnly` | JavaScriptからのアクセスを防ぎXSS耐性を持たせる |
| 属性 | `SameSite=Lax` | フロントエンドとバックエンドが別ポート（localhost:4201 / localhost:8001）でも同一サイト扱いとなり送信される。将来別ドメイン構成になった場合は別途見直す |
| 属性 | `Secure`（環境依存） | ローカル開発（HTTP）では無効、本番相当環境（HTTPS）では有効にする設定値を追加する |
| 有効期限 | 5時間（JWTと同じ） | JWT自体の有効期限と矛盾しないようにする |
| 値 | JWT文字列そのもの | サーバーサイドセッションストアを導入せず、既存のJWT検証ロジックをそのまま流用するため |

## 認証検証ロジックの変更概要

現状はAuthorizationヘッダー必須（`HTTPBearer` 依存）になっている認証チェックを、以下の優先順位でトークンを取得するよう変更する。

1. リクエストCookie（`access_token`）にトークンがあればそれを使う
2. なければ `Authorization: Bearer <token>` ヘッダーの値を使う
3. どちらもなければ401を返す

取得したトークン以降の検証処理（署名検証・ペイロード確認・ユーザー存在確認）は現状のロジックを流用する。

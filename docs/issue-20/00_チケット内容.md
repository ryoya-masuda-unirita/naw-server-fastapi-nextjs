# ログイン後、リロードやAPI呼び出しで認証状態が失われる

## 概要

ログイン自体は成功するが、ログイン後の各種API呼び出しおよびページリロード時に認証が失われ、未認証状態（401）に戻ってしまう。issue-18（CORS未設定・セッションAPIパス重複の修正）の動作確認中に発見した。

## 説明

### 現象

`frontend-angular`（`secuaigent-client` をモノレポに取り込んだもの）を使い、Playwrightで実際にログイン操作を確認したところ、以下の挙動を確認した。

1. `POST /auth/login` は200で成功し、ダッシュボードへ遷移する
2. ログイン直後の `GET /api/users/profile` が401 Unauthorizedになる
3. ページをリロードすると、セッション確認 `GET /api/auth` が401になり、ログイン画面に戻ってしまう

### 原因（調査結果）

移植元の Spring Boot 版（`~/Documents/naw-server`）は Spring Session による**Cookieベースのセッション認証**を採用している（`SecurityConfig.java` の `CookieSerializer` 参照）。

これに対し、`frontend-angular`（Angular）・`frontend`（React、issue-15/17で移植中）はいずれも移植元の実装に合わせて `withCredentials: true` / `credentials: 'include'` でCookie送信を前提としたHTTPクライアント実装になっている一方、ログインレスポンスのJWTトークンをAuthorizationヘッダーに再設定する処理はどちらのフロントエンドにも実装されていない。

一方で、FastAPI版バックエンド（Issue #7 で実装したJWT認証基盤）は以下の方式になっている。

- ログイン成功時にCookieを発行しない（JWTをレスポンスボディの `token` フィールドで返すのみ）
- 認証が必要なAPI（`GET /api/auth`、`GET /api/users/profile` 等）は `Authorization: Bearer <token>` ヘッダーを要求する（`HTTPBearer` セキュリティスキーム）

フロントエンド側はCookie前提、バックエンド側はBearerトークン前提となっており、ログイン直後を含めて認証が必要な通信が一切成立しない状態になっている。

### 影響範囲

- `frontend-angular`（Angular）: ログイン後のAPI呼び出しが軒並み401になり、リロードでログイン画面に戻る
- `frontend`（React）: 同様の実装（`credentials: 'include'`、トークン再付与処理なし）のため、同じ問題が起きる想定（今回はバックエンド優先方針のため未検証）

# 01 要件定義

## 背景

- Issue #5 で `tenants` / `users` テーブルを構築済み
- 認証基盤がないと他のすべての API が保護できず、フロントエンドとの結合もできない
- 参照実装（naw-server）では JWT（HS512）を用いたステートレス認証を採用している

## 機能要件

### 1. パスワード管理方式の変更

- 現在の `users.password` カラムを **削除** する
- `password_histories` テーブルを新設し、パスワードをここで管理する
  - 最新レコードがカレントパスワード
  - 将来のパスワード履歴チェック（パスワードリセット時）にも使用する

### 2. ログイン（POST /auth/login）

- リクエスト: `username`（login_id）、`password`（body）、`X-Tenant-ID`（ヘッダー）
- `password_histories` の最新レコードと bcrypt 照合してパスワードを検証する
- 成功時: JWT トークン + ユーザー情報を返す
- パスワードリセット要求時（`is_required_password_reset=true` またはパスワード有効期限切れ）: トークンなしで `REQUIRES_PASSWORD_RESET` ステータスを返す

### 3. 現在のユーザー情報取得（GET /api/auth）

- JWT が有効であれば、現在のユーザー情報と新しいトークンを返す
- `X-Tenant-ID` ヘッダー必須

### 4. ログアウト（POST /auth/logout）

- JWT はステートレスのためサーバー側では何もしない
- 200 を返すのみ（クライアント側でトークンを破棄する）

### 5. パスワードリセット（POST /auth/password/reset）

- リクエスト: `loginId`、`oldPassword`、`newPassword`、`X-Tenant-ID`（ヘッダー）
- 旧パスワードを `password_histories` 最新レコードと照合して検証する
- テナントのパスワードポリシー（最小文字数・大文字/小文字/数字/記号の要否）に適合しているか検証する
- テナントの `pw_histories_limit` 件分の過去パスワードと重複していないか検証する
- 成功時: `password_histories` に新規レコードを追加、`is_required_password_reset = false` に更新、JWT トークンを返す

### 6. JWT 認証ミドルウェア

- `Authorization: Bearer <token>` ヘッダーからトークンを取得・検証する
- トークンから `login_id` と `tenant_id` を取り出してリクエストコンテキストに注入する
- 保護対象エンドポイント（`/api/**`）への未認証アクセスは 401 を返す

## 非機能要件

- JWT 有効期限: 5時間（参照実装に合わせる）
- JWT アルゴリズム: HS512
- JWT payload: `sub` = login_id、`tenantId` = テナント ID
- パスワードハッシュ: bcrypt

## スコープ外

- ログインキー認証（`POST /auth/login-key`）: `login_key` カラムは存在するが、groups テーブル未作成のため次 Issue 以降
- ログイン失敗ロックアウト（`password_mismatch_histories` テーブル）: 別 Issue で対応
- グループ情報のレスポンス: `groups` テーブル未作成のため、ログインレスポンスの `groups` は空リストで返す

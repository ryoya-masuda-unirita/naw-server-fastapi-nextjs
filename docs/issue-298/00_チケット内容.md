# 生成AIアダプタとcoreのチャット部分をPythonに移植しWaha!エミュレーターに差し込む

## 概要

移植元 `generative-ai-adapter/generative-ai-adapter`（App・controller・service・vendor 等）と、それが使う `generative-ai-core` のチャット・プロバイダ・ネットワークの部分を移植し、#274 のエミュレーターの仮のチャット用ワークフローと差し替える。

## 説明

### 対象

- 通常チャット（`outputType=0/2`）と RAG 回答（その他。検索アダプタの出力を入力にする）の両経路。RAG 経路は検索アダプタ（別 Issue）ができるまで、入力の RAG コンテキスト JSON（`docs/rag-context-json-contract.md`）を受け取れるところまで
- プロバイダ（Azure OpenAI・OpenAI・Anthropic・Gemini・SecuAiGent（クラウドの `/api/llm/chat` を呼ぶ）など移植元にあるもの）
- textData（tools・createLibrary・accessToken・messageId）、推論の途中経過・ストリームファイル、ライブラリ生成
- 出力の `RetrievalAnswer` JSON

依存: #274（マージ済み）

### 方針

- 移植元 `secuaigent-ref/generative-ai-adapter/`（Java。`generative-ai-core`・`generative-ai-adapter`・`embedding-adapter`・`retrieval-adapter` の 4 プロジェクト）を、同じ 4 つの分け方のまま Python に移植する（完璧なクローン）。置き場所はルートの `generative-ai-adapter/` 配下に 4 つの Python パッケージ
- アダプタはサーバーではなくライブラリ。`waha-emulator/`（#274）のワークフローから import して呼ぶ。Waha! 固有の受け口（番号付きプロパティ・ColumnData・出力ファイル）は、エミュレーター側の設定・入出力に置き換える
- 本物の Waha! のワークフロー定義（どのサービス ID でどのアダプタをどの設定で動かすか）はどちらのリポジトリにもないため、移植元のアダプタのコード・テスト・docs（`docs/`・`specs/`）から読み取って決め、docs に根拠を書く
- 動かして理解できるよう、チャット 1 回でどのアダプタがどの順に何を受け取り何を返したかを、エミュレーターのログ（INFO）で追えるようにする

## その他

- 依頼時の追加条件: 実際の LLM には接続しない（テストは HTTP をモック。`echo` プロバイダは確認用に残す）、Docker でもアダプタを含めて動くこと、移植元の Java のテストのうち今回の範囲に当たるものを Python のテストとして移すこと、`server-local` と `waha-emulator` のテストが通り続けること、ルートの README・CLAUDE.md の更新、`generative-ai-adapter/README.md` にログの読み方と Docker での通しの確認手順を書くこと
- docstring は NumPy 形式（日本語。`Parameters`・`Returns`・`Raises`）。追加・変更したすべての関数・メソッド・クラスに書く

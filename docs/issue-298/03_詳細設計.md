### ワークスペースかパス依存かの判断

| 観点 | ワークスペース（採用） | 別プロジェクトのパス依存だけ |
|---|---|---|
| テスト | ルートで `uv run pytest` 1 回で core・adapter の両方 | パッケージごとに仮想環境・ロックが要る |
| core → adapter の依存の向き | 各パッケージの `pyproject.toml` で移植元と同じ | 同じ |
| Docker ビルド | ルートをビルドコンテキストにして core・adapter のソースをコピーするだけ | 同じ |
| エミュレーターからの利用 | adapter だけをパス依存で入れれば core も入る（ロックにも相対パスで入る） | 同じ |

ワークスペースの方が、テスト・lint を 1 か所で回せるため採用した。エミュレーターは独立した uv プロジェクトのまま、adapter をパス依存（編集可能）で使う。embedding・retrieval は、同じワークスペースにメンバーを足すだけで増やせる。

mypy は core と adapter の `tests/` に同名の `conftest.py` があるため、パッケージごとに 2 回実行する。pytest は `importlib` のインポートモードで衝突を避ける。

## core の詳細

### chat

- `CoreChatRequest`（プロバイダ・ネットワーク設定・出力モードのヒント・メッセージ・属性）と `CoreChatRequestBuilder`、`CoreMessage`・`CoreMedia`・`CoreChatTool`・`CoreGenerationOptions`・`CoreRagRequest`・`CoreRagContext`・`CoreChatResult`・画像説明の入出力。移植元の record の正規化（空白の除去・空は null 扱いなど）をそのまま移す
- `CoreChatResult` は失敗ありなら回答なしにする（移植元の 4 引数コンストラクタ相当）
- 属性のキー（生成オプション・RAG の JSON 応答・RAG のツール意図・tools・ストリームコールバック）は移植元と同じ文字列
- `CoreChatRuntime.chat/rag/explain_image`: プロバイダのランタイムを呼び、例外は `CHAT_PROVIDER_FAILURE`・`RAG_PROVIDER_FAILURE`・`IMAGE_EXPLANATION_PROVIDER_FAILURE` の失敗に変える。INFO で入口・結果を 1 行ずつログに出す
- `rag_prompt`: RAG 回答の契約プロンプト（移植元と 1 文字も変えない）・検証用の指示・コンテキスト 1 件の書式。移植元の `%n`（実行する OS の改行）は、Linux（Docker）で動かす前提のため `\n` に固定した

### network

- `CoreProxySetting`（なし・手動・システム）・`CoreNetworkSetting`（タイムアウトは 60〜86400 秒、既定 180 秒）の検証は移植元どおり
- 移植元は Apache HttpClient（SecuAiGent・Spring AI の RestClient）と Reactor Netty（Azure SDK）を使い分ける。Python は `httpx` に揃え、設定の当て方を揃えた: 手動プロキシはそのプロキシ（認証情報はユーザー名があるときだけ）、システムプロキシは環境変数、プロキシなしは環境変数も使わない、SSL 検証の無効化は証明書・ホスト名の検証なし、タイムアウトは接続・読み取り・書き込み・プール待ちの全部に同じ秒数
- SecuAiGent の送信は、手動プロキシの認証情報がユーザー名・パスワードの片方だけなら検証失敗にする（移植元 `CoreHttpTransportFactory.validate`）

### provider

- `CoreProviderId`: vendorId・正式名・別名（記号を除いた小文字で照合）。数字だけの文字列は vendorId として引く。**Python 版だけ `Echo`（99）を足した**（確認用）
- `CoreCredential`・`RuntimeProviderConfiguration`: 値を `repr`/`str` に出さない。属性は空白を除く。能力が空なら CHAT・RAG・IMAGE_EXPLANATION
- `CoreProviderRuntime`: プロバイダ × 能力ごとの実行器。登録がない・リクエストの型が違うときは `ProviderExecutionError`、実行器の例外は「Provider execution failed for …」で包む
- `CoreProviderRuntimeFactory`: 設定からクライアントを選んでランタイムを作る。**埋め込みの登録は後続の Issue**（移植元の `registerEmbedding` に当たる部分）
- クライアント: `GenericCoreProviderChatClient`（送信に任せ、例外を失敗に変える。tools があれば `unavailable_tools_mapping`／MCP の承認が `never` でなければ `unsupported_approval_continuation`）、`UnsupportedCoreProviderChatClient`（理由付きの失敗）

### OpenAI・Azure OpenAI（Spring AI の代替）

移植元は Spring AI 1.1.7 の `OpenAiChatModel`・`AzureOpenAiChatModel` を呼ぶ。Python では Spring AI が作る HTTP リクエストを `httpx` で直接作る。移植元の jar・SDK を読んで確かめた値は次のとおり。

| 項目 | 内容 | 根拠 |
|---|---|---|
| 呼び方 | ストリーミングしない 1 回の呼び出し（`stream: false`）。推論の途中経過は出ない | 移植元は `chatModel.call(...)` |
| OpenAI の URL・認証 | `{URL}/v1/chat/completions`・`Authorization: Bearer` | Spring AI の `OpenAiApi` の既定パス |
| Azure の URL・認証 | `{URL}/openai/deployments/{モデル名}/chat/completions?api-version=2025-01-01-preview`・`api-key` | Azure SDK（azure-ai-openai 1.0.0-beta.16）の `OpenAIServiceVersion.getLatest()` と、移植元の `serviceVersion(getLatest())` |
| 既定の temperature | 指定がなければ 0.7 を送る | Spring AI の両モデルの既定オプション |
| 生成パラメータ | `max_completion_tokens`・`top_p`・`frequency_penalty`・`presence_penalty`・`stop`（1 件の配列）・`reasoning_effort`（`none`・空は送らない）・`verbosity`（OpenAI だけ） | 移植元の `applyOpenAiGenerationOptions`・`applyAzureGenerationOptions` |
| RAG 回答 | 回答 1 回（OpenAI は JSON スキーマ、Azure は JSON オブジェクトの応答形式）→ 参照 ID があれば検証 1 回（JSON オブジェクト）。検証が真で、参照 ID がすべて範囲内のときだけ回答あり | 移植元の `toRagResult` |
| 画像付きメッセージ | 先頭に画像説明の system プロンプトを足す。画像は `image_url`（data URL） | 移植元の `toSpringMessages` |
| 参照 ID の判定 | `0` または先頭が 0 でない整数の表記だけ。重複は最初の 1 つ。JSON の数値を書かれたままの表記で読む（Gson の `getAsString` 相当） | 移植元の `parseRagAnswer` |

### SecuAiGent

移植元の `SecuAiGentCoreChatClient`・`SecuAiGentTransport`・`SecuAiGentAuthClient`・`SecuAiGentRequestMapper`・`SecuAiGentSseParser`・失敗の分類と、textData の読み込み（`CoreSecuAiGentTextDataLoader`）を移す。

- ログイン: アクセストークン（textData）があればそれ、なければ `POST {URL}/auth/login-key`（`X-Tenant-ID`）で JWT。失敗は `SECUAIGENT_AUTH_FAILURE`（407 は `…PROXY_AUTH_FAILURE`）
- chat: `POST {URL}/api/llm/chat`（multipart。`textData` の JSON と添付 `attachmentFiles`）。添付のファイル名（`/`・`\`・`"`・制御文字なし・重複なし）・MIME（具体的）・中身（空でない）を確かめる
- SSE: `data:` の行の JSON。`reasoning_delta`・`library_title_delta`・`library_content_delta` はコールバックへ、`text_delta` はつないで回答に、`message_stop` で成功。`error` や途中で切れたときは分類した固定の失敗
- RAG: 回答 1 回と検証 1 回。検証の呼び出しにはコールバックを渡さない
- 失敗の分類（SSL・検証・タイムアウト・プロキシ認証・認証・ネットワーク）と固定の要約は移植元どおり。JSON が壊れた SSE などの分類が Python の `ValueError`（検証に分類されてしまう）にならないよう、専用の例外を使って分類を揃えた
- textData の読み込み: 許可するキー・型・範囲（temperature は 0〜1、maxTokens は正の整数など）、重複キーの拒否、Bearer 付きのトークンの拒否、tools（`web_search` は 1 つ、`mcp` は `server_label` で同一性を判定）、streamfilepath の制御文字の拒否。不正はすべて固定メッセージの `SECUAIGENT_TEXTDATA_INVALID`

### 確認用の Echo（移植元にない）

キーなしで動く。chat は最後の本文のあるユーザー発言（画像の添付があれば添付名の注記付き）を回答にし、回答を 8 文字ずつ `reasoning_delta` としてコールバックへ流す。RAG は渡されたコンテキストをすべて参照したことにして、質問（`Question: ` を除く）を回答にする。画像説明は固定の文言。

### media（テキスト・画像だけ）

- `CoreMediaPreprocessingRuntime`: ファイルがない（`CORRUPT_FILE`）・空（`EMPTY_FILE`）・処理器がない（`UNSUPPORTED_MIME`）・例外（`PARSER_FAILURE` など）・内容がない（`PARSER_FAILURE`）を、移植元と同じコードの失敗にする
- 画像: 画像説明が無効なら画像のバイト列を添付に、有効なら core の chat に画像説明を頼み、`{名前}の内容は次の通り:` + 説明を本文にする
- **Tika の代替**: MIME 判定は先頭のバイト（PNG・JPEG・GIF・WebP・BMP・TIFF・PDF・ZIP/OOXML・OLE）→ 拡張子 → テキストとして読めるか、の順。テキストの読み込みは UTF-8（BOM 可）→ CP932 で、HTML はタグ・script・style を除く。Tika が読める Office の旧形式などは `UNSUPPORTED_MIME` になる
- PDF・Word・Excel・PowerPoint は未移植（後続）

## アダプタの詳細

### App

移植元の `App` の各メソッドを同じ順序・同じメッセージで移す。

- `validate_column_information`: 4・6 は FILE、3・5 は文字でなければ例外（移植元の日本語メッセージのまま）
- `validate_property`: URL・API キー・出力先（Windows パス形式）・途中経過ファイル（Windows パス形式）・プロキシのポート・ID・パスワード・数値・タイムアウトの検証と、日本語のメッセージ（保存時のチェック。ENUM は検証しない）
- `set_property`: 任意のプロパティの空は無視。数値の変換失敗は `Invalid number format for property ID …`。ベンダー（0〜5、Python 版は 99）、画像説明モード、推論の深さ・詳細度（未知の値は MEDIUM）、ライブラリ生成（49。`0`・空はデフォルト、`1` はオフ、それ以外は例外）
- `before_execute`: textData を読み、SecuAiGent なら資格情報・生成パラメータを上書きする。ライブラリ生成オフなら `createLibrary=false`・`messageId` なし。`createLibrary=true` で `messageId` が空なら textData の失敗。途中経過ファイルは textData の `streamfilepath` を優先し、なければプロパティ 42。textData が使えれば tools を解決する（textData → tools JSON → プロパティ 44〜47。通常チャットかつ SecuAiGent だけ。JSON の `tools: []` はプロパティに戻らない）
- `write`: textData・tools の失敗があれば出力して終わる。出力モード 0・2 は通常チャット（モデル名・出力先・実行できるプロバイダを確かめる）、それ以外は RAG（列 6 があれば RAG Context JSON、なければ旧経路）

### controller

- 通常チャット: リクエストを core のリクエストに変え（途中経過ファイルがあればコールバックを付ける）、tools の失敗は回答として出力、それ以外の失敗は例外（`コード: 要約`、512 文字まで）。出力モード 2 は本文だけ、それ以外は `RetrievalAnswer` の JSON
- RAG: 入力不足は回答として出力して core を呼ばない。tools があれば `unsupported_tools_route`。コンテキストを `File ID`・`FileName`・`Content` の囲みにして user メッセージに足し、`Question: …` を足し、JSON 応答と `submit_question` のツール意図を付けて core の RAG へ。回答なしなら固定の文言とすべてのパス。参照 ID が範囲外なら不整合を回答として出力
- `RetrievalAnswer` の JSON: 項目順は `answer`・`filepaths`・`references`・`imageExplanations`、画像説明が null のときは項目ごと省く（Gson と同じ）。1 行・UTF-8

### RAG Context JSON・textData・途中経過

- RAG Context JSON v1（`rag_context_json.py`）: 1 MiB・20 件・本文 8000 文字・allow root の中の通常ファイルだけ、未知の項目・型違い・`graph` と `graphEvidence` の食い違い・`path` の形（ノードと辺の交互・深さと辺の数）・`RAG_CONTEXT_BEGIN` などの印・役割の印・制御文字を拒否し、固定の失敗（理由・パスを出さない）にする。各コンテキストは data-only の囲みにする。シンボリックリンクは辿った先が root の外なら拒否
- 途中経過（`reasoning_output_sink.py`）: 既存のファイルを追記で開く（作らない）。開けなければ 50〜150 ms 待って最大 20 回・2 秒以内で再試行し、だめなら固定のコード（`REASONING_OUTPUT_INVALID_PATH`・`…NOT_FOUND`・`…ACCESS_DENIED`・`…NOT_APPENDABLE`・`…RETRY_INTERRUPTED`）だけの失敗。回復したら WARNING を 1 回。1 行ごとに flush。書き込み・flush の失敗は再試行せず、close の失敗は無視

## エミュレーターの詳細

### ワークフローの設定（`workflow_config.py`）

```json
{ "default": {"outputType": 0, "properties": {…}},
  "services": {"<サービスID>": {"outputType": 0|1|2, "ragContextJson": "<パス>", "properties": {…}}} }
```

- `properties` のキーは `PropertyIds` の名前。値の `${環境変数}` は読み込み時に展開（ない環境変数は起動時のエラー）。`VENDOR` は名前でも ID でもよい。予約（`OUTPUT_DIR`・`REASONING_OUTPUT_PATH`・`TEXT_DATA_JSON_FILE_PATH`）・未知の名前・未知の項目は拒否。各値はアダプタの `validate_property` を通す
- 設定ファイルは `WAHA_WORKFLOWS_FILE`（空文字列は未設定）。なければ `LLM_PROVIDER`（echo・azure_openai）から出力モード 0 の既定を作る。Azure の場合 `AZURE_OPENAI_API_VERSION` は廃止（SDK の最新で固定）

### ワークフロー（`workflows/generative_ai.py`）

- `build_adapter_job`: ジョブごとの一時ディレクトリに添付（名前のディレクトリ部分は取り除く）・履歴・textData を書き、列（`question`＝ユーザー・文字、`attachmentfile`＝ユーザー・FILE（RAG 以外）、`history`＝会話履歴・FILE、RAG なら RAG Context JSON パス・FILE）とプロパティ（設定の値 + 出力先・途中経過・textData のパス）を作る。`question` がない・UTF-8 でない、textData の `streamfilepath` が `STREAM_ALLOWED_DIR` の外のときは `WorkflowError`
- `GenerativeAiWorkflow.run`: 同期のアダプタを別スレッドで動かす。`set_property` → `connect` → `set_column_information` → `set_view_name` → `before_execute` → `write` の順。出力ファイルの中身を outputfile にする。アダプタの例外は `生成AIアダプタの実行に失敗しました: …` の `WorkflowError`（理由は core がサニタイズ済み）
- ジョブ（`jobs.py`）はストリームファイルを開き、`WorkflowRequest` に許可ディレクトリを渡す。成功なら outputfile を保存してから `completed`、失敗なら `error` を書く（#274 のまま）

### ログ

INFO で、受け取った入力スロット（名前・サイズ）→ execute（サービス ID・選ばれたワークフロー）→ スロット → 列・プロパティの対応（プロパティは名前だけで値を出さない）→ `beforeExecute` の textData・tools の解決結果 → `write` の経路（chat/rag）→ メッセージ数 → core の入口・プロバイダの呼び出し（HTTP のメソッド・パス・状態コード・件数だけ）→ 結果（回答の文字数・参照 ID）→ 出力ファイルの書き込み → 途中経過の件数 → ジョブの成否、の順に 1 行ずつ出る。API キー・トークン・パスワード・textData の中身・質問の本文はログに出さない。

## 移植元と変えた点・再現できていない点

| # | 内容 | 理由・影響 |
|---|---|---|
| 1 | Spring AI・Azure SDK を使わず、HTTP リクエストを直接作る | Python に同等のライブラリを入れない方針。URL・ヘッダー・本文・既定値は jar・SDK から確かめた値に揃えた。自動リトライ（Spring AI・Azure SDK 内蔵）は再現していない |
| 2 | Tika を使わない MIME 判定・テキスト抽出 | テキスト・画像の範囲だけ。Tika が読める他の形式は `UNSUPPORTED_MIME` |
| 3 | PDF・Word・Excel・PowerPoint の前処理、画像のページ全体の説明 | 後続。画像説明モード `FULL_PAGE` は、画像ファイルでは `EMBED_ONLY` と同じ動き |
| 4 | ログ出力先（`WAHA_GENERATIVE_AI_LOG_*`）を標準の `logging` に置き換え | Waha! 固有の仕組み。出力先はエミュレーターが決める |
| 5 | `HttpUtil`・`HttpClientConfig`（テスト接続用）・`DerivedResourceName*`（埋め込み・検索用）・`PromptTemplate`・`Answer`・`CheckAnswer` を移植していない | 今回の経路から使われない（`testConnect` は移植元でも通信しない） |
| 6 | embedding の登録・`CoreProviderConnectivityProbe`・Graph/ベクトル関連 | 後続 |
| 7 | `Echo` プロバイダ・ベンダー ID 99 | Python 版だけの確認用 |
| 8 | OpenAI・Azure で temperature 未指定のとき、既定の 0.7 を実際に送る | Spring AI は既定値をオプションに持つため、送信される値を揃えた |
| 9 | SecuAiGent の SSE を `message_stop` で打ち切る | 移植元と同じ（残りは読まない） |

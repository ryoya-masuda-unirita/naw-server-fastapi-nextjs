# 02_基本設計

## 変更対象

- `routers/auth.py`（ルーティング追加）
- `services/auth_service.py`（ログインキー認証ロジック追加）
- `repositories/user_repository.py`（ログインキー検索メソッド追加）
- `schemas/auth.py`（リクエストスキーマ追加）

## 画面 / API 変更概要

| メソッド | パス | 概要 |
|---|---|---|
| POST | `/auth/login-key` | ログインキーによる認証、成功時はJWTトークンを返す |

- リクエスト: `{ "loginKey": string }`
- レスポンス: 既存の `AuthResponse`（`/auth/login` と共通）
- ヘッダー: `X-Tenant-ID` 必須（未指定時は既存の `/auth/login` と同様、FastAPIの必須ヘッダーバリデーションにより422を返す。これは既存実装の踏襲であり、移植元Javaの400とは異なるが、本リポジトリで既に確立されたパターンに合わせる）

## 影響範囲

- `routers/auth.py` に新規エンドポイントを追加するのみで、既存エンドポイントの挙動には影響しない
- `user_repository.py` にメソッドを追加するのみで、既存メソッドには影響しない

## 移植方針

- 移植元Javaの `findByLoginKeyAndTenantId` は `loginKey` と `tenantId` の両方をクエリ条件に含めている。そのため、ログインキーが存在しないケースと、テナントが一致しないケース（＝別テナントの同じログインキー）は、クエリ結果としてどちらも「該当ユーザーなし」に収束する
- 移植元Javaのコントローラには `userDetails.getTenantId()` との追加比較（不一致時403）があるが、上記の理由によりこの分岐は実質到達不能なコード（クエリ自体がテナントで絞り込み済みのため）。FastAPI版では、この防御的だが実質デッドコードな分岐を再現せず、`find_by_login_key` のクエリで `tenant_id` も条件に含めることで同等の安全性を確保する
- この設計により、存在しないログインキーとテナント不一致のケースが同一の401レスポンスとなり、タイミング攻撃・情報漏洩対策としても既存の `/auth/login`（ユーザー不存在時401）と一貫性が取れる
- 認証成功時のレスポンス生成ロジックは、既存の `AuthService.login` 内のトークン生成・`AuthResponse` 組み立て部分をほぼそのまま再利用する（パスワード検証・パスワードリセット必須判定は行わない）

# 02_基本設計

## 変更対象

- LLMチャットAPI（新規）
- LLM埋め込みAPI（新規）
- テナント月次クレジット上限チェック（新規、両APIから共通利用）

## 画面 / API 変更概要

- `POST /api/llm/chat`: 会話履歴を受け取り、Azure OpenAI Chatモデルの応答をSSEでストリーミング返却する。完了後にトークン使用量を永続化する。
- `POST /api/llm/embedding`: 入力テキストを受け取り、Azure OpenAI Embeddingsモデルでベクトル化して返却する。呼び出し後にトークン使用量を永続化する。

いずれも認証必須（`X-Tenant-ID`ヘッダー＋JWT）。テナントに紐づく`TenantEndpoint`（Azure OpenAI Chat/Embedding種別）と`AIModel`（デプロイ名に対応するモデル定義）を解決して呼び出す。

## 影響範囲

- 新規追加のみで、既存のRoom/Message関連API・スキーマは変更しない
- テナント設定更新API（`PATCH /api/admin/tenants/{id}`）が既に持つクレジット上限チェックロジックと同種の判定を、チャット・埋め込み呼び出し前にも追加する（既存ロジックとは別実装だが、判定式は同一）
- `pyproject.toml`に新規依存（Azure OpenAI呼び出し用SDK）を追加する

## 移植方針

- 移植元Java版はチャット用（`openai-java`, Responses API）と埋め込み用（Spring AI経由の`azure-ai-openai`）で異なるSDK系統を使っているが、FastAPI側はPython公式`openai`SDKの`AsyncAzureOpenAI`クライアント1本に統一する（Azure Chat Completions API・Embeddings APIの両方をカバーできるため、SDKを分ける必要がない）
- SSEストリーミングは、移植元の`SseEmitter`+専用スレッドではなく、FastAPI/Pythonのイディオムである`StreamingResponse`＋非同期ジェネレータで実装する
- クレジット上限チェック・トークン使用量永続化・AIModel/TenantEndpoint解決は、移植元の「チャット送信前にDBを検証してコンテキストを構築する」設計を踏襲するが、Spring版の「読み取り専用トランザクション→非同期タスクでストリーミング」という2段階構成は、FastAPIの非同期モデルでは不要なため素直な非同期関数として実装する
- ストリーミング応答を返す`StreamingResponse`のボディ（非同期ジェネレータ）は、エンドポイント関数に注入されたDBセッションのライフサイクルとは独立して動作する必要があるため、ストリーミング中のDB操作（完了後のトークン使用量永続化）は新たに取得したセッションで行う
- 本Issueのスコープ外（tools/添付ファイル/ライブラリ生成/response_format）に対応するフィールドは、リクエストスキーマに含めない

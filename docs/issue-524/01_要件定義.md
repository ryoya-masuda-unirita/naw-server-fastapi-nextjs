# 01_要件定義

## 背景

- 画面（#522）は、開発サーバーで別に動かす必要がある。`onprem/` の compose は、社内側の環境を 1 つで立ち上げる検証用で、画面もそこで立ち上がれば、組んだワークフローを server-local から呼ぶところまで、compose だけで通せる

## 機能要件

- compose に、画面のサービスを足す。`docker compose up` で、エミュレーターと一緒に立ち上がる
- ブラウザから、ホストの `127.0.0.1` の決まったポートで画面を開ける（外には公開しない）
- 画面から、エミュレーターの管理用 API へ、compose のネットワーク経由でつながる。エミュレーターの管理用 API・servicerun を、ホストに新しく公開しない（今ある `127.0.0.1` の公開のまま）
- 画面が中継するのは、管理用 API（`/admin`）だけ。servicerun（server-local が呼ぶ経路）は中継しない
- エミュレーターは、compose で保存先（`WAHA_STUDIO_DIR`）を設定し、保存したワークフローをボリュームに残す。コンテナを作り直しても、保存したワークフローが残る
- 画面が使えるようになってから、起動完了（healthy）になる。エミュレーターが healthy になってから、画面を起動する
- `onprem/` と `waha-emulator/` の README に、開き方と、サービス ID を server-local から呼ぶ流れを書く

## 非機能要件

- 検証用の道具のため、認証・HTTPS は持たない。ホストの `127.0.0.1` だけに公開することで、外から使えないようにする
- 画面は、ビルドした静的ファイルを配信する（開発サーバーを本番のコンテナで動かさない）
- 既存のサービス（server-local・エミュレーター・vector-db）の動作・ポートを変えない
- 画面のイメージのビルドに、リポジトリ全体を送らない（画面のディレクトリだけ）

## スコープ外

- 本番向けの配信、認証、HTTPS
- ルートの compose（クラウド側）

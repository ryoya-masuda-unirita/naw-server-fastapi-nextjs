# 04_テスト設計

## テスト方針

- パスワード再設定 API にログインIDを `username` キーで送った場合に、業務処理（成功・認証エラー）まで到達することを結合テストで確認する
- 既存の `loginId` キーでの成功ケース（既存テスト）が引き続き通ることを確認する
- リクエストスキーマ単体で、キー名の受け付けルールを確認する
- 既存テスト全体の回帰がないことを確認する

| No | 観点 | 条件 | 期待結果 |
|---|---|---|---|
| 1 | 別名での成功 | `username` + 正しい旧パスワード + ポリシーを満たす新パスワード | 200、`loginStatus=SUCCESS`、トークンあり |
| 2 | 別名での業務エラー到達 | `username` + 誤った旧パスワード | 403（422 ではない） |
| 3 | 正式名での成功（既存） | `loginId` + 正しい旧パスワード | 200 |
| 4 | ログインID未指定 | `loginId` / `username` どちらもなし | 422 |
| 5 | スキーマ: 正式名 | `loginId` を指定 | ログインIDとして取り込まれる |
| 6 | スキーマ: 別名 | `username` を指定 | ログインIDとして取り込まれる |
| 7 | スキーマ: 両方指定 | `loginId` と `username` を異なる値で指定 | `loginId` の値が優先される |
| 8 | スキーマ: 未指定 | どちらもなし | 入力エラー |
| 9 | 回帰 | backend テスト全体 | 全件成功 |

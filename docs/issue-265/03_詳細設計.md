## `password_mismatch_store.py`

### 記録の保持（変更）

- Redis のキー `password_mismatch:{tenant_id}:{user_id}` の Sorted Set（メンバー: 失敗ごとの一意な ID、スコア: 失敗時刻の UNIX 秒）は変えない
- `record_failure_and_check_lockout`（パスワード再設定用）から `ZREMRANGEBYSCORE`・`EXPIRE` を削除する。ログインの判定は通算件数を使うため、期間外の記録を捨てると数え方が移植元と変わる
- 代わりに、記録のたびに `ZREMRANGEBYRANK key 0 -(N+1)` で新しい方から N 件だけ残す。N は `max(LOGIN_FAILURE_THRESHOLD, パスワード再設定の上限回数)`。ログインの判定は「通算件数が 6 以上か」と「2 番目に新しい失敗」、パスワード再設定の判定は「15 分以内の件数が上限以上か」しか見ないため、N 件あれば判定は変わらない（code-review の指摘 4）
  - パスワード再設定の判定は `ZCOUNT`（15 分以内の件数）のままなので、結果は変わらない
- 記録は `clear_failures`（ログイン成功・パスワード再設定成功）でだけ消える。移植元の `password_mismatch_histories` も成功時の `deleteAllByUserIdAndTenantId` でしか消えない

### 追加する定数

```python
# 移植元`LoginAttemptService.FAILURE_THRESHOLD`・`RATE_LIMIT_MINUTES`
LOGIN_FAILURE_THRESHOLD = 6
LOGIN_RATE_LIMIT_MINUTES = 15
```

### 追加する関数

```python
async def is_login_locked_out(user_id, tenant_id, redis_client) -> bool
async def record_login_failure_and_check_lockout(user_id, tenant_id, redis_client) -> bool
```

- どちらも 1 つのトランザクション（`MULTI`）で `ZCARD`（通算件数）と `ZREVRANGE key 1 1 WITHSCORES`（2 番目に新しい失敗の時刻）を取る。記録する方は先頭に `ZADD` を加える
- 判定は内部関数 `_is_login_locked(count, previous_failure_at, now)` にまとめる
  - `count >= LOGIN_FAILURE_THRESHOLD` かつ 2 番目に新しい失敗があり、その時刻 `> now - LOGIN_RATE_LIMIT_MINUTES * 60` なら `True`
  - 移植元の `recent.size() >= 2` は、件数 6 以上なら常に満たすが、`ZREVRANGE` の結果が空のときに備えて同じ確認をする

## `auth_service.py`

### 定数

```python
# 移植元`AuthService`が`AccessDeniedException`に渡す文言（`APIControllerAdvice`で403）
LOGIN_FAILED_MESSAGE = "Authentication failed"
# 移植元`TooManyLoginAttemptsException`の文言（`APIControllerAdvice`で429）
LOGIN_LOCKED_MESSAGE = "Too many failed login attempts"
```

### `AuthService.login(username, password, tenant_id, session, redis_client)`

1. `UserRepository.find_by_login_id` でユーザーを探す。いなければ 403 `LOGIN_FAILED_MESSAGE`（記録しない）
2. `is_login_locked_out` が真なら 429 `LOGIN_LOCKED_MESSAGE`
3. 最新のパスワード履歴がない、またはパスワードが一致しない場合、`record_login_failure_and_check_lockout` で記録し、真なら 429、偽なら 403 `LOGIN_FAILED_MESSAGE`
4. 成功したら `clear_failures` で記録を消してから、既存のパスワード再設定判定・トークン発行に進む

- 移植元は存在しないユーザーでもロック判定（`isLockedOut`）を呼ぶが、ユーザーがいなければ偽を返すだけなので、先にユーザーの有無で 403 にしても応答は同じになる
- 3 の記録と例外の送出は内部関数 `_fail_login(user_id, tenant_id, redis_client) -> NoReturn` にまとめる。403・429 の例外は `_login_failed_error()`・`_login_locked_error()` で作る

## `routers/auth.py`

- `login` は既に `redis_client` を受け取っている（セッション作成用）。これを `AuthService.login` にも渡す

## 移植元との対応

| 移植元 | 移植先 |
|---|---|
| `LoginAttemptService.isLockedOut` | `password_mismatch_store.is_login_locked_out` |
| `LoginAttemptService.handleFailure` | `password_mismatch_store.record_login_failure_and_check_lockout` |
| `LoginAttemptService.handleSuccess` | `password_mismatch_store.clear_failures`（既存） |
| `LoginAttemptService.assertTenantMatch` | 不要（テナントとログイン ID の組で検索するため） |
| `TooManyLoginAttemptsException` + `APIControllerAdvice` | `HTTPException(429)` + 既存のエラー応答ハンドラ |
| `AccessDeniedException("Authentication failed")` | `HTTPException(403)` |

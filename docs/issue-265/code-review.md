## 詳細

### 1. 同時リクエストでロック判定をすり抜ける（🟡 注意）→ 対応しない

移植元 `AuthService.login` も、`isLockedOut`（読み取り専用トランザクション）→ 認証 → `handleFailure` の順で、同じようにすり抜けられる。Issue の方針は数え方を移植元に揃えることなので、そのとおりにした。照合の前に試行を記録する方式に変えると、成功時の扱いなど移植元の数え方が変わるので、ここでは変えない。必要なら別の Issue で、移植元とあわせて検討する。

### 2. 429 と 403 の違いでログインIDの有無が分かる（🟡 注意）→ 対応しない

移植元 `LoginAttemptService.handleFailure` も、存在しないユーザーは記録せずに `false`（403）を返すので、同じ違いがある。Issue の指示は「移植元の応答に揃える」なので、そのとおりにした。1 回ごとの応答（ステータス・文言）は、存在しないユーザーとパスワード誤りで同じになっている。この点は `01_要件定義.md` にも書いた。応答時間の差（存在しないユーザーはパスワードを照合しない）は以前からある挙動で、今回の範囲外として `01` に書いた。

### 3. 失敗を送り続けるとロックされ続ける（🟡 注意）→ 対応しない

移植元も、成功するまで記録を消さず、ロック中は成功もできないので、同じ性質がある。回数でロックする仕組みにはどれもある性質で、移植元に揃えた。

### 4. 記録が上限なく増える（🟡 注意）→ 対応済み

記録のたびに `ZREMRANGEBYRANK key 0 -(N+1)` を実行し、新しい方から N 件（`max(ログインの上限 6, パスワード再設定の上限)`）だけ残すようにした。ログインの判定に使うのは「通算件数が 6 以上か」と「2 番目に新しい失敗」、パスワード再設定の判定に使うのは「15 分以内の件数が上限以上か」だけなので、N 件残っていれば判定は変わらない。`test_caps_retained_failures_without_changing_lockout` で、残る件数が N であることと、ロックの判定が変わらないことを確かめた。有効期限は付けていない。付けると、時間がたつと通算件数が消えて、移植元と数え方が変わるため。削除済みユーザーのキーが残ることはあるが、1 キーあたり N 件までに収まる。

### 5. アプリの時計のずれ（🔵 提案）→ 対応しない

移植元も、失敗時刻と判定の基準時刻にアプリ側（JVM）の時刻を使っている。今の構成（ECS の小さなタスク）ではずれの影響は小さいので、Redis の `TIME` や Lua スクリプトで時刻を揃える変更は入れない。

### 6. フロントのモックが 401 のまま（🔵 提案）→ 対応しない

この Issue の範囲は backend だけ。React のログイン画面は 401 と 403 を同じ文言で表示するので、画面の動きは変わらない。モックを 403 / 429 に揃える変更は、フロントエンドの Issue で扱うのがよい。

### 7. `raise await` の形（🔵 提案）→ 対応済み

`_record_login_failure` を `_fail_login`（戻り値の型は `NoReturn`）に名前を変え、関数の中で 403 / 429 を送出するようにした。呼び出し側は `await _fail_login(...)` になり、`raise` を書き忘れる余地がなくなった。`reset_password` の例外の組み立て方は #248 のコードで、この Issue の範囲外なので変えていない。

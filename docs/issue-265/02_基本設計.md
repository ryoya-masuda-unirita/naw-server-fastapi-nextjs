# 02_基本設計

## 変更対象

| 層 | 変更内容 |
|---|---|
| 失敗記録（Redis） | ログイン用のロック判定（通算件数と 2 番目に新しい失敗の時刻）を追加する。記録を期間で捨てる処理と有効期限をやめ、成功するまで残す |
| 認証サービス（ログイン） | 認証前のロック判定・失敗の記録・成功時の記録削除を追加し、認証失敗の応答を 403 に揃える |
| ログイン API | 失敗記録を保存する Redis クライアントを認証サービスに渡す |
| テスト | 失敗記録の単体テスト、認証サービスの単体テスト、ログイン API の結合テストを追加・更新する |

## 画面 / API 変更概要

`POST /auth/login`

| 条件 | 変更前 | 変更後 |
|---|---|---|
| ユーザーが存在しない | 401 `Invalid credentials` | 403 `Authentication failed`（記録しない） |
| パスワード誤り・パスワード履歴なし | 401 `Invalid credentials` | 失敗を記録し、ロックに達したら 429 `Too many failed login attempts`、達しなければ 403 `Authentication failed` |
| ロック中 | （ロックなし） | 認証せず 429 `Too many failed login attempts` |
| 成功 | 200 | 200（失敗記録を削除する） |

`POST /auth/password/reset` は応答を変えない。記録をログインと共有するため、ログインの失敗もロックの判定に数える点と、記録を期間で捨てなくなる点だけが変わる（判定は 15 分以内の件数で行うため結果は変わらない）。

## 影響範囲

- React のログイン画面は 401・403 を同じ「ログイン失敗」の文言、429 を「ロック」の文言で表示しているため、変更不要
- `POST /auth/login-key` は変更しない

## 移植方針

- 移植元はロック判定を `LoginAttemptService`（サービス）に置き、`AuthService` から呼ぶ。backend は「サービスが別のサービスを呼ばない」規約のため、判定は #248 の失敗記録モジュール（共通処理）に置き、認証サービスから呼ぶ
- 回数・期間は移植元と同じく設定にせず定数にする
- 移植元のテナント不一致チェック（`assertTenantMatch`）は、backend がテナントIDとログインIDの組でユーザーを探すため不要（別テナントのユーザーは「存在しない」になる）

# 02_基本設計

## 変更対象

1. **ログの出力（4 か所）**: 上の A〜D のログを、本文を出さない形に変える。出す内容は、要件のとおり（件数・長さ・ツール名・トークンの有無などの、中身を含まない情報）
2. **認証キーのフィルタ**: ヘルスチェックの除外の判定を、完全一致（`/api/hello`）、または `/api/hello/` で始まる、に変える
3. **テスト**: ログに本文が出ないことを確かめるテストと、除外パスの判定のテストを足す

## 画面 / API 変更概要

- API の入出力は変えない
- ログの内容が変わる（本文が消え、件数などに置き換わる）
- 認証: `/api/hello`・`/api/hello/…` 以外で、`/api/hello` で始まるパス（例: `/api/helloX`）は、認証キーが必要になる（現在、そのようなルートはなく、挙動の変化は、将来のルートの安全性のみ）

## 影響範囲

- **ログを見る人**: 本文が見えなくなる（意図した変更）。調査では、件数・長さ・ID・ツール名・トークンの有無が残る。本文が必要な場合は、データベース（メッセージ内容）を、権限のある人が確認する
- **運用の検索・監視**: ログの項目名（例: `Preparing histories.json: wahaSessionId=…, filename=…`）は、本文（`content=…`）の項目を、件数（`count=…`）などに置き換える。`content=` で検索している運用があれば、影響を受ける（有無は、確認できていない）
- **移植元との差**: 移植元は、A・B だけを直した。**この変更は、C・D も直す**（移植元の NAW-1438 の範囲外）。移植元と同じ範囲では、会話の本文（質問・履歴）が、リクエストの受信のログに残り、Issue の目的を満たせないため。移植元が直していないものを、先に直すので、移植元との挙動の差になる（ログの差だけで、機能には影響しない）
- **認証**: 除外パスの判定の厳格化。`/api/hello`（ヘルスチェック）は、これまでどおり、認証なしで通る
- **費用・インフラ**: なし。`secuaigent-server-local/` のコードのみ。この PR のマージで、`Deploy` の `backend`・`frontend` は動かない（`server/`・`client/` に触れない）

## 移植方針

- 移植元（65b8778f1・e31491ed4）の A・B・除外パスの変更に揃える
  - A: 件数（`count=`）。移植元と同じ項目名
  - B: ストリームファイルのパス、ライブラリ作成の有無、ツール名、メッセージ ID、トークンの有無（`hasAccessToken`）。移植元と同じ
  - 除外パス: 「完全一致、または、`/` を足した前方一致」。移植元の `isSameOrUnder`
- 移植元から**拡張する**もの（理由つき）
  - C: リクエスト全体を出す代わりに、本文を含まない項目だけを出す。移植元は、アクセストークンの除外だけで、質問・履歴を出し続けている
  - D: 出力ファイルの本文を、長さだけにする。移植元は、500 文字までを出している
  - 拡張した理由は、Issue の目的（会話の本文を、INFO ログに出さない）を満たすため。拡張が不要と判断する場合は、C・D を外し、移植元と同じ範囲（A・B・除外パス）にできる
- 移植元の、DEBUG に下げる案は、採らない（有効にすれば、同じ漏えいが起きるため）

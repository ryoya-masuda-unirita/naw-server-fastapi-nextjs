## 詳細

### 1. 報告された症状の根本原因が特定されていない（🟡 注意）→ 一部対応

指摘のとおり、修正前のコードでも、表示名が互いに異なるユーザーだけなら表示名順の昇順・降順で先頭行は入れ替わる。今回の修正で直るのは次の点。

- ソートキーが同値の行（同名ユーザー、同時刻の追加日時、権限）の並びが DB 任せになり、昇降を切り替えても反転しない
- 表示名順が大文字小文字を区別していた（移植元と違う）
- 方向の大文字小文字を区別していた（移植元と違う）

報告の症状（先頭行が変わらない）は、同値キーのまま方向だけを切り替えたときに起きる。例えば、並べ替え項目の選択が効かずに初期値の追加日時順（シード投入で同時刻）のまま昇降を切り替えた場合。ただし、共有のローカル DB は使えないため、報告環境のデータでの直接再現・確認はしていない。

`frontend-angular/` は上流 `secuaigent/client` のコピーで、本 PR では変更しない方針のため `test.skip` は外していない。`08_動作確認.md` と PR 本文に未確認事項として明記した。マージ後に `test.skip` を外して E2E で確認し、症状が残っていれば Issue を再オープンしてほしい旨を Issue #181 にコメントした。

### 2. 他の一覧 API にも同じ問題が残る（🟡 注意）→ 対応しない

ユーザー管理一覧は #172（PR #206、マージ済み）で同じ対策をした。本 PR のブランチは #206 マージ前の origin/develop から切ったため、差分上は未対応に見える。その他の一覧（チーム一覧・アシスタント・ファイル・インデックス等）は本 Issue のスコープ外。

### 3. sort 解析の共通化（🔵 提案）→ 対応しない

Issue ごとに develop から別ブランチを切る運用のため、#172・#181 の時点では共通ヘルパーを共有できなかった。両方がマージされた後で、別 Issue として横断的に共通化するのが妥当。

### 4. 列名の表記ゆれ（🔵 提案）→ 対応しない

フロントエンドは固定値（`updatedAt` / `name` / `role`）しか送らない。移植元（Spring Data）もプロパティ名を正規化しない。

### 5・6. 利用クレジット順の第 2 キー（🔵 提案）→ 対応しない

移植元 `UserBillingUsageService.orderByTotalCreditsForGroupUser` は、方向に関係なく `cb.asc(root.get("user").get("name"))`（大文字小文字を区別）を第 2 キーにしている。移植元の API 仕様に合わせるため変えない。この例外は `01_要件定義.md` に明記している。

### 7. インデックスが使えない（🔵 提案）→ 対応しない

移植元も ignoreCase 指定で `lower(user.name)` を使っており、同じ条件。チーム所属ユーザー数は管理画面のページング範囲に収まる規模を想定しており、マイグレーションを避ける方針から式インデックスは追加しない。

### 8. ステータスコードの確認（🔵 提案）→ 対応済み

`test_sort_by_role_reverses_rows` で、`content` を読む前に昇順・降順の両方で `status_code == 200` を確認するようにした。

### 9. 未知のソートキーの扱い（🔵 提案）→ 対応しない

移植元は未知キーを無視し、並びが不定になる。こちらは従来どおり表示名順にして並びを決定的にしている。フロントエンドは既知のキーしか送らないため、実害のない意図的な差分として `02_基本設計.md` に記載している。

# 02_基本設計

## 変更対象

- バックエンドのチーム管理サービス（所属ユーザー一覧のソート方向の解釈）
- バックエンドのチーム所属ユーザーのリポジトリ（所属ユーザー一覧の並び順組み立て）
- 対応する自動テスト

## 画面 / API 変更概要

- 対象 API: チーム所属ユーザー一覧取得（管理者向け）
- リクエスト・レスポンスの形式は変更しない
- 並び順の変更点
  - ユーザー表示名順は表示名を小文字にしてから並べる（移植元と同じ）
  - すべての並べ替えで、最後のキーとしてユーザー ID を主キーと同じ方向で加える。同値の行も含めて並びが決まり、降順は昇順の完全な逆順になる
  - ソート方向は大文字小文字を区別せずに `desc` を降順、それ以外を昇順と解釈する

## 影響範囲

- チーム詳細の所属ユーザー一覧画面の並び順
- ユーザー管理一覧など他の一覧には影響しない

## 移植方針

- 移植元は API のソートキーを `role` → チーム管理者フラグ、`name` → ユーザー表示名（大文字小文字を区別しない）、`updatedAt` → 所属レコードの更新日時に読み替える。利用クレジット順は請求期間内のクレジット合計＋表示名昇順で並べる。これに合わせる
- 移植元は同値の行の並びを決めていない（DB 任せ）。こちらで最終キーを加えても、移植元で起こりうる並びの一つに確定させるだけなので、移植元の API 仕様からは外れない
- 移植元は未知のソートキーを無視する（並び順を指定しない）が、こちらは従来どおり表示名順にする。並びが不定になるのを避けるためで、フロントエンドは既知のキーしか送らない

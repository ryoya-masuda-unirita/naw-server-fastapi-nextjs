# 01_要件定義

## 背景

クラウドの RAG は、質問を埋め込み、ベクトル DB から近い文書を探す。ベクトル DB の接続先は、テナントのエンドポイント（種別 `VDB`）で、今は Azure AI Search（`https://...` と API キー）を前提としている。Azure AI Search がない環境（ローカル）では、RAG の検索の段階で止まる。

## 機能要件

| No | 要件 |
|---|---|
| F1 | 種別 `VDB` の接続先が、PostgreSQL（`postgresql://ユーザー@ホスト:ポート/DB名`、API キー欄はパスワード）なら pgvector、`https://` なら従来どおり Azure AI Search として扱う |
| F2 | pgvector で、質問のベクトルに近い文書（上位 `DEFAULT_TOP_K` 件）を、内容と、元のファイルの ID つきで検索できる。表がないテナントは、0 件として扱う（Azure の「インデックスなし」と同じ） |
| F3 | pgvector で、ベクトルの保存（同じ id なら更新）と、ファイル単位の削除ができる。表がなければ作る（拡張・表・索引）。#462 が使う |
| F4 | 表の形は、オンプレ側アダプタ（`embedding-adapter`）と同じ `(id uuid, fileid, filepath, content, embedding vector(1536))` にする |
| F5 | テナントごとに、別の表を使う（テナント ID から、衝突しない安全な表名を作る）。他のテナントの文書が検索に出ない |
| F6 | クラウドの RAG（メッセージ送信）が、接続先の種別に応じて、pgvector か Azure AI Search で検索する |
| F7 | 接続・検索の失敗は、Azure と同じ形（400、`Failed to connect to vector database`）で返し、パスワードなどをログ・応答に出さない |
| F8 | ローカルの docker compose（ルート）に、pgvector のコンテナを足す |

## 非機能要件

- Azure AI Search の挙動と、既存のテストの結果が変わらない
- pgvector の部品は、専用のファイルと、目印（`pgvector-ext`）つきの少数の行に収める
- SQL に入れる値は、すべてパラメータにする。表名は、検証済みの識別子だけを使う（SQL 注入の防止）
- 追加する関数に、日本語の NumPy 形式の docstring を書く。テストのメソッド名は英語、意図は日本語の docstring

## スコープ外

- 学習データ登録で、分割・埋め込み・保存を呼ぶ処理（#462）
- 画面（`client/`）での、VDB 接続先の登録（接続先の編集は、移植元の仕様でも画面からできない）
- Graph・全文検索（PGroonga）など、オンプレ側アダプタの高度な検索

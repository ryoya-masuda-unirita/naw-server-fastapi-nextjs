# 02_基本設計

## 変更対象

- ベクトルの保存・検索・削除のクライアント（pgvector 用を新規に追加）
- クラウドの RAG（メッセージ送信）の検索の呼び出し（接続先の種別で、使うクライアントを切り替える）
- ローカルの docker compose（ルート）

## 接続先の表し方（種別 `VDB` のまま、列は増やさない）

| 項目 | Azure AI Search | pgvector |
|---|---|---|
| `endpoint` | `https://xxx.search.windows.net` | `postgresql://ユーザー@ホスト:ポート/DB名` |
| `api_key` | API キー | パスワード |

- ベンダーは、`endpoint` の先頭（`postgresql://` か `https://`）で見分ける。DB に列を足さない（マイグレーション不要）

## 表

- テナントごとに 1 つ。名前は `docs_<テナント ID を英小文字・数字・_ にしたもの>_<テナント ID の短いハッシュ>`（63 文字以内）。ハッシュで、`a-b` と `a_b` のような衝突を避ける
- 列: `id uuid`（主キー）・`fileid text`・`filepath text`・`content text`・`embedding vector(1536)`（オンプレ側アダプタと同じ）。近い順の検索のため、`embedding` に索引（HNSW・コサイン距離）を作る

## 影響範囲

- Azure AI Search を使っている既存のテナント: 変わらない
- PostgreSQL の接続先を登録したテナント: クラウドの RAG の検索が、pgvector で動く（登録は #462 のあと）
- ローカルの compose に、コンテナが 1 つ増える

## 移植方針

- 移植元にない、Python 版だけの拡張。移植元の設計（接続先ごとに、ベクトルストアのクライアントを使い分ける）に沿う
- オンプレ側のアダプタ（`generative_ai_core.vector.pgvector`）の表の形と、検索の向き（`embedding <=> ベクトル`）に合わせる。コードの共有は、依存関係が増えるため、今回は表の形だけを合わせる

# 04_テスト設計

外部への通信（`asyncpg`）は、接続の代わりのモックで行う。実際の pgvector は、`08_動作確認.md` で、compose のコンテナで確かめる。

| No | 観点 | 条件 | 期待結果 |
|---|---|---|---|
| 1 | ベンダーの判定 | `postgresql://`・`postgres://`・`https://`・空 | 前 2 つだけ pgvector |
| 2 | 表名 | 通常・記号入り・大文字・長い・空のテナント ID | 英小文字・数字・`_` だけで 63 文字以内。記号違いの ID は別の表名 |
| 3 | 接続先の解析 | ユーザー・ホスト・ポート・DB 名・パスワード | 正しく分かれて、`asyncpg.connect` に渡る。ポート省略は 5432 |
| 4 | 検索 | 結果の行 | `VectorSearchResult(content, fileid)`。SQL が `<=>` の近い順・`LIMIT` で、ベクトルがパラメータ |
| 5 | 表がない | `UndefinedTableError` | 0 件 |
| 6 | 接続・SQL の失敗 | `OSError`・`PostgresError` | 400（`Failed to connect to vector database`）。パスワードが応答・ログに出ない |
| 7 | 保存 | 行を追加 | 拡張・表・索引を作ってから、`ON CONFLICT` の挿入。次元数が違う行は拒否 |
| 8 | 削除 | `fileid` を指定 | `DELETE ... WHERE fileid = $1`。行数を返す |
| 9 | RAG の切り替え | VDB の接続先が PostgreSQL / https | PostgreSQL なら pgvector、https なら Azure が呼ばれる |
| 10 | SQL 注入 | テナント ID に `"; DROP TABLE x; --` | 表名が安全な識別子になり、SQL が壊れない |
| 11 | 回帰 | 既存のテストをすべて実行する | Azure の検索・RAG の既存のテストの結果が変わらない |

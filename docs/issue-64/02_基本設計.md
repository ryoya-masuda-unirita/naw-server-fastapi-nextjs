# 02_基本設計

## 変更対象

- 新規テーブル `token_usages`（migration追加）
- 新規モデル `TokenUsage`（SQLModel）
- 新規リポジトリ・サービス・ルーター・スキーマ

## 画面 / API 変更概要

- `GET /api/admin/token-usages`: クエリパラメータ `from`, `to`（ISO-8601, 必須）, `userId`（任意）, `page`（デフォルト0）, `size`（デフォルト10）, `orderBy`（`createdAt`|`totalTokens`, デフォルト`createdAt`）, `reverse`（デフォルトtrue）を受け取り、`contents`/`totalCount`/`hasNext` を返す。
- `GET /api/admin/token-usages/summary`: クエリパラメータ `from`, `to`（必須）, `userId`（任意）を受け取り、トークン数・クレジット数の合計を返す。
- 両エンドポインとも管理者（テナント管理者 or グループ管理者）のみアクセス可能。

## 影響範囲

- 既存の`users`テーブルへの参照（`userId`指定時の存在確認）のみで、既存機能への影響はない。新規テーブル追加のため既存データへの影響もなし。

## 移植方針

- レスポンスのフィールド名・構造（`contents`/`totalCount`/`hasNext`、トークン・クレジット関連フィールド名）は移植元Spring Boot版に厳密に合わせ、既存の`PagedUserResponse`等の共通ページングパターンは使わない（構造が異なるため専用クラスとする）。
- 期間・順序バリデーション（ISO8601形式・from<=to・31日以内）は、プロジェクト方針（Pydantic v2 `@field_validator`）に従いスキーマ内に直接実装する。
- 権限チェックは移植元の`AdminAuthorizationFilter`（ADMIN/SYSTEMロール or グループ管理者）に対応する既存の`require_admin_or_group_admin`依存を使用する。
- `total_tokens`はDB生成列（`GENERATED ALWAYS AS ... STORED`）として移植元通り再現する。`total_credits`はDB列を持たず、アプリケーション側で`input_credits+output_credits+embedding_credits`を都度計算する（移植元と同様、永続化しない導出値）。
- RLSは導入せず、既存パターン同様アプリケーション側の`tenant_id`フィルタで分離する。

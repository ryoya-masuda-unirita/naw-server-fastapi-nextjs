# 01_要件定義

## 背景

管理者（テナント管理者・グループ管理者）がインデックス配下のファイルを一覧・アップロード・更新・削除・ダウンロードできるようにする。移植元Spring Bootの`FileController`/`FileService`を、FastAPIのアーキテクチャ規約（router:service 1対1、repositories集約、N+1回避）に沿って移植する。

## スコープ

### 含む

- ファイルメタデータのCRUD（一覧・作成・更新・削除）
- ファイル実体のストレージへの保存・ダウンロード・物理削除（抽象化レイヤー経由）
- アップロード・置換更新時の当月クレジット上限チェック（429）
- `Index.type == LOCAL`の場合の400エラー

### 含まない（スコープ外、要フォローアップ）

- **コンテンツ抽出（Tika）・分割（ContentSplitter）・ベクトルDB（Azure AI Search）への埋め込み登録**: Issue #88「LLMチャット・埋め込みAPIを移植」のスコープとする。本Issueではファイルのメタデータ管理とストレージ保存のみを行い、`file_parts`テーブル・埋め込み関連のトークン使用量記録は行わない。
- フィードバック学習（`additionalLearning`）・ファイル一括同期（`syncFiles`）: `FileController`に対応エンドポイントが存在しない内部メソッドのため対象外。
- Indexのグループ可視性チェック（`IndexService._ensure_visible`相当）: 移植元`FileService`にも実装されていないため、移植元の挙動をそのまま踏襲し追加しない。

## 移植方針上の判断（要確認事項への回答）

全自動モードのため、以下は判断して進める。

1. **`GET /{id}`の実体**: 移植元はJSON詳細取得ではなく`application/octet-stream`のバイナリダウンロードAPI（`Content-Disposition: attachment`）。Issue本文の「詳細取得」という記載より実装（ソースコード）を正としてダウンロードAPIとして移植する。
2. **ファイルストレージ抽象化**: 移植元はAzure Blob Storageに直接依存（抽象化なし）。バックエンドに既存の抽象化パターンは存在しないため、`app/core/file_storage.py`に`FileStorage`という抽象インターフェース（Protocol）を新設し、当面の実装はローカルファイルシステム（`LocalFileStorage`）とする。AWS S3への切り替えはインフラ（Terraformでのバケット作成含む）が未整備のため本Issueでは行わず、同インターフェースの背後で将来差し替え可能な設計にとどめる。
3. **クレジット上限チェック（429）**: 移植元`TenantMonthlyCreditQuotaService.enforceWithinQuota`に相当する処理が`backend/`にまだ存在しないため新設する。`credit_usage_service.py`が持つ請求期間解決ロジック（`_resolve_active_billing_period`・`_resolve_credit_limit`）と重複させないよう、共通ロジックを`app/core/credit_quota.py`に切り出し、`credit_usage_service.py`・`file_service.py`の双方から利用する（`xxx_service.py`が別の`yyy_service.py`を呼ぶことを避けるため）。
4. **Indexが存在しない場合の挙動**: 移植元はNPEになりうる潜在バグがあるため、FastAPI版では404を返すよう修正する。

## 受け入れ条件

- 5エンドポイントがそれぞれ移植元の入出力仕様（フィールド名・ステータスコード）を満たす
- アップロード・ファイル添付更新時、当月クレジット上限超過で429を返す
- `Index.type == LOCAL`のインデックスへの作成・削除は400を返す
- 一覧取得でN+1が発生しない（`updatedBy`解決を一括取得で行う）
- 既存のrouter:service 1対1規約・repositories集約規約に従う
- 自動テスト（pytest）で主要シナリオを検証する

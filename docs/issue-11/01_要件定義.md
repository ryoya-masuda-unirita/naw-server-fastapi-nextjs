# 01_要件定義

## 背景

Issue #9（ユーザー管理API CRUD・プロフィール実装）の `/code-review` で、テナント分離バイパス・パスワードポリシー未適用といった致命的指摘とあわせて、🟡注意・🔵提案レベルの指摘が複数挙がった。致命的指摘の修正を優先したため、🟡🔵レベルの指摘は「リファクタIssueへ」として対応を見送った。本Issueはその見送り分をまとめて解消する。

調査の結果、見送り項目のうち2件（認証APIのステータスコード差異、ユーザー削除の冪等設計）は、移植元の Spring Boot 実装と完全に一致した意図的な設計であることが判明した。これらはバグではないため実装変更は行わず、調査結果の記録のみを対応とする。

## 機能要件

### 1. ユーザー一覧検索のセキュリティ・正確性強化

- 検索文字列に含まれる LIKE 検索のワイルドカード文字を検索条件の特殊文字としてではなく、通常の検索対象文字として扱えるようにする
- ソート対象の列指定を許可リストに基づいて解決し、リクエストで任意の内部属性名を指定してソートできてしまう状態を解消する
- 許可リスト外の列名が指定された場合は、既定の並び順にフォールバックする（エラーにはしない。移植元の類似実装の挙動に倣う）

### 2. 認証関連の意図確認・記録（実装変更なし）

- ログインAPIとパスワードリセットAPIでエラー時のステータスコードが異なる点について、移植元の設計と一致した意図的な仕様であることを調査・記録する
- ユーザー削除APIが対象不在時にエラーを出さず冪等に成功扱いとする設計について、移植元の設計と一致した意図的な仕様であることを調査・記録する

### 3. テストの拡充

- パスワード履歴が1件も存在しない状態でのログイン失敗ケースを検証するテストを追加する
- パスワードリセット成功時にパスワード履歴が保存されることを検証するテストを追加する

### 4. コード品質改善

- レスポンス変換処理に型ヒントを付与する（CLAUDE.md規約準拠）
- ユーザー・テナントをIDで取得する処理が複数のサービスに分散重複している状態を解消し、リポジトリ層に集約する
- ユーザー作成・更新時のパスワード発行処理（パスワード生成・テナント取得・パスワード履歴保存）の重複を解消する
- パスワード照合処理がイベントループをブロックしうる点を解消し、非同期実行に変更する

### 5. APIコントラクトの明確化（実装変更なし）

- グループ除外パラメータについて、グループ機能が未実装のため現状「受理するが無視する」挙動であることを設計として明文化する

## 非機能要件

- 既存のAPIレスポンス形式・正常系のステータスコードを変更しない
- 既存の単体・結合テストが全て通ること
- 追加・変更するコードはCLAUDE.mdのコーディング規約（型ヒント・docstring・PEP8等）に準拠すること
- リファクタによってAPIのリクエスト・レスポンス契約を変更しないこと（ソート許可リスト外指定時のフォールバック挙動を除く）

## スコープ外

- グループ機能そのものの実装（グループ除外パラメータは「受理するが無視する」挙動を維持する）
- ユーザーレスポンスのID（内部識別子）とパス変数（ログインID）の不一致問題（issue-9のcode-reviewで移植元の意図的仕様と確認済みのため対応しない）
- 一覧取得時の件数取得クエリと本体取得クエリの並列実行化（非同期DBセッションの制約上、同一セッションでの並行クエリ実行ができないため対応しない）

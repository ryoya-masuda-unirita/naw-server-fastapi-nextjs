# 08_動作確認

## 実施日

2026-06-30

## 環境

- DB: ローカルDocker（`naw-fastapi-postgres`、PostgreSQL）、`alembic upgrade head` 実行済み
- サーバー: `uvicorn app.main:app --port 18123`（既存プロセスとのポート競合のため18123を使用）
- 検証用テナント: `verify-tenant`、検証用管理者: `verify-admin`（ADMINロール）

## Step 1: ログイン

```
POST /auth/login
X-Tenant-ID: verify-tenant
{"username":"verify-admin","password":"AdminPass1!"}
```

結果: `200`、`loginStatus: "SUCCESS"`、JWTトークン取得。

✅ ログインAPIが正常に動作することを確認

## Step 2: 検証用ユーザー作成（LIKEエスケープ検証の準備）

`name="ab%c"`（loginId: literal-user）と `name="abc"`（loginId: plain-user）の2件を作成。

結果: 両方とも `200`、`initialPassword` が返却された。

✅ ユーザー作成APIが正常に動作することを確認（`_issue_initial_password` 共通化後も挙動変わらず）

## Step 3: LIKEワイルドカードエスケープの確認

```
GET /api/admin/users?searchText=b%25c
```

結果:
```json
{
  "content": [
    {"loginId": "literal-user", "name": "ab%c", ...}
  ],
  "totalElements": 1
}
```

✅ `searchText="b%c"` で検索した結果、`%` がワイルドカードとして機能せずリテラル一致のみ返り（`ab%c` のみ、`abc` は除外）、エスケープが効いていることを実機確認

## Step 4: ソート許可リストの確認

```
GET /api/admin/users?sort=name,asc
```

結果: `["ab%c", "abc", "Verify Admin"]`（name昇順で正しくソートされた）

✅ フロントエンドが実際に送信するキャメルケースの `sort=name,asc` で正しくソートされることを確認

```
GET /api/admin/users?sort=login_key,asc
```

結果: `200`（エラーにならず3件返却。許可リスト外のため既定列＝作成日時へフォールバックして実行された）

✅ 許可リスト外のソート指定でもエラーにならず、フォールバックして正常応答することを確認

## Step 5: ユーザー更新・パスワードリセット

```
PATCH /api/admin/users/plain-user  {"name":"Plain User Updated"}
→ 200, name更新を確認

PATCH /api/admin/users/plain-user  {"resetPassword":true}
→ 200, initialPassword・passwordExpiredAtが返却された
```

✅ ユーザー更新・パスワードリセットの両方で `_issue_initial_password` 共通化後も従来どおり動作することを確認

## Step 6: プロフィール取得・更新

```
GET /api/users/profile → 200, 自分のプロフィールが取得できた
PATCH /api/users/profile {"password":"NewAdminPass1!"} → 200
```

✅ プロフィール取得・パスワード変更が正常に動作することを確認

## Step 7: パスワード変更の反映確認（非同期化したパスワード照合の検証）

```
POST /auth/login {"username":"verify-admin","password":"NewAdminPass1!"}
→ loginStatus: "SUCCESS"
```

✅ `verify_password_async` への変更後も、変更後の新パスワードで正しくログインできることを確認（非同期化によるロジック破壊がないことを実機確認）

## Step 8: ユーザー削除（冪等性確認）

```
DELETE /api/admin/users/literal-user → 204
DELETE /api/admin/users/literal-user（再実行）→ 204
```

✅ 削除・再削除（対象不在）ともに `204` が返り、冪等設計が維持されていることを確認

## Step 9: テナント分離

```
GET /api/admin/users  (X-Tenant-ID: other-tenant、JWTのtenant_idと不一致)
→ 403
```

✅ `UserRepository`/`TenantRepository` への置き換え後もテナント分離（`get_verified_tenant_id`）が機能していることを確認

## まとめ

全9ステップで期待どおりの結果を確認した。リファクタ後も既存6エンドポイントの挙動・ステータスコードに変化はなく、今回追加したLIKEエスケープ・ソート許可リストも意図どおり動作している。

# 02_基本設計

## 変更対象レイヤー

- `models`（`Assistant`・`GroupAssistant`の新規テーブル定義）
- `schemas`（アシスタント一覧レスポンススキーマ）
- `repositories`（`assistants`・`groups_assistants`テーブルへのDBアクセス）
- `services`（Group紐づけによるフィルタリングロジック）
- `routers`（`GET /api/assistants`エンドポイント）

## データモデル概要

### assistants テーブル

- `id`：UUID hex 32文字、主キー
- `tenant_id`：所属テナント
- `type`：`SECURE` / `SAAS_CHAT` / `SAAS_RAG`（Enum）
- `index_id`：RAG用インデックスID（nullable）
- `name`：アシスタント名
- `description`：説明（nullable）
- `include_history`：履歴を含めるかどうか（boolean）
- `icon_color`：アイコン色（nullable）
- `created_at`・`updated_at`

### groups_assistants テーブル（中間テーブル）

- `group_id` + `assistant_id` + `tenant_id` の複合主キー（`groups_users`と同様のパターン）
- `updated_at`

いずれも既存の`tenants`・`groups`テーブルと同様、テナントIDによる明示的な絞り込みを行う（実DBのRLSは使わず、既存コードと同じくクエリ側でtenant_idを条件に含める）。

## API変更概要

### `GET /api/assistants`

- 認証必須（`get_current_user`・`get_verified_tenant_id`）。ロール不問
- ログインユーザーが所属する全Groupを取得し、それらのGroupに紐づくAssistantを重複排除して返す
- レスポンスは配列（ページネーションなし）
- `endpoints`は常に空配列、`category`はnull、`categories`は空配列で返す

## レスポンス形式

`frontend-angular`のチャット機能側実装（`AssistantsService`・`parseAssistantsListResponse`）を確認した結果、レスポンスは生の配列で、`category`/`categories`/`endpoints`が欠損していても安全にフォールバックする実装であることを確認済み。よって以下の形式でよい。

```json
[
  {
    "id": "string",
    "tenantId": "string",
    "type": "SECURE",
    "endpoints": [],
    "name": "string",
    "indexId": null,
    "category": null,
    "categories": [],
    "description": "string",
    "includeHistory": false,
    "iconColor": null
  }
]
```

## 影響範囲

- 新規テーブル追加のためAlembicマイグレーションが必要
- 既存の認証・ユーザー管理・グループ管理コードへの変更はなし（新規ファイル追加のみ）
- `frontend-angular`のコード変更は不要（既存実装がそのまま繋がる想定）
- `frontend`（React）は対象外

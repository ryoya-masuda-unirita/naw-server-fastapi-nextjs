# アシスタント一覧取得API（GET /api/assistants）の実装

## 概要

NAW-XXXX（複数チケットにまたがる機能）の一部移植。issue-24（チーム管理API）で保留していたアシスタント一覧取得APIをFastAPIで実装する。

## 説明

### 背景

issue-20の動作確認で `GET /api/assistants` が404であることを確認していた。issue-24でチーム（Group）管理APIを実装したことで、Group紐づけによるアシスタント一覧のフィルタリングが可能になった。

移植元のAssistantドメインを調査した結果、以下の依存関係があることが判明した。

- `assistants`（本体）
- `groups_assistants`（Group⇔Assistant紐付け中間テーブル。Groupは実装済みのため中間テーブルのみ新規）
- `assistants_endpoints`・`tenant_endpoints`（AI接続先情報。APIキー等の機微情報を扱う別ドメイン）
- `assistant_categories`・`assistant_category_mappings`（カテゴリ機能）
- `ai_models`（管理者向けAIモデル選択肢取得専用。本APIには不要と判明）

このうち `assistants_endpoints`・`tenant_endpoints`・カテゴリ関連は独立した別ドメインであり、特に `tenant_endpoints` はAPIキー等の機微情報を扱うため、別チケットとして慎重に設計する。

### やること（今回のスコープ）

- `assistants` テーブル・モデルを新規作成する（`id`, `tenant_id`, `type`, `index_id`, `name`, `description`, `include_history`, `icon_color`, `created_at`, `updated_at`）
- `groups_assistants` 中間テーブル・モデルを新規作成する（`GroupUser`と同様のパターン：`group_id`・`assistant_id`・`tenant_id`複合PK）
- `GET /api/assistants`：ログインユーザーが所属するGroupに紐づくアシスタント一覧を返す（`~/Documents/naw-server`の`AssistantService.getAssistantsByUserIdAndTenant`相当のロジック）
  - レスポンスの`endpoints`配列は空配列、`category`/`categories`はnull/空で返す（値が空でも一覧APIとして成立することを移植元コードで確認済み）

### スコープ外（後続チケット）

- `assistants_endpoints`・`tenant_endpoints`（AI接続先・APIキー管理。別チケットで設計する）
- `assistant_categories`・`assistant_category_mappings`（カテゴリ機能）
- `ai_models`（管理者向けAIモデル一覧取得）
- 管理者向けアシスタントCRUD（作成・更新・削除、エンドポイント/AIModel参照、カテゴリ管理）

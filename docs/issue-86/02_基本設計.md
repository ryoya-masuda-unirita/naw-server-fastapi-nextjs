# 02_基本設計

## 変更対象

- ルーター層: テナント管理API（`/api/admin/tenants`配下）にリソースコスト取得エンドポイントを追加
- サービス層: テナントサービスにコスト取得ロジックを追加
- インフラ層: Azure Cost Management APIを呼び出すクライアントを新規追加
- リポジトリ層: テナントリソースの取得に、リソースIDとテナントIDの組み合わせで1件取得するメソッドを追加
- スキーマ: コスト取得レスポンスのスキーマを追加
- 設定: Azure連携用の環境変数設定を追加
- 依存パッケージ: Azure Cost Management SDK・Azure認証SDKを追加

## 画面 / API 変更概要

- `GET /api/admin/tenants/resources/{resourceId}/cost`
  - パスパラメータ: `resourceId`（リソースID）
  - クエリパラメータ: `from`（任意、ISO8601日時文字列）、`to`（任意、ISO8601日時文字列）
  - 認証: 管理者ロール必須
  - レスポンス: リソースタイプ・日付ごとのコスト一覧（配列）
  - エラー: リソースが認証テナントに属さない場合、または`from`/`to`がISO8601形式でない場合は400

## 影響範囲

- 既存のテナント管理API（`/api/admin/tenants`, `/api/admin/tenants/{tenant_id}`）には影響しない
- テナントリソースリポジトリに新規メソッドを追加するのみで、既存メソッドの挙動は変更しない
- 新規に外部SDK依存（Azure Cost Management, Azure Identity）が増える

## 移植方針

- 移植元のControllerメソッド（`getTenantResourceCost`）・Serviceメソッド（`TenantService.queryCost`）・Azure連携クラス（`AzureCostManageService`）の3層構造を踏襲する
- ただし、このリポジトリのアーキテクチャ規約「serviceが別serviceを呼ばない」に抵触しないよう、Azure SDK呼び出しを行うクラスは`services/`ではなく`core/`（インフラ層）に配置する（`AzureCostClient`）。移植元の役割分担自体は維持しつつ、配置レイヤーのみこのリポジトリの規約に合わせる
- ルーターへの追加先は、Issue本文が言及する`tenant_endpoints.py`ではなく`tenants.py`とする。このエンドポイントはパスにtenant_idを含まず（`X-Tenant-ID`相当は認証済みユーザーのテナントIDを用いる）、既存の`tenants.py`（router:service 1対1で`tenant_service.py`と対応）にある他のテナントAPIと同じ性質を持つため
- 移植元は`tenant.getResources()`の線形検索でテナント⇔リソースの紐付けを検証しているが、FastAPI側はN+1回避規約・1クエリ原則に従い、`TenantResourceRepository.find_by_id_and_tenant_id`で1クエリの絞り込みに置き換える
- 移植元は`from`/`to`のパース失敗時に例外ハンドラが存在せず500相当になるが、FastAPI側は入力エラーとして400を返すよう改善する（移植先の一般的なバリデーションエラーの扱いに合わせる）
- 移植元のAzure SDK呼び出し（`com.azure.resourcemanager.costmanagement`）は、Python版SDK（`azure-mgmt-costmanagement`, `azure-identity`）に対応させて移植する。認証方式（サービスプリンシパル、`ClientSecretCredential`）・リクエスト構造（`QueryFilter`/`QueryDataset`/`QueryDefinition`）・レスポンスの行マッピングロジックは移植元と同一の考え方を踏襲する

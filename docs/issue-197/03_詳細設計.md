## `deploy-backend.yml` のステップ追加詳細

既存フロー: `Build Docker image` → `Render new task definition` → `Register new task definition` → `Update ECS service` → `Wait for service stabilize`

このうち `Build Docker image` の直後・`Render new task definition` の直前に、以下を追加する。

1. **Render migration task definition**: `aws ecs describe-task-definition --task-definition <backend_migrate family>` を取得し、`jq` で `containerDefinitions[0].image` を今回pushしたイメージタグに差し替える（既存の `backend` 用ステップと同じパターン）
2. **Register migration task definition**: `aws ecs register-task-definition` で新リビジョンを登録し、ARNを保存する
3. **Run DB migration task**: `aws ecs run-task --cluster <cluster> --task-definition <上記ARN> --capacity-provider-strategy capacityProvider=<既存CP>,weight=1 --count 1` を実行し、タスクARNを保存する
4. **Wait for migration task to stop**: `aws ecs wait tasks-stopped --cluster <cluster> --tasks <タスクARN>` で完了を待つ
5. **Check migration exit code**: `aws ecs describe-tasks --cluster <cluster> --tasks <タスクARN>` の結果からコンテナの `exitCode` を `jq` で取得し、`0` 以外ならこのジョブを失敗させる（`exit 1`）。これにより、マイグレーションが失敗した場合は後続の `backend` サービス更新（新しいアプリコードの反映）が実行されない

## `seed_via_bastion.sh` の設計

- 引数・環境変数で受け取るもの: SSH秘密鍵のパス、DBパスワード（`terraform output` には含まれない秘匿情報のため、呼び出し側から明示的に渡す）
- `terraform output -raw bastion_public_ip` / `terraform output -raw rds_endpoint` を `infra/` ディレクトリ内で実行し、接続先を自動取得する（手動でのIPコピペを廃止）
- 処理順序: SSHトンネルをバックグラウンドで確立 → 接続確立をポーリングで待つ → `alembic upgrade head`（オプションでスキップ可能） → `psql` で `seed.sql` 投入 → 終了時（正常・異常問わず）に必ずSSHトンネルを閉じる（`trap` で担保）
- seedの非冪等性を隠蔽しない: `psql` のエラーはそのまま標準エラーに出力し、スクリプト側で握りつぶさない

# 03_詳細設計

## 方針

- 新しい部品は、`waha-emulator/waha_emulator/studio/` に集める（グラフの定義・保存・管理・実行）
- 管理用の API は `waha-emulator/waha_emulator/routers/admin.py`
- 既存の `workflow_config.py`（プロパティの検証と環境変数の展開）と `workflows/generative_ai.py`（アダプターを動かす処理）は、そのまま使う
- 保存先の環境変数 `WAHA_STUDIO_DIR` が**未設定のときは、管理用 API を載せず、今の動作と変わらない**（既存のテストと onprem を壊さない）

## 変更するファイル

| ファイル | 変更 |
|---|---|
| `waha_emulator/config.py` | `studio_dir`（`WAHA_STUDIO_DIR`）を足す |
| `waha_emulator/workflows/registry.py` | 動的に登録・解除できるワークフロー置き場を足す。`resolve` は、動的 → 既存の順にする |
| `waha_emulator/main.py` | `studio_dir` があるとき、保存場所の読み込みと管理用 API の組み込みをする |
| `waha-emulator/README.md`、`.env.example` | 使い方を書く |

## 新規ファイル

### `studio/graph.py`

- `GraphError`（`ValueError`）: 定義が不正（メッセージに、どのノード・項目かを含める）
- `GraphNode`（id・type・name・position・properties・output_type）、`GraphEdge`（source・target）、`GraphDefinition`（id・name・service_ids・nodes・edges）。いずれも frozen の dataclass
- `parse_graph(data, environ) -> GraphDefinition`: JSON の値を検証して定義にする
- `compile_graph(graph, environ) -> WorkflowDefinition`: 検証済みのグラフから、今のワークフローの定義を作る

検証の規則（最初の PR）:

| 規則 | エラー |
|---|---|
| 版（`version`）は 1 | 未対応の版 |
| `id` は英小文字・数字・`-`・`_` の 1〜64 文字 | id が不正 |
| `name` は 1〜100 文字 | name が不正 |
| `serviceIds` は 1 つ以上、重複なし、各 1〜200 文字 | serviceIds が不正 |
| ノードの `id` は重複なし。`type` は `start`・`retrieval`・`generative-ai`・`end` | ノードが不正 |
| `start`・`generative-ai`・`end` は各 1 つ、`retrieval` は 0 または 1 つ | ノードの数が不正 |
| `position` は `x`・`y` が数値 | position が不正 |
| 線の端は、存在するノード | 線が不正 |
| 線は `start →（retrieval →）generative-ai → end` の 1 本の鎖。余りの線・枝分かれ・輪・つながっていないノードは不可 | つなぎ方が不正 |
| `generative-ai` の `outputType` は、`retrieval` がないときだけ 0 か 2（省略は 0）。`retrieval` があるときは書けない（1 になる） | outputType が不正 |
| `start`・`end` は `properties` を持たない | properties が不正 |

- プロパティの検証・環境変数の展開は、`workflow_config` の定義の読み込み（`_definition`）に任せる。ノードの `properties` を今の設定ファイルの形に組み直して渡し、`WorkflowConfigError` は `GraphError` に包む
- 鎖の順は、`start` から線を 1 本ずつたどって決める（たどった数がノード数に一致すること）

### `studio/store.py`

- `GraphStore(directory)`:
  - `load_all()`: ディレクトリの `*.json` を読み、`(id, 生の JSON)` を返す。読めない・壊れたファイルは、警告ログを出して読み飛ばす
  - `read(id)`、`write(id, data)`（一時ファイルに書いてから置き換える）、`delete(id)`、`exists(id)`
  - ファイル名は `<id>.json`。`id` の検証は `parse_graph` が済ませてから呼ぶ（パスの組み立てに使うため、保存層でも `id` の形を再確認する）

### `studio/graph_workflow.py`

- `GraphWorkflow(graph, definition, chat_runtime_factory, retrieval_runtime_factory)`: 今の `Workflow` インターフェース（`run`）を実装する
- `run` は、コンパイルした定義で今の生成AIのワークフローを動かす（検索 → 生成AI の順序・ジョブの扱い・ストリームは今のまま）
- 失敗は `WorkflowError` のまま上に投げる。ただしメッセージの頭に、失敗したノードの名前を付ける（検索アダプターの失敗は検索ノード、それ以外は生成AI ノード）。例: `ノード「検索」: 検索アダプタの実行に失敗しました: …`

### `studio/service.py`

- `StudioService(store, registry, workflow_factory)`:
  - `load()`: 起動時。保存ファイルを読み、検証できたものだけ登録する。サービス ID が他と重なったものは、警告ログを出して読み飛ばす
  - `list()`、`get(id)`（秘密情報を伏せた定義）、`create(data)`、`update(id, data)`、`delete(id)`、`validate(data)`
  - 作成・更新は、検証 → サービス ID の重複確認 → 保存 → 登録の順。保存に失敗したら、登録は変えない
  - 更新は、古いサービス ID の登録を外し、新しい登録を入れる（保存の成功後）
  - 同時の呼び出しで重複確認がすり抜けないよう、更新系は 1 つのロックで直列にする
- 秘密情報を伏せる: プロパティ名に `API_KEY`・`PASSWORD`・`SECRET`・`TOKEN` を含み、値が `${…}` だけの参照でないものは、応答で `********` にする。更新で `********` のまま送られた値は、保存済みの値を引き継ぐ

### `routers/admin.py`

| メソッド・パス | 応答 |
|---|---|
| `GET /admin/workflows` | 200。`[{id, name, serviceIds}]` |
| `POST /admin/workflows` | 201。定義（伏せたもの）。不正は 400、id・サービス ID の重複は 409 |
| `POST /admin/workflows/validate` | 200 `{ok: true}`。不正は 400 |
| `GET /admin/workflows/{id}` | 200 定義。なければ 404 |
| `PUT /admin/workflows/{id}` | 200 定義。本文の id とパスの id が違えば 400。なければ 404。不正は 400、重複は 409 |
| `DELETE /admin/workflows/{id}` | 204。なければ 404 |

- 応答は JSON。エラーは `{"detail": "メッセージ"}`
- `/admin/workflows/validate` は `{id}` のパスと衝突しないよう、先に宣言する

### `registry.py`

- `set_dynamic(service_id, workflow)`、`remove_dynamic(service_id)`、`has_dynamic(service_id)` を足す
- `resolve` は、動的 → 登録 → ひな形 → 学習 → 同期 → 既定の順（先頭に動的を足すだけ）

## 保存データ（例）

```json
{
  "version": 1,
  "id": "assistant-1",
  "name": "社内QA",
  "serviceIds": ["assistant-1"],
  "nodes": [
    {"id": "start", "type": "start", "position": {"x": 0, "y": 0}},
    {"id": "ret", "type": "retrieval", "name": "検索", "position": {"x": 200, "y": 0},
     "properties": {"VENDOR": "Echo", "URL": "http://echo.invalid", "API_KEY": "echo", "MODEL_NAME": "echo"}},
    {"id": "gen", "type": "generative-ai", "name": "生成AI", "position": {"x": 400, "y": 0},
     "properties": {"VENDOR": "Echo", "URL": "http://echo.invalid", "API_KEY": "echo", "MODEL_NAME": "echo"}},
    {"id": "end", "type": "end", "position": {"x": 600, "y": 0}}
  ],
  "edges": [
    {"source": "start", "target": "ret"},
    {"source": "ret", "target": "gen"},
    {"source": "gen", "target": "end"}
  ]
}
```

- 検索ノードの `properties` に、ベクトルDB の接続（`VDB_*`）を書く。検索のないワークフローは、`start → gen → end` の 3 ノード

## 注意

- エンジンは、この PR では、鎖状のグラフを今の生成AIのワークフローに写して動かす。ノードの種類が増える次の PR で、ノードごとに動かす作りに広げる。保存の形（版 1）は、そのとき変えない
- 管理用 API は認証を持たない（検証用の道具）。`WAHA_STUDIO_DIR` を設定したときだけ有効になる

# 01_要件定義

## 背景

- waha-emulator は、サービス ID ごとに決まった流れ（検索 → 生成AI など）を、設定ファイルに書いて起動時に読む作りになっている。流れを自由に組めず、変えるたびに再起動が必要
- 本物の Waha! Transformer は、Designer 上で、データと処理をアイコンと矢印でつないでジョブを組む
- 目的は、Dify のように対話的にワークフローを組み、SecuAiGent（server-local）から、組んだワークフローをサービス ID で呼んで動作を確かめること
- この Issue は大きいため、複数の PR に分ける。ここでは**最初の PR**の要件を書く。画面（ノードと線のキャンバス）は、次の PR で作る

## 機能要件（最初の PR）

### ワークフローの定義と保存

- ワークフローは、ノードと線（どのノードの出力がどのノードの入力になるか）で表す
- ワークフローには名前と、結びつけるサービス ID（1 つ以上）を持たせる
- ワークフローを作成・取得・一覧・更新・削除できる管理用の API を作る
- 保存したワークフローは、エミュレーターを再起動しても残る
- 保存・更新・削除は、再起動なしで、すぐ呼び出しに反映される
- 保存の内容を、人が読める形で確認できる（巻き戻しや差分の確認に使う）

### ノードの種類（最初の PR）

| ノード | 役割 |
|---|---|
| 開始 | server-local から届く入力（質問・会話履歴・textData・添付ファイル）を、後ろのノードへ渡す |
| 検索 | 質問を検索語にして、ベクトルDB から引用資料を得る（既存の検索アダプターを使う） |
| 生成AI | 質問と、あれば引用資料を渡して回答を得る（既存の生成AIアダプターを使う） |
| 終了 | 生成AI の出力を、outputfile として返す |

- 各ノードの設定（接続先・モデル・API キーなど）は、今の設定ファイルのプロパティと同じ名前・同じ値の規則で書ける
- API キーなどの秘密情報は、保存したファイルに書かず、環境変数の参照（`${名前}`）で書ける。管理用 API の応答には、秘密情報を出さない

### 実行

- 保存したワークフローに結びつけたサービス ID で、server-local の `execute` を呼ぶと、そのワークフローが動く
- ノードは、線の向きに従って順に動く。線のつなぎ方が不正なワークフロー（開始がない・終了がない・つながっていない・輪になっている・最初の PR で扱えない組み合わせ）は、保存の時点でエラーにする
- 途中のノードが失敗したら、そこで止め、どのノードの失敗かが分かる失敗理由を返す
- 途中経過（推論の差分など）は、今と同じ形でストリームファイルに書く

### 今ある動作の維持

- servicerun API（セッション・スロット・ジョブ・`execute`・`result`・`download`）は変えない
- 保存したワークフローに結びつかないサービス ID は、今の設定ファイル（`WAHA_WORKFLOWS_FILE`）の定義で動く。学習・削除・同期は、この PR では今のまま（次以降の PR でノード化する）
- 同じサービス ID を、保存したワークフローと設定ファイルの両方に書いたときは、保存したワークフローを優先する

## 非機能要件

- 作り変えの前の状態に、いつでも戻せる（`waha-emulator-before-studio` タグ。PR 単位で revert できること）
- 保存の形式は、今後ノードの種類を増やしても、既存の保存データが読めるよう、バージョンを持つ
- 管理用の API は、検証用の道具のため認証を持たない。ただし、サービス ID を受け付ける API（servicerun）とは別の経路にする
- 既存のテストが、変更なしで通る

## スコープ外

- 画面（ノードと線のキャンバス、設定フォーム、試し実行）。次の PR
- 学習・削除・同期のノード化、設定ファイルの廃止
- エージェント（ツールを呼びながら考える動き）、条件分岐、コード・HTTP 呼び出しなどの追加ノード、複数の生成AI を直列に呼ぶこと
- 本物の Waha! の「標準」ノード（ビューフィルタ・関数）の再現
- デプロイ

# 02_基本設計

## 全体像

```
SecuAiGent（server-local）
   │  execute(サービス ID)   ← servicerun API。変えない
   ▼
レジストリ ──┬─ 保存したワークフロー（新規。再起動なしで増減）
             └─ 設定ファイルの定義（今のまま。学習・削除・同期はここ）
   │ 保存したワークフローに当たったら
   ▼
グラフの実行エンジン（新規）
   開始 → [検索] → 生成AI → 終了
   │            │
   既存の検索・生成AI アダプター（今のまま使う）

管理用 API（新規）──→ ワークフローの保存場所（新規）
   ▲
   画面（次の PR）
```

## 設計の方針

1. **servicerun の層に触れない。** 変えるのは「サービス ID からワークフローを選ぶ部分」と「ワークフローの中身」だけ
2. **ワークフローを動かす入口は今のまま。** 新しいエンジンは、今のワークフローと同じ呼び方で動き、ジョブの管理・ストリーム・結果の保存は今の仕組みをそのまま使う
3. **アダプターの呼び方は今のまま。** ノードは、今の設定（プロパティ）から、アダプターへの入力を作る処理を使い回す。新しいのは、ノードの順番決めと、ノード間の受け渡しだけ
4. **今の設定ファイルは、この PR では残す。** 保存したワークフローを優先し、当たらないサービス ID は今の定義に回す

## ワークフローの定義（概念）

| 項目 | 内容 |
|---|---|
| バージョン | 保存形式の版。読み込み時に確認する |
| 名前 | 人が付ける名前 |
| サービス ID | このワークフローを呼ぶサービス ID の一覧。他のワークフローと重ならないこと |
| ノード | ID・種類・設定（プロパティ）・画面上の位置（次の PR で使う。この PR では保存するだけ） |
| 線 | 出力元ノードの ID と、入力先ノードの ID |

- 画面上の位置を、最初から定義に含める。後から足すと、保存形式を変えることになるため
- 設定の書き方（プロパティ名・`${環境変数}`・ベンダー名）は、今の設定ファイルと同じ規則にし、同じ検証を通す。不正な値は、保存の時点で 400 で返す

## 実行の流れ

1. execute のサービス ID から、保存したワークフローを選ぶ
2. 線をたどって、実行の順番を決める（開始から終了へ）
3. 開始ノードが、届いた入力を持つ
4. 検索ノードがあれば、質問を検索語にして動かし、引用資料を後ろへ渡す
5. 生成AI ノードが、質問と引用資料から回答を作る
6. 終了ノードが、回答を outputfile の中身として返す

- 受け渡す値は、ノードごとの出力に名前を付けて持つ。最初の PR は決まった種類（質問・引用資料・回答）だけ

## 保存場所

- 1 ワークフロー = 1 ファイル（JSON）。置き場所は設定で指定できる（環境変数）。onprem の compose では、ボリュームに置く
- 理由: 人が読める・差分が見える・巻き戻しやコピーが簡単。検証用の道具のため、データベースは持たない
- 書き込みは、一時ファイルに書いてから置き換える（途中で止まっても壊れない）
- 起動時に全ファイルを読み、不正なファイルは、ログに出して読み飛ばす（他のワークフローは動かす）

## 管理用の API（概念）

| 操作 | 内容 |
|---|---|
| 一覧 | 名前・サービス ID の一覧 |
| 取得 | 1 件の定義（秘密情報は伏せる） |
| 作成 | 定義を保存し、すぐ呼べるようにする。不正なら 400。サービス ID の重複は 409 |
| 更新 | 同上。実行中のジョブには影響しない |
| 削除 | 保存を消し、サービス ID の登録を外す |
| 検証 | 保存せずに、定義が正しいかだけを確かめる（画面の保存前チェックに使う） |

- servicerun とは別の経路（パス）に置く

## 失敗の扱い

| 場面 | 扱い |
|---|---|
| 定義が不正（保存時） | 400。どのノード・どの項目かを返す |
| サービス ID の重複 | 409 |
| ノードの実行が失敗 | ジョブを失敗にし、ノード名と今の失敗理由（アダプターが秘密を伏せた文言）を返す |
| 保存ファイルが壊れている（起動時） | ログに出して読み飛ばす |

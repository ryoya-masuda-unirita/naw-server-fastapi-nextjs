# 04_テスト設計

## 方針

- 既存のテストを変えずに通す（`WAHA_STUDIO_DIR` 未設定の動作が変わらないことの確認）
- 新しい部品を、定義の検証・保存・管理・API・実行の 5 つの観点で確かめる
- 実行は、偽のプロバイダ（echo）で、server-local と同じ `execute` の経路を通す

## 観点

### 定義の検証

- 正しい定義（検索あり・なし）を読める
- 版・id・name・サービス ID・ノード・位置・線の不正を、それぞれ弾く（どの項目かがメッセージに出る）
- つなぎ方の不正（開始なし・終了なし・生成AI なし・生成AI が 2 つ・枝分かれ・輪・つながっていないノード・逆向き）を弾く
- outputType の不正（検索ありで指定・0 と 2 以外）を弾く
- プロパティの不正（未知の名前・不正な値・環境変数がない）を弾く
- 検索ありは RAG の定義に、なしは通常チャットの定義になる

### 保存

- 保存して読み直せる、削除できる
- 壊れたファイル・不正な定義のファイルは読み飛ばし、他は読める
- 書き込みの途中で止まったときに、元のファイルが残る（一時ファイルの置き換え）

### 管理（サービス）

- 作成すると、すぐサービス ID で呼べる。更新・削除が、すぐ反映される
- サービス ID の重複・id の重複で 409 になり、保存も登録も変わらない
- 更新で、外したサービス ID が呼べなくなる
- 削除すると、設定ファイルの定義（同じサービス ID があれば）に戻る
- 取得の応答で、秘密情報が伏せられる。伏せた値のまま更新しても、保存済みの値が残る
- 起動時の読み込みで、サービス ID が重なるものを読み飛ばす

### API

- 各エンドポイントの正常・不正・存在しない・重複の応答
- `WAHA_STUDIO_DIR` 未設定のとき、管理用 API が 404

### 実行（結合）

- 保存したワークフローのサービス ID で execute → result → download し、回答が返る
- 検索ノードのあるワークフローで、検索 → 生成AI の順に動く（偽の検索ランタイム）
- 失敗したとき、失敗理由にノード名が付く
- 設定ファイルの定義と同じサービス ID を保存したとき、保存したワークフローが動く

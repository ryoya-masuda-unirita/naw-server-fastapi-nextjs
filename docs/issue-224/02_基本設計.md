# 02_基本設計

## 変更対象

- 汎用チャット API の入口（リクエストの受け取り方）
- 汎用チャット API のリクエスト定義
- 汎用チャットのビジネスロジック（添付ファイルの紐付け、SSE の組み立て）
- 送信 API と共通にする処理（SSE イベントの組み立て、`textData` と添付ファイルパートの解釈）
- テスト（単体・結合）

## 画面 / API 変更概要

### `POST /api/llm/chat`

- Content-Type: `application/json` → `multipart/form-data`
- パート:
  - `textData`（必須）: 条件・会話履歴の JSON
  - `attachmentFiles`（任意・複数）: 添付ファイル
- 応答: `text/event-stream`。各イベントは `data: {"type": "<種別>", ...}` の 1 行（イベント名の行なし）。

送信例（`textData`）:

```json
{
  "deployName": "gpt-4o",
  "messages": [
    {"role": "system", "content": "あなたは有能なアシスタントです"},
    {"role": "user", "content": "この画像を説明して", "attachments": ["photo.png"]}
  ],
  "response_format": {"type": "json_object"}
}
```

応答例:

```text
data: {"text": "これは", "type": "text_delta"}

data: {"text": "猫です", "type": "text_delta"}

data: {"inputTokens": 10, "outputTokens": 5, "type": "message_stop"}
```

JSON 内の項目の順序は送信 API（#183）の実装に合わせる（移植元は `type` が先頭だが、JSON として同じ内容であり、受け手の判定に影響しない）。

## 影響範囲

- 汎用チャット API の呼び出し元: 本リポジトリのフロントエンドからは呼ばれていないため影響なし。
- 送信 API（`/api/messages/content`）: 共通化した処理を使うように置き換えるだけで、リクエスト・応答の形式は変わらない。既存テストで回帰を確認する。
- DB: 変更なし。

## 移植方針

- 移植元の汎用チャット API と同じく、`textData` パートと `attachmentFiles` パートで受け取る。`textData` の解釈は送信 API（#182）で作った方式（JSON の解釈エラー・項目の検証エラーを 422 で返す）に揃える。
- 添付ファイルの紐付けは移植元の「ファイル名で索引を作り、ユーザー発話ごとに突き合わせる」処理に合わせる。
- SSE は移植元の SSE イベント定義と同じ形式にし、送信 API と同じ組み立て処理を使う。
- Azure OpenAI と Bedrock の振り分け（#149）はそのまま維持する。

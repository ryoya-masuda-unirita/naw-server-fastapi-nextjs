# 01_要件定義

## 背景

汎用チャット API は、会話履歴を渡して LLM の回答をストリーミング（SSE）で受け取る API である。移植元では、Web 画面ではなく SECURE 経路（Waha / local-server）から呼ばれる。移植元クライアント（Angular）には自動生成された型定義があるだけで、画面からは呼ばれていない。本リポジトリのフロントエンド（`frontend-angular/`・`frontend/`）も呼んでいない。

移植元の最新実装と本ポートを比べた結果、次の差異があった。

| # | 項目 | 移植元 | 本ポート（修正前） |
|---|---|---|---|
| A | リクエストの送り方 | `multipart/form-data`。`textData` パートに条件・会話履歴の JSON、`attachmentFiles` パートに添付ファイル | JSON ボディ。添付ファイルは JSON 内に Base64 で埋め込む |
| B | 添付ファイルと発話の紐付け | 各発話の `attachments`（ファイル名の一覧。綴り違いの `attatchments` も受け付ける）と、アップロードされたファイルのファイル名を突き合わせ、ユーザー発話ごとに添付する | 添付ファイルは常に最後のユーザー発話にまとめて添付する |
| C | 出力フォーマット指定の項目名 | `response_format` | `responseFormat` |
| D | SSE の形式 | イベント名の行なしの `data:` 行に `{"type": "<種別>", ...}` の JSON（#183 で送信 API に適用した形式と同じ） | `event: <種別>` 行と、`type` を含まない `data:` 行 |

SSE の種別と項目は次のとおり（移植元の SSE イベント定義と同じ）。

| 種別 `type` | 項目 | 送出条件 |
|---|---|---|
| `text_delta` | `text` | 回答の差分（ライブラリ生成時は補足コメントの差分と完了メッセージ） |
| `library_title_delta` | `text` | ライブラリ生成時のタイトルの差分 |
| `library_content_delta` | `text` | ライブラリ生成時の本文の差分 |
| `message_stop` | `inputTokens`, `outputTokens` | 正常終了時に最後に 1 回 |
| `error` | `message` | LLM 呼び出し中のエラー時 |

## 機能要件

1. リクエストを移植元と同じ `multipart/form-data` で受け付ける。
   - `textData` パート（必須）: 次の項目を持つ JSON。`deployName`・`messages` は必須。
     - `deployName`, `messageId`, `additionalPrompt`, `temperature`, `maxTokens`, `createLibrary`, `tools`, `response_format`, `messages`
     - `messages` の各要素: `role`, `content`, `attachments`（ファイル名の一覧。省略時は空。`attatchments` でも受け付ける）
   - `attachmentFiles` パート（任意・複数可）: 添付ファイル。
   - `textData` はファイルパート（`application/json` の Blob）でも通常のフォーム値でも受け付ける（送信 API と同じ）。
2. 添付ファイルは、ユーザー発話ごとに `attachments` のファイル名と一致するファイルを添付する（移植元と同じ）。
   - 発話の `attachments` に、アップロードされていないファイル名がある場合は 400 とする（移植元と同じ文言）。
   - 空のファイルは突き合わせの対象にしない（移植元と同じ）。同じファイル名のファイルが複数アップロードされた場合は入力エラーとする（移植元の `@UniqueFileNames` 相当）。
   - ユーザー以外（`system`・`assistant`）の発話の `attachments` は無視する（移植元と同じ）。
3. SSE を移植元と同じ形式で送る（上表）。
4. Azure OpenAI・Bedrock の両経路で 1〜3 が同じように動作する。

## 非機能要件

- 送信 API（`/api/messages/content`）と同じ処理（SSE イベントの組み立て、`textData` と添付ファイルパートの解釈）は共通化し、二重に持たない。送信 API の挙動は変えない。
- エラー応答の形式（`detail`）と、入力エラーのステータスコード（`textData` の不正・項目の検証エラーは 422、業務的なエラーは 400）は変えない。
- マイグレーションは発生させない。

## スコープ外

移植元との差異のうち、リクエスト形式・SSE 形式以外のもの、またはこのリポジトリで実現手段がないものは本 Issue では扱わない。

- `reasoning_effort`・`verbosity`: 受け付けるが無視する（本ポートの LLM クライアントは推論設定に未対応のため。移植元でも `verbosity` は未適用）。推論の差分イベント `reasoning_delta` も同じ理由で送出しない。
- ライブラリ生成時のライブラリ保存: 移植元は最新版で「SECURE 経路では local-server が保存するため、本 API では保存しない」に変わったが、本ポートは保存を続ける（挙動の変更であり、本 Issue の範囲外）。
- 未対応の `role` を 400 にする検証、`response_format` と `createLibrary` の同時指定を 400 にする検証、`content` の空文字を許可する変更（いずれも本ポートの現状のまま）。
- エラー応答の形式（`detail` / `message`）、入力エラーのステータスコード（422 / 400）。
- 非画像ファイルのテキスト抽出（Issue #97 のとおり未対応のまま）。
- フロントエンド（`frontend-angular/`・`frontend/`）の変更。

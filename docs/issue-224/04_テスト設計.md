# 04_テスト設計

## テスト方針

- API の入口から SSE の応答までを、実際の multipart リクエストで確認する（結合テスト。LLM 呼び出しは差し替える）。Azure OpenAI と Bedrock の両経路で確認する。
- 添付ファイルの紐付け・SSE の組み立ては単体テストで分岐を確認する。
- 送信 API は共通化した処理に置き換えるため、既存テストがすべて通ることで回帰がないことを確認する。

| No | 観点 | 条件 | 期待結果 |
|---|---|---|---|
| 1 | SSE 形式（Azure） | Azure のモデルを指定して multipart で送信する | `event:` 行がなく、`data:` の JSON に `type` があり、`text_delta`（`text`）→ `message_stop`（`inputTokens`・`outputTokens`）の順に届く。トークン使用量が保存される |
| 2 | SSE 形式（Bedrock） | Bedrock のモデルを指定して multipart で送信する | No.1 と同じ形式で届き、Bedrock 側の呼び出しが使われる |
| 3 | 発話ごとの添付（Azure） | 2 つのユーザー発話がそれぞれ別の画像を `attachments` で指定する | 各発話に、指定した画像だけが添付されて LLM に渡る |
| 4 | 発話ごとの添付（Bedrock） | ユーザー発話が画像を `attachments` で指定する | 指定した画像が添付されて LLM に渡る |
| 5 | `textData` を通常のフォーム値で送る | `textData` を文字列のフォーム値として送る | 受け付けられ、SSE が届く |
| 6 | 旧形式（JSON ボディ）の拒否 | JSON ボディで送信する | 422 |
| 7 | `textData` の不正 | `textData` が JSON として解釈できない | 422 |
| 8 | 添付ファイル名の不一致 | `attachments` に、アップロードしていないファイル名を指定する | 400（移植元と同じ文言） |
| 9 | 添付ファイル名の重複 | 同じファイル名のファイルを 2 つアップロードする | 422 |
| 10 | `response_format` の項目名 | `response_format` を指定する | 出力フォーマット指定として扱われる |
| 11 | `attatchments` の別名 | 発話に `attatchments` でファイル名を指定する | `attachments` と同じに扱われる |
| 12 | ユーザー以外の発話の添付 | `system`・`assistant` の発話に `attachments` を指定する | 無視される（添付されず、エラーにもならない） |
| 13 | 空のファイル | 空のファイルを `attachments` で指定する | 突き合わせの対象外となり 400 |
| 14 | ライブラリ生成時の降格 | ライブラリ生成で、`system` 発話に `attachments` を指定する | 降格後の発話に添付されない |
| 15 | エラーイベント | LLM 呼び出し中に例外が発生する | `{"type": "error", "message": ...}` が届く |
| 16 | ライブラリ生成の SSE | ライブラリ生成で送信する | `library_title_delta`・`library_content_delta`・`text_delta`・`message_stop` が `type` 付きで届く |
| 17 | 未認証 | 認証なしで送信する | 401（添付ファイルの検証より先に認証が行われる） |
| 18 | 送信 API の回帰 | 既存の送信 API のテスト | すべて成功する |

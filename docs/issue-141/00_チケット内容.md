# backend app主要範囲のmypyエラーを修正する

## 概要

backend の mypy 対象範囲を主要アプリコードへ段階的に拡大し、検出された型エラーを修正する。

## 説明

mypy を CI に組み込む前に、まずアプリ本体の主要モジュールで型チェックが通る状態を作る必要がある。特に core / services / repositories / routers / schemas は今後の移植作業でも変更頻度が高く、型チェックの効果が出やすい。

対応内容（想定）:

- `backend/app/` 配下の対象範囲を決めて mypy を実行する
- Optional / None、SQLModel / SQLAlchemy、Pydantic schema、AsyncSession 周辺の型エラーを修正する
- 必要な helper 型や cast は最小限に留める
- 型エラー修正によって挙動が変わらないことを既存テストで確認する

受け入れ条件:

- 決めた `backend/app/` 対象範囲で mypy が通る
- 修正範囲に対する pytest / ruff が通る
- 不自然な `type: ignore` を増やしていない

スコープ外:

- tests 配下すべての mypy 対応
- strict mode の全面適用
- CI 必須化

## その他

- 前提: Issue #139（現状調査、PR #143、未マージ）・Issue #140（mypy設定整備、PR #144、未マージ）が完了済み
- #140 の PR #144 時点で、`backend/pyproject.toml` の `[tool.mypy]` に対象範囲・除外設定・警告設定が整備され、`uv run mypy app tests` のエラーは435件→2件（実バグ疑いのみ）まで削減されている
- 残る2件（`app/services/index_service.py:594`・`app/services/message_service.py:1028`）は、SQLModel/SQLAlchemy型推論の構造的問題ではなく、コード側のOptional/None扱いに起因する実バグ疑いとして#140で意図的に除外せず可視化されたもの
- 本Issueはこの2件を含む、#140でignore対象外とされたmypy対象範囲（主要アプリコード）のエラー修正がスコープ
- `develop` にはまだ#139/#140の変更が未マージのため、本Issueの作業ブランチ（`feature/issue-141`、`develop`から作成）に#140のPR #144と同等のmypy設定（`backend/pyproject.toml`の`[tool.mypy]`整備、`tests/unit/test_azure_cost_client.py`の不要`# type: ignore`削除）を先に反映した上で着手した

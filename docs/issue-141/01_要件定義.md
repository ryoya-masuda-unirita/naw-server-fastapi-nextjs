# 01_要件定義

## 背景

Issue #140（PR #144、未マージ）により `backend/pyproject.toml` の `[tool.mypy]` が段階導入向けに整備され、`uv run mypy app tests` のエラーは435件→2件まで削減された。除外されたのは `app.repositories.*`・`app.services.user_service`・`app.services.user_import_service`・`app.core.credit_quota` で、いずれもSQLModel/SQLAlchemyの型推論に起因する構造的な問題（`Model.field == value`のような比較式を`.where()`等に渡す書き方がmypy上は型エラーになる）であり、根本解消にはリポジトリ層のクエリ構築パターン自体の見直しが必要なため、初期導入では対象外とされた。

一方、除外されず可視化されたまま残っている以下の2件は、上記の構造的問題とは性質が異なり、コード側のOptional/None安全性に起因する実バグ疑いである。

- `app/services/index_service.py:594`: `find_by_id_and_tenant_id`の第1引数に`str | None`型の`room_id`をそのまま渡している
- `app/services/message_service.py:1028`: `None`を`MessageContentResponse`型変数へ代入している

## 機能要件

- 上記2件のmypyエラーについて、実際の挙動に影響を与えない範囲で型エラーを解消する
  - `index_service.py:594`: `additional_learning`メソッドの`room_id`は、直前の`learning_source_not_specified`/`confused_learning_source`チェックにより、到達時点で`feedback_id`がNoneかつ`room_id`はNoneではないことが実行時には保証されている。この不変条件をmypyにも伝える形で修正する（既存の `assert request.tenantName is not None`（`tenant_service.py:102`）と同様のパターンを踏襲する）
  - `message_service.py:1028`: `content_response`変数は`_persist_message_content`の戻り値（`MessageContentResponse`、非Optional）による最初の代入からmypyが非Optional型と推論してしまうため、`ValueError`捕捉時の`None`代入と両立する型注釈を明示する
- 上記2件以外に、mypy対象範囲（#140で`ignore_errors`対象外とされたモジュール）で新規にエラーが発生していないか、`uv run mypy app tests`で確認する
- 修正によって既存の挙動（HTTPレスポンス・永続化内容・エラーハンドリング）を変えない

## 非機能要件

- 既存のテスト（`pytest tests/unit`）に影響を与えないこと
- 不自然な `# type: ignore` や `cast()` を新規に増やさないこと（`assert`・型注釈による不変条件の明示を優先する）
- `develop`未マージの#139/#140の内容を前提にするため、作業ブランチ（`feature/issue-141`）に#140のPR #144と同等の`[tool.mypy]`設定・`test_azure_cost_client.py`の修正を先に反映してから着手する

## スコープ外

- tests 配下すべての mypy 対応
- strict mode の全面適用
- CI 必須化
- #140 で `ignore_errors = true` により除外されたモジュール（`app.repositories.*`・`app.services.user_service`・`app.services.user_import_service`・`app.core.credit_quota`）の型エラー解消・除外解除（別Issueで判断）

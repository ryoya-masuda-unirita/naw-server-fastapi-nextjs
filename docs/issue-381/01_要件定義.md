# 01_要件定義

## 背景

- Terraform の state を置く S3 バケットを、インフラ本体と同じ構成で管理している。そのため `terraform destroy` で state の置き場所まで消え、バケットのない状態から作り直す手順（backend 設定の一時的なコメントアウトなど）が必要になる。実際に過去に起きている
- バケット名が設定ファイルに直書きされており、別の AWS アカウントでは使えない。S3 のバケット名は全世界で一意なので、アカウントに依存しない固定名は他者と衝突しうる
- state バケットに暗号化の設定がない。state には DB パスワードなどが平文で入る
- develop への push で、インフラの変更が確認なしにそのまま本番相当の環境へ適用される。インフラの構成を作り直す一連の作業（#380）の間に、意図しない適用が起きる危険がある
- 移植元（secuaigent-infra）には、state 用のリソースを独立して一度だけ作る手順があり、その考え方に揃える

## 機能要件

1. state 用の S3 バケットを、インフラ本体とは別の構成（独立した state）で作れること
   - バージョニング有効、AES256 暗号化、パブリックアクセスの全面ブロック
   - 誤った削除を防ぐ（`prevent_destroy` 相当）
   - バケット名にアカウント ID を含め、アカウントごとに一意になること
2. インフラ本体は、state バケットを管理対象に持たないこと。本体を destroy しても state は残ること
3. インフラ本体の backend 設定に、バケット名などの環境依存の値を直書きしないこと。実行時に外から渡せること（ローカルは設定ファイル、CI は GitHub の変数）
4. develop への push では、インフラの apply が自動実行されないこと。手動で明示的に実行したときだけ apply されること
   - backend・frontend のデプロイは、これまでどおり push で自動実行されること（インフラのジョブが実行されない場合でも止まらない）
5. 新しい AWS アカウントで、最初から構築する手順が文書化されていること（state バケットの作成 → backend の設定 → GitHub の Secrets / Variables の登録 → 初回 apply）

## 非機能要件

- state のロックは、これまでどおり S3 のネイティブロックを使う（DynamoDB は使わない。Terraform 1.11 以降の方式。CI の Terraform は 1.15.8）
- AWS のプロファイルは設定ファイルに固定しない（CI で OIDC の一時クレデンシャルを使うため）。ローカルでは環境変数で `oic` を指定する
- `terraform fmt` と `validate` が通ること。`apply` は実行しない（plan も、別アカウントの認証情報が必要なため、実行できる範囲で確認する）

## スコープ外

- インフラ本体のディレクトリ再構成（#382）、変数化（#383）、各リソースの設定変更（#384〜#387）、GitHub Actions のロール権限（#388）
- 既存アカウントにある旧 state バケットとリソースの移行・削除（新アカウントに新規構築する前提のため）
- 手元にある未コミットの backend 設定の変更の扱い（この作業とは別。退避済み）

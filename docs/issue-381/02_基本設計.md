# 02_基本設計

## 変更対象

1. **state 用バケットの構成（新規）**: インフラ本体とは別の Terraform 構成を、インフラ用ディレクトリの下に新設する。バケット、バージョニング、暗号化、パブリックアクセスブロックを持ち、`prevent_destroy` を付ける。バケット名は「プロジェクト名 + tfstate + アカウント ID」。バケット名と backend に渡す設定の例を出力する
2. **インフラ本体の backend 設定**: バケット名・リージョンなどを持たない部分設定にし、実行時に渡す。state のキーとロック方式（S3 ネイティブ）は本体側に残す。本体にあった state バケットのリソース定義は削除する
3. **backend 設定の渡し方**
   - ローカル: 設定ファイルで渡す（実体は git 管理しない。雛形のみ管理する）
   - CI: 初期化の手順で、GitHub の変数に入れたバケット名を渡す
4. **デプロイのワークフロー**: 全体のデプロイを呼び出す側のワークフローで、インフラのジョブを「手動実行で、明示的に指定したときだけ」実行する。backend・frontend のジョブは、インフラのジョブがスキップされても実行される（現行の条件を維持する）
5. **README**: 鶏卵問題の説明と作り直し手順を、新しい手順に置き換える。新アカウントでの初回構築の手順と、登録する Secrets / Variables を書く。ローカルのプロファイル名の記述を `oic` にする

## 画面 / API 変更概要

なし（インフラ・CI のみ）。

## 影響範囲

- **CI**: develop への push でインフラが自動適用されなくなる。インフラの変更は、手動実行で反映する運用になる。backend・frontend の自動デプロイは変わらない
- **CI の初期化**: GitHub に新しい Variable（state バケット名）が必要になる。登録するまでインフラのジョブは初期化に失敗する（手動実行のときだけ走るので、push は止まらない）
- **既存の state / リソース**: 旧アカウントの state バケットは本体の管理から外れる。旧アカウントに apply し直さない前提（新アカウントへの新規構築）
- **他の Issue**: #382 以降は、この構成の上で進める

## 移植方針

- 移植元の state 用構成の設定（バージョニング、AES256、パブリックブロック、`prevent_destroy`、アカウント ID 入りの名前）に揃える
- 移植元との違い
  - ロックは DynamoDB ではなく S3 ネイティブ（現状維持。Terraform の推奨に合わせる）
  - プロジェクト名の既定値は、移植元の `secuaigent` ではなくこのリポジトリの名前を使う
- サブドメイン関連は関係しない
- 手動実行のみにする方法は、呼び出し側のワークフローに「インフラを実行するか」の入力（既定: 実行しない）を足す案を採る。呼び出される側のワークフローは、他から呼ばれる形のままにする（二重に手動実行の入口を作らない）

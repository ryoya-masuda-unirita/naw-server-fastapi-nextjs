# 01_要件定義

## 背景

- Issue #160でTerraformによるAWS環境のコード化が完了したが、frontend-angularのデプロイ・backendのデプロイ・Terraformのplan/applyは現状すべて手動
- #186〜#188でユーザーインポート機能の非同期化（SQS/S3）が完了し、そのTerraformコードもデプロイフローに乗せる必要がある
- 手動デプロイは属人化・ヒューマンエラー・作業コストの面で課題がある

## 機能要件

- `develop`ブランチへのpush/mergeをトリガーに、変更されたパス（`frontend-angular/**`, `backend/**`, `infra/**`）に応じて必要なジョブのみ実行するCI/CDパイプラインを構築する
- frontend-angular: ビルド → S3へのアップロード → CloudFrontキャッシュ無効化を自動化する
- backend: テスト・lintの実行 → Dockerイメージビルド（ECSのCPUアーキテクチャ=ARM64に合わせる） → ECRへのpush → ECSサービスの強制新規デプロイを自動化する
- infra: `terraform plan`の実行 → `terraform apply`の自動実行を行う。Route53サブディレクトリ（別state）は対象外とする
- GitHub ActionsからAWSへの認証はOIDC（IAMロールの一時クレデンシャル）を使い、長期的なアクセスキーは使用しない
- Terraformのstateをリモートバックエンド（S3、`use_lockfile`によるS3ネイティブロック）に移行し、CIからの自動applyとローカルでの手動操作が競合しないようにする（`dynamodb_table`によるロック方式はTerraform 1.11で非推奨化されているため使用しない）

## 非機能要件

- OIDC用のIAMロールは、GitHub Actionsの対象リポジトリ・対象ブランチ（`develop`）に権限を限定する（`sub`条件での絞り込み）
- 機密情報（DBパスワード、SECRET_KEY等）はGitHub Secretsで管理し、ワークフローファイルやリポジトリに平文で残さない
- 既存の`backend-tests.yml`（PR時のテスト実行）の挙動は変更しない。新設するデプロイ用ワークフローは別ファイルとして追加する

## スコープ外

- `frontend/`（React移植版）のデプロイ（現在の開発方針によりbackend優先のため対象外）
- 本番環境向けの設定（dev/staging環境のみが対象）
- Terraform apply自体の実行（コード化・plan確認まではClaudeが行うが、実際のCI経由apply動作の最終確認はユーザーが実施）

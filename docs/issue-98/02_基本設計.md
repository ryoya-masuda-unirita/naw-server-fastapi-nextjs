# 02_基本設計

## 変更対象

- LLM呼び出し用の共通クライアント層（Azure OpenAIをラップするモジュール）
- チャット送信のビジネスロジック層
- メッセージ送信のビジネスロジック層
- 上記2つのリクエストスキーマ

## 画面 / API 変更概要

- `POST /api/llm/chat` のリクエストボディに `tools`（任意、配列）を追加する。
- `POST /api/messages/content` のリクエストボディに `tools`（任意、配列）を追加する。
- レスポンス・SSEイベントの形状は変更しない（既存の `text_delta` / `message_stop` / `error` / `complete` のみ）。

## 影響範囲

- `tools` 未指定時は既存のChat Completions API呼び出し経路を変更しないため、既存の呼び出し元・既存テストへの影響はない。
- `tools` 指定時のみ、LLM呼び出しクライアント内部でAzure OpenAI Responses APIへの呼び出しに切り替わる新しい経路が追加される。
- メッセージ送信時に既に永続化されている `tools`（メッセージ作成API側、編集・再生成のクライアント側再利用用）の仕組みは変更しない。

## 移植方針

- 移植元（Spring Boot）はOpenAI Responses APIの組み込みツール宣言をそのまま渡すだけで、独自のWeb検索実装・MCPクライアント実装を持たない。FastAPI側もこの方針を踏襲し、Azure OpenAI Responses APIの `tools` パラメータへ変換して渡すのみとする（自前のWeb検索・MCP実装は行わない）。
- FastAPI側は現状Chat Completions APIのみを使用しているため、tools指定時に限りResponses APIを呼び出す分岐を追加する。全面的にResponses APIへ移行するのではなく、既存の非tools呼び出し経路（Chat Completions API）は温存し、リスク・変更範囲を最小化する。
- Responses APIのストリーミングイベント（`response.output_text.delta` / `response.completed`）を、既存の `ChatStreamChunk`（`text_delta` / `input_tokens` / `output_tokens`）へマッピングし、呼び出し元（サービス層）からは呼び出し方式の違いを意識させない設計とする。
- Azure OpenAI Responses APIの利用には、Chat Completions APIより新しいプレビューAPIバージョンが必要なため、tools呼び出し用に別のAPIバージョン定数を設ける。
- `web_search` / `mcp` 以外のツール名はリクエストスキーマのバリデーションで既に拒否されるため、LLM呼び出しクライアント内部での想定外ツール名の扱いは防御的なエラーに留める。

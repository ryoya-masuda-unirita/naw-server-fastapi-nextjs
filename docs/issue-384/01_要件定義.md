# 01_要件定義

## 背景

- 現在のコンテナ実行基盤は、EC2（t4g.nano 1 台）上の ECS（EC2 起動タイプ、bridge モード）。コスト削減のための選択だったが、1 台構成とホストポート固定のためデプロイがデッドロックしやすく（過去に発生）、EC2 の OS・エージェントの管理も要る。移植元は Fargate で、その運用に合わせる方針を #380 で決めた
- Fargate のタスクは、イメージの取得やログの送信のために、外部のサービスへ通信できる必要がある。タスクを外から直接アクセスできない場所（private サブネット）に置くには、NAT が要る。移植元も同じ構成
- 現在の network は、private サブネットが外に出る経路を持たず、public サブネットの EC2 にパブリック IP を付けて外に出ている
- backend のイメージは ARM64 向けにビルドされている（EC2 が ARM のため）。実行基盤を変えても、イメージは変えずに動かしたい
- マイグレーション（DB のスキーマ更新）は、デプロイのたびに ECS の一時タスクとして実行している。実行基盤が変わるため、起動の仕方も変わる

## 機能要件

1. ECS を Fargate（awsvpc）で動かすこと。EC2 起動タイプ用のリソース（起動テンプレート、Auto Scaling グループ、キャパシティプロバイダ、EC2 のロールとインスタンスプロファイル、AMI の取得）は削除する
2. タスク（backend のサービスと、マイグレーション用の一時タスク）が、ARM64 で動くこと（既存のイメージをそのまま使えること）
3. タスクの CPU とメモリを、タスク単位で指定すること（移植元の既定値に合わせる）。コンテナ単位のメモリ指定は、不要になるため削除する
4. backend のサービスは private サブネットに置き、パブリック IP を付けないこと。起動直後のヘルスチェックで落とされないよう、猶予時間を設けること。デプロイは、既定のローリング更新にする（ホストポート固定のデッドロックがなくなるため）
5. ネットワーク:
   - VPC の CIDR を、移植元と同じ範囲にし、変数で変えられること
   - public / private のサブネットを、2 つの AZ に CIDR の自動計算で作ること
   - NAT GW（1 台）と EIP を作り、private サブネットの外向きの通信を NAT 経由にすること
   - VPC の DNS ホスト名と DNS サポートを有効にすること
6. ALB のターゲットを、IP アドレス単位（awsvpc の Fargate 向け）にすること。ヘルスチェックのパス、ALB の HTTP のみのリスナー、CloudFront と管理者に限定した入力の制限は変えないこと
7. セキュリティグループ: ECS が ALB から 8000 番だけ受けること、RDS・キャッシュが ECS から受けることは変えない。踏み台・RDS・キャッシュ・ALB の置き場所と SG の関係は維持する
8. マイグレーション用の一時タスクを、Fargate で起動できること。CI が、起動に必要なサブネットと SG を、固定値で持たず、稼働中のサービスの設定から取得すること
9. `deploy-backend.yml` から、キャパシティプロバイダに関する設定を削除すること
10. 手順書とプロジェクトの説明（CLAUDE.md のクラウドインフラの表）を、新しい構成（Fargate + NAT）に直すこと

## 非機能要件

- コスト: 固定費が増える。NAT GW の分と、Fargate の常時稼働の分の月額の目安を、PR に書く
- 命名: リソース名（クラスタ、サービス、タスク定義、ログ、ECR）は変えないこと。CI が組み立てる名前との一致を保つ
- `fmt`・`validate` が通ること。`plan` で、追加・削除されるリソースが想定どおりであること

## スコープ外

- CPU・メモリの最適化、オートスケーリング、複数 AZ の NAT（高可用性）
- Secrets Manager の導入（#386）、RDS・ElastiCache・ECR の設定値（#385）、CloudFront の挙動（#387）、CI ロールの権限（#388）
- ログの保持期間の変更、コンテナインサイトの有効化
- ALB の HTTPS 化（サブドメイン関連のため持ち込まない）
- 既存の環境からの移行（新アカウントへの新規構築が前提）

# 02_基本設計

## 変更対象

1. **network**
   - VPC の CIDR を変数にし、既定値を `10.10.0.0/16` にする。サブネットの CIDR は、VPC の CIDR から計算する（public は先頭から、private は 10 番目から。移植元と同じ）
   - NAT GW と EIP を 1 つ、先頭の public サブネットに作る。private のルートテーブルに、外向きの経路（NAT 経由）を足す
   - DNS ホスト名・DNS サポートを有効にする
   - サブネットの名前（AZ の識別子）は、今のとおり変えない
2. **alb**: ターゲットグループを IP 単位にする。そのほかは変えない
3. **ecs**
   - Fargate 用のタスク定義（awsvpc、CPU・メモリ、ARM64）にする。backend とマイグレーションの 2 つとも
   - サービスは Fargate で、private サブネットに置き、パブリック IP なし。ヘルスチェックの猶予時間を持たせる。デプロイは既定のローリング更新
   - EC2 起動タイプ用のリソースをすべて削除する
   - 入力に、private サブネットの ID、CPU、メモリ、猶予時間を追加し、public サブネットの入力は削除する
4. **環境（dev）**: VPC の CIDR を新しい変数で受ける。ecs には private サブネットを渡す
5. **CI（backend のデプロイ）**: キャパシティプロバイダの環境変数を削除する。マイグレーションの一時タスクは、稼働中のサービスのネットワーク設定を取得して、そのまま渡して起動する
6. **手順書とプロジェクトの説明**: README と CLAUDE.md を、Fargate + NAT の構成に直す。NAT のコストの注意も書く

## 画面 / API 変更概要

なし（インフラ・CI のみ）。

## 影響範囲

- **コスト**: NAT GW が固定費として増える。金額は、東京リージョンの単価を確認できていないため、書かない（README に、確認方法と、根拠のない概算を載せないことを書いた）。Fargate は常時 1 タスクが動くので、EC2 の t4g.nano 1 台より高い。CLAUDE.md の「低コスト」の方針とは、トレードオフになる（#380 で Fargate に揃えると決めたため受け入れる）
- **ネットワーク**: VPC の CIDR が変わる。RDS・キャッシュ・ALB・踏み台は、新しい CIDR のサブネットに作られる。bastion は public サブネットのまま
- **ECS のデプロイ**: 実行基盤が変わるため、新アカウントへの新規構築が前提（既存環境への適用は、ほぼ全リソースの作り直しになる）
- **CI**: backend のデプロイが、新しい起動方法に対応する。キャパシティプロバイダの名前は、もう使わない
- **起動時の依存**: Fargate のタスクは、ECR からのイメージ取得とログ送信に NAT が必要。NAT が使える状態になる前にサービスを作ると、起動に失敗する（ルートの作成に依存させる）
- **イメージ**: ARM64 のまま。ビルドの設定は変えない
- **後続の Issue**: #385 以降は、この構成の上で進める

## 移植方針

- 移植元の Fargate・NAT の構成（awsvpc、private サブネット、パブリック IP なし、EIP + NAT GW 1 台、`cidrsubnet`、DNS 有効化、猶予時間）に揃える
- 移植元との違い（このリポジトリの事情で維持するもの）
  - ALB は HTTP のみ（HTTPS・ACM はサブドメイン関連のため持ち込まない）
  - ヘルスチェックのパスは FastAPI の健康確認用のもの
  - ARM64 を明示する（移植元は Java のイメージを x86 で動かしている）
  - ECS の SG の入力は 8000 番（FastAPI のポート）
  - bastion・SQS・user-import・CloudFront Function は維持
- 移植元の CPU・メモリの既定値（タスク単位）は、移植元の変数の既定値に合わせる

# 08_動作確認

## 確認環境

- ローカル環境（`docker compose`によるPostgreSQL 18 + `uvicorn app.main:app --port 8001`）
- `alembic upgrade head`（012→013まで適用）
- `seed.sql`投入済み（`test-tenant` / `admin`（ルーム所有者）/ `user01`（動作確認用グループのメンバー）/ `user02`（グループ未所属）/ 動作確認用グループ`20000000000040008000000000000001`）
- 認証は`/auth/login`で取得したCookie（`access_token`）を、`admin`・`user01`・`user02`の3ユーザーそれぞれで取得して使用

## 確認手順・結果

すべて`curl`で直接APIを呼び出して確認した。

1. **共有リンク作成**
   `admin`が所有するルームに対し、`POST /api/shares`で`teamIds=[動作確認用グループ]`を指定 → `200`、`{"id", "roomId", "teamIds"}`を返却。

2. **アクセス解決（所有者）**
   `GET /api/shares/{shareId}/access`を`admin`（所有者本人）で呼び出し → `200`、`isReadOnly: false`。

3. **アクセス解決（共有先グループメンバー）**
   同じ`shareId`を`user01`（動作確認用グループのメンバー）で呼び出し → `200`、`isReadOnly: true`。

4. **アクセス解決（無関係ユーザー）**
   同じ`shareId`を`user02`（どのグループにも属さない）で呼び出し → `403`。

5. **削除（無関係ユーザー）**
   `user02`が`DELETE /api/shares/{shareId}`を実行 → `403`。

6. **削除（所有者）**
   `admin`が同じ共有リンクを削除 → `204`。

7. **削除後のアクセス解決**
   削除直後に`admin`で`GET /api/shares/{shareId}/access`を実行 → `404`（共有リンクが存在しないため）。

## code-review対応後の再確認

- `upsert`の2回commit問題を修正後（`ShareRepository.save`をflushのみに変更し、共有先グループ置き換えとあわせて1トランザクションでcommit）、同一ルームへの再`POST /api/shares`が同一`shareId`のまま成功することを`curl`で再確認
- `resolve_access`のクエリ統合（`exists_shared_access`削除・`find_group_ids_by_share_id`の結果をPython側の集合演算で判定するよう変更）後、所有者・共有先グループメンバー・無関係ユーザーの3パターンを`curl`で再確認し、いずれも修正前と同じ結果（`isReadOnly`の値・403判定）になることを確認
- ルーム所有権チェックを`app/core/room_access.py`の共通関数に統合した後も、`pytest`（307件）が全て通過することを確認

# 02_基本設計

## 変更対象

新規にチャットルーム共有リンク関連のテーブル・API を追加する（既存テーブルの変更なし）。

- 共有リンク本体（対象ルームに1:1）
- 共有リンクと共有先グループの中間テーブル

## API 変更概要

以下のエンドポイントを新規追加する。

| メソッド | パス | 概要 |
|---|---|---|
| POST | `/api/shares` | 共有リンクを作成・更新する（upsert）。ルーム所有者のみ |
| GET | `/api/shares/{shareId}/access` | 共有リンク経由のアクセスを解決する（roomId・roomName・isReadOnly・teamIds） |
| DELETE | `/api/shares/{shareId}` | 共有リンクを削除する。ルーム所有者のみ |

移植元は`{"data": {...}}`という共通ラッパーでレスポンスを返すが、本リポジトリの既存API（アシスタント・ルーム等）は
ラッパーなしでレスポンスモデルを直接返す方針のため、本issueもラッパーなしのレスポンスに変更する。

## 影響範囲

- 新規テーブル2つ（共有リンク・共有先グループの中間テーブル）を追加するため、マイグレーションが必要
- 既存のルーム・グループテーブルへの参照（外部キー）が発生するのみで、既存テーブルへの変更はない
- ルームアクセス制御に「共有リンク経由のグループアクセス」という新しい判定軸が追加される。ただし本issueで新規追加するエンドポイント（共有リンクのアクセス解決）でのみ使用し、既存のルーム・メッセージAPI（所有者のみアクセス可）には反映しない

## 移植方針

- 共有リンクの発行（upsert）は、対象グループがテナント内に実在することを検証したうえで、既存の中間テーブル行を全削除してから指定グループで再作成する（既存の`GroupPromptTemplateRepository.replace_groups_for_template`と同じ「全削除→再作成」パターンを踏襲する）
- 共有リンクの削除は、移植元の`Share.deleteShare`と同様「対象ルームの所有者本人であること」を条件とする（共有リンクの発行者ではなく、常に現在のルーム所有者で判定する）
- 「閲覧専用かどうか」の判定は、ルーム所有者本人なら`false`、それ以外（共有先グループ経由でアクセスできる場合）は`true`とする。この判定・アクセス可否チェックのロジックは`share_service.py`内に実装し、既存の`room_service.py`・`message_service.py`とは独立させる（サービス間呼び出し禁止のため）
- 共有先グループの検証には既存の`GroupRepository.find_by_tenant_id_and_ids`を、リクエストユーザーの所属グループ解決には既存の`GroupUserRepository.find_belonging_group_ids`をそのまま利用する
- テナント管理者による閲覧バイパスは、移植元の共有リンクアクセス解決でも適用されない仕様のため実装しない

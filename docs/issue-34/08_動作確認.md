# 動作確認

## 新方式（`pre-commit`フレームワーク）での確認結果

### クリーンアップ結果（実施済み・変更なし）

```
$ uv run ruff format --check .
72 files already formatted

$ uv run ruff check .
All checks passed!

$ .venv/bin/python -m pytest tests/ -q
160 passed, 165 warnings in 17.27s
```

### ローカルでのpre-commitフック動作確認

`uv sync`・`uv run pre-commit install`を実行後、`backend/app/routers/health.py`に意図的なフォーマット崩れ・未使用import（`import os`）を追加してコミットした。

```
$ git commit -m "test: ..."
ruff format..............................................................Failed
- hook id: ruff-format
- files were modified by this hook

1 file reformatted

ruff (legacy alias)......................................................Failed
- hook id: ruff
- files were modified by this hook

Found 1 error (1 fixed, 0 remaining).
```

（上記ログの`ruff (legacy alias)`／`hook id: ruff`は、code-review指摘を受けて`.pre-commit-config.yaml`の`id`をforward-compatibleな`ruff-check`に変更する前の実行結果。挙動は同一で、`id`名のみの変更のため再検証はしていない。）

- 1回目のコミットは失敗し、ファイルが自動修正された（`pre-commit`フレームワークの標準動作）
- `git add`でステージし直し、再度`git commit`すると成功した

### リモートの実態確認（`git ls-remote`）

旧`pre-push`方式で「`git log`はamend後に見えるが、実際にpushされる内容は古いまま」という見落としがあったため、今回は`git log`だけでなく`git ls-remote`でリモートの実態も確認した。

```
$ git push
$ git rev-parse HEAD
03295be6f669e78796930f90126bb2bd25f77890

$ git ls-remote origin refs/heads/feature/issue-34
03295be6f669e78796930f90126bb2bd25f77890	refs/heads/feature/issue-34

$ git show 03295be:backend/app/routers/health.py
from fastapi import APIRouter

router = APIRouter()


@router.get("/health")
async def health_check() -> dict[str, str]:
    return {"status": "ok"}


@router.get("/health/ping")
async def ping() -> dict[str, str]:
    return {"status": "pong"}
```

ローカルHEADのSHAとリモートのSHAが一致し、リモートの内容も自動修正後の正しいコードであることを確認した。`pre-commit`はコミット時（コミットオブジェクト確定前）に動作するため、旧`pre-push`方式で発生した「修正がpushに反映されない」問題は発生しない。

### GitHub Actionsでの確認

上記の検証用コミットをプッシュした後、[Run #28775605609](https://github.com/ryoya-masuda-unirita/naw-server-fastapi-nextjs/actions/runs/28775605609)で以下を確認した。

| ジョブ | 結果 |
|---|---|
| `unit-tests` | ✅ success |
| `lint` | ✅ success |
| `integration-tests` | ⏭️ skipped（`develop`ブランチでないため） |

確認後、検証用コミットは`git reset --soft`で取り除き、`git push --force-with-lease`でリモートも本チケットの成果物のみの状態（`9b02db5`）に戻した。`git ls-remote`で復旧後のリモートSHAが`9b02db5`と一致することも確認済み。

## 結論

- クリーンアップ後、`ruff format --check`・`ruff check`とも指摘0件、既存テストも全件成功することを確認した
- `pre-commit`フックが実際に「自動修正→失敗→再コミットで成功」という標準動作をすることを実機確認した
- `git ls-remote`によりリモートの実態が修正済みの内容と一致することを確認した（旧方式の見落としが再発しないことを確認済み）
- GitHub Actionsの`lint`ジョブが成功することを確認した

## 参考：旧方式（`.githooks/pre-push`）の記録

`.githooks/pre-push`方式では、`git log`（ローカル）はamend後のコミットに見えていたが、`git ls-remote`で確認するとamend前のフォーマット崩れが残った内容（`a6b4778`）が実際にはリモートに届いていた。Gitのpre-pushフックは「pushする内容（SHA）」をフック実行前に確定するため、フック内で`git commit --amend`しても、その修正はpushに反映されないという致命的な欠陥があった。この問題を受けて`pre-commit`フレームワーク方式に設計変更した経緯は`01_要件定義.md`を参照。

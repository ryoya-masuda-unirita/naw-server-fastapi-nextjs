# 01_要件定義

## 背景

- プロジェクト名の既定値が、過去の Issue 番号入りの名前（`naw-fastapi-issue160`）になっている。リソース名のほぼすべてがここから作られるため、新しいアカウントにそのまま作ると Issue 番号入りの名前が付く。state 用のバケット（`naw-fastapi`）とも名前がそろっていない
- CI の backend デプロイが、クラスタ名・サービス名・リポジトリ名などを、プロジェクト名と同じ文字列で直書きしている。プロジェクト名を変えると、インフラと CI の名前が食い違い、デプロイが失敗する
- CI ロールの信頼条件に、GitHub のリポジトリ名が直書きされている。フォークや別のリポジトリへ移したときに、設定ファイルの修正が要る
- 「プロジェクト」を示すタグが、約 30 のリソースに手書きされている。付け忘れや書き間違いが起こりうる。移植元は provider の既定タグでまとめている
- 別 state の `infra/route53/` は、カスタムドメイン廃止（#195）で不要になった残骸で、CI の変更検出にも除外条件が残っている
- CloudFront 向けの IP 範囲（マネージドプレフィックスリスト）が ID で直書きされている。この ID はリージョンごとに違うため、別リージョンでは動かない

## 機能要件

1. プロジェクト名の既定値を、Issue 番号のない名前（state 用バケットと同じ `naw-fastapi`）にすること
2. プロジェクト名の唯一の出どころを 1 つにすること
   - ローカル: 変数の既定値と `terraform.tfvars`
   - CI: GitHub の Variable。インフラのデプロイは、この値を Terraform の変数として渡す
3. backend のデプロイのワークフローが、クラスタ名・サービス名・リポジトリ名・タスク定義の名前・キャパシティプロバイダ名を、プロジェクト名から組み立てること。Variable が未登録のときは、原因が分かるメッセージで失敗すること
4. CI ロールの信頼条件に使う GitHub のリポジトリ名を、変数にすること（既定値は、このリポジトリの名前）
5. provider の既定タグに `Project` を設定し、リソースごとの `Project` タグを削除すること。これまで `Project` が付いていたリソースは、実際に付くタグ（既定タグ込み）が変わらないこと。これまでタグのなかったリソースにも `Project` が付くのは、意図した変化として許容する。Auto Scaling グループの伝播タグと、起動テンプレートのインスタンス用タグ指定は、既定タグが効かないため手書きのまま残すこと
6. CloudFront 向けの IP 範囲は、ID の直書きをやめ、名前から引くこと（リージョンを変えても動く）
7. `infra/route53/` を削除し、CI の変更検出の除外条件と、手順書の関連する記述を削除すること
8. 新アカウント向けの手順書に、Variable `PROJECT_NAME` の登録を追加すること

## 非機能要件

- タグ以外のリソース設定値は変えない。再構成前後の比較で、タグ以外の差分がないこと
- AWS のプロファイルは設定ファイルに固定しない
- `fmt`・`validate` が通ること

## スコープ外

- VPC の CIDR とサブネットの割り当て（#384 でネットワークごと作り直す）
- ECS の起動タイプ、RDS・ElastiCache・ECR・CloudFront の設定値の変更（#384〜#387）
- リージョンの変数化。リージョンは backend の設定（変数が使えない）と GitHub Actions の環境変数にも出てくるため、別の機会に扱う
- CI ロールの権限の見直し（#388）
- 旧ホストゾーン（`infra/route53/` が作っていた AWS 上のリソース）の削除。新アカウントには存在しない

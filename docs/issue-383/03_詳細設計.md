# 03_詳細設計

## 1. プロジェクト名

- `infra/environments/dev/variables.tf`: `project_name` の既定値を `"naw-fastapi"` にする（説明コメントに「CI では GitHub の Variable `PROJECT_NAME` が TF_VAR_project_name で渡される」と書く）
- `.github/workflows/deploy-infra.yml`: `Terraform Plan` と `Terraform Apply` の `env` に `TF_VAR_project_name: ${{ vars.PROJECT_NAME }}` を足す。`Check state bucket variable` と同じ形で、`PROJECT_NAME` が空なら原因を示して失敗するステップを足す（既存のチェックと 1 つのステップにまとめる。ステップ名は `Check required variables`）。形式は小文字・数字・ハイフンの 3〜30 文字（`^[a-z0-9-]{3,30}$`）。リソース名の長さ制限（ロードバランサ名は 32 文字）に収まるよう、30 文字までにする
- `.github/workflows/deploy-backend.yml`: ワークフロー全体の `env` で `PROJECT_NAME: ${{ vars.PROJECT_NAME }}` を受け、各名前を組み立てる。`env` の値は他の `env` を参照できないため、組み立ては最初のステップ（`Resolve resource names`）で `$GITHUB_ENV` に書き出す

```bash
# 空チェック(正規表現はインフラ側と同じ)の後
echo "ECR_REPOSITORY=${PROJECT_NAME}-backend" >> "$GITHUB_ENV"
echo "ECS_CLUSTER=${PROJECT_NAME}-cluster" >> "$GITHUB_ENV"
echo "ECS_SERVICE=${PROJECT_NAME}-backend" >> "$GITHUB_ENV"
echo "ECS_MIGRATE_TASK_FAMILY=${PROJECT_NAME}-backend-migrate" >> "$GITHUB_ENV"
echo "ECS_CAPACITY_PROVIDER=${PROJECT_NAME}-cp" >> "$GITHUB_ENV"
```

  元の `env` の 5 つの直書き（`ECR_REPOSITORY` ほか）は削除する。`AWS_REGION` は残す
- `deploy-frontend.yml`: 名前の直書きはないので変更しない（フロントエンドのバケット名・配信 ID は、すでに Variable から取っている）

## 2. GitHub のリポジトリ名

- `infra/modules/github-actions/variables.tf`: 変数 `github_repository`（string、説明: `OIDC の信頼条件に使う「<オーナー>/<リポジトリ>」`）を足す。既定値は持たせない
- `infra/modules/github-actions/main.tf`: 信頼条件の `repo:ryoya-masuda-unirita/naw-server-fastapi-nextjs:ref:refs/heads/develop` を `"repo:${var.github_repository}:ref:refs/heads/develop"` にする（ブランチ `develop` は変えない）
- `infra/environments/dev/variables.tf`: 変数 `github_repository`（既定値 `"ryoya-masuda-unirita/naw-server-fastapi-nextjs"`）を足す。`main.tf` の `module "github_actions"` に渡す
- `infra/environments/dev/terraform.tfvars.example`: 変更しない（既定値があるため）

## 3. 既定タグ

- `infra/environments/dev/main.tf` の `provider "aws"` に `default_tags { tags = { Project = var.project_name } }` を足す
- `infra/modules/*/main.tf` の `tags = { ... }` から、`Project = var.project_name` の行（約 30 か所。インデントの揃え方が違う行を含む）を削除する。`Name` などほかのキーは残す。`tags` の中身が `Project` だけになるリソースがあれば、`tags` ブロックごと削除する
- 残すもの: `infra/modules/ecs/main.tf` の Auto Scaling グループの `tag { key = "Project" ... propagate_at_launch = true }`（既定タグは起動したインスタンスに伝播しないため）。起動テンプレートの `tag_specifications` も変更しない
- 注意: `tags` から `Project` を消すと、リソースの `tags` 属性には出なくなり、`tags_all`（既定タグ込み）に出る。実際に AWS 上に付くタグは変わらない

## 4. CloudFront 向けの IP 範囲

- `infra/modules/network/main.tf`: `data "aws_ec2_managed_prefix_list" "cloudfront"`（`name = "com.amazonaws.global.cloudfront.origin-facing"`）を足し、ALB のセキュリティグループのルールの `prefix_list_ids = ["pl-58a04531"]` を `[data.aws_ec2_managed_prefix_list.cloudfront.id]` にする。コメント（「ap-northeast-1 での」）は、「リージョンごとに ID が違うため名前から引く」に直す

## 5. `infra/route53/` の削除と手順書

- `git rm -r infra/route53/`
- `.github/workflows/deploy.yml`: paths-filter の `"!infra/route53/**"` を削除する
- `infra/README.md`:
  - ディレクトリ構成の図から `route53/` の行を削除する
  - 次の節をすべて削除する: `### Route53（もう不要）`、`## なぜRoute53だけ別ディレクトリ（別state）にしているか`、`## ムームードメイン側の設定（…）`、`## Route53のNSレコードとホストゾーンの料金`、末尾の注意の中の Route53 の項目
  - 1〜2 行の注記を残す: 「独自ドメイン（Route53・ACM・ワイルドカード）は #195 で廃止した。`infra/route53/` は #383 で削除した」
  - 新アカウントの手順の Variable の登録に、`PROJECT_NAME` を足す（`gh variable set PROJECT_NAME --body "naw-fastapi"`）。`terraform.tfvars` で `project_name` を変えた場合は、同じ値を登録すること、と書く
  - 手順 3 の `terraform.tfvars` の説明に、`project_name` を指定している場合の注意を足す

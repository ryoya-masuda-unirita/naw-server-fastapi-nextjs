# 02_基本設計

## 変更対象

1. **プロジェクト名**
   - 環境（dev）の変数の既定値から、Issue 番号を取る
   - インフラのデプロイのワークフローは、GitHub の Variable（`PROJECT_NAME`）を Terraform の変数として渡す。ローカルは既定値または `terraform.tfvars`
   - backend のデプロイのワークフローは、同じ Variable から、各リソース名を組み立てる。命名規則（`<プロジェクト名>-backend` など）は、インフラ側の名前の付け方と同じにする
2. **GitHub のリポジトリ名**: CI ロールのモジュールに入力として渡す。環境（dev）の変数にし、既定値はこのリポジトリの名前
3. **既定タグ**: 環境（dev）の provider に `Project` を設定する。各モジュールのリソースの手書きの `Project` タグを削除する。Auto Scaling グループのタグと、起動テンプレートのタグ指定は、既定タグが効かないため残す
4. **CloudFront 向けの IP 範囲**: プレフィックスリストを、名前（CloudFront のオリジン向けのマネージドリスト）から引くデータソースに置き換える
5. **`infra/route53/` の削除**: ディレクトリごと削除する。インフラの変更検出の除外条件、手順書のホストゾーン関連の節（別 state にした理由、構築手順、ネームサーバー登録、削除時の注意）も削除する。ドメイン廃止の経緯は、手順書に 1〜2 行だけ残す
6. **手順書**: 新アカウントの構築手順に、Variable の登録（`PROJECT_NAME`）を足す

## 画面 / API 変更概要

なし（インフラ・CI のみ）。

## 影響範囲

- **リソース名**: プロジェクト名の既定値が変わるため、新アカウントに作られるリソースの名前が変わる（Issue 番号がなくなる）。新アカウントへの新規構築が前提なので、再作成は問題にならない
- **タグ**: 実際に付くタグは、既定タグ込みで変わらない。リソースの属性としては、手書きのタグから既定タグ由来のタグに移る
- **CI**: backend のデプロイが、Variable に依存する。登録前は失敗する（原因が分かる形で）。インフラのデプロイは、Variable を渡す形に変わる
- **手元の設定**: `terraform.tfvars` の `project_name` を指定している場合は、新しい名前にそろえる必要がある
- **既存の環境への適用**: 旧名のリソースがある環境に適用すると、名前の違うリソースを新しく作ろうとする。この構成は新アカウント前提であり、既存環境の引き継ぎは想定しない（#382 と同じ）

## 移植方針

- 移植元は、プロバイダの既定タグでプロジェクト名を付けている。同じ方式にする
- 移植元では、リポジトリ名にあたる信頼条件は既存のロールに手動で設定している。このリポジトリは OIDC プロバイダとロールを作るため、変数にして既定値を持たせる
- プロジェクト名を CI で単一の Variable にするのは、このリポジトリ独自の判断。移植元は CI が名前を直書きしておらず、環境ごとの設定ファイルで渡している
- サブドメイン関連は関係しない。`infra/route53/` の削除は、廃止方針（#195）の仕上げ

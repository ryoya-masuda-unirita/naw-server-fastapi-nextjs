# 02_基本設計

## 変更対象

| 対象 | 変更 |
|---|---|
| infra（CloudFront） | エラーページ置き換え（403/404/405 → `index.html`）を削除。S3 のビヘイビアに SPA フォールバック用の CloudFront Function を付ける。`/auth/*` を backend に転送するビヘイビアを廃止し、`/backend/auth/*` を backend に転送するビヘイビア（プレフィックスを外す CloudFront Function 付き）を追加する |
| infra（CloudFront Function のテスト・CI） | 2 つの関数のロジックを Node.js で単体テストする。インフラのデプロイワークフローでも実行する |
| frontend（API クライアント） | 認証 API（`/auth/` で始まるパス）だけ、別のベース URL（環境変数）を前に付けて呼べるようにする。本番ビルドでは `/backend` を設定する |
| ドキュメント | infra の README の「API は `/api/*`・`/auth/*` で CloudFront が backend に転送する」記述を更新する |

backend は変更しない。

## 画面 / API 変更概要

### 現状の課題

| リクエスト | 現在の振り分け | 問題 |
|---|---|---|
| `GET /dashboard`（画面の再読み込み） | S3 → 403 → エラーページ置き換えで `index.html`（200） | 問題なし（置き換えの本来の目的） |
| `GET /api/rooms/xxx`（存在しない） | backend → 404 → **`index.html`（200）に置き換わる** | フロントが 404 を検知できず、HTML を JSON として読んで失敗する |
| `GET /api/admin/...`（権限なし） | backend → 403 → **`index.html`（200）に置き換わる** | 同上 |
| `GET /auth/login`（ログイン画面の再読み込み） | backend → 405 → `index.html`（200） | 置き換えで画面は出るが、API の 405 全般も置き換わる |
| `GET /auth/pw-reset`（画面の再読み込み） | backend → 404 → `index.html`（200） | 同上（404 置き換えに依存している） |

エラーページ置き換えはディストリビューション全体に効き、ビヘイビア（オリジン）ごとに分けられない。そのため「S3 の 403/404 だけ置き換える」ことは置き換え機能では実現できず、別の仕組みが必要になる。

### 論点1: SPA フォールバックを S3 側だけに効かせる方法

| 案 | 内容 | 評価 |
|---|---|---|
| 1-A（採用） | S3 のビヘイビアに viewer-request の CloudFront Function を付け、拡張子のないパス（画面パス）を `/index.html` に書き換えてから S3 に取りに行く。エラーページ置き換えは削除する | API のビヘイビアには関数が付かないため、API の応答はそのまま返る。SPA 配信で一般的な方式。関数のロジックは AWS に接続せず単体テストできる |
| 1-B | S3 の静的ウェブサイトホスティングのエラードキュメント機能を使う | ウェブサイトエンドポイントは OAC が使えず、バケットを公開する必要がある。不採用 |
| 1-C | Lambda@Edge（origin-response）で S3 の 403/404 のときだけ `index.html` を返す | us-east-1 へのデプロイ・IAM ロールが必要で、構成とコストが重い。不採用 |

1-A の書き換え規則:
- パスの最後の区切り（`/`）以降に `.` を含まないもの（`/`・`/dashboard`・`/auth/login` など）は `/index.html` に書き換える
- `.` を含むもの（`/assets/index-xxx.js`・`/i18n/ja.json`・`/favicon.ico` など）は書き換えない。存在しなければ S3 の 403 をそのまま返す（HTML を JS として読み込むことを防ぐ）
- クエリ文字列は書き換えない

### 論点2: 画面 `/auth/login` と認証 API `POST /auth/login` の衝突

backend の `/auth/` 配下の API はすべて POST（`/auth/login`・`/auth/login-key`・`/auth/logout`・`/auth/password/reset`）、React の `/auth/` 配下の画面は `/auth`・`/auth/login`・`/auth/pw-reset`。どちらも同じパスを使っている。

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| 2-A | `/auth/*` ビヘイビアに CloudFront Function を付け、`GET`/`HEAD`（または `Accept: text/html`）のリクエストだけオリジンを S3 に切り替え、パスを `/index.html` にする | フロント変更なし。URL も API パスも変わらない | オリジン切り替えは CloudFront Functions の比較的新しい機能で、AWS 上で確認できない今は動作を保証できない。`/auth/*` ビヘイビアは全ヘッダー（Host を含む）を転送する設定のため、そのまま S3 に回すと S3 側で失敗するおそれがあり、ビヘイビアの設定を API 用と画面用で両立させる必要がある。「GET は画面」という判定は backend に `GET /auth/...` の API が増えると壊れる |
| 2-B | React の画面ルートを `/auth` の外に移す（例: `/login`・`/pw-reset`） | infra は SPA フォールバックだけで済む。最も単純 | 画面 URL が移植元 Angular（`/auth/login` など）と変わり、移植の対応関係が崩れる。今後移植する `/auth/` 配下の画面もすべて読み替えが必要になる |
| 2-C（推奨・採用） | 認証 API だけ、フロントがプレフィックス（`/backend`）を付けて呼ぶ（`/backend/auth/login`）。CloudFront は `/backend/auth/*` を backend に転送し、viewer-request の CloudFront Function でプレフィックスを外す（backend には `/auth/login` で届く）。`/auth/*` の backend 転送は廃止し、`/auth/...` は画面として S3（論点1 の SPA フォールバック）で配信する | 画面 URL は移植元どおり。backend の API パスも変わらない。移植元 Angular の「認証 API だけ別のベース URL（`authBaseUrl`）で呼ぶ」作りと同じ形になる。パスの書き換えは CloudFront Functions の基本機能で、ロジックを単体テストできる。メソッドやヘッダーで判定しないため、backend に API が増えても壊れない | フロントの API クライアントと本番ビルドの設定に変更が入る。CloudFront Function が 2 つになる |
| 2-D | Lambda@Edge（origin-request）で `Accept: text/html` の GET だけ S3 に振り分ける | 柔軟 | 1-C と同じく構成とコストが重い。不採用 |

**推奨は 2-C。** 理由:
- 画面 URL・API パスとも移植元と一致したままにでき、移植元が別ドメインで実現していた分離を、単一ドメインのままパスのプレフィックスで再現できる
- AWS に接続できない現状でも、使う機能（パスの書き換え）が確実に動く範囲に収まり、ロジックを手元のテストで確認できる
- 2-A のようにメソッドやヘッダーで画面と API を判定しないため、将来 backend に API が増えても画面が壊れない

### 振り分け（変更後）

| パス | ビヘイビア | CloudFront Function | オリジン |
|---|---|---|---|
| `/api/*` | API 用（変更なし） | なし | backend（ALB） |
| `/backend/auth/*` | 認証 API 用（新設） | プレフィックス `/backend` を外す | backend（ALB）に `/auth/*` として届く |
| 上記以外（既定） | S3 用 | 拡張子のないパスを `/index.html` に書き換え | S3 |

エラーページ置き換え（403/404/405）は削除する。backend の応答は、エラーを含めてそのまま返る。

### フロントの API クライアント

- 認証 API（パスが `/auth/` で始まるもの）のベース URL を、環境変数で他の API とは別に指定できるようにする
- 未指定なら他の API と同じベース URL を使う。ローカル開発（`.env` で backend の URL を指定）の挙動は変わらない
- 本番ビルドの設定では `/backend` を指定する。認証 API は配信元と同じオリジンの `/backend/auth/...` で呼ばれる
- `/api/auth`（セッション取得）は `/api/` で始まるため、従来どおり `/api/*` ビヘイビアで backend に届く

### Cookie への影響

backend はセッション Cookie を `Path=/` で発行する（Starlette の既定値）。ログイン API を `/backend/auth/login` で呼んでも Cookie はサイト全体に送られるため、`/api/*` の呼び出しに影響しない。

## 影響範囲

- dev 環境の CloudFront（AWS 上には現在存在しないため、反映は dev 環境の復旧後の apply 時）
- フロントの認証 API の呼び出し URL（本番ビルドのみ。ローカル開発・テストは変わらない）
- 画面の直接表示・再読み込み（`/auth/...` を含む全画面）は S3 の SPA フォールバックで `index.html` が返る
- 存在しない静的ファイル（拡張子あり）は `index.html` ではなく S3 の 403 が返るようになる
- backend の変更はない

## 移植方針

- 移植元 `secuaigent-infra` は CloudFront で `/api/*` だけを backend に転送し、認証 API は別ドメイン（`authBaseUrl`）で呼ぶ。エラーページ置き換え（403/404）はディストリビューション全体に設定しているが、移植元では認証 API が同じディストリビューションを通らないため、`/api/*` の 403/404 も置き換わる同じ問題を潜在的に持っている
- このリポジトリは #195 でカスタムドメインを廃止して単一ドメインにしたため、移植元の「認証 API だけ別のベース URL」をパスのプレフィックスで再現する
- サブドメインによるテナント識別は使わない（#193・#195 の方針どおり）

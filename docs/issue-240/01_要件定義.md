# 01_要件定義

## 背景

- dev 環境は 1 つの CloudFront ディストリビューション（デフォルトドメイン `*.cloudfront.net`）で、フロント（S3）と backend（ALB）の両方を配信している。独自ドメイン・サブドメインは #195 で廃止した
- SPA の画面パス（`/dashboard` など）を直接開いたときに S3 が 403/404 を返すため、ディストリビューション全体の「エラーページ置き換え」で 403/404 を `index.html`（200）に置き換えている
- エラーページ置き換えはオリジンを区別しないため、backend の API が返した 403（権限なし）・404（対象なし）・405 も HTML（200）に置き換わる。フロントは API のエラーを検知できず、HTML を JSON として読もうとして失敗する
- React の画面 `/auth/login`・`/auth/pw-reset` は backend の認証 API（`POST /auth/login` など）と同じ `/auth/` 配下にあり、CloudFront は `/auth/*` を backend に転送している。画面として GET（ログアウト時の全画面遷移・再読み込み）すると backend が 405 を返すため、#223 で 405 も置き換え対象に加えていた
- 移植元（`secuaigent/client`）は認証 API を画面とは別ドメイン（`authBaseUrl`）で呼んでおり、画面と API のパスが衝突しない。このリポジトリは単一ドメインにしたため衝突が起きている

## 機能要件

1. backend（ALB）に転送した API の応答（403/404/405 などのエラーを含む）は、ステータス・本文とも置き換えずにそのまま返す
2. SPA の画面パス（拡張子のないパス）を直接開く・再読み込みしたときは、React の `index.html` を 200 で返す
3. `/auth/login`・`/auth/pw-reset`・`/auth` を画面として GET したとき（全画面遷移・再読み込み・ブックマーク）、React の画面を返す
4. React からの認証 API（ログイン・ログアウト・パスワードリセット・キーログイン）は dev 環境でも backend に届き、これまでどおりセッション Cookie で認証できる
5. ローカル開発（Vite 開発サーバーから backend を直接呼ぶ）の挙動は変えない
6. 静的ファイル（JS・CSS・画像・翻訳 JSON など、拡張子のあるパス）が存在しない場合は `index.html` に置き換えない（HTML を JS として読み込むのを防ぐ）

## 非機能要件

- dev 環境は AWS 上に存在しないため、AWS に接続する確認（plan / apply）は行わない。Terraform はフォーマット・構文検証で確認する
- CloudFront 上で動かすパス書き換えのロジックは、AWS に接続せずに単体で検証できる形にする
- フロントの変更はテスト・lint・型チェック・ビルドを通す
- backend（API のパス・仕様）は変更しない（移植元 Spring Boot の API 仕様どおりのまま）

## スコープ外

- 5xx をキャッシュしない設定（移植元 `secuaigent-infra` の NAW-1338 相当）。本 Issue とは別の課題のため対象外
- 実環境（AWS）での動作確認。dev 環境が復旧してから行う
- ログイン画面まわりの他の未対応事項（テナントID入力欄など）

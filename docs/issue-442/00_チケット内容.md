# messages に索引を足す（room_id と parent_id）

## 概要

Issue #442。`messages` に、`(tenant_id, room_id)` で引ける索引を足す。計測で、**削除が遅い本当の原因は `parent_id`（自己参照の外部キー、`ON DELETE CASCADE`）の索引がないこと**と分かったため、`parent_id` の索引も足すかを、第 1 承認で決める。どちらも、移植元（Liquibase）にはない、こちら独自の改善。

## 背景

- `messages` の索引は、主キーと `(id, tenant_id)` の一意制約だけ
- `room_id` を使うクエリ: ルームのメッセージ一覧（`message_repository`）、ルームのライブラリ一覧（`library_repository`）。どちらも `tenant_id` と `room_id` の両方で絞り込む。外部キー `fk_messages_room_id`（`(room_id, tenant_id)` → `rooms`、`ON DELETE CASCADE`）の探索も、両方の等価条件
- `parent_id` は、`messages.id` への外部キー（`ON DELETE CASCADE`）。メッセージ・ルームを消すと、消す行ごとに「`parent_id` が自分の行」を探す。索引がないと、そのたびに `messages` 全体を走査する

## 計測結果（450,000 メッセージ、本文 450,000 件、ルーム 22,500、20 メッセージの一本道、使い捨ての PostgreSQL 18、`EXPLAIN ANALYZE`）

| クエリ | 索引なし | `(tenant_id, room_id)` | さらに `parent_id` |
|---|---|---|---|
| ルームのメッセージ一覧 | 12.2 ms（`messages` を Parallel Seq Scan） | 0.19 ms（Index Scan） | 0.15 ms |
| ルーム 1 件の削除（CASCADE） | 421.8 ms | 398.7 ms | **1.4 ms** |
| メッセージ 1 件の削除（`parent_id` の CASCADE） | 328.2 ms | 351.5 ms | **0.3 ms** |

- 索引のサイズ: `(tenant_id, room_id)` が 3.6 MB（`messages` は 29 MB）
- **#433 の PR で書いた「メッセージ 1 件の削除 84 ms → 13 ms」は、その計測のデータに `parent_id` がなかった（すべて NULL）ための数字**。`parent_id` がつながった実際の形では、削除は、`message_contents` の索引を足しても、`parent_id` の走査が支配的で数百 ms かかる

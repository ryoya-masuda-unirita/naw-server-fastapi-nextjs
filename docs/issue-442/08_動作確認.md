# 08_動作確認

## 確認環境
- ローカル（macOS）。性能の確認は、使い捨ての PostgreSQL 18（Docker、`tmpfs`、確認後に停止）。他のセッションの PostgreSQL には触れていない。AWS・インフラには触れていない（費用なし）
- データ: 3 テナント × 7,500 ルーム × 20 メッセージ = **450,000 メッセージ**（各ルーム内は、直前のメッセージを親にした一本道）、ルーム 22,500、本文 450,000 件。外部キーの検査を切って、`generate_series` で作った

## 確認結果

| No | 確認内容 | 結果 |
|---|---|---|
| 1 | **実装前の失敗** | 新規テスト 4 件がすべて失敗 |
| 2 | 実装後 | 4 件すべて成功。サーバー全体 **1471 件すべて成功**。`ruff format --check`・`ruff check`・`mypy app` エラーなし |
| 3 | PostgreSQL でマイグレーション | 手で作った索引を消した状態から、`upgrade head`（`issue433` → `issue442`）で 2 つの索引ができ、`downgrade -1` で 0 件になり、`upgrade head` でもう一度できる |
| 4 | 実行計画（`EXPLAIN ANALYZE`） | 下の表 |

| クエリ | 索引なし | マイグレーションの索引 |
|---|---|---|
| ルームのメッセージ一覧 | 12.2 ms（`messages` を Parallel Seq Scan） | 0.25 ms（Index Scan） |
| ルーム 1 件の削除（CASCADE） | 421.8 ms | 1.5 ms |
| メッセージ 1 件の削除（`parent_id` の CASCADE） | 328.2 ms | 0.35 ms |

- 索引のサイズ: `(tenant_id, room_id)` が 3.6 MB、`parent_id` が 13 MB（`messages` 本体は 29 MB）
- 途中の計測で、`(tenant_id, room_id)` だけでは、削除は変わらない（ルーム 399 ms、メッセージ 352 ms）ことが分かり、`parent_id` を足すことにした

## 確認の途中で分かったこと
- **#433 の PR の「メッセージ削除 84 ms → 13 ms」は、そのときの計測データの `parent_id` がすべて NULL だったための数字**。実際の形（メッセージがつながっている）では、削除は `parent_id` の走査が支配的。#433 の一覧・本文取得（169〜201 ms → 10〜12 ms）の効果は、正しい
- 前回と同じく、zsh では、スペースを含む文字列の変数をそのままコマンドにできない（関数にした）

## 未確認事項
- **実データの規模・分布では確認していない**。計測データは、ルームごとに 20 メッセージの一本道。編集・再生成で枝分かれするデータや、ルームあたりのメッセージが多いデータでは、確認していない
- **本番の `CREATE INDEX` の所要時間・書き込みの待ち時間、書き込みへの影響は、計測していない**
- **`messages` 以外の、索引のない外部キー**（`libraries.message_id`・`token_usages.message_id`・`message_files.message_id`・`message_feedbacks` など）が、削除に与える影響は、計測していない
- **実環境へは適用していない**（Deploy は旧環境向けで、AWS の OIDC ログインで失敗する）

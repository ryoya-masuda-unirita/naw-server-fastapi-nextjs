# 01_要件定義

## 背景

issue-88（LLMチャット・埋め込みAPI移植）・issue-93（メッセージ送信API移植）では、SAAS_RAGタイプのアシスタント（ベクトル検索付き）は意図的にスコープ外とされ、SAAS_CHATタイプの基本チャットのみが移植された。

移植元（Spring Boot）を調査した結果、以下が判明した。

- ベクトルDB製品はAzure AI Search（Spring AIの`AzureVectorStore`経由）。テナントごとに1つのAzure Searchインデックスを持ち、インデックス名は「アシスタントに紐づくインデックス（`Index`エンティティ）のID」ではなく「ベクトルDB接続情報（VDBタイプのテナントエンドポイント）が属するテナントID」である。
- RAG分岐が実際に使われているのはメッセージ送信のストリーミング経路（`MessageService.buildRagContext`）のみ。非ストリーミング版（`AdvisorFactory`使用）はどのコントローラからも呼ばれていないデッドコードのため移植対象外とする。
- LLMチャットAPI（`LlmChatService.java`、移植先`llm_chat_service.py`）はアシスタント/インデックスの概念を持たない汎用チャットAPI（deployName直接指定）であり、そもそもRAG分岐が存在しない。Issue本文のタイトルには「Message送信・LLM Chat両方」とあるが、調査の結果**対応が必要なのは`message_service.py`のみ**と判断する。

## 機能要件

- `message_service.py`の`stream_message_content`が、アシスタント種別`SAAS_RAG`のメッセージ送信を受け付けること（現状は400エラーで拒否している）。
- `SAAS_RAG`のメッセージ送信時、以下の順でRAGコンテキストを構築すること。
  1. アシスタントに紐づくインデックス（`assistants.index_id`）を解決する。紐付けがない場合は400エラーとする。
  2. アシスタントに紐づくAzure OpenAI Chatエンドポイント・AIモデルを解決する（既存のSAAS_CHATと同じ解決ロジックを流用する）。
  3. インデックスに紐づく埋め込み（Azure OpenAI Embedding）エンドポイントを解決する。紐付けがない場合は400エラーとする。
  4. テナントのベクトルDB接続情報（VDBタイプのテナントエンドポイント）を解決する。存在しない場合は400エラーとする。
  5. ユーザー入力をベクトル化（Embeddings API呼び出し）し、ベクトルDB（Azure AI Search）へ類似検索を実行する。
  6. 検索結果のメタデータ（`fileUniqueId`）に対応するファイルをテナント内から解決できたものだけをコンテキストとして採用し、システムメッセージとして会話履歴の先頭に追加する。採用したファイルの`reference`を参照ファイルパスとして保持する。
  7. ベクトル検索・ファイル解決に失敗した場合は400エラーとする。
- ストリーミング完了後の永続化で、構築したRAGコンテキスト・参照ファイルパス・埋め込みトークン数（消費クレジット換算含む）を保存すること。
- 新規にベクトルDBクライアント層（Azure AI Search呼び出し）を実装すること。

## 非機能要件

- ベクトルDB・埋め込みAPIへの呼び出しはいずれもストリーミング開始前（SSEレスポンスを返す前）に完了させ、失敗時は通常のHTTPエラー（400）として返すこと（SSE開始後のエラーイベントにしない）。既存のSAAS_CHATと同じ「事前検証はストリーミング開始前」という設計方針を踏襲する。
- ベクトルDBクライアント層は`core/`に配置し、`services/`からはこのクライアントのみをモックすればテストできるようにすること（既存の`AzureLlmChatClient`/`AzureLlmEmbeddingClient`と同じ方針）。
- ファイル解決はテナント内の対象ファイルIDをまとめて1クエリで取得し、検索結果件数分の個別クエリ（N+1）を発生させないこと。

## スコープ外

- 非ストリーミング版メッセージ送信・再生成（`messageContentId`指定）へのRAG対応（issue-93と同様、本Issueでも対象外）
- ファイルアップロード時のベクトルDBへの登録（インデックス作成・ドキュメント追加、移植元`FileService.connectToVectorStore`相当）。File/Index管理API自体が本リポジトリ未移植のため別Issueで対応する。ベクトル検索対象のAzure Searchインデックスは既に存在する前提とする。
- Azure Searchインデックスのスキーマ自動作成（移植元`AzureVectorStore`の`initializeSchema(true)`相当）。既存インデックスへの検索のみを実装する。
- `llm_chat_service.py`（汎用LLMチャットAPI）へのRAG対応（そもそも移植元にRAG分岐が存在しないため）
- ライブラリ生成（createLibrary）・添付ファイル・toolsとRAGの組み合わせ（いずれも既存のSAAS_CHATパスも含め未実装のため、本Issueでも対象外のまま据え置く）

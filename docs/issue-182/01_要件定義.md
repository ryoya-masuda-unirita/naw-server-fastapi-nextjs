# 01_要件定義

## 背景

### 原因の切り分け結果

調査の結果、原因はフロントエンドの親メッセージ決定ロジックではなく、**バックエンドのメッセージ送信（アシスタント応答生成）APIのリクエスト形式が移植元と異なり、クライアントからの送信が常に入力エラーで失敗していること**と判断した。

1. フロントエンド（移植元クライアントのコピー）は、新規送信時の親メッセージを「画面に表示されている会話スレッドの末尾のメッセージ」として決める。表示スレッドは、メッセージ一覧取得で得たメッセージの親子関係を根から辿り、各メッセージについてメッセージ内容一覧取得で得た本文（質問・回答）を当てはめて組み立てる。**本文が存在しないメッセージは表示スレッドに現れない。**
2. フロントエンドは、メッセージ送信（アシスタント応答生成）APIを、移植元サーバーの仕様どおり `multipart/form-data`（JSON の本体部 `textData` ＋添付ファイル部）で呼び出す。
3. 移植元サーバーはこの形式を受け付けるが、本ポートのバックエンドは JSON ボディのみを受け付けるため、フロントエンドからの送信は常に入力エラー（HTTP 422）になる。その結果、**質問・回答の本文（メッセージ内容）が一切保存されない**。
4. 同一ページ内ではフロントエンドが送信したメッセージを画面上の状態として保持しているため、次の送信の親は直前のメッセージになる（Issue の「同一セッション内は正しくチェインされる」に一致）。
5. ページを開き直すとサーバーから会話を読み直すが、本文が保存されていないメッセージは表示スレッドに現れない。表示スレッドの末尾は「本文を持つ最後のメッセージ」＝シードデータで本文を持つ最初のメッセージになり、これが次の送信の親になる（Issue の「10件中8件が最初のメッセージを親に持つ」に一致）。

メッセージ作成 API 自体の親メッセージ保存処理（指定された親が存在すれば保存する）は移植元と同じ挙動であり、問題はない。メッセージ一覧取得の並び順も移植元と同じく指定なしで、親の決定には影響しない（親子関係を辿って組み立てるため）。

### 実測による裏付け

- 現行バックエンドへ、フロントエンドと同じ形式（`textData` を `application/json` のファイル部として送る `multipart/form-data`）でメッセージ送信 API を呼ぶと HTTP 422 になることを自動テスト環境で確認した。
- Issue #166 の E2E テストは「回答欄が空でないこと」のみを確認しており、送信失敗時のエラー文言でも合格してしまうため、この不具合を検出できていなかった。

## 機能要件

1. メッセージ送信（アシスタント応答生成）API は、移植元と同じく `multipart/form-data` でリクエストを受け付ける。
   - `textData`: リクエスト本体（JSON）。必須。ファイル部（`application/json` の Blob）として送られた場合と、通常のフォーム値として送られた場合の両方を受け付ける。
   - `attachmentFiles`: 今回の質問に添付するファイル（複数可・任意）。
   - `historyAttachmentFiles`: 過去の会話に添付されていたファイル（複数可・任意）。
2. `textData` のフィールドは移植元のリクエスト定義に合わせる。
   - `assistantId` / `messageId` / `messageContentId` / `additionalPrompt` / `userInput` / `historyMessages` / `tools` / `createLibrary` / `response_format`
   - `historyMessages` の各要素は `type`（`SYSTEM` / `ASSISTANT` / `USER`）・`content`・`attachmentsCount` とする。
3. `textData` が JSON として解釈できない、または必須項目の不足・相関チェック違反がある場合は、従来どおり入力エラー（HTTP 422）を返す。
4. 上記により、フロントエンドから送信したメッセージの本文（質問・回答）が保存され、ページを開き直しても会話スレッドの末尾が直前のメッセージになる。その結果、次に送信したメッセージの親は直前のメッセージになる。

## 非機能要件

- 送信以降の処理（アシスタント解決、クレジット上限チェック、LLM 呼び出し、本文・添付ファイル・トークン使用量の保存）は変更しない。
- マイグレーションは発生させない。

## スコープ外

- ストリーミング応答（SSE）のイベント形式の移植元との差異。フロントエンドは移植元形式のイベントを前提としているため、本 Issue の対応後も送信直後の画面では回答表示がエラー扱いになりうる。これは編集・再送信の不具合（Issue #183）の原因でもあるため、Issue #183 で対応する。本 Issue の対応で本文は保存されるため、ページを開き直した後の親メッセージ決定は正しくなる。
- フロントエンド（`frontend-angular/`・`frontend/`）の変更。
- LLM Chat API（汎用チャット API）のリクエスト形式。移植元は同様に `multipart/form-data` だが、フロントエンドからは呼ばれておらず本 Issue の症状に関係しないため対象外とする（形式差異は会話内で報告し、対応要否はユーザー判断とする）。

# 02_基本設計

## 変更対象

- テナントID解決ユーティリティ（サブドメイン抽出を行っている2系統の実装。一方は共通のテナント解決処理、もう一方はユーザー管理一覧機能専用の別実装）
- HTTPリクエストへのテナントIDヘッダ付与処理（インターセプター、およびSSE通信で同種の処理を行っている箇所）
- ログイン画面（フォーム・型定義・送信処理）
- テナントIDのセッション保存キーへ直接アクセスしている箇所（定数を経由していない箇所を含む）

## 画面 / API 変更概要

- ログイン画面に、ユーザー名・パスワードと並ぶ入力項目としてテナントIDを追加する。
- ログインAPI呼び出し時のリクエスト内容にテナントIDを含める。
- サブドメインからテナントIDを推測する処理は削除し、入力値またはセッション保存値のみを参照する構成に変更する。
- URLクエリ経由でテナントIDをセッションに保存する既存の代替経路（サブドメイン非依存）は変更せず維持する。

## 影響範囲

- ログイン画面本体
- テナントIDを利用する全てのAPIリクエスト（テナント解決処理を共通で参照している箇所）
- ユーザー管理一覧機能（別実装のテナント解決ロジックを利用している）
- ログイン失敗時・認証エラー時にテナント情報をセッションから削除する処理
- モックAPIハンドラ（テナント保存キーへの直接アクセス箇所を含む）
- 上記に対応する既存の単体テスト一式

## 移植方針

- 本Issueは移植（Angular→React）ではなく、frontend-angular内の既存実装の改修である。
- 既存の「セッション保存値を優先し、無ければ別経路で解決する」という2段構成の考え方は維持しつつ、フォールバック先をサブドメインからログインフォームの入力値に置き換える。
- 重複するテナント解決ロジックは共通実装に一本化する。ユーザー管理一覧機能専用の実装は廃止し、共通実装を利用する形に置き換える。無効値判定などサブドメイン非依存の差分ロジックのみ必要に応じて共通実装側に統合する。
- セッション保存キーへのアクセスは、既存で定義済みの共通定数経由に統一する。

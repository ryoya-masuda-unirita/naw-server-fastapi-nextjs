# 01_要件定義

## 背景

- frontend-angular（バックエンド動作確認用フロントエンド）は現在、ログイン時のテナント識別を「アクセスしたホスト名のサブドメイン部分」から推測する方式を採っている。
- サブドメインは実質この用途以外に使われておらず、ローカル開発・動作確認のたびにサブドメイン付きホスト名でアクセスする必要があるなど運用が煩雑になっている。
- バックエンドはテナント識別を常にリクエストヘッダで受け取る設計になっており、サブドメインの有無に依存していない。フロントエンド側の実装だけがサブドメインに依存している状態。
- 通常ログイン画面には現状テナントIDの入力手段が無く、サブドメイン以外でテナントを識別する経路が用意されていない（別途、URLクエリ経由でテナントIDをセッションに保存する代替経路は一部の画面にのみ存在する）。

## 機能要件

- ログイン画面から、ユーザーがテナントIDを直接入力してログインできること。テナントID入力欄は必須項目とする。
- 入力されたテナントIDは、以降のAPIリクエストで一貫してテナント識別に使われること。
- ホスト名（サブドメイン）からテナントIDを推測する処理を廃止すること。
- サブドメイン推測ロジックが重複して存在する既存の2つの実装は、共通実装に一本化し、機能固有実装は廃止すること。
- URLクエリ経由でテナントIDをセッションに保存する既存の代替経路（サブドメインに依存しない仕組み）は、サブドメイン廃止後も引き続き機能すること。

## 非機能要件

- 既存のログインフォームの入力バリデーション方式（必須・文字数制限等）と一貫したパターンでテナントID入力欄を実装すること。
- テナントID関連のセッション情報（保存キー）へのアクセス箇所は、共通の定数を通して行い、直接の文字列リテラルによるアクセスを残さないこと。

## スコープ外

- バックエンド（FastAPI）側の変更（既にヘッダ経由でのテナント識別に対応済みのため対象外）。
- インフラのワイルドカードサブドメイン前提の証明書・CDN設定の見直し（別Issueで検討）。
- React移植版（frontend/）への対応。

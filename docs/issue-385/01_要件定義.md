# 01_要件定義

## 背景

- 現在の RDS は、保存時の暗号化・バックアップ・自動のマイナーバージョン更新・パラメータグループが設定されておらず、エンジンのバージョンも指定されていない（作成時点の既定のバージョンが入る）。バージョンを指定しないと、いつ作っても同じ構成になる保証がない
- ElastiCache は、エンジンのバージョン・保存時の暗号化・ポートが明示されていない。移植元は、これらを明示している
- ECR は、イメージのスキャンはあるが、古いイメージの削除ルールがない。backend のデプロイのたびに `latest` タグが付け替わるため、タグの外れたイメージが蓄積し続ける
- 移植元のエンジンバージョンの既定値（PostgreSQL 16.4）は、同じ移植元のパラメータグループ（PostgreSQL 18 用）と食い違っており、さらに、そのバージョンは現在のリージョンでは存在しない。そのまま写すと、`apply` が失敗する
- 開発環境（ローカル）は PostgreSQL 18 と Redis 7 で動いており、本番相当の環境をそれに合わせておくと、環境差による不具合を避けられる

## 機能要件

1. RDS（PostgreSQL）
   - 保存時の暗号化を有効にすること
   - 自動バックアップの保持期間を 7 日にすること
   - 自動のマイナーバージョン更新を有効にすること
   - エンジンのバージョンを明示し、**PostgreSQL 18 系**にすること（ローカルと同じ。移植元のパラメータグループと同じ）。マイナーバージョンは指定せず、メジャー 18 の最新を使う
   - パラメータグループを作り、エンジンと同じファミリ（18 系）にすること。パラメータの値は、移植元と同じく、既定のまま（空）にする
   - ストレージ、インスタンスクラス、DB 名、ユーザー名、マルチ AZ なし、公開なし、最終スナップショットなし、削除保護なし、は、現状のまま変えない
2. ElastiCache（Redis）
   - エンジンのバージョンを 7.1 にすること
   - 保存時の暗号化を有効にすること。通信の暗号化は、backend が平文の接続を使っているため、無効のままにすること
   - ポートを 6379 と明示すること。自動フェイルオーバーは、1 ノード構成のため、無効と明示する
   - ノードの種類・数は、現状のまま変えない
3. ECR
   - タグの付いていないイメージを、プッシュから 30 日後に削除するルールを足すこと
   - イメージのスキャン（プッシュ時）、タグの上書き可、destroy 時にイメージごと削除、は、現状のまま維持する
4. 変更後の設定値は、変数で変えられること（バージョン、バックアップの保持日数など。移植元と同じく、既定値を持つ）
5. 手順書に、変更内容と、既存の環境へ適用した場合の影響（RDS・ElastiCache の再作成）を書くこと

## 非機能要件

- エンジンのバージョンは、`oic` のリージョンで実際に提供されていること（読み取りで確認済み）
- DB への接続情報（ホスト・ユーザー・DB 名）の出力は変えない（ECS の環境変数が使っているため）
- `fmt`・`validate` が通ること。`plan` で、変更されるリソースと属性が想定どおりであること
- 費用: 暗号化とパラメータグループに追加費用はない。バックアップは、保持期間が増える分の保管量がかかりうる。デプロイ（`apply`）はしない

## スコープ外

- DB パスワードの自動生成と Secrets Manager（#386）、CloudFront（#387）、CI ロールの権限（#388）
- RDS のインスタンスクラス・ストレージ・マルチ AZ の見直し、ElastiCache のノード構成の見直し
- pgvector の拡張の作成と、アプリ用のロールの作成（`scripts/db-init`）。移植元の Java サーバーが使うもので、この Python のサーバーは、PostgreSQL の pgvector を使っていない（ベクトル検索は別の仕組み）。必要になったら別の Issue で扱う
- 既存の環境からの移行（新アカウントへの新規構築が前提）

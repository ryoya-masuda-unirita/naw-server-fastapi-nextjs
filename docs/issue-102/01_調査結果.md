# 01_調査結果

調査日: 2026-11-23。参照リポジトリは `secuaigent-ref`（`origin/develop` = `599384d81`、`git fetch` 後に detached）。パスは特記なき限り `secuaigent-ref` 配下（移植元）またはこのリポジトリ（移植先）。

## 結論（先に）

1. **移植元には「サーバーが SECURE のチャットを送る・回答を生成する」実装がない。** SECURE の質問は、ブラウザから顧客社内の server-local へ直接送る設計で、クラウドの server は「送り先と API キーを教えるだけ」。Issue #102 の想定スコープ「backend から ローカルLLM へチャット呼び出し」は、移植元の設計と食い違っている。
2. **過去の調査コメントの「フロントに SECURE 送信フローはない」は誤り。** Angular の `messages.service.ts` は送信・編集・再生成のすべてで SECURE をローカルへ振り分けている（下記 a）。
3. **ブラウザ → server-local → Waha!（エミュレーター）→ アダプタの経路は、移植先にすでに揃っている**（#210・#274・#289・#298〜#300）。#289 の `08_動作確認.md` で、実物の server-local に対する通しのテストが通っている（NAW 側は MSW）。
4. backend の SECURE を 400 にする箇所は、移植元と同じ挙動で、**現時点で変更不要**。足りないのは「実物の backend を含めた通しの確認」と、テナント ID の扱いなど周辺の確認（下記 c）。

## (a) 移植元 Angular が SECURE のときオンプレへ直接つなぐ仕組みと範囲

### 仕組み

- `client/src/app/features/chat/utils/message-content-endpoint.resolver.ts`
  - `resolveAssistantEndpoint(assistant)`: アシスタントが `SECURE` 以外なら `{kind: 'naw'}`。`SECURE` なら `endpoints` から `LOCAL_SERVER`（なければ先頭）を選び、`destination`・`apiKey` が空なら `invalid`（`no_endpoint` / `missing_destination` / `missing_api_key`）、そろっていれば `{kind: 'local', contentsUrl, contentUrl, apiKey}`。
  - 組み立てる URL: `{destination}/api/messages/contents`（取得）、`{destination}/api/messages/content`（送信 SSE）、`{destination}/api/libraries/{id}/content`・`/api/libraries/{id}`（ライブラリ）。
  - `resolveAssistantModel`: エンドポイントの `model`（なければアシスタント直下の `model`）。SECURE では textData の `assistantId` に **model（Waha! のサービス ID）を入れ替えて**送る。
- `client/src/app/features/chat/services/messages.service.ts` の `prepareSecureStreamContext`（L842〜）
  - 履歴を textData に付け、`getAccessTokenForLocalContent()`（`GET /api/auth` の `token`。Waha! → アダプタがクラウドの `/api/llm/chat` を呼ぶための委譲トークン）と `tenantId` を textData に入れ、`target: {kind: 'local', contentUrl, apiKey}` を返す。
  - 認証ヘッダーは `X-Server-Auth-Key`（server-local 側は `X-SERVER-AUTH-KEY`）。Cookie と `X-Tenant-ID` は付けない。

### 対象範囲（取得のみ**ではない**。送信もローカル）

`prepareSecureStreamContext` は次の 3 箇所すべてから呼ばれる（`messages.service.ts`）。

| 呼び出し箇所 | 操作 |
|---|---|
| L316 | 新規送信 |
| L571 | 編集して再送信 |
| L647 | 再生成（ライブラリ再生成を含む） |

加えて、メッセージ内容の取得（`message-contents-api.service`）、ライブラリ本文の取得（`library-content-api.service.ts`）、ビューワー（`viewer.service.ts`）もローカルへ向く。つまり SECURE では「質問の送信・回答の SSE 受信・本文の取得」がすべてブラウザ ⇔ server-local で完結し、クラウドの server に質問・回答の本文は渡らない。

## (b) 移植元の server / server-local に SECURE のチャット送信・回答生成があるか（最新 develop）

### server（Spring Boot）

- `server/src/main/java/com/example/naw/service/MessageService.java`
  - L306（`createMessageContent`、同期系）・L486（`resolveStreamContext`、SSE 系）: `case SECURE -> throw new BadRequestException("セキュアタイプのアシスタントが使えません")`。**SECURE の回答生成は server にない**（意図的。ブラウザがローカルへ送るため、クラウドには来ない）。
  - `AssistantService.java` L351: SECURE は `LOCAL_SERVER` エンドポイントだけ紐づけ可。
  - `GetMessagesViewModel.java` L15〜30: SECURE かつ `LOCAL_SERVER` のエンドポイントにだけ `apiKey` を返し、それ以外は空文字。これが「クラウドは送り先を教えるだけ」の実体。
- `server/src/main/java/com/example/naw/api/LlmController.java`（`/api/llm/chat`・`/api/llm/embedding`）と `LlmChatService.java`
  - 説明文に「**本 API は SECURE 経路（Waha）専用**。libraries への保存は行わない。スタブ作成と title 更新は local-server が担当」とある。
  - これは SECURE の回答生成ではなく、**オンプレ側のアダプタが LLM の代わりに呼ぶクラウド側の LLM 中継**（アダプタの `SecuAiGent` ベンダー）。`persistTokenUsageInNewTransaction` でトークン使用量はクラウドに記録される。

### server-local（`secuaigent-server-local`）

- `interfaces/MessageController.java`: `POST /api/messages/content`（SSE）・`/content/sync`・`/content/stream`・`/contents`（取得）・`DELETE /api/messages/{id}`。
- `service/ServiceRunService.java`: Waha! の `startsession` → `upload` → `execute` → `result` → `download` を呼ぶ（回答の生成は Waha! 側のワークフロー＝アダプタ）。
- つまり**回答生成の実体は Waha! + `generative-ai-adapter`**（Java）で、server-local はそれを呼んで SSE に整える役。

### まとめ

| 層 | SECURE の送信・回答生成 |
|---|---|
| Angular | あり（送信・編集・再生成・取得・ライブラリ。すべてローカルへ） |
| server | なし（400。送り先と API キーを返すだけ。`/api/llm/chat` はアダプタ用の中継） |
| server-local | あり（Waha! を呼び SSE で返す） |
| Waha! + generative-ai-adapter | あり（実際の生成。LLM 直接 or クラウドの `/api/llm/chat` 経由） |

### 足りない・未確認の部分

1. **実物の backend を含めた通しの確認がない。** #289 は「実物の backend（`GET /api/auth` の `token`）との通しはコードで確認しただけ」と明記（`docs/issue-289/08_動作確認.md` 未確認事項）。さらに、エミュレーターが SecuAiGent ベンダーで backend の `/auth/login-key` → `/api/llm/chat` を呼び、トークン使用量が記録されるところまでの通しも見ていない。
2. **テナント ID の経路。** Angular は textData に `tenantId: resolveTenantId()` を入れる（サブドメイン由来のフォールバックを持つ）。このリポジトリはサブドメインを廃止している（`CLAUDE.md`）。React でこの `tenantId` を何から取るか、server-local → NAW（`X-Tenant-ID`）・アダプタ → `/auth/login-key` の `X-Tenant-ID` に正しく渡るかは、実物で未確認。`frontend/src/store/messages-store.ts`・`auth-store.ts` が `tenantId` を扱っているが、textData の `tenantId` に何が入るかは本調査では読み切っていない（要確認）。
3. **backend 側のガードが SSE 系だけ。** 移植元は同期系（Java L306）・SSE 系（L486）の 2 箇所で SECURE を 400 にする。backend は SSE 系（`message_service.py` L922）にあるが、同期系に相当する経路（`createMessageContent` 相当）が backend にあるかは未確認。
4. **トークン使用量・クレジットの SECURE の扱い。** 移植元は `/api/llm/chat`（SecuAiGent ベンダー経由）でだけクラウドに記録される。LLM を直接呼ぶ構成（OpenAI・Azure をアダプタが直接呼ぶ）ではクラウドには記録されない。これは移植元の設計どおりで、backend 側に足すものはないが、仕様として確認する価値がある（要確認）。
5. **Issue #102 の記載自体が古い。** 移植元パス（`~/Documents/naw-server`）、参照調査（`docs/調査結果/20260711.md`）、「`llm_chat_service.py` へ SECURE を足す」想定は、現在の設計と合わない。

## 1. 経路（ブラウザ相当 → server-local → エミュレーター → SSE）

- `GET /api/messages?roomId=…` の `assistants[].endpoints` は、SECURE の LOCAL_SERVER に `destination = http://localhost:57110/`・`apiKey = onprem-local-key`、`model = onprem-chat` を返す（#309）
- backend の `POST /api/messages/content` に SECURE のメッセージを送ると、**400**（`Unsupported assistant type (SECURE is not supported yet)`）。移植元と同じで意図どおり
- server-local の `POST /api/messages/content`（`X-SERVER-AUTH-KEY: onprem-local-key`）に、`textData`（`assistantId`=model、`messageId`、`userInput`、`accessToken`、`tenantId`）を送ると、SSE で `reasoning_delta` → `text_delta` → `message_stop` → `message_content`（`status: OK`、回答 = 質問の Echo）が返る
- ブラウザの `Origin: http://localhost:57101` からのプリフライト（`x-server-auth-key,content-type`）は、server-local が 200 で `access-control-allow-origin` を返す。認証キーが違うと 401（CORS ヘッダー付き）

## 2. `GET /api/auth` の token と Bearer

- `GET /api/auth`（Cookie + `X-Tenant-ID`）は `token`（JWT。`sub` = ログイン ID、`tenantId`）を返す。レスポンスに `tenantId` はない
- その token を `accessToken` に入れ、`createLibrary: true` で server-local に送ると、server-local が backend の `POST /api/libraries`（Bearer、`X-Tenant-ID`）を呼んで 200。`libraries` にメッセージ ID 付きのスタブが作られ、SSE の先頭に `library_id` が出る
- `accessToken` が `SecuAiGent` ベンダーの `/api/llm/chat` に使われる（エミュレーターのログ `secuaigent auth: using access token from textData`）。このとき `/auth/login-key` は呼ばれない

## 3. `SecuAiGent` ベンダー（`/auth/login-key` → `/api/llm/chat`）

- textData に `accessToken` がないと、エミュレーターのログに `secuaigent auth: POST /auth/login-key` → `POST /api/llm/chat` が出て、backend は `login-key` 200 → `llm/chat` 200。SSE の回答（偽の LLM の `FAKE-LLM-ANSWER`）が返る
- **トークン使用量**: backend に直接（curl で終わりまで読む）呼ぶと `token_usages` に 1 行（`gpt-4o`、入力 11・出力 7、`message_id` 付き）できる。一方、**アダプタ経由（`accessToken` あり・なしの両方）では記録されなかった**。アダプタは `message_stop` を読むと接続を閉じる（`transport.py`）。`message_stop` を読んだ直後に閉じるクライアントで再現でき、記録されない。原因の見立ては 09 の 1
- 参考: この再現の直後に、`/api/llm/chat` が一度 500（`InterfaceError: connection is closed`、ユーザー取得の SQL）になり、次のリクエストでは回復した

## 4. `tenantId`・`X-Tenant-ID`（サブドメインなし）

- React は textData の `tenantId` に `resolveTenantId()`（`sessionStorage` の `TENANT_ID`。ログイン画面で入力した値を `auth-store.ts` が保存）を入れる。サブドメインは使わない
- server-local は textData の `tenantId` を、ライブラリのスタブ作成・タイトル更新の `X-Tenant-ID` に使う。Waha! に渡す textData.json には `tenantId` を入れない（`accessToken` のみ。`_build_text_data`）
- `tenantId` が JWT と違うと backend は 403（`Tenant mismatch`）、textData に `tenantId` がないと `X-Tenant-ID` が送られず 400。いずれも server-local は SSE の `error` と `status: ERROR` で返す
- アダプタが `/auth/login-key` に使う `X-Tenant-ID` は、textData ではなく**エミュレーターのワークフロー定義の `TENANT_ID`**（本物の Waha! ではサービスの設定）。textData の `tenantId` は使われない

## 設計案 4 章の要確認

1. **tenantId の出どころ**: 上記 4。サブドメインは使わず、ログインで入力した値（`sessionStorage`）を textData に入れる。移植元 Angular は `resolveTenantId()`（サブドメインのフォールバックあり）で、このリポジトリの意図的な差分
2. **トークン使用量・クレジット**: SecuAiGent ベンダー経由の `/api/llm/chat` でだけ backend に記録される（移植元と同じ）。アダプタが Azure・OpenAI を直接呼ぶ構成では記録されない（backend に足すものはない）。ただし、SecuAiGent 経由でも記録漏れがある（09 の 1）
3. **同期系の SECURE ガード**: backend にメッセージ回答を生成する経路は SSE の `POST /api/messages/content` だけで（`routers/messages.py`）、同期系（移植元 `createMessageContent`）の経路はない。ガードは SSE の 1 か所（`message_service.py`）に揃っており、**変更なし**

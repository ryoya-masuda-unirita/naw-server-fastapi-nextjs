# 02_設計案

> 設計案のみ。実装・コード変更・PR は行わない。事実の根拠は [01_調査結果.md](./01_調査結果.md)。

## 1. 設計は可能か

**可能。ただし、Issue #102 の元の想定（backend が ローカルLLM を呼ぶ）は採らない。** 移植元の設計は「SECURE の質問はブラウザから server-local へ直接送り、クラウドの server は送り先と API キーを返すだけ」で、この経路は移植先にすでに揃っている（#210・#274・#289・#298〜#301）。したがって #102 は「新規に機能を足す」のではなく、**移植元どおりの経路が実物の backend を含めて通ることを確かめ、不足があれば最小限で埋める**Issue に置き換えるのが妥当。

## 2. 案の比較

### 案A（推奨）: 移植元どおり。backend は変えず、通しの確認と周辺の穴埋めに絞る

- 方針
  - backend の SECURE 400（`message_service.py` L922）は**そのまま残す**（移植元 `MessageService.java` L306・L486 と同じ）。
  - 実物の backend（ルートの compose）+ `onprem/`（server-local + エミュレーター）+ React で、SECURE の質問が通ることを確認する。確認項目:
    1. `onprem/cloud-seed.sql` の SECURE アシスタントで、React から送信 → server-local → エミュレーター（Echo）→ 回答が SSE で返る
    2. `GET /api/auth` の `token` が textData の `accessToken` に入り、server-local がライブラリのスタブ作成で backend を呼べる（Bearer）
    3. エミュレーターの `SecuAiGent` ベンダーで `/auth/login-key` → `/api/llm/chat` が通り、トークン使用量が backend に記録される（`llm_chat_service.py` L413 付近）
    4. textData の `tenantId`・`X-Tenant-ID` がサブドメインなしで正しく渡る
  - 確認で見つかった不具合・不足は、**個別の Issue に切り出す**（#102 自体は「確認と設計の固定」で完了）。
  - backend に同期系（Java `createMessageContent` L264〜306 相当）の経路があれば、SECURE を 400 にする（移植元と揃える）。なければ何もしない。
- 移植元との関係: 移植元と同じ。**移植元に無いものを足さない**
- 利点: 移植元と挙動が一致する、変更量が最小、既存の「SECURE は質問がクラウドを通らない」という設計目的（機密保持）を守れる
- 欠点: 「backend が回答を作る」機能は増えない（これは移植元に無いので問題ではない）

### 案B: backend が server-local を中継する（プロキシ方式）

- 方針: ブラウザ → backend → server-local。backend の `stream_message_content` が SECURE のとき、`LOCAL_SERVER` エンドポイントの URL・API キーで server-local の `/api/messages/content` を呼び、SSE を中継する。
- **移植元に無い提案**（移植元は SECURE を 400 にしている）
- 利点: ブラウザに API キーを渡さなくてよい。ブラウザからオンプレへの CORS・ネットワーク到達性が要らない
- 欠点
  - 質問・回答の本文がクラウドを通る。SECURE の存在理由（質問や社内文書を社外に出さない。`README.md`）と矛盾する
  - backend からオンプレへ届く経路（インターネット越しに顧客社内へ）が必要。移植元は「クラウドから server-local へ向かう通信はない」前提
  - 既存の frontend（#289 で移植済みの直接送信）と二重になる

### 案C: backend が OpenAI 互換などで ローカルLLM を直接呼ぶ（Issue 本文の想定どおり）

- 方針: `llm_chat_service.py` に SECURE の分岐を足し、`LOCAL_SERVER` のエンドポイントを LLM として直接呼ぶ。
- **移植元に無い提案**。さらに、移植元の `LOCAL_SERVER` は LLM ではなく server-local（`/api/messages/content` 等の独自 API）で、OpenAI 互換のプロトコル仕様もない
- 欠点: 案B の欠点に加え、プロトコル仕様が存在しない。server-local・Waha!・アダプタを迂回するため、RAG・学習データ・ライブラリ本文の保管と整合しない

### 比較表

| 観点 | 案A（推奨） | 案B | 案C |
|---|---|---|---|
| 移植元との一致 | 一致 | 無い仕組みを足す | 無い仕組みを足す |
| 質問・回答がクラウドを通らない | 守られる | 破られる | 破られる |
| backend の変更量 | ほぼなし | 大（SSE 中継・オンプレ到達性） | 大（プロトコルも新規設計） |
| frontend（#289）との整合 | そのまま | 二重になる・作り直し | 無関係になる |
| 決める必要のある仕様 | 少ない（確認のみ） | 中継の認証・タイムアウト・到達性 | プロトコル・認証・SSE 形式 |

**推奨は案A。** 過去の調査コメントが挙げた「要プロダクトオーナー判断」の 2 点（プロキシかクライアント直接か、オンプレ API のプロトコル）は、移植元が「クライアント直接」「`/api/messages/content` 互換（server-local の API）」と**すでに答えを持っている**ため、新規の意思決定は要らない。案B・C を選ぶ場合だけ、本当の意味で新規設計が必要になる。

## 4. 要確認（決めきれない点）

1. **Issue #102 を案A に作り替えてよいか**（Issue の閉じ方・Status の扱い。本調査では Issue・Status に触れていない）。推奨: 案A に合わせて Issue 本文を更新し、通しの確認の Issue に分ける。
2. **textData の `tenantId` の出どころ**（Angular は `resolveTenantId()`＝サブドメインのフォールバックあり。このリポジトリはサブドメインを廃止している）。React の送信（`frontend/src/store/messages-store.ts`）で何を入れているか、server-local・アダプタが `X-Tenant-ID` として使う値と一致するかを確認する。移植元と違う点は意図的な差分として記録する。
3. **トークン使用量・クレジットの SECURE の扱い。** 移植元は SecuAiGent ベンダー経由（`/api/llm/chat`）のときだけクラウドに記録され、アダプタが LLM を直接呼ぶ構成では記録されない。これを仕様として許容するか。
4. **backend の同期系の経路に SECURE のガードが要るか**（Java `createMessageContent` L306 に対応する経路の有無）。
5. 案B・C を将来検討する場合は、**プロダクトオーナーの判断**が必要（質問・回答をクラウドに通してよいか、オンプレへのクラウドからの到達性を許すか）。いずれも移植元に無い新機能になる。

## 5. 移植元に無い提案の明記

- 案A は移植元に無いものを足さない（backend の SECURE 400 を維持）。
- 案B（プロキシ）・案C（backend からの直接呼び出し）は**移植元に無い新規設計**で、推奨しない。

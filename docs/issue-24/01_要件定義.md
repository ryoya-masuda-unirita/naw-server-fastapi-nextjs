# 01_要件定義

## 背景

issue-20の動作確認で、ログイン後のダッシュボードが呼び出す `GET /api/assistants` 等が404になることを確認した。次の機能候補としてアシスタント管理APIを検討したところ、Spring Boot版の `GET /api/assistants` はユーザーが所属する **Group（チーム）** に紐づくアシスタントのみを返す仕様であり、Groupドメインが本リポジトリに未実装であることが判明した。

Groupエンティティは Assistant・PromptTemplate（いずれも本リポジトリ未実装）ともM2M関連を持つため、まずGroup自体のCRUD・ユーザー所属管理のみを本チケットのスコープとし、Assistant・PromptTemplateとの紐付けは各ドメイン実装後の別チケットで対応する。

なお、`frontend-angular`（動作確認用フロントエンド）は既にGroup管理画面のAPIクライアント・型定義を備えており、Group APIが動けばそのまま画面が繋がる状態にある。

## 機能要件

移植元 `~/Documents/naw-server` の `GroupController`（`~/Documents/naw-server/src/main/java/com/example/naw/api/GroupController.java`）のうち、以下を実装する。

### エンドポイント

- `GET /api/groups`：グループ一覧取得。`isBelonged`パラメータ（デフォルトfalse）がtrueならログインユーザーが所属するグループのみ、falseならテナント内の全グループを返す（権限チェックなし、閲覧は誰でも可）
- `GET /api/admin/groups`：管理者向け一覧（検索・ページネーション）。テナント管理者は全件、グループ管理者は自分が管理するグループのみが自動的に絞り込まれる
- `GET /api/admin/all-groups`：テナント管理者専用。テナント内全グループ一覧（検索・ページネーション）
- `GET /api/admin/groups/{id}`：詳細取得
- `POST /api/admin/groups`：作成（グループ名のみ指定、テナント管理者専用）
- `PATCH /api/admin/groups/{id}`：更新（グループ名のみ）
- `DELETE /api/admin/groups/{id}`：削除（テナント管理者専用）
- `GET /api/admin/groups/{groupId}/users`：グループ所属ユーザー一覧（検索・ページネーション・グループ内ロールでの絞り込み）
- `POST /api/admin/groups/{groupId}/users`：ユーザー追加（複数ID指定）
- `DELETE /api/admin/groups/{groupId}/users/{userId}`：ユーザー削除
- `PATCH /api/admin/groups/{groupId}/users/{userId}`：グループ内管理者フラグ（`groupAdmin`）の更新

### 権限モデル

- **テナント管理者**（`User.role == ADMIN`）：全操作が可能
- **グループ管理者**（対象グループの `groups_users.is_admin = true`）：自分が管理するグループの詳細取得・更新・所属ユーザーの閲覧/追加/削除/ロール更新が可能。グループの新規作成・削除は不可（テナント管理者専用）
- **一般ユーザー**：`GET /api/groups`（一覧・自分の所属確認）のみ利用
- グループ管理者は、**自分自身の所属削除・自分自身のロール変更はできない**（誤って自分を降格・除外できないようにするため）
- 権限不足時は403を返す

### バリデーション

- グループ名は必須（空文字は不可、DBの `NOT NULL` 制約に対応）。移植元では長さ制限・重複チェックは行われていないため、本移植でも同様に長さ制限・重複禁止は設けない
- ユーザー追加時、`userIds` は1件以上必須。存在しないユーザーID・他テナントのユーザーIDは404
- 既に所属済みのユーザーを追加した場合はエラーにせずスキップする（冪等）
- 既に非所属のユーザーを削除しようとした場合もエラーにしない（冪等）
- 存在しない・他テナントのグループIDを指定した場合は404

### 削除時の挙動

グループ削除時は、所属ユーザー関連（`groups_users`）を含め関連レコードを削除する（確認や拒否は行わない）。Assistant・PromptTemplateとの関連テーブルは本スコープでは存在しないため対象外。

### フロントエンドとの契約

`frontend-angular` の既存実装を調査した結果、以下の応答形式が期待されている。

- グループ一覧（`GET /api/admin/groups`, `GET /api/admin/all-groups`）：`{ data: [...], total, page, size }` 形式（Spring Boot側の `GroupListPageResponse` 相当。既存の `/api/admin/users` が使う `content/totalElements/...` 形式とは異なる）
- グループ所属ユーザー一覧（`GET /api/admin/groups/{groupId}/users`）：`{ content: [...], totalElements, number, size }` 形式（Spring Data の `Page<T>` そのままの形式。フィールド名は `number`。`page` という名前ではない点に注意）
- グループ所属ユーザー一覧のレスポンスには `totalCredits`・`usedTokens` 等ビリング関連フィールドがあるが、本スコープでは常に `null`（またはフィールド省略）でよい。フロントエンドは `includeUsage=true` を常に付与してくるが、値の算出はビリング機能実装後の対応とする

## 非機能要件

- 既存の `backend/.claude/CLAUDE.md` のレイヤー構成（routers/services/repositories/models）に従う
- グループIDは既存のGroup同様、UUID（ハイフンなし32文字hex）で生成する
- ページネーションは0始まりのページ番号、デフォルトサイズ20を踏襲する
- 動作確認のため、`backend/seed.sql` に一般ユーザーを2名追加する（現状は管理者ユーザー1名のみで、グループへのユーザー追加・削除・グループ内管理者フラグ切り替えの複数人操作を確認できないため）

## スコープ外

- `groups/{groupId}/assistants`・`groups/{groupId}/prompt-templates` に関するエンドポイント（Assistant・PromptTemplateドメイン未実装のため）
- `includeUsage` によるクレジット利用量の実際の算出（ビリング機能未実装のため）
- `frontend`（React）側の対応（当面不問方針のため）

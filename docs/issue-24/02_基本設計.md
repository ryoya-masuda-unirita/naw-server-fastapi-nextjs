# 02_基本設計

## 変更対象レイヤー

- `models`（Group・GroupUserの新規テーブル定義）
- `schemas`（グループ関連のリクエスト・レスポンススキーマ）
- `repositories`（groups・groups_usersテーブルへのDBアクセス）
- `services`（グループ管理・所属ユーザー管理のビジネスロジック）
- `routers`（`GET /api/groups`、`/api/admin/groups`系エンドポイント）
- `core`（既存の `get_current_user`・`require_admin`・`get_verified_tenant_id` を流用。グループ管理者判定のための新規依存関数を追加）

## データモデル概要

### groups テーブル

- `id`：UUID hex 32文字、主キー
- `tenant_id`：所属テナント
- `name`：グループ名（NOT NULL、長さ制限・重複制約なし）
- `created_at`・`updated_at`

### groups_users テーブル（中間テーブル）

- `group_id` + `user_id` + `tenant_id` の複合主キー
- `is_admin`：グループ内管理者フラグ
- `updated_at`

いずれも既存の `tenants`・`users` テーブルと同様、RLSによるテナント分離の対象とする。

## API変更概要

### グループCRUD

- `GET /api/groups`：`isBelonged` クエリパラメータで、全件かログインユーザー所属分かを切り替える。認証のみ必須（ロール不問）
- `GET /api/admin/groups`・`GET /api/admin/all-groups`：検索（`q`）・ページネーション（`page`・`size`）対応。`all-groups` はテナント管理者専用、`groups` はテナント管理者は全件・グループ管理者は自分の管理グループのみに自動絞り込み
- `GET /api/admin/groups/{id}`：詳細取得。テナント管理者またはグループ管理者のみ許可
- `POST /api/admin/groups`：テナント管理者専用
- `PATCH /api/admin/groups/{id}`：テナント管理者またはグループ管理者
- `DELETE /api/admin/groups/{id}`：テナント管理者専用

### グループ所属ユーザー管理

- `GET /api/admin/groups/{groupId}/users`：検索・ページネーション・グループ内ロール（`ADMIN`/`USER`）での絞り込みに対応。テナント管理者またはグループ管理者のみ許可
- `POST /api/admin/groups/{groupId}/users`：複数ユーザーIDを一括追加。既存所属はスキップ
- `DELETE /api/admin/groups/{groupId}/users/{userId}`：単一ユーザーの除外。非所属なら何もしない
- `PATCH /api/admin/groups/{groupId}/users/{userId}`：グループ内管理者フラグの更新。操作対象が自分自身の場合は拒否

### 権限判定の実装方針

既存の `get_current_user`（Cookie/Authorizationヘッダー両対応）・`require_admin`（テナント管理者専用）に加えて、「テナント管理者 or 対象グループのグループ管理者」を判定する新規の依存関数を用意する。判定はグループごとに行うため、パスパラメータの `group_id`（または`id`）を受け取って `groups_users` を検索する形にする。

自分自身への操作（所属削除・ロール変更）を拒否するチェックは、対象 `user_id` が現在の認証ユーザーと一致するかで判定する。

## レスポンス形式（フロントエンド契約に合わせる）

`frontend-angular` の既存実装を調査した結果、グループ関連のページネーションはエンドポイントごとに異なる形式が期待されている。

| エンドポイント | 形式 |
|---|---|
| `GET /api/admin/groups`・`GET /api/admin/all-groups` | `{ data: [...], total, page, size }`（`GroupListPageResponse`相当） |
| `GET /api/admin/groups/{groupId}/users` | `{ content: [...], totalElements, number, size }`（Spring `Page<T>`相当。フィールド名は`number`） |

この2系統は既存の `/api/admin/users`（`content/totalElements/totalPages/page/size`、CLAUDE.mdの`PagedResponse[T]`をベースにした独自形式）とも異なるため、グループ関連は上表の形式を新規スキーマとして定義し、既存の`PagedResponse`とは併用しない。

参考: `/api/admin/users` のレスポンス（`page`フィールド）は `frontend-angular` 側が `Page<T>`判定時に読む `number`フィールドと名前が一致しておらず、フロントエンド側でページ番号がずれる可能性があるが、これは既存実装の問題であり本チケットのスコープ外。ユーザーには会話内で一言触れるに留める。

## 影響範囲

- 新規テーブル追加のためAlembicマイグレーションが必要
- 既存の認証・ユーザー管理コードへの変更はなし（新規の権限判定用依存関数を追加するのみ）
- `frontend-angular`のコード変更は不要（既存実装がそのまま繋がる想定）
- `frontend`（React）は対象外

# 01_要件定義

## 背景

server-local は DB に SQLite を使う。SQLite は WAL モードでも同時に書き込めるのは 1 接続だけで、書き込み中の接続がある間、ほかの書き込みは待たされ、待ち時間（5 秒）を過ぎると失敗する。

学習ファイルの差し替えでは、旧データの削除を DB に書き込んだ状態のまま Waha! の削除ジョブ・学習ジョブ（数分かかることがある）の完了を待っていた。その間、チャットの回答保存や他の学習ファイル操作がすべて失敗する。

移植元は H2（行ロック）のため、1 つのトランザクションで Waha! を待っても他の書き込みは止まらない。移植先では DB の性質が違うため、トランザクションの範囲を変える必要がある。

## 機能要件

1. 学習ファイルの差し替えで、Waha! の削除ジョブ・学習ジョブを待つ間、DB の書き込みロックを持たない
2. 差し替えの DB 更新（旧ファイルの削除と新ファイルの保存）は、Waha! の処理をすべて終えた後に 1 回のトランザクションで行う
3. Waha! の処理が途中で失敗した場合、DB は変更しない（移植元がロールバックした後と同じ状態）
4. 新規登録・削除・追加学習・同期の経路も、Waha! を待つ間に書き込みロックを持たない
5. Waha! を待つ間に別のリクエストで元のファイルが削除されていても、差し替えは完了する
6. API の入出力（パス・パラメーター・応答・ステータスコード）は変えない

## 非機能要件

- Waha! を待つ間、別の接続からの書き込みが待たされずに成功することを自動テストで確認する
- 修正前のコードで、そのテストが失敗する（問題を再現できる）ことを確認する

## スコープ外

- Waha! 側のデータと DB の不整合を自動で修復する仕組み（Waha! の削除が成功した後に学習ジョブが失敗した場合の不整合は移植元と同じく残る）
- メッセージ（チャット）系の経路の変更（調査の結果、Waha! の処理後に書き込む構造で問題がないため）

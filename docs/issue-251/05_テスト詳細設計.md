# 05_テスト詳細設計

## テストファイル

`server-local/tests/test_file_service_db_lock.py`（新規）

### 仕組み

- `FakeWahaClient.on_get_results`: `get_results`（Waha! のジョブ完了待ち）の中で呼ばれる非同期処理。テストごとに設定する
- `ConcurrentWriter.write()`: テスト用の `session_factory` から別セッションを開き、`PRAGMA busy_timeout=0` を実行してから `message_contents` に 1 行追加してコミットする。成否を `results` に記録する（失敗時は例外を投げ、API 側の 500 としても現れる）。接続はプールに戻って再利用されるため、最後に `busy_timeout` を `SQLITE_BUSY_TIMEOUT_MS` に戻す
- `delete_file_row()`: 別セッションで `files` の行を削除する（待機中の同時削除の再現用）
- DB はテストごとの一時ファイルの SQLite（WAL、`conftest.make_settings`）。アプリと同じ engine を使うため、接続はプール内の別接続になる

### テストケース（クラス `TestDbLockWhileWaitingWaha`）

| No | メソッド | 内容 | 確認内容 |
|---|---|---|---|
| 1 | `test_update_with_file_does_not_lock_db` | `f1`（パート `p1`）を PATCH で差し替え。Waha! は `f-new\tq1` を返す | 200、`writer.results == [True, True]`、`f1` は削除、`f-new` のパートは `q1` |
| 2 | `test_create_file_does_not_lock_db` | POST で新規登録 | 200、`writer.results == [True]` |
| 3 | `test_delete_file_does_not_lock_db` | `f1` を物理削除 | 204、`writer.results == [True]`、`f1` は削除 |
| 4 | `test_update_when_file_deleted_while_waiting` | 差し替え中、`get_results` の間に別セッションで `DELETE FROM files WHERE id='f1'` | 200、応答の `id` が `f-new`、`f1` は存在しない |
| 5 | `test_logical_delete_does_not_lock_db` | `f1` を論理削除 | 204、`writer.results == [True]`、`f1` の状態は `DELETED` |
| 6 | `test_logical_delete_when_file_deleted_while_waiting` | 論理削除中、`get_results` の間に別セッションで `f1` を削除 | 204（`StaleDataError` の 500 にならない）、`f1` は存在しない |
| 7 | `test_additional_learning_does_not_lock_db` | 追加学習（`feedbackId=fb1`） | 204、`writer.results == [True]`、`fb-file` が登録される |

### 既存テスト

- `tests/test_indexes_router.py::TestUpdateFile::test_update_with_file_rolls_back_delete_on_failure`: 学習ジョブ失敗時に元のファイル・パートが残ること（docstring を「DB は変更せず」に修正。アサーションは変えない）
- `test_update_with_same_ids_recreates_parts`: 差し替えで同じファイル ID・パート ID が返ってもパートが残ること（`expunge` + 一括 DELETE の確認）
- `TestDeleteFile` の各テスト: 物理削除・論理削除・Waha! 失敗時に DB を変えないこと

### 修正前の再現手順

`git show origin/develop:server-local/app/services/file_service.py` で修正前のサービスに一時的に戻し、`uv run pytest tests/test_file_service_db_lock.py` を実行する。No.1・No.4 が `database is locked` で失敗することを確認したら、修正後のコードに戻す。

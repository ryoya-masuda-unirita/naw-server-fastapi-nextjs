# 02_基本設計

## 変更対象

- 学習ファイル管理のサービス（登録・差し替え・削除・追加学習）
- テスト用の Waha! の偽物（ジョブ完了待ちの間に処理を割り込ませる仕組み）
- server-local の README（移植元との違い）

## 画面 / API 変更概要

API の入出力は変更しない。内部の処理順とトランザクションの範囲だけを変える。

### 処理順（差し替え）

| 順 | 修正前 | 修正後 |
|---|---|---|
| 1 | 旧ファイルとパートを読む | 旧ファイルとパートを読む（読み取りのみ。書き込みロックは取らない） |
| 2 | Waha! の削除ジョブを実行 | Waha! の削除ジョブを実行し、セッションを終了 |
| 3 | DB から旧ファイルを削除（未確定・**書き込みロック取得**） | Waha! の学習ジョブを実行し、結果を取得してセッションを終了 |
| 4 | Waha! の学習ジョブを実行（**ロックを持ったまま数分待つ**） | 学習結果（ファイル ID・パート ID）を解析 |
| 5 | DB に新ファイルを保存してコミット | 1 回のトランザクションで旧ファイルを削除し、新ファイルを保存してコミット |

### Waha! 途中失敗時の DB と Waha! の整合

| 失敗箇所 | Waha! の状態 | DB の状態（修正後） | 移植元 |
|---|---|---|---|
| 削除ジョブ | 旧データが残る（または一部削除） | 変更しない | ロールバックで変更なし |
| 学習ジョブ | 旧データは削除済み・新データなし | 変更しない（旧ファイルが一覧に残る） | ロールバックで変更なし |
| DB 更新 | 新データ登録済み | ロールバックで変更なし | 同じ |

学習ジョブ失敗時に「旧ファイルが DB に残り、Waha! 側は削除済み」となる不整合は移植元と同じ。DB の行を残すことで、利用者は同じファイルに対して差し替えをやり直せる。DB だけ削除して Waha! に合わせる案もあるが、移植元の失敗時の状態から変えることになるため採らない。

### 他の経路の確認結果

| 経路 | 修正前 | 修正後 |
|---|---|---|
| 新規登録・追加学習 | Waha! の学習ジョブ後に DB に保存（問題なし） | 処理順は同じ。差し替えと共通の部品に整理 |
| 削除 | Waha! の完了後・セッション終了前に DB を更新・コミット（ロックは短い） | Waha! のセッション終了まで済ませてから DB を更新（セッション終了の失敗で DB を変えない点を移植元に揃える） |
| 同期 | Waha! の処理後に DB に保存（問題なし） | 変更なし |
| メッセージ（同期・SSE） | Waha! の処理前後で個別に短くコミット（問題なし） | 変更なし |

## 影響範囲

- 学習ファイルの登録・差し替え・削除・追加学習 API（応答は変わらない）
- 削除 API で Waha! のセッション終了が失敗した場合、修正前は DB が更新された後に 500 だったが、修正後は DB を更新せず 500（移植元と同じ）

## 移植方針

- 移植元 `FileService` の処理内容（Waha! の呼び出し順・DB に保存する値）は変えない
- トランザクションの範囲だけを SQLite の性質に合わせて変え、その理由を README の「移植元との違い」に書く

## `file_service.py` の関数構成

| 修正前 | 修正後 | 役割 |
|---|---|---|
| `_run_waha_create(session, waha, ...)`（Waha! 実行 + `_save`） | `_run_waha_create_job(waha, *, service_name, upload, split_length, reference) -> tuple[str, list[str]]` | Waha! の学習ジョブだけを実行し、`end_session` 後に TSV を解析してファイル ID・パート ID を返す。DB に触れない |
| `_run_waha_delete(session, waha, ..., commit=True)`（検索 + Waha! 実行 + DB 更新） | `_find_part_ids(session, file_id, index_id) -> list[str]` | 対象ファイルのパート ID を読む（なければ `EntityNotFoundError`）。読み終えたら `rollback` で接続をプールに返し、`expunge_all` でセッションを空にする |
| 〃 | `_run_waha_delete_job(waha, *, service_name, part_ids)` | Waha! の削除ジョブだけを実行（`end_session` まで）。DB に触れない |
| 〃 | `_delete_from_db(session, file_id, *, physical_delete)` | ID 条件の DELETE / UPDATE で物理削除・論理削除する（commit は呼び出し側） |
| `_save` / `_upsert_part` | 変更なし | 新ファイル・パートを保存して commit |

`server-local/app/core/database.py` の `busy_timeout` の値を定数 `SQLITE_BUSY_TIMEOUT_MS`（5000）にし、テストから参照する（code-review 対応）。

### 各 API の処理

- `create_file` / `additional_learning`: `_run_waha_create_job` → `_save`（commit）
- `delete_file`: `_find_part_ids` → `_run_waha_delete_job` → `_delete_from_db` → `commit`
- `update_file`（ファイルあり）: `_find_part_ids` → `_run_waha_delete_job` → `_run_waha_create_job` → `_delete_from_db(physical_delete=True)` → `_save`（commit）。旧ファイルの削除と新ファイルの保存が同じトランザクションになる
- `update_file`（ファイルなし）・`sync_files`: 変更なし

### 読み取りでロックを取らないこと

SQLAlchemy + aiosqlite（pysqlite の既定の分離レベル）は、INSERT/UPDATE/DELETE の直前に `BEGIN` を出し、SELECT では `BEGIN` を出さない。そのため `_find_part_ids` の読み取りは書き込みロックを取らない。テスト（下記）で実際に確認する。

### DB 接続を Waha! 待ちの間に持たないこと（code-review 対応）

SQLAlchemy のセッションは、一度 SELECT するとトランザクションが終わるまでプールの接続を持ち続ける。書き込みロックは取らなくても、差し替え・削除が多数同時に Waha! を待つと接続プールが尽きる。そこで `_find_part_ids` は、必要なパート ID を `list[str]` に取り出した後に `session.rollback()` で読み取りを終えて接続を返す。読み込んだ ORM オブジェクトは後で使わないため `session.expunge_all()` でセッションから外す（同じ ID で再登録するとき、`_save` の検索や `_upsert_part` の `session.get` が削除済みのオブジェクトを既存扱いしないためでもある）。

### 物理削除・論理削除の方法

修正前は ORM のオブジェクト経由（`session.delete()` / 属性の更新）で消していた。修正後は読み込みから削除までの間に Waha! の処理（数分）が挟まるため、その間に別のリクエストが同じファイルを削除すると、ORM の削除・更新が 0 件で `StaleDataError`（500）になる。そこで ID 条件の SQL で更新する（0 件でもエラーにならない）。

- 物理削除: `DELETE FROM file_parts WHERE file_id = ?` → `DELETE FROM files WHERE id = ?`
- 論理削除: `UPDATE files SET status = 2（DELETED）, updated_at = 現在時刻 WHERE id = ?`（修正前の `touch()` と同じく更新日時も変える）

型チェックのため、列の比較は `sqlmodel.col()` を使う。

### 同じファイルへの同時操作

Waha! を待つ間に別のリクエストが同じファイルを削除・差し替えした場合、後から終わった方の DB 更新は 0 件の削除になり、エラーにせずそのまま進める（差し替えなら新しいファイルを保存する）。移植元も、同じ行の削除は行ロックで待った後に 0 件となり（Spring Data JPA 3 の `deleteById` は存在しない ID を無視する）、新しいファイルを保存するため、同じ挙動になる。

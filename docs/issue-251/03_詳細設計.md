## `file_service.py` の関数構成

| 修正前 | 修正後 | 役割 |
|---|---|---|
| `_run_waha_create(session, waha, ...)`（Waha! 実行 + `_save`） | `_run_waha_create_job(waha, *, service_name, upload, split_length, reference) -> tuple[str, list[str]]` | Waha! の学習ジョブだけを実行し、`end_session` 後に TSV を解析してファイル ID・パート ID を返す。DB に触れない |
| `_run_waha_delete(session, waha, ..., commit=True)`（検索 + Waha! 実行 + DB 更新） | `_find_file_with_parts(session, file_id, index_id)` | 対象ファイルとパートを読む（なければ `EntityNotFoundError`） |
| 〃 | `_run_waha_delete_job(waha, *, service_name, parts)` | Waha! の削除ジョブだけを実行（`end_session` まで）。DB に触れない |
| 〃 | `_delete_from_db(session, file, parts, *, physical_delete)` | DB の物理削除・論理削除（flush まで。commit は呼び出し側） |
| `_save` / `_upsert_part` | 変更なし | 新ファイル・パートを保存して commit |

### 各 API の処理

- `create_file` / `additional_learning`: `_run_waha_create_job` → `_save`（commit）
- `delete_file`: `_find_file_with_parts` → `_run_waha_delete_job` → `_delete_from_db` → `commit`
- `update_file`（ファイルあり）: `_find_file_with_parts` → `_run_waha_delete_job` → `_run_waha_create_job` → `_delete_from_db(physical_delete=True)` → `_save`（commit）。旧ファイルの削除と新ファイルの保存が同じトランザクションになる
- `update_file`（ファイルなし）・`sync_files`: 変更なし

### 読み取りでロックを取らないこと

SQLAlchemy + aiosqlite（pysqlite の既定の分離レベル）は、INSERT/UPDATE/DELETE の直前に `BEGIN` を出し、SELECT では `BEGIN` を出さない。そのため `_find_file_with_parts` の読み取りは書き込みロックを取らない。テスト（下記）で実際に確認する。

### 物理削除の方法

修正前は ORM の `session.delete()` で消していた。修正後は読み込みから削除までの間に Waha! の処理（数分）が挟まるため、その間に別のリクエストが同じファイルを削除すると、ORM の削除が 0 件で `StaleDataError`（500）になる。そこで:

1. セッションから旧ファイル・パートを `expunge` する（同じ ID で再登録するとき、`_save` の検索や `_upsert_part` の `session.get` が削除済みのオブジェクトを既存扱いしないため）
2. `DELETE FROM file_parts WHERE file_id = ?` と `DELETE FROM files WHERE id = ?` を実行する（0 件でもエラーにならない）

型チェックのため、列の比較は `sqlmodel.col()` を使う。

論理削除は修正前と同じく ORM で状態を `DELETED` に更新する。

# 04_テスト設計

## テスト方針

- `alembic upgrade head` でテーブルが正しく作成されることを確認する
- SQLModel モデルを通じて CRUD 操作が正常に行えることを確認する
- 制約（FK、UNIQUE、CHECK）が DB レベルで機能することを確認する
- テスト用 DB は `docker-compose.yml` の同一コンテナを使用する

---

## テストケース一覧

### マイグレーション

| # | テストケース | 確認内容 |
|---|---|---|
| M1 | `alembic upgrade head` が正常終了すること | exit code 0、`tenants`・`users` テーブルが作成される |
| M2 | `alembic downgrade base` が正常終了すること | テーブルが削除される |
| M3 | 再度 `alembic upgrade head` が冪等であること | 2回実行してもエラーにならない |

### Tenant モデル

| # | テストケース | 確認内容 |
|---|---|---|
| T1 | Tenant を INSERT できること | 必須カラムのみで INSERT 成功 |
| T2 | デフォルト値が正しく設定されること | `is_deleted=False`、パスワードポリシーデフォルト値 |
| T3 | `pw_histories_limit=0` で CHECK 制約違反になること | `IntegrityError` が発生する |
| T4 | `id` が重複すると PK 制約違反になること | `IntegrityError` が発生する |

### User モデル

| # | テストケース | 確認内容 |
|---|---|---|
| U1 | User を INSERT できること | tenant が存在する状態で INSERT 成功 |
| U2 | `id` が UUID として自動生成されること | 明示的に指定しなくても UUID が入る |
| U3 | `is_required_password_reset` のデフォルトが `true` であること | 明示的に指定しなくても `True` になる |
| U4 | `(login_id, tenant_id)` 重複で UNIQUE 制約違反になること | `IntegrityError` が発生する |
| U5 | 存在しない `tenant_id` で FK 制約違反になること | `IntegrityError` が発生する |
| U6 | Tenant 削除時に User が CASCADE 削除されること | `tenant.delete()` 後に User が消える |
| U7 | 不正な `role` 値で ENUM 制約違反になること | `IntegrityError` が発生する |

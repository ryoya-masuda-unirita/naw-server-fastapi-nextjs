# 02_基本設計

## 変更対象

新規にメッセージ関連のテーブル・エンティティ・API を追加する（既存テーブルの変更なし）。

- メッセージ（質問スレッド本体。ルーム・アシスタント・親メッセージへの参照、編集/再生成用の tools・プロンプトテンプレート本文・ライブラリ生成フラグを保持）
- メッセージ内容（質問・回答本文、ステータス、参照ファイルパス）
- メッセージ添付ファイル（メッセージ内容に紐づく添付ファイルの実体。本issueでは取得のみ）
- メッセージフィードバック（メッセージ1件につき1件、GOOD/BAD の評価）

## 画面 / API 変更概要

以下のエンドポイントを新規追加する。

| メソッド | パス | 概要 |
|---|---|---|
| POST | `/api/messages` | メッセージ（質問スレッド）を作成する。ルームIDが未指定なら新規ルームも作成する |
| GET | `/api/messages?roomId=` | 指定ルームのメッセージ一覧と関連アシスタント情報を取得する |
| POST | `/api/messages/contents` | メッセージID群を指定してメッセージ内容一覧を取得する |
| DELETE | `/api/messages/{messageId}` | メッセージを削除する（子孫・内容も再帰的に削除） |
| DELETE | `/api/messages/content/{messageContentId}` | メッセージ内容IDを指定してメッセージを削除する（内部的にメッセージ削除と同じ） |
| POST | `/api/messages/{messageId}/feedback` | メッセージへの評価（GOOD/BAD）を登録・更新する |

移植元は作成成功時にメッセージIDを文字列そのまま返す（`ResponseEntity<String>`）が、本リポジトリの他API
（例: ルーム作成）はJSONオブジェクトで返す方針のため、本issueでは `{"id": "..."}` 形式のレスポンスに変更する。
その他のレスポンス構造（一覧のフィールド名・型）は移植元に合わせる。

## 影響範囲

- 新規テーブル4つ（メッセージ・メッセージ内容・メッセージ添付ファイル・メッセージフィードバック）を追加するため、マイグレーションが必要
- 既存のルーム・アシスタント・テナントエンドポイントテーブルへの参照（外部キー）が発生するのみで、既存テーブルへの変更はない
- ルームの更新日時（`updated_at`）は、メッセージ作成時に既存ルーム移植と同様の仕組みで更新する

## 移植方針

- ルームへのアクセス制御は、移植元の `RoomAccessService`（グループ共有・共有リンク・テナント管理者バイパスを含む一般化された実装）ではなく、
  既存の #45 ルーム移植で使っている「ルームの `user_id` が自分であること」という所有者チェックのみを適用する
  （共有機能自体がこのリポジトリに存在しないため、対応する仕組みも作らない）
- 月次クレジット上限チェック（`enforceWithinQuota`）は実装しない（プラン・請求期間・トークン使用量の各基盤が未移植のため）
- メッセージの `tools`（チャット送信時に指定した web_search / mcp ツール設定）は、移植元同様 JSON文字列としてカラムに保存する。
  ツール設定のスキーマ自体（`ToolConfig` 相当）はこのissueで新規に定義するが、`authorization` / `headers` は
  秘密情報のため移植元と同様に永続化・レスポンス出力しない（受信のみ）
- メッセージ内容の参照ファイルパス（`referenceFilePaths`）は、移植元同様カンマ区切り文字列としてカラムに保存し、
  読み書き時にリストへ変換する
- メッセージ・メッセージ内容・メッセージフィードバックの削除/参照制約は移植元のテーブル定義（CASCADE / SET NULL の方針）をそのまま踏襲する
- `message_feedbacks.index_id`（RAGインデックスへの参照）は、インデックス機能自体が未移植のため、外部キー制約なしの
  nullableカラムとして定義する（既存の `assistants.index_id` と同じ扱い）

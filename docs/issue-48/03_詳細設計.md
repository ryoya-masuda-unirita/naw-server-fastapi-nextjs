# 03_詳細設計

## 対象テーブル・カラム定義

移植元の Liquibase changelog（`messages` / `message_contents` / `message_files` / `message_feedbacks`）の最終状態を再現する。

### `messages`

| カラム | 型 | 制約 |
|---|---|---|
| id | varchar(32) | PK |
| tenant_id | varchar(32) | NOT NULL, FK→tenants.id (CASCADE) |
| room_id | varchar(32) | NOT NULL, FK→(rooms.id, rooms.tenant_id) (CASCADE) |
| assistant_id | varchar(32) | NULL可, FK→assistants.id (SET NULL) |
| parent_id | varchar(32) | NULL可, FK→messages.id (CASCADE、自己参照) |
| tools | text | NULL可（`ToolConfig` のリストを JSON 文字列で保存） |
| prompt_template_content | text | NULL可 |
| is_create_library | boolean | NOT NULL, default false |

`created_at` / `updated_at` は移植元エンティティに存在しないため追加しない。

### `message_contents`

| カラム | 型 | 制約 |
|---|---|---|
| id | varchar(32) | PK |
| tenant_id | varchar(32) | NOT NULL, FK→tenants.id (CASCADE) |
| message_id | varchar(32) | NOT NULL, FK→messages.id (CASCADE) |
| status | varchar(32) | NOT NULL（`OK` / `ERROR`） |
| question | text | NOT NULL |
| answer | text | NOT NULL |
| context | text | NULL可 |
| file_paths | text | NULL可（参照ファイルパスのリストをカンマ区切り文字列で保存） |
| created_at | timestamptz | NOT NULL, default now() |
| updated_at | timestamptz | NOT NULL, default now() |

インデックス: `(id, created_at)` に非ユニークインデックス。

### `message_files`

| カラム | 型 | 制約 |
|---|---|---|
| id | varchar(32) | PK |
| tenant_id | varchar(32) | NOT NULL, FK→tenants.id (CASCADE) |
| name | varchar(255) | NOT NULL |
| type | varchar(128) | NOT NULL（MIME type） |
| data | bytea | NOT NULL |
| message_id | varchar(32) | NOT NULL, FK→message_contents.id (CASCADE)（カラム名は `message_id` だが実体は message_content の ID） |
| created_at | timestamptz | NOT NULL, default now() |
| updated_at | timestamptz | NOT NULL, default now() |

### `message_feedbacks`

| カラム | 型 | 制約 |
|---|---|---|
| id | varchar(32) | PK |
| tenant_id | varchar(32) | NOT NULL, FK→tenants.id (CASCADE) |
| user_id | uuid | NOT NULL, FK→users.id (CASCADE)（既存の`rooms.user_id`と同様、単一カラムFK） |
| message_id | varchar(32) | NOT NULL, UNIQUE, FK→messages.id (CASCADE) |
| rating | varchar(16) | NOT NULL（`GOOD` / `BAD`） |
| index_id | varchar(64) | NULL可、外部キー制約なし（indexes テーブル未移植のため） |
| created_at | timestamptz | NOT NULL, default now() |
| updated_at | timestamptz | NOT NULL, default now() |

移植元は4テーブルすべてに PostgreSQL RLS を設定しているが、このリポジトリは現時点で RLS を未導入で、
既存テーブル（`rooms` 等）もアプリケーション層（クエリの `tenant_id` 条件）でテナント分離している。
本issueもこの既存方針に合わせ、RLS は設定せず各リポジトリのクエリに `tenant_id` 条件を必ず含める。

## 実装対象ファイル

### マイグレーション

- `backend/alembic/versions/012_add_messages.py`
  - `messages` / `message_contents` / `message_files` / `message_feedbacks` の4テーブルを作成
  - 既存マイグレーションの RLS 有効化方式（`ai_models` 等）を踏襲する

### モデル

- `backend/app/models/message.py`
  - `Message`（SQLModel, table=True）
  - `MessageContent`（`MessageContentStatus` Enum: `OK` / `ERROR`）
  - `MessageFile`
  - `MessageFeedback`（`MessageRating` Enum: `GOOD` / `BAD`）

### スキーマ

- `backend/app/schemas/message.py`
  - `ToolConfig`（`name` は `web_search` / `mcp` のみ許可。`authorization` / `headers` は入力専用でレスポンスに含めない）
  - `MessageCreateRequest` / `MessageCreateResponse`（`{"id": str}`）
  - `EndpointResponse` / `AssistantResponse` / `MessageItemResponse` / `GetMessagesResponse`
  - `MessageContentListRequest` / `MessageContentAttachmentFileResponse` / `MessageContentResponse`
  - `MessageFeedbackCreateRequest` / `MessageFeedbackResponse`

### リポジトリ

- `backend/app/repositories/message_repository.py`
  - `find_by_tenant_id_and_id`
  - `find_by_tenant_id_and_room_id`（一覧取得、フィードバックを一括取得できるよう JOIN 等で N+1 を避ける）
  - `find_by_tenant_id_and_content_id`（メッセージ内容IDからメッセージを逆引き。削除用）
  - `exists_by_tenant_id_and_id`（親メッセージ存在チェック用）
  - `delete_message_cascade`（対象メッセージ本体を1回 `DELETE` し、子孫メッセージ・メッセージ内容は DB の `ON DELETE CASCADE` に任せる。ループでの個別削除は行わない）
- `backend/app/repositories/message_content_repository.py`
  - `find_by_message_id_in`（`message_id IN (...)` と `Message` の JOIN で1クエリ取得。添付ファイルも同時に取得し N+1 を避ける）
- `backend/app/repositories/message_feedback_repository.py`
  - `find_by_tenant_id_and_message_id`

### サービス

- `backend/app/services/message_service.py`
  - `create_message`：アシスタント存在チェック→ルーム解決（`room_id` 指定時は所有権チェック、未指定時は新規作成）→親メッセージ存在チェック→保存→ルームの `updated_at` 更新
  - `get_messages_and_assistants`：ルームへのアクセス権チェック（所有者のみ）→メッセージ一覧とその参照アシスタント一覧を取得
  - `get_message_contents`：指定 `messageIds` からメッセージ内容を取得し、紐づくルームすべてに対して所有権チェックを行う
  - `delete_message` / `delete_message_by_content_id`：所有権チェック→カスケード削除
  - `feedback_message`：所有権チェック→既存フィードバックがあれば `rating` を更新、なければ新規作成

### ルーター

- `backend/app/routers/messages.py`（`prefix="/api/messages"`）

### `main.py`

- `backend/app/main.py` に `messages.router` を追加登録

## 移植元との差分（意図的な仕様変更）

- ルームアクセス制御は「ルーム所有者本人であること」のみをチェックする（`RoomAccessService` のグループ共有・共有リンク・管理者バイパスは実装しない）
- `POST /api/messages` の成功レスポンスを `{"id": "..."}` に変更する（移植元は生文字列）
- 月次クレジット上限チェック（`enforceWithinQuota`）は呼び出さない

## シードデータ

新規シードデータの追加は不要と見込む（既存の `test-tenant` / 固定アシスタントID `10000000000040008000000000000001` を使ってメッセージ作成・ルーム自動作成を確認できるため）。
ただし `message_contents` / `message_files` は本issueでは作成経路を持たないため、取得・削除APIの動作確認には手動INSERTしたテストデータを使用する。

## 詳細

### 1. 同順位が ID 順で、作成順ではない（🔴 重要の指摘）→ 対応しない

指摘は、同順位のとき、ランダムな ID（`uuid4().hex`）で並ぶので、「最新の版」を末尾から選ぶ処理が、不定になりうる、というもの。事実は、そのとおりだが、実際には、同順位がほとんど起きない。コードで確認した。
- メッセージを作る箇所は、`message_service.py` の 1 か所だけで、1 リクエストにつき 1 メッセージ
- 内容（`MessageContent`）は、そのあと、回答の生成時の、**別のトランザクション**（別のセッション）で作られる。PostgreSQL の `now()`（`server_default`）はトランザクションの開始時刻なので、メッセージごとの内容は、別々の時刻になる。1 つのトランザクションで複数のメッセージの内容を作る箇所はない
- 移植元の規則も、`ORDER BY c.createdAt ASC NULLS LAST, m.id ASC`（同じタイブレーク）で、Issue の仕様（「同順位は `messages.id` の昇順」）どおり

提案された、単調に増える作成順の列を足す案は、`messages` に作成日時の列がなく、列の追加（マイグレーション）が要るため、この変更には含めない。代わりに、docstring に、「同順位は決定的であることだけを保証し、作成順ではない。同時刻になることは、実際にはほとんどない」ことを明記した。`NULL`（内容なし）が複数あるとき、ID 順になる点も同じ。

### 2. `MIN` の意味（🔵 提案）→ 対応しない

再生成が内容の行を追加する場合の指摘。コードを確認した（`message_service.py` の再生成の分岐）。`existing_content_id` があるとき、`MessageContentRepository.update_answer` で、**既存の内容を更新する**（行は増えない）。新しい内容の行を作るのは、初回だけ。したがって、1 メッセージに内容は 1 つで、`MIN` は、その作成日時。移植元も、1 つの内容の `createdAt` で並べる。1 メッセージに内容が複数ある場合は、DB の制約上はありうるが、その場合に、行が重複しないこと、最も古い作成日時で並ぶことを、テストで確認している。

### 3. 性能（🟡 注意）→ 対応済み。私の記述の誤りも修正

指摘のとおり。確認したところ、`message_contents` の索引 `message_contents_created_at_idx` は、`id` と `created_at` の索引で、`message_id` での絞り込みには効かない。つまり、設計書と PR 本文に書いた「作成日時の索引もあるため、問題にならない見込み」は、**根拠のない誤り**だった。直した。
- 実装を、メッセージごとの相関サブクエリから、**ルームのメッセージに絞った、1 回の集計（`GROUP BY message_id`）を結合する形**に変えた。メッセージの数だけ走査する問題は、なくなる。結果の意味は同じ（テスト 52 件、全体 1,432 件が成功）
- ただし、索引がなければ、`message_contents` の走査は、1 回は起きる。**`message_id`（と `tenant_id`、`created_at`）の索引の追加は、フォローアップ**にする。マイグレーションが要り、並行する別の作業と、マイグレーションの先頭が衝突するおそれがあるため（懸念で、確認はしていない）
- 設計書・PR 本文の誤った記述を、修正した

### 4. 同順位のテストが任意の規則を固定している（🔵 提案）→ 一部対応

テストの意図を、「同順位も、毎回同じ順序（ID の昇順）で返ること。順序が決定的であることの確認」に書き直した。ID 順そのものを契約とするのではなく、決定的であることを確かめるテストにした。ランダムな ID での再現テストは、ID の大小が実行ごとに変わり、順序を検証できなくなるため、足さない。

`ruff format --check` は、すでに通っていた（233 ファイル）。長いコメントを短くした。

# 02_基本設計

## 変更対象

1. **メッセージの取得処理（リポジトリ）**: ルームのメッセージ一覧を取得するクエリに、並び順を足す。並びのキーは、1) メッセージ内容の作成日時（昇順。内容がないものは末尾）、2) メッセージ ID（昇順）
2. **テスト**: 並び順を確かめるテストを足す（API を通した統合テスト）

## 画面 / API 変更概要

- `GET /api/messages?roomId=…` の返す一覧の**並び順だけ**が決まる（以前は不定）。項目・形式・ステータスコード・権限は変えない
- 画面側（`client/`）の変更はない。並びが決まることで、`client/` の「最新の版を、配列の末尾から選ぶ」処理が、一貫して同じ結果になる

## 影響範囲

- **呼び出し元**: このクエリの呼び出し元は、メッセージ一覧の取得（サービスの 1 か所）だけ
- **既存の挙動**: これまで、並びは DB 任せで、実質、挿入順に近かったと見られるが、保証はない。新しい並び（内容の作成日時）は、通常は、挿入順と一致する。編集・再生成で、内容が更新される（作成日時は変わらない）ので、「最新の版」は、枝分かれした新しいメッセージ（作成日時が新しい）を指す
- **性能**: 並びのために、ルームのメッセージ分の、内容の作成日時を集計する（1 回の集計クエリ）。**`message_contents` には、`message_id` の索引がない**（既存の索引 `message_contents_created_at_idx` は `id` と `created_at` の索引で、`message_id` での絞り込みには効かない）。そのため、メッセージごとの相関サブクエリにすると、メッセージの数だけ `message_contents` を走査してしまう。これを避けるため、ルームのメッセージに絞った集計を 1 回だけ行って結合する（それでも、索引がなければ、`message_contents` の走査は 1 回は起きる）。索引の追加（マイグレーション）は、並行する別の作業とのマイグレーションの衝突のおそれがあるため、この変更には含めず、フォローアップとする。実測はしていない
- **データベース**: SQLite（テスト）と PostgreSQL（本番）の両方で動く書き方にする
- **費用・インフラ**: なし

## 移植方針

- 移植元（`MessageRepository`、`LEFT JOIN` で内容と結合し、`ORDER BY c.createdAt ASC NULLS LAST, m.id ASC`）と同じ並びにする
- 移植元との違い: 移植先の `message_contents.message_id` には、データベース上の一意制約がない。そのため、内容を直接結合して並べると、1 つのメッセージに内容が複数あるとき、メッセージの行が重複しうる。移植元（JPA の 1 対 1）と同じ結果を保ちつつ、行を増やさないよう、**メッセージごとに内容の作成日時（最も古いもの）を `GROUP BY` で 1 行にまとめた副問い合わせを、ルームのメッセージに絞って結合して**並べる（内容は 1 メッセージに 1 つが通常で、その場合は結果が同じ。再生成は、既存の内容を更新する）
- 「内容がないものは末尾」は、`NULLS LAST` を明示する（SQLite と PostgreSQL で、NULL の既定の扱いが違うため）
- 同順位のメッセージ ID の昇順は、順序を決定的にするためのもので、作成順ではない（ID はランダム）。メッセージを作る箇所は 1 か所で、内容は、そのあとの別のトランザクション（回答の生成時）で作られるので、複数のメッセージが同じ作成日時になることは、実際にはほとんどない。移植元と同じ規則
- 共通部品 `build_order_by(tie_breaker=...)` は、利用者が指定する並べ替えの仕組みで、この一覧は、並べ替えの指定を受けない固定の並びなので、使わない（#427 の「一意キーを足す」方針とは、一意キーとして `messages.id` を最後に足す点で揃う）

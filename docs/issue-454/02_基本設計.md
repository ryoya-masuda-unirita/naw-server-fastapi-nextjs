# 02_基本設計

## 変更対象

- Bedrock の RAG の回答を読む処理（回答の返答と、検証の返答の、読み取りの前処理）

## 画面 / API 変更概要

- 画面・外部 API の変更はない
- 利用者への見え方: 学習データがあるのに定型文が返っていた場合が、文書の内容に基づく回答になる

## 影響範囲

- Bedrock（Claude）を使う RAG の回答だけ。通常のチャット、OpenAI 系・Azure・SecuAiGent の RAG は変わらない
- 読み取りを寛容にしても、`answer` と `id` が取り出せなければ、従来どおり却下する。参照 ID の範囲の確認と、検証の呼び出しは、これまでどおり

## 移植方針

- 移植元にない、Python 版だけの Bedrock の拡張なので、移植元との突き合わせは要らない
- 読み取りの前処理を 1 つの関数にまとめ、回答の返答と検証の返答の両方に使う
  1. 前後の空白を取り除く
  2. 先頭がコードフェンスなら、開きのフェンス（言語名つきを含む）と、末尾の閉じのフェンスを取り除く
  3. それでも JSON として読めなければ、最初の `{` から、対応する最後の `}` までを取り出す（前後の説明文を許す）
- 取り出したあとの検証（`answer`・`id` の型、参照 ID の範囲、検証の呼び出し）は、既存のものを変えずに使う
- ベストプラクティスの根拠: 形式の指示をプロンプトに頼ると、モデルが従う保証がなく、モデルの更新で挙動が変わる。読み取り側で、形式の揺れを許すほうが、モデル・接続先を問わず効く。形式をプロトコルで強制する方法（構造化出力・ツール呼び出し）は、接続先の対応を確認できていないため、スコープ外とし、別に検討する

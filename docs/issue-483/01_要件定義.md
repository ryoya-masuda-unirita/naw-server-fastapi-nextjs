# 01_要件定義

## 背景

- Waha! の代わりのエミュレーターを Docker で動かす compose が 2 つある。1 つはエミュレーター単体用、もう 1 つは社内側の環境（server-local・エミュレーター・ベクトル DB）をまとめて起動する検証用
- エミュレーターの環境変数の定義が 2 か所に重複している。実際に差も出ている（まとめて起動する側には、学習で読むファイルの許可ディレクトリが渡されていない）
- README の手順が 2 系統あり、どちらを使えばよいか分かりにくい。古くなった記述も残っている

## 機能要件

- 2 つの compose の用途と差を明らかにし、残す必要のある違いを決める
- 「server-local をホストで動かし、エミュレーターだけ Docker で動かす」使い方が、今後も必要かを決める（まとめて起動する側の compose は、ストリームファイルを named volume で共有するため、この使い方に対応できない）
- 決めた結果に応じて、次のどちらかにする
  - 案 A: 単体の compose を廃止し、まとめて起動する compose に寄せる。足りない設定（学習で読むファイルの許可ディレクトリなど）は、まとめて起動する側に補う
  - 案 B: 2 つを残し、共通する定義を 1 か所にまとめる（compose の `include` や `extends`）
- README・手順書の記述を、整理後の構成に合わせる（古い記述の修正を含む）
- 整理後の構成で、server-local → エミュレーター → アダプタ（チャット・学習・削除）が動くことを実機で確かめる

## 非機能要件

- 既存の自動テストと、ホストで動かす手順（`uv run`）に影響を与えない
- 既存の利用者が迷わないよう、廃止する場合は代わりの手順を README に書く
- エミュレーターの機能（ワークフロー、アダプタ）は変更しない

## スコープ外

- Tika の導入（#482）
- エミュレーター・アダプタ・server-local の機能変更
- クラウド側（ルートの compose）の変更

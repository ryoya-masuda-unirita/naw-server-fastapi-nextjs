# 02_基本設計

## 変更対象

- エミュレーター単体用の compose と、まとめて起動する側の compose（どちらを残すか、案による）
- それらを参照する README・手順書（エミュレーター、生成AIアダプタ、ルート、フロントエンドのチャット）
- エミュレーターの `.env` の例

## 画面 / API 変更概要

画面・API の変更はない。Docker の構成と手順書だけを変える。

## 影響範囲

- エミュレーターを Docker で動かす手順（開発者の日常の確認）
- 生成AIアダプタの動作確認の手順（server-local → エミュレーター → アダプタ）
- フロントエンドの手動の通しテストの手順
- 過去の Issue のドキュメント（`docs/issue-*`）は、当時の記録なので書き換えない

## 移植方針

移植元にない検証用の道具なので、移植元との対応はない。次の 2 案を比べて決める。

| | 案 A（推奨）: 単体を廃止して、まとめて起動する側に寄せる | 案 B: 2 つを残し、共通部分をまとめる |
|---|---|---|
| 構成 | compose は 1 つ。エミュレーターだけ動かしたいときは、サービス名を指定して起動する | 単体用と、まとめて起動する側の両方を残す |
| 重複 | なくなる | 共通の定義を 1 か所に置くが、compose は 2 つのまま |
| 手順書 | 1 系統に減る | 2 系統のまま |
| 失うもの | 「server-local をホストで動かし、エミュレーターだけ Docker」の構成（ストリームファイルをホストのディレクトリで共有する構成） | なし |
| 補う設定 | 学習で読むファイルの許可ディレクトリ、実行ユーザーなど、単体側にあってまとめて起動する側にない設定 | なし |
| 作業量 | 中（手順書の書き換えが主） | 中（compose の `include`・`extends` の検証が要る） |

**推奨の理由**: 差を調べた結果、単体側にだけ必要な機能は「ホストのディレクトリで共有する構成」だけだった。この構成は、ホストで両方を動かす手順（`uv run`）で代用できる。一方、まとめて起動する側は、ベクトル DB を含めて学習・削除まで通しで確かめられ、日常の確認にはこちらで足りる。重複の解消と、手順書の一本化の効果が大きい。

**決定（第1承認、2026-11-25）**: 案 A にする。

- エミュレーターは、顧客のオンプレには入らず、本物の Waha! の代わりに手元で確かめるための道具。単独で起動する compose を別に持つ理由は薄い。社内側の環境をまとめて起動する compose でも、エミュレーターだけを指定して起動できる
- 「server-local をホストで動かし、エミュレーターだけ Docker で動かす」構成は使わない。必要なときは、両方をホストで動かす手順で代わりにする
- 顧客のオンプレで動かす server-local 単体の compose は、この Issue では変更しない
- 単体側が固定していたコンテナ名に依存する手順（ログの確認など）は、まとめて起動する側の名前に直す

# 08_動作確認

実際に確認したことだけを書く。

## 確認した環境

- `waha-emulator/Dockerfile` から、別名のイメージ（`naw-waha-emulator-482:test`）をビルドして、コンテナの中で確認した
- 稼働中の `onprem/` のコンテナ（`naw-onprem-*`）は、置き換えていない

## ビルド

- ビルドは成功した。jar の SHA-512 の検証（`sha512sum -c`）を含む
- イメージのサイズは 968MB。手元の既存の `onprem` のイメージ（`naw-onprem-waha-emulator:latest`）は 559MB で、約 400MB 増えた（JRE と Tika の jar の分）

## コンテナの中での前処理（Tika あり。環境変数は既定のまま）

実際のファイルを `CoreMediaPreprocessingRuntime().preprocess()` に通した。

| ファイル | 結果 | 本文（先頭） | 時間 |
|---|---|---|---|
| `a.doc`（macOS の `textutil` で作成） | OK | `Hello RTFbody.` | 1.8s（Tika の起動を含む） |
| `a.xls`（`xlwt` で作成、日本語を含む） | OK | `売上` `商品` `数量` `りんご` `10`（末尾に Tika が出すヘッダー・フッター `&P` `&F`） | 0.1s |
| `a.rtf` | OK | `Hello RTFbody.` | 0.0s |
| `a.html` | OK | `見出し` `本文です`（`<script>` と `<title>` は出ない） | 0.1s |
| `a.txt` | OK | 日本語を含む本文 | 0.0s |
| `book.epub`（最小の EPUB を作成） | OK | `第一章の本文です` | 0.0s |
| `bad.doc`（OLE の先頭＋ゴミ） | `CORRUPT_FILE`（Tika が 422） | 要約に出たのはファイル名だけ | 0.0s |
| `unknown.bin`（乱数） | `UNSUPPORTED_MIME`（`application/octet-stream`） | | 0.0s |

- 前処理の終了後に `shutdown_tika()` を呼ぶと、Tika は止まった（`127.0.0.1:9998` に接続できなくなった）

### 実機で見つけて直した問題

- 初回の確認で、`a.rtf` の本文に `{\rtf1\ansi...` の制御語がそのまま出た。core の MIME 判定が RTF を `text/plain` と判定していたため。判定に RTF と EPUB を足して直し、イメージを作り直して、上の結果になった（03 に記載）

## コンテナの中での前処理（Tika なし。`TIKA_SERVER_JAR` を空にした）

- `a.doc`・`a.xls`・`bad.doc` は `UNSUPPORTED_MIME`、`a.txt`・`a.html` は従来どおり読めた
- `a.rtf`・`book.epub` は `UNSUPPORTED_MIME`（RTF は、判定を足す前は制御語が本文に入っていた）

## Shift_JIS のテキスト（code-review の指摘の確認）

Tika を通すと、短い Shift_JIS（CP932）の日本語が文字化けするのではないか、という指摘があった。コンテナの中で、Tika あり・なし（従来の自前デコード）を比べた。

| ファイル | 結果 |
|---|---|
| CP932 の短い文（`こんにちは`）、1 行、20 行の繰り返し、CP932 の CSV、UTF-8 の文 | どれも Tika あり・なしで同じ本文（文字化けなし） |

- 確認したのは、この 5 つのファイルだけ。すべての CP932 のファイルで文字化けしないことは、確かめていない

## イメージを作り直したあとの再確認

code-review の指摘への対応（ステータスの割り当ての変更）のあと、イメージを作り直し、上の「Tika あり」のファイルを通し直した。結果は同じ（壊れた `.doc` は `CORRUPT_FILE`、終了後は Tika が止まる）。

## 詳細

### 1. テキスト系も Tika を通る（🟡 注意）→ 対応しない

実際のコンテナで確かめた。CP932 の短い文（`こんにちは`）・1 行・20 行の繰り返し・CP932 の CSV・UTF-8 の文を、Tika あり・なし（従来の自前デコード）で通したところ、すべて同じ本文で、文字化けはしなかった（`08_動作確認.md`）。移植元も、テキスト系を含めて Tika を通す（要件 F5）。再現しないため、従来の経路を残す分岐は足さない。確認したのは 5 つのファイルだけで、すべての CP932 のファイルで文字化けしないとは言えない（08 に書いた）。

### 2. 4xx のすべてを `CORRUPT_FILE` にしている（🟡 注意）→ 対応済み

ファイルの問題にするのは、415（`UNSUPPORTED_MIME`）と 400・422（`CORRUPT_FILE`）だけにした。それ以外の成功でない状態（404・405・413・429・3xx・5xx）は、Tika 側の障害（`PARSER_FAILURE`）にする。`TIKA_URL` の誤りで、ファイルが壊れていると誤って報告されることを防ぐ。テスト（`test_non_file_status_raises_unavailable`）で、500・503・404・405・413・429・302 を確かめた。3xx は、指摘にはなかったが、同じ穴だったので足した（これまでは本文として返していた）。

### 3. RTF・EPUB で、Tika なしの動きが変わる（🔵 提案）→ 対応済み

意図した変更として、`01_要件定義.md` の F4 に明記した（RTF・EPUB だけは `UNSUPPORTED_MIME` になる）。RTF は、これまでは制御語がそのまま本文に入っており、不正な結果だった。判定を Tika が使えるときだけに限る案もあるが、判定が設定で変わるのは分かりにくいため、採らなかった。README にも書いてある。

### 4. 不正な `TIKA_URL`（🔵 提案）→ 対応済み

`TikaSettings` が、`http`・`https` 以外、またはホストがない URL を `ValueError` にする（`tika:9998`・`http://`・`ftp://...`・`localhost` をテスト）。設定の誤りは、起動時（`default_processors()`）に分かる。

### 5. 子プロセスの出力を捨てている（🔵 提案）→ 対応しない

クラウド側 #469 の `TikaClient` と同じ方式で、両方に同時に手を入れるほうがよい。また、ログに出すと、Tika のリクエストごとのログ（ファイル名を含む）を扱うことになり、出す範囲の判断が要る。別の Issue で、#469 と合わせて検討する。起動に失敗したときの手がかりは、今は「Tika did not become ready」と、ホストの JRE・ポートの確認に限られる。

### 6. `_borrowed` のロックの外の書き換え（🔵 提案）→ 対応済み

`extract_text` の失敗の処理で、ロックを取ってから書き換えるようにした。ロックを持った状態で HTTP の呼び出しは行わないため、デッドロックはない。

### 7. docstring・型ヒント（🔵 提案）→ 対応済み

`from_env` の入れ子の関数、テストの偽物のクラスと入れ子の関数に docstring を足し、`monkeypatch` に型を付けた。

### 8. `shutdown_tika()` のあとの再起動（🔵 提案）→ 対応済み

`shutdown()` で「止めた」印を立て、止めたあとの呼び出しは `TikaUnavailableError` にする（`test_no_restart_after_shutdown`）。`get_tika_client()` は、`shutdown_tika()` のあとに新しいクライアントを作るため、影響しない。

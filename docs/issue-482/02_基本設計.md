# 02_基本設計

## 構成（移植元・#469 に合わせる）

```
waha-emulator のコンテナ（1 つ）
├─ uvicorn（waha-emulator + アダプタ + core） ──HTTP（127.0.0.1:9998）──▶  Tika サーバー（java -jar、子プロセス）
└─ /opt/tika-server.jar（ビルドのときに取得・検証）
```

- 移植元は Tika をアダプタのプロセスの中で使う。Python は Java のライブラリを直接呼べないため、同じコンテナの中で子プロセスとして起動し、`localhost` で呼ぶ。コンテナは増やさない
- Tika を入れるのは `waha-emulator` のコンテナだけ。`secuaigent-server-local` と本物の Waha! には入れない

## 変更対象

- `waha-emulator` のコンテナのイメージ: JRE と jar を追加し、`TIKA_SERVER_JAR` を設定する
- core の前処理: Tika のクライアント（新規。同期版）と、設定の読み込み
- core のテキスト系プロセッサ: 対象を移植元に合わせ、Tika が使えるときは Tika で取り出す
- Tika サーバーの設定ファイル: 移植元の設定の再現
- エミュレーターの終了時: 起動した Tika を止める
- README: Tika の節の「現状」を更新し、移植元との差を書く

## 流れ

1. 埋め込みアダプタが、ファイルの前処理を呼ぶ
2. 専用プロセッサが読まない形式（画像・PDF・docx・pptx・xlsx・octet-stream 以外）で、Tika の設定があれば Tika に渡す（`TIKA_URL` → `TIKA_SERVER_JAR` → なし）
3. 起動していなければ起動して待つ → `PUT /tika` → 本文を受け取る
4. 設定がなければ、今のテキスト系の取り出し。以降（分割・埋め込み・保存）は変わらない

## 影響範囲

- コンテナのサイズが JRE と jar の分、メモリが Tika の JVM の分（ヒープ上限 256MB。遅延起動のため、使うまでは増えない）増える
- 設定がない環境（core の単体テストなど）は、今のまま
- Tika を使う環境では、これまでテキスト系の自前デコードで読んでいた形式（プレーンテキスト・CSV・HTML など）も Tika を通る（移植元と同じ）

## 移植元との差・未確認事項

- Tika サーバーの設定ファイルで、OCR なし・埋め込み画像の読み飛ばしを移植元と同じに再現できるかは未確認（詳細設計で、実際の Tika 3.1.0 で確かめる）。再現できない部分は、差として README に書く
- 同期クライアントの子プロセス管理（起動の直列化・プロセスをまたぐ複数 worker での起動の取り合い）は、#469 の考え方を踏襲する

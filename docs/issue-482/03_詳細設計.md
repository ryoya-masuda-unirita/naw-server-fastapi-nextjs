# 03_詳細設計

## 事前の実機確認（Tika 3.1.0 の jar を取得して確かめた）

jar は `tika-server-standard-3.1.0.jar`。SHA-512 は `server/Dockerfile` の固定値と一致した。

| 確かめたこと | 結果 |
|---|---|
| `PUT /tika`（`Accept: text/plain`、判定済みの MIME）で、テキスト・HTML・RTF・`.doc` | 本文が取れる。HTML の `<script>` の中身と `<title>` は出ない |
| 壊れた `.doc` | 422（ファイルの問題） |
| `Content-Type` を付けない（curl の既定の `application/x-www-form-urlencoded` のまま）送り方 | 200 だが本文が空になる。**必ず判定済みの MIME を付ける** |
| OCR | ローカルに `tesseract` があると、Tika が呼ぶ（画像の中の文字が出る）。設定の `DefaultParser` から `TesseractOCRParser` を除外すると、呼ばれなくなる（ログの呼び出し 0 件）。→ **再現できる** |
| 埋め込み画像の読み飛ばし | 画像のパーサー（`ImageParser`・`JpegParser`・`TiffParser`）を除外しても、本文に `[image: ]` と埋め込みのファイル名（`image1.png`）が出る。→ **設定では再現できない**。画像の中の文字は出ない（OCR なし） |
| `tika-config.xml`（Parser の一覧） | 移植元の中で、この設定ファイルを読み込む箇所が見つからなかった（ファイル名・`tika.config` の参照なし）。→ 再現しない。差として README に書く |

## 実機の確認で分かったこと（実装後に追記）

コンテナの中で、実際のファイルを前処理に通したところ、**RTF が読めなかった**（`{\rtf1...` の制御語がそのまま出た）。core の MIME 判定が、RTF を中身がテキストとして読めることから `text/plain` と判定し、その MIME を Tika に渡していたため。EPUB も、ZIP としか判定されず（`application/zip`）、同じ問題が起きる。当初の設計の「MIME の判定は変えない」を変えた。

- 先頭が `{\rtf` なら `application/rtf`、ZIP の先頭＋拡張子 `.epub` なら `application/epub+zip` と判定する
- Tika を使わない環境では、RTF・EPUB は `UNSUPPORTED_MIME` になる（RTF は、これまでは制御語がそのまま本文に入っていた）
- `.hwp` などは、判定を足していない（実際のファイルを用意できず、確かめられない）

## 設定（環境変数。core は pydantic を使わないため、標準の dataclass で読む）

| 環境変数 | 既定 | 内容 |
|---|---|---|
| `TIKA_SERVER_JAR` | なし | jar のパス。あれば遅延起動する |
| `TIKA_URL` | なし | 既存のサーバーを使う（起動しない）。`TIKA_SERVER_JAR` より優先 |
| `TIKA_JAVA_COMMAND` | `java` | JRE のコマンド |
| `TIKA_PORT` | 9998 | 子プロセスの待ち受けポート（1〜65535） |
| `TIKA_HEAP` | `256m` | 子の JVM のヒープ上限（数字＋`m`/`g`） |
| `TIKA_START_TIMEOUT_SECONDS` | 60 | 起動を待つ時間（0 より大きい） |
| `TIKA_REQUEST_TIMEOUT_SECONDS` | 120 | 1 回の抽出の時間（0 より大きい） |

不正な値は `ValueError`。`TIKA_URL` も `TIKA_SERVER_JAR` もなければ、Tika は使わない。

## Tika のクライアント（core に新規。同期版）

#469 の `TikaClient` を、同期にして移植する。

- 起動の直列化は `threading.Lock`（呼び出しは `asyncio.to_thread` の別スレッドから来る）。起動は Popen（標準入出力は捨てる）。親の JVM は `-Xmx64m`、子の JVM は設定ファイルの `forkedJvmArgs` で `-Xmx{heap}` と `-Djava.awt.headless=true` を渡す
- 起動前に `/version` が 200 を返すか確かめ、返すなら起動せずに借りる（複数のプロセスで同じポートを取り合わない）。借りた先が落ちたら、次の呼び出しで自分で起動する
- 子プロセスが落ちていたら、次の呼び出しで起動し直す
- 設定ファイルは一時ファイルに作り、終了時に消す。中身は #469 の設定（ヒープ）に、**`DefaultParser` から `TesseractOCRParser` を除外する指定を足す**
- HTTP: `PUT {base}/tika`、ヘッダは `Accept: text/plain`、`Content-Type`（判定済みの MIME）、`Content-Disposition: attachment; filename*=UTF-8''<パーセントエンコードしたファイル名>`
- `shutdown()` で子プロセスを止める（terminate → 5 秒待って kill）。終了時の呼び出しは、エミュレーターの `lifespan` から

### エラーの区別

| 状況 | 例外 | 前処理の失敗のコード |
|---|---|---|
| Tika が 415 | ファイルの問題 | `UNSUPPORTED_MIME` |
| Tika が 422 などの 4xx | ファイルの問題 | `CORRUPT_FILE` |
| Tika が 5xx、接続できない、起動できない、時間内に起動しない、設定が不正 | Tika 側の障害 | `PARSER_FAILURE`（要約に「Tika が利用できない」と書く） |

- 移植元は、Tika の失敗をすべて `RuntimeException`（→ `PARSER_FAILURE`）にする。**ファイルの問題を `CORRUPT_FILE`・`UNSUPPORTED_MIME` にするのは、区別するための差**
- 失敗の要約・ログに、ファイルの中身は出さない。ファイル名（`source_name`）は、既存の失敗と同じく要約に入れてよい
- 新しい失敗のコードは足さない（core の固定の集合を変えない）

## `TextCoreMediaProcessor` の変更

- `supports`: Tika が使えるとき（`is_enabled`）は、画像・`.pdf`・`.docx`・`.pptx`・`.xlsx`・`application/octet-stream` 以外すべて True（移植元と同じ）。使えないときは、今のとおり（テキスト系の MIME だけ）
- `process`: Tika が使えるときは、ファイルを読み、Tika で取り出し、前後の空白を除いて成功の結果にする。使えないときは、今のとおり
- 本文が空なら、既存の検証（`_validate`）が `PARSER_FAILURE` にする。変更しない
- MIME の判定（`detect_mime_type`）は変えない。判定できず `application/octet-stream` になったものは、今のとおり、どのプロセッサも受け持たず `UNSUPPORTED_MIME`（移植元も同じ）

## コンテナ（`waha-emulator/Dockerfile`）

`server/Dockerfile` と同じ形で、`TIKA_VERSION=3.1.0`・`TIKA_SHA512`（固定）・JRE（`default-jre-headless`）・curl（取得後に削除）を入れ、`/opt/tika-server.jar` を置き、`ENV TIKA_SERVER_JAR=/opt/tika-server.jar` を設定する。`USER app` の前に行う。`tesseract` は入れない（OCR は動かない。設定でも除外する）。`onprem/docker-compose.yml` は変更しない（同じ Dockerfile から作る）。

## エミュレーター

`lifespan` の終了処理に、起動した Tika を止める呼び出しを足す（`session_store.close()` の後）。

# 02_基本設計

## 変更対象

- LLM Chat API のビジネスロジック（`LlmChatService` 相当）
- メッセージ送信API のビジネスロジック（`MessageService` 相当）
- ライブラリ生成用の固定システムプロンプトを保持するマスタデータ（新規テーブル）
- ライブラリ生成ストリームのマーカー区切りロジック（新規の共有ユーティリティ）

## 画面 / API 変更概要

- LLM Chat API のリクエストに `createLibrary`（真偽値、デフォルト `false`）を追加する。
- メッセージ送信API のリクエストに `isCreateLibrary`（真偽値、デフォルト `false`）を追加する。
- 両APIとも、`createLibrary` 系フラグが真の場合、SSEストリームで新しいイベント種別 `library_title_delta`・`library_content_delta` を配信する。従来の `text_delta` は、ライブラリ生成モードでは「補足コメント」区間のみに使う。
- ライブラリ生成完了後、確定したタイトル・本文を新規ライブラリとして永続化する。

## 影響範囲

- LLM Chat API・メッセージ送信APIのリクエストスキーマ（後方互換: 新規フィールドはデフォルト `false` のためオプトイン）。
- 両APIのストリーミングイベント種別が増える（クライアント側が新イベントを無視しても既存動作は壊れない）。
- 新規テーブル（ライブラリ生成用固定システムプロンプト）の追加。既存テーブルへの破壊的変更はない。

## 移植方針

- 移植元 Java 版は `LibraryStreamRouter`（ステートマシン）を `Consumer<String>` コールバックで駆動する設計だが、Python版では非同期ジェネレータで直接 SSE バイト列を `yield` する構造に合わせ、コールバック方式ではなく「デルタを1件受け取り、配信すべき (区分, テキスト) のリストを返す」関数型のインターフェースとして移植する。区切り判定アルゴリズム自体（チャンク境界をまたぐマーカーの hold-back処理を含む）は移植元と同一のロジックを踏襲する。
- ライブラリ生成用の固定システムプロンプト（移植元の `system_prompt_templates` テーブル・`SystemPromptTemplateService`）は、Python側に対応するテーブル・モデルが存在しないため新規に作成する。テナントに依存しないアプリケーション共通マスタデータのため、Alembicマイグレーションでテーブル作成とシード投入（`type='LIBRARY'`の1行）を同時に行う（既存の `ai_models` 等のマスタデータ投入パターンを踏襲）。
- マーカー区切りロジック・マーカー定数・ユーザー指示前置テキストは、`message_service.py`・`llm_chat_service.py` の両方から使う共有クラス/定数のため、既存の `AzureLlmChatClient` 等と同様に `app/core/` に配置する（`service` が別の `service` を呼ばない規約は維持しつつ、`core/` の共有インフラとして扱う）。
- 一方、「追加プロンプトの前置」「ライブラリ用固定指示の前置」といった、リクエストごとの小さな変換ロジック（`_apply_additional_prompt` 相当）は、既存コードが「serviceがserviceを呼ばない」規約のもとで意図的に両ファイルへ複製している既存パターンに合わせ、新規に追加する「ライブラリ用固定指示の前置」ヘルパーも同様に両ファイルへ複製する。
- ライブラリの永続化は `LibraryRepository.save`（issue-65で実装済み）をそのまま利用する。

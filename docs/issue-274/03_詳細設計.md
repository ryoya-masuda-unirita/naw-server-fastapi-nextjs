## 環境変数（`Settings`）

| 環境変数 | 既定値 | 説明 |
|---|---|---|
| `WAHA_AUTHKEY` | なし（必須・空不可） | `startsession` の `authkey` と照合する。server-local の `WAHA_AUTHKEY` と同じ値を設定する |
| `EXECUTE_WAIT_FOR_COMPLETION` | `true` | `true`: execute はジョブの完了まで応答しない。`false`: 受け付けたらすぐ `OK` を返す（02 参照） |
| `STREAM_ALLOWED_DIR` | 未設定 | 設定すると、`streamfilepath` はこのディレクトリの中（シンボリックリンクを解決した後）だけを許す。Docker イメージでは `/app/data/stream-output` |
| `SESSION_IDLE_TIMEOUT_SECONDS` | `3600` | この時間使われていないセッション（実行中のジョブがないもの）を、次の `startsession` で破棄する（code-review #2） |
| `LLM_PROVIDER` | `echo` | `echo` / `azure_openai` |
| `AZURE_OPENAI_ENDPOINT` | 空 | `azure_openai` のとき必須 |
| `AZURE_OPENAI_API_KEY` | 空 | `azure_openai` のとき必須 |
| `AZURE_OPENAI_DEPLOYMENT` | 空 | `azure_openai` のとき必須（chat completions の `model`） |
| `AZURE_OPENAI_API_VERSION` | `2024-10-21` | backend の `AZURE_OPENAI_API_VERSION` の既定値と同じ |
| `LOG_LEVEL` | `INFO` | 大文字にそろえる。logging にない名前は起動時にエラー |

`azure_openai` で必須の値が空なら、`Settings` の検証で起動時にエラーにする。

## API（`routers/servicerun.py`）

ルーターのプレフィックスは `/WahaServer/servicerun/api`（server-local の `SERVICE_RUN_PATH`）。応答は `PlainTextResponse`（`text/plain; charset=utf-8`）。

| 関数 | 処理 |
|---|---|
| `start_session(authkey)` | `hmac.compare_digest` で照合。不一致は 401（本文に authkey を含めない）。一致したら `SessionStore.create()` の ID を返す |
| `end_session(sessionid)` | `SessionStore.end()`。実行中のジョブはキャンセルする |
| `upload(slot, sessionid, file)` | `INPUT_SLOTS` 以外は 400。`UploadFile` を読み、`SlotFile(filename, content_type, data)` として上書き保存 |
| `execute(service_id, request, sessionid)`・`execute_without_service_id`（`/execute/`） | server-local はアシスタント ID・サービス名が未指定だと空文字列で呼ぶため、`/execute/` も同じ処理（サービス ID は空）で受ける。`sessionid` 以外のクエリを `params` にする。実行中なら 409。`registry.resolve()` でワークフローを選び、`jobs.start_job()` でタスクを作る。同期なら `asyncio.shield()` でジョブの完了を待ち、`result_text()` を返す |
| `result(sessionid)` | `session.result_text()`: ジョブなし → `RUNNING`、実行中 → `RUNNING`、成功 → `SUCCESS`、失敗 → `FAILURE: 理由` |
| `download(slot, sessionid)` | スロットの中身を UTF-8 で返す。空なら 404 |

エラーは `EmulatorError(status_code, message)` を投げ、例外ハンドラーでテキストの応答にする。

## セッション（`sessions.py`）

- `SlotFile`: `filename`・`content_type`・`data: bytes`
- `JobStatus`: `RUNNING` / `SUCCESS` / `FAILURE`
- `Job`: `task`・`status`・`error`。`cancel()` はタスクを止め、まだ `RUNNING` なら「ジョブが中断されました」で失敗にする（タスクが一度も動く前に止めた場合も `RUNNING` のまま残さない）
- `Session`: `id`・`last_used`・`slots: dict[str, SlotFile]`・`job: Job | None`。`result_text()` を持つ
- `SessionStore(idle_timeout_seconds)`: `create()`（ID は `uuid4().hex`。その前に、`last_used` が `SESSION_IDLE_TIMEOUT_SECONDS` より古く実行中のジョブがないセッションを破棄する）・`get()`（ないと 404。`last_used` を更新）・`end()`（取り除き、ジョブを `cancel()`）・`close()`（アプリ終了時に全ジョブを `cancel()`）
- 破棄を入れたのは、server-local の学習データの同期（`file_service.py`）が `get_results` の失敗時に `end_session` を呼ばず、エミュレーターは同期を常に失敗させるため、呼ぶたびにセッションが残り続けるから

## ジョブ（`jobs.py`）

`start_job(session, workflow, service_id, params, settings) -> Job` がタスクを作り、`session.job` に入れる。タスクの中身（`_run`）:

1. `params` に `streamfilepath`（空でない）があれば `StreamFile.open(path, settings.stream_allowed_dir)`
2. `WorkflowRequest(service_id, params, inputs=セッションのスロットの写し, stream)` で `workflow.run()` を呼ぶ
3. 成功: 戻り値を `outputfile` スロットに保存 → ストリームに `{"type":"completed"}` → `SUCCESS`。`completed` を書けなくても（回答は outputfile で返せるため）成功にする
4. `WorkflowError`・`StreamFileError`（想定内の失敗）: 理由をそのまま記録して `FAILURE`。それ以外の例外: スタックトレースをログに出し、`型名: メッセージ` を記録して `FAILURE`。どちらもストリームに `{"type":"error","message":理由}` を書く（書けなければ警告ログのみ）
5. キャンセル: `FAILURE`（理由「ジョブが中断されました」）にし、ストリームに `error` を書いて再送出
6. 最後にストリームファイルを閉じる（閉じられなくても警告ログのみ）

## ストリームファイル（`stream_file.py`）

### server-local の読み取り処理（根拠）

`server-local/app/services/message_content_stream_service.py` と `app/services/stream/tail_reader.py` を読んだ結果:

| 項目 | server-local の動作 | 根拠 |
|---|---|---|
| 読み取り | 前回のバイト位置から追記分を読む。UTF-8 の途中で切れた文字は次回に回す | `StreamFileTailReader.read_new`・`_decode` |
| イベントの区切り | 空行区切りの SSE ブロック（`\n\n`）と、`data:` で始まる 1 行（`data:{...}\n`）の両方を 1 イベントにする。改行で終わっていない最後の行は書き込み途中として残す | `_extract_complete_events` |
| 終端 | `data:` の JSON の `type` が `completed` なら COMPLETED、`error` なら ERROR | `_detect_terminal_type` |
| NAW_COMPATIBLE（`POST /api/messages/content`） | `reasoning_delta`・`library_title_delta`・`library_content_delta` だけをブラウザへ中継する。**`text_delta`・`message_stop`・`message_content`・`completed`・`error` は無視する**（コメント「完了・回答は Waha! の outputfile から確定するため」）。ただし終端が `error` ならエラーで確定する | `FORWARD_EVENT_TYPES`・`IGNORED_EVENT_TYPES`・`_handle_stream_chunk`・`_process_stream_file_read` |
| LEGACY_PASSTHROUGH（`POST /api/messages/content/stream`） | `data:` のペイロードを種類を問わずそのままブラウザへ中継する | `_handle_stream_chunk` |
| 完了の判定 | `result` が `SUCCESS` になった時点で、ストリームの読み残しを読み切ってから outputfile を download して確定する。ストリームの終端（`completed`）は必須ではない（なければ警告ログを出すだけ） | `_result_loop`・`_try_finalize`・`_drain_pending_stream_events` |
| NAW_COMPATIBLE の回答 | 確定時に outputfile の `answer` を `text_delta` 1 回で送り、続けて `message_stop`・`message_content` を送る | `_try_finalize` |

### どの形式で書けば NAW_COMPATIBLE で回答が逐次表示されるか

**結論: server-local（移植元どおり）の NAW_COMPATIBLE では、ストリームファイルに何を書いても回答本文は逐次表示されない。** 回答は outputfile から確定時に 1 回の `text_delta` で送られる。ストリームファイルから逐次中継されるのは `reasoning_delta`（推論の途中経過）と `library_*_delta`（ライブラリ生成）だけ。

- 移植元アダプタ（`generative-ai-adapter` の `ReasoningOutputSink`）も、ストリームファイルには `data:{"type":"reasoning_delta","text":"..."}` + `\n`（1 行形式・追記）で**推論の要約だけ**を書き、回答本文は書かない。ブラウザ（移植元 `client` の `message-content-stream.service.ts`）は `reasoning_delta` を回答とは別の欄（`onReasoningDelta`）に出す
- 回答本文を `reasoning_delta` として書けば NAW_COMPATIBLE でも逐次届くが、推論の欄に回答が出て、確定時に同じ回答がもう一度出るため採らない
- 回答を NAW_COMPATIBLE で逐次表示するには server-local 側（`IGNORED_EVENT_TYPES` から `text_delta` を外す等）の変更が要る。本 Issue では server-local を変更しないため、未確定事項として報告する

### エミュレーターが書く形式

移植元アダプタと同じ 1 行形式（`data:` の直後に空白なし、JSON は 1 行、末尾 `\n`）で、1 イベントごとに書いて flush する。

| タイミング | 書く内容 | NAW_COMPATIBLE | LEGACY_PASSTHROUGH |
|---|---|---|---|
| LLM の応答の差分ごと | `data:{"type":"text_delta","text":"差分"}\n` | 無視（回答は確定時にまとめて表示） | そのまま中継（逐次表示される） |
| 成功時（outputfile を書いた後、`SUCCESS` にする前） | `data:{"type":"completed"}\n` | 終端として認識。無視 | そのまま中継 |
| 失敗時 | `data:{"type":"error","message":"理由"}\n` | 終端 ERROR としてエラーで確定 | そのまま中継 |

- `text_delta` にしたのは、回答本文の差分を表す種類で、LEGACY_PASSTHROUGH では逐次表示され、NAW_COMPATIBLE では害なく無視されるため（server-local が受け付ける種類の中で、回答の途中経過として意味が合うのはこれだけ）
- 空の差分は書かない（移植元アダプタの `appendDelta` と同じ）
- `completed` を書くのは、server-local が「終端なしで確定」の警告を出さないようにするため。outputfile を保存した後に書く
- JSON は `ensure_ascii=False`（server-local は UTF-8 として読む）

### 開き方

- `os.open(path, O_WRONLY | O_APPEND)`（`O_CREAT` なし）。ファイルがなければ `FileNotFoundError` でジョブを失敗させる（移植元アダプタの `StandardOpenOption.APPEND` と同じ）
- `STREAM_ALLOWED_DIR` が設定されていれば、`Path(path).resolve()` が `Path(dir).resolve()` の中でなければ失敗にする。確かめた解決後のパスを `O_NOFOLLOW` 付きで開き、確かめた後にシンボリックリンクへ差し替えられても辿らない

## ワークフロー（`workflows/`）

```python
@dataclass(frozen=True)
class WorkflowRequest:
    service_id: str
    params: Mapping[str, str]
    inputs: Mapping[str, SlotFile]
    stream: StreamFile | None

class Workflow(Protocol):
    async def run(self, request: WorkflowRequest) -> str: ...  # outputfile の中身

class WorkflowError(Exception): ...  # 理由をそのまま result に出す失敗
```

- `WorkflowRegistry(default, by_service_id=None)`: `register(service_id, workflow)`・`resolve(service_id, params)`（02 の順序）
- `UnsupportedWorkflow(name)`: `WorkflowError(f"{name}は未対応です")` を投げる。`LEARNING`（学習）・`SYNC`（同期）を用意する
- `ChatWorkflow(llm)`:
  - `question` がなければ `WorkflowError("question がありません。チャット以外のサービス（学習データの削除など）は未対応です")`
  - `history` は `[{"role": "USER"|"ASSISTANT"|"SYSTEM"|null, "content": ...}]`（server-local の `waha_inputs.py`）。role を小文字にして `ChatMessage` にする。role が null・不明なものは渡さない。JSON として読めなければ `WorkflowError`
  - `textdata` は JSON。`createLibrary` が true なら `WorkflowError("ライブラリ生成（createLibrary）は未対応です")`。`tools` は使わない（ログに出すだけ）
  - 出力: `json.dumps({"answer": ..., "filepaths": [], "references": []}, ensure_ascii=False)`

## LLM（`llm/`）

```python
Role = Literal["system", "user", "assistant"]

@dataclass(frozen=True)
class ChatMessage:
    role: Role
    content: str

class LlmClient(Protocol):
    def stream_chat(self, messages: Sequence[ChatMessage]) -> AsyncIterator[str]: ...
```

- `EchoLlmClient`: 最後のメッセージ（質問）の内容を `ECHO_CHUNK_SIZE`（8 文字）ずつ返す
- `AzureOpenAiLlmClient(endpoint, api_key, deployment, api_version)`: backend の `AzureLlmChatClient.stream_chat` と同じく、リクエストごとに `AsyncAzureOpenAI` を `async with` で作り、`chat.completions.create(model=deployment, messages=..., stream=True)` の `choices[0].delta.content` を返す。temperature・max_tokens は送らない（モデルの既定値）
- `create_llm_client(settings)`: `LLM_PROVIDER` で選ぶ

## アプリ（`main.py`）

- `create_app(settings=None, *, llm_client=None, registry=None)`: テストで LLM・ワークフローを差し替えられるようにする。既定の registry は `WorkflowRegistry(default=ChatWorkflow(llm_client))`
- lifespan の終了時に `SessionStore.close()`
- `app_factory()`: uvicorn の `--factory` 用

## Docker

- `Dockerfile`: server-local と同じ（`python:3.12-slim`、`ghcr.io/astral-sh/uv:0.11.25`、`uv sync --no-dev --frozen`、uid 1000 の `app` ユーザー）。`ENV STREAM_ALLOWED_DIR=/app/data/stream-output`。起動は `uvicorn waha_emulator.main:app_factory --factory --host 0.0.0.0 --port 8080 --no-access-log`
- `docker-compose.yml`: ホストの `${WAHA_EMULATOR_PORT:-8091}` → 8080。`${WAHA_EMULATOR_STREAM_DIR:-../server-local/data/stream-output}` を `/app/data/stream-output` にマウントする（server-local のコンテナ内のパスと同じにし、`STREAM_WAHA_OUTPUT_DIR` を設定しなくて済むようにする）。マウントは `create_host_path: false` にし、ディレクトリがなければ起動エラーにする（Docker に root 所有で作らせると、Linux で uid 1000 の server-local が書けなくなるため。code-review #1）。`user` は server-local と同じ UID/GID（ストリームファイルは server-local が作るため）。`TZ`（既定 `Asia/Tokyo`）でログの時刻を server-local と揃える

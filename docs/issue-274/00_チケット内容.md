# #274 issue-274 Waha!エミュレーターの土台を作る

## 概要

SECURE アシスタントの処理で `server-local/` が呼ぶ Waha!（ユニリタの ETL 製品）の代わりに、同じ HTTP API を持つ Python のサービス（Waha! エミュレーター）を作る。本 Issue はその**土台**で、`server-local/` から通しで動く最小の形までを作る。

方針（2026-11-13 決定）:

- 移植元のリポジトリに Waha! 本体はないため、こちらで Waha! の代わりを作る
- 先にエミュレーターを薄く作り、そのあと `generative-ai-adapter`（生成AI・検索・埋め込みのアダプタ）を 1 つずつ Python に移植して差し込む
- 経路と部品の担当は README の「アシスタントの種類ごとの通信経路」を参照

## 説明

### 作るもの

新しいモジュール（ルートに `waha-emulator/`。FastAPI・uv の独立したプロジェクト）。

`server-local/app/clients/waha_client.py` が使っている API だけを、同じパス・パラメータ・応答で作る（ベースパス `WahaServer/servicerun/api`）。

| API | パラメータ | 応答 |
|---|---|---|
| `GET /startsession` | `authkey` | セッション ID（テキスト） |
| `GET /endsession` | `sessionid` | テキスト |
| `POST /upload/{slot}` | `sessionid`、multipart の `file` | テキスト |
| `GET /execute/{serviceId}` | `sessionid`。チャットは `streamfilepath`、学習は `splitLength`・`filepath`、同期は `start`・`end` | テキスト |
| `GET /result` | `sessionid` | `SUCCESS` で始まる／`RUNNING`／それ以外は失敗 |
| `GET /download/{slot}` | `sessionid` | 出力ファイルの中身（テキスト） |

- スロット: `file`・`question`・`attachmentfile`・`history`・`textdata`（入力）、`outputfile`（出力）
- `authkey` を確認する。セッションごとにスロットのファイルを保持し、`endsession` で破棄する
- ジョブの状態（実行中・成功・失敗）を `result` で返せるようにする

### ワークフロー（土台では仮の中身）

- サービス ID からワークフローを選ぶ仕組みだけを作る（チャットではサービス ID = アシスタントのモデル指定）
- 仮のチャット用ワークフロー: `question`（と `history`）を LLM に 1 回渡し、回答を `outputfile` に移植元と同じ形式（`{"answer", "filepaths", "references"}` の JSON）で書く。途中経過は `streamfilepath` のファイルに、`server-local/` が読める形式で書く
- 学習・削除・同期のワークフローは、土台では「未対応」の失敗を返すだけでよい
- LLM の接続先の設定方法（環境変数など）は着手時に決める

### 完了条件

- `server-local/` の `WAHA_URL` をエミュレーターに向け、SECURE アシスタントのチャットが通しで動く（ブラウザ → server-local → エミュレーター → LLM → 回答の表示）。自動テストでも、`server-local/` の `WahaClient` から呼んだときの往復を確かめる
- Docker（Linux）で起動できる（`server-local/` と同じく）
- README に起動方法と、`server-local/` との組み合わせ方を書く

### 対象外（後続の Issue）

- アダプタ（生成AI・検索・埋め込み）の移植と差し込み
- ワークフローの定義（どのサービス ID で、どのアダプタを、どの設定で動かすか）の仕様。本物の Waha! の設定はどちらのリポジトリにもないため、別途決める
- 学習データの登録・削除・同期

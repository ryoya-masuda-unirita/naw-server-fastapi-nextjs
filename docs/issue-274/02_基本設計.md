## 画面 / API 変更概要

画面の変更はない。エミュレーターが次の API を提供する（ベースパス `WahaServer/servicerun/api`。応答はすべてテキスト）。

| API | 正常時の応答 | エラー |
|---|---|---|
| `GET /startsession?authkey=` | セッション ID | 認証キーの不一致は 401 |
| `GET /endsession?sessionid=` | `OK` | 存在しないセッションは 404 |
| `POST /upload/{slot}?sessionid=`（multipart の `file`） | `OK` | 入力スロット以外は 400、存在しないセッションは 404 |
| `GET /execute/{serviceId}?sessionid=&...` | 同期実行: ジョブの結果（`/result` と同じ文字列）。非同期実行: `OK` | 実行中のジョブがあれば 409、存在しないセッションは 404 |
| `GET /result?sessionid=` | `RUNNING` / `SUCCESS` / `FAILURE: 理由` | 存在しないセッションは 404 |
| `GET /download/{slot}?sessionid=` | スロットの中身 | スロットが空・存在しないセッションは 404 |

- HTTP エラーはすべて server-local で `ExternalServiceError`（ジョブの失敗）として扱われる。エラーの本文には認証キーを含めない
- 認証キーは `startsession` だけで確かめる。以降はセッション ID で呼び出し元を見分ける（server-local の呼び出し方と同じ）

### execute の方式（同期で完了まで返さない／非同期で返す）

**方式: 既定は同期（ジョブの完了まで応答しない）。環境変数で非同期（受け付けたらすぐ応答）にも切り替えられる。**

server-local の呼び出し方を読んだ結果は次のとおり。

| server-local の処理 | 呼び出しの順序 | 同期の場合 | 非同期の場合 |
|---|---|---|---|
| SSE（`/api/messages/content`・`/content/stream`） | `startsession` → upload → **結果のポーリングと tail の読み取りを開始** → `execute`（応答を待つ） | 動く。execute を待つ間も、ポーリングは別タスクで続く。結果が `SUCCESS` になった時点で確定する | 動く。ポーリングに回数の上限がなく、SSE のタイムアウト（既定 10 分）まで待つ |
| 同期 API（`/content/sync`）・学習・削除・同期 | `startsession` → upload → `execute` → `get_results`（ポーリング）→ download | 動く。execute が返った時点でジョブは終わっているため、最初のポーリングで `SUCCESS` になる | ジョブが「ポーリング間隔 × 上限回数」（既定 2 秒 × 10 回 = 20 秒）を超えると、`get_results` が**例外にせず戻り**、終わっていない outputfile を download して失敗する |

- server-local は Waha! への HTTP のタイムアウトを無制限にしており、「execute はジョブ完了まで応答しないことがある」とコメントしている。本物の Waha! が同期で応答する前提の作り
- LLM の応答は数十秒かかることがあるため、非同期にすると同期 API で失敗しうる。同期ならどちらの経路でも動く
- 以上から既定を同期にする。非同期は「すぐ応答する Waha!」を想定した確認用に残す（両方の方式で server-local が動くことを自動テストで確かめる）
- ジョブは HTTP リクエストとは別のタスクで動かす。同期の execute で呼び出し元が切断しても、ジョブは最後まで動いて結果を残す

### execute 前の result

server-local の SSE は execute を呼ぶ**前**に結果のポーリングを始める（初回は間隔を空けてから）。execute の前に `result` が呼ばれても失敗と判定されないよう、**ジョブがまだないセッションの `result` は `RUNNING` を返す**。同期 API などは execute の後にしか `result` を呼ばないため、この扱いで困る呼び出しはない。

## ワークフロー

### 選び方

execute のサービス ID とパラメータから、次の順で選ぶ。

1. サービス ID に登録されたワークフローがあれば、それを使う（後続の Issue でアダプタを差し込むときはここに登録する）
2. パラメータに `splitLength` または `filepath` があれば「学習」（未対応）
3. パラメータに `start` または `end` があれば「同期」（未対応）
4. それ以外は既定のワークフロー（仮のチャット）

削除は server-local からパラメータなしの execute（`file` スロットに部品 ID の一覧）で呼ばれ、チャットと見分けられない。仮のチャットは `question` がないと「未対応」で失敗するため、削除も結果として「未対応」の失敗になる。

### 仮のチャット

1. `question`（必須）・`history`（任意）・`textdata`（任意）を読む
2. `textdata` の `createLibrary` が true なら「ライブラリ生成は未対応」で失敗にする
3. 履歴（役割 SYSTEM / ASSISTANT / USER）と質問を LLM に 1 回渡し、応答をストリーミングで受け取る
4. 応答の差分ごとに、ストリームファイルへ `text_delta` を書く（形式は 03）
5. 応答をつないだものを `{"answer": 回答, "filepaths": [], "references": []}` の JSON にして `outputfile` に書く。移植元アダプタ（`RetrievalAnswer`）はチャットで `filepaths`・`references` を空リストで出力するため同じにする

### ジョブの共通処理

- `streamfilepath` があればジョブの最初にストリームファイルを追記で開く。**ファイルがなければ作らずにジョブを失敗させる**（移植元アダプタも作らずに追記で開き、開けなければ失敗にする。server-local は execute の前にファイルを作っている）
- 書き込み先を制限するディレクトリが設定されていれば、その外のパスは失敗にする
- 成功したら outputfile を書いた後、ストリームに `completed` を書き、状態を `SUCCESS` にする。失敗したらストリームに `error` を書き（書けなくても続ける）、状態を `FAILURE` にする

## LLM の接続先

| 設定値 | 動作 |
|---|---|
| `echo`（既定） | 質問の文字列を、数文字ずつに区切って差分として返す。キー不要 |
| `azure_openai` | Azure OpenAI の chat completions をストリーミングで呼ぶ（backend の Azure OpenAI クライアントと同じ SDK・呼び方）。エンドポイント・API キー・デプロイ名は必須、API バージョンは backend と同じ既定値 |

## 影響範囲

- 既存のモジュールの動作に影響はない（新規追加のみ。ドキュメントと pre-commit の対象の追記）
- エミュレーターのテストは server-local のコードを読み込んで使うため、server-local の Waha! クライアント・ストリーム処理が変わったときは、エミュレーターのテストで食い違いが分かる

## 移植方針

- 移植元に Waha! 本体はないため、API の仕様は server-local の Waha! クライアント（移植元 `ServiceRunService` の移植）を正とする
- ストリームファイル・outputfile の形式は、server-local のストリーム処理（移植元 `MessageContentStreamService`・`StreamFileTailReader` の移植）と、移植元アダプタ（`ReasoningOutputSink`・`RetrievalAnswer`）を根拠に決める（詳細は 03）
- パッケージ名は `app` ではなく `waha_emulator` にする。server-local のパッケージ名が `app` で、結合テストで両方を同じプロセスに読み込むため
- セッションはメモリに持つ（再起動で消える）。server-local は 1 回の処理の中で startsession から endsession までを呼ぶため、永続化は要らない
- 認証キーがアクセスログに残らないよう、uvicorn のアクセスログは出さない（server-local の #252 と同じ考え方）

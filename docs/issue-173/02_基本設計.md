# 02_基本設計

## 変更対象

- ライブラリのリポジトリ層（一覧取得の絞り込み条件組み立て）
- ライブラリ一覧取得の自動テスト

## 画面 / API 変更概要

- API仕様の変更なし（リクエストパラメータ名・型・レスポンス形式は従来どおり）
- タグ絞り込みでHTTP 500になっていた不具合のみを解消する

## 影響範囲

- ライブラリ一覧取得APIのタグ絞り込み処理のみ
- ライブラリ更新時のタグ付け替え処理は、もともとタグIDを文字列で扱っており影響なし

## 移植方針

### 原因の詳細

起票時の見立てに加えて、調査で以下が分かった。

- ORM（SQLAlchemy）は、文字列型の列に対する `IN` 比較でも、渡された値がUUIDオブジェクトの場合はバインドパラメータの型をUUID型と推論する
- SQLite方言ではUUID型のバインド処理が値をハイフンなし32桁hex文字列に変換するため、保存値（同じくハイフンなしhex）と一致してしまい、既存の自動テストは成功していた
- PostgreSQL（asyncpg）方言ではUUIDがネイティブ型のまま送られるため、文字列型の列との比較でエラーになる

### 対応方針

| 案 | 内容 | 採否 |
|---|---|---|
| A | タグID列をUUID型に変更する（移植元に合わせる） | 不採用。タグテーブル・中間テーブル双方のマイグレーションが必要で、既存データの変換も伴う。本Issueはバグ修正のため影響が大きすぎる |
| B | 起票時案: 比較前に `str(UUID)` で文字列化する | 不採用。`str(UUID)` はハイフン付き形式になり、保存値（ハイフンなしhex）と一致しない |
| C | APIのパラメータを文字列で受ける | 不採用。移植元はUUID型で受けており、不正な値の入力チェックが失われる |
| D | APIではUUIDとして受け（入力チェック維持）、リポジトリでDBの保存形式（ハイフンなし32桁hex文字列）に変換して比較する | **採用** |

案Dにより、DBスキーマ・API仕様を変えずに、PostgreSQLへ渡す値を列の型（文字列）と一致させる。DBの保存形式を知っているのはリポジトリ層であるため、変換はリポジトリ層で行う。

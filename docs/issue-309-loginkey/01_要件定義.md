# 01_要件定義

## 背景

ログインキーは、URL に付けるだけでログインできる秘密情報である。backend はユーザー一覧・プロフィール・グループのメンバー一覧で、保存しているログインキーの値をそのまま返している。管理画面を開ける人や、本人のブラウザの通信を見られる人が、他人のキーを知ってなりすませる。

移植元 Spring Boot（NAW-1342 AC-03、2026-10-26）は、発行したとき以外はログインキーを返さず、設定済みかどうかだけを `hasLoginKey` で返す。React の型（移植元 client の複製）も `hasLoginKey` を読む。

## 機能要件

1. プロフィール取得・更新、ユーザー一覧の各行は、ログインキーの値を返さず、`hasLoginKey`（真偽値）を返す
2. グループのメンバー一覧の各行は、ログインキーの値を返さない（移植元は `hasLoginKey` も返さない）
3. ユーザー作成・更新の応答は、移植元と同じ項目（`id`・`loginId`・`name`・`role`・`loginKey`・`hasLoginKey`・`isRequiredPasswordReset`・`initialPassword`・`passwordExpiredAt`）にする。`loginKey` には、**そのリクエストで設定したキーだけ**を入れ、設定していなければ null にする。保存済みのキーは返さない
4. ユーザー作成・更新の応答には `Cache-Control: no-store` を付ける（初期パスワードやキーを平文で返すため。移植元と同じ）
5. プロフィールの応答は、移植元の `@JsonInclude(NON_NULL)` と同じく null の項目（`totalCredits`）を出さない

## 非機能要件

- DB の構造は変えない（マイグレーションなし）
- ログインキーでのログイン（`POST /auth/login-key`）の動きは変えない

## スコープ外

次は 2 本目の PR（`feature/issue-309`）で扱う。

- ユーザー作成の `issueLoginKey`・更新の `loginKeyAction`（KEEP・REISSUE・REVOKE）によるサーバー側でのキー発行と、廃止した `loginKey` リクエスト項目の 400 拒否（移植元 NAW-1342 AC-01・NCM-02）
- ログインキーを DB にハッシュ値だけで保存する変更（移植元 NAW-1343。列の置き換えにマイグレーションが要る）
- CSV 取り込みの `createLoginKey` 列の廃止（移植元 NAW-1342 AC-04）
- ユーザー一覧のページングの `page` → `number` など、Issue の「そのほか」の項目

# 02_基本設計

## 変更対象

- テナントエンドポイントの種別定義（`EndpointType`）
- チャットAPI（ストリーミング応答）の呼び出し先解決ロジック
- LLM呼び出しクライアント（新規追加）
- 依存パッケージ（Anthropic公式SDK追加）

## 画面 / API変更概要

- チャットAPI自体のリクエスト/レスポンス形式は変更しない
- テナント管理者向けのテナントエンドポイント登録UI（フロントエンド）で、種別選択肢に
  Bedrock用の項目が増える想定（本Issueではバックエンドのみ対応し、フロントエンド対応は
  別途優先度を確認する）
- 呼び出すAIモデル（`deployName`相当）に紐づくエンドポイント種別に応じて、内部的に
  呼び出し先のクライアント実装が切り替わる（クライアントから見た呼び出し方は変わらない）

## 影響範囲

- 現状Azure OpenAI固定になっているチャットAPIの呼び出し分岐ロジック
  （AIモデル・テナントエンドポイントの検索条件）
- 新規LLM呼び出しクライアント
- トークン使用量記録（呼び出したプロバイダに応じて記録内容が変わりうる）
- 依存パッケージ・環境変数（Anthropic公式SDK追加。Bedrock固有の環境変数追加は不要、
  テナントごとの接続情報は`tenant_endpoints`にDB管理する既存方針を踏襲する）

## 移植方針

- 移植元（Spring Boot / naw-server）にBedrock関連の実装は無いため、完全に新規設計とする
- Bedrock Mantleエンドポイントは、Anthropic公式APIと同一のMessages API形式で呼び出せるため、
  Anthropic公式SDKをそのまま使い、`base_url`にBedrock Mantleのエンドポイント、`api_key`に
  Bedrock API keyを渡すだけで対応する（AWS SigV4署名・`boto3`は使わない）
- 既存の`AzureLlmChatClient`（Azure OpenAI SDKをラップしたクライアント）と同じ位置づけで、
  Bedrock用のクライアントを新設する
- チャットAPIの呼び出し分岐ロジックは、現状の「Azure OpenAI固定」から「AIモデルに紐づく
  エンドポイント種別を見て呼び出し先を切り替える」形に一般化する。これにより、元々
  マルチプロバイダを想定していた`ai_models`・`tenant_endpoints`のテーブル設計を実際に
  活かす形にする

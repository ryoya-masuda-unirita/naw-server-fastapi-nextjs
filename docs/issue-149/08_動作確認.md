# 08_動作確認

## 確認環境

- `docker compose up -d postgres`でPostgreSQLをローカル起動（既存稼働中のコンテナを利用）
- `uv run alembic upgrade head`でマイグレーション適用（`023_add_bedrock_chat_endpoint_type`含む）
- `docker exec -i naw-fastapi-postgres psql -U root -d postgres < backend/seed.sql`でシードデータ投入
  （Bedrock用の`ai_models`・`tenant_endpoints`行を含む）
- `uv run uvicorn app.main:app --host 0.0.0.0 --port 8001`でbackendをローカル起動
- ユーザーが実際に発行したAWS Bedrock API key（Bearerトークン）・エンドポイント
  （`https://bedrock-mantle.ap-northeast-1.api.aws/anthropic`）を`tenant_endpoints`に設定
- 確認方法: ブラウザ（frontend-angular）ではなく、AIエージェントが`curl`でAPIを直接呼び出して確認した

## 確認手順・結果

### Step 1: ログインしてセッションを確立

`POST /auth/login`（`admin`/`admin@1234`、`X-Tenant-ID: test-tenant`）を実行。

✅ 200が返り、`session_id` Cookieが発行された（issue-147で実装済みの認証機構）

### Step 2: チャットAPIをBedrock経由で呼び出す

`POST /api/llm/chat`に`deployName: "anthropic.claude-haiku-4-5"`を指定して実行。

```
event: error
data: {"message": "Error code: 403 - {'type': 'error', 'request_id': '...', 'error': {'type': 'permission_error', 'message': 'anthropic.claude-haiku-4-5 is not available for this account. ...'}}"}
```

✅ ログイン・セッション認証・`BedrockLlmChatClient`への分岐・実際のBedrock Mantleエンドポイントへの
   HTTPS呼び出し・エラー時のSSE `error`イベントへの変換まで、パイプライン全体が正しく動作することを
   確認した
❌ 実際のテキスト応答の取得は未確認（AWSアカウント側でこのモデルへのアクセス許可が
   下りていないため、`permission_error`で終了した）

### 補足調査: モデルIDの形式

AWSコンソールのモデルカタログには`anthropic.claude-haiku-4-5-20251001-v1:0`という、日付・バージョン
付きの形式（従来の`InvokeModel`/`Converse` API用）が表示されていたが、これは`ai_models.name`
（`VARCHAR(32)`、40文字必要）に収まらずDB投入時にエラーになった。一方、Bedrock Mantle
（`/anthropic/v1/messages`）向けの短い形式`anthropic.claude-haiku-4-5`はAPI側に認識されており
（`permission_error`という具体的なエラーが返ったため、モデルID自体は不正扱いされていない）、
短い形式が正しいIDであると判断した。

### Step 3: モデルアクセス許可後の再確認（2026-11-12）

#### 確認環境の差分

- `develop`取り込み後のブランチを使い、`alembic upgrade head`（022→023）と`seed.sql`を再投入した
- ログインセッションの保存先として`naw-fastapi-redis`（6380）を起動した
- Bedrock API keyは、AWS CLIの`oic`プロファイル（IAMユーザー）の認証情報から、AWS公式の
  `aws-bedrock-token-generator`で短期キー（最長12時間有効）を生成して`tenant_endpoints.api_key`に
  設定した（IAMに長期キーは作成していない。確認後はダミー値に戻した）

#### 事前確認: Mantleで使えるモデルID

`anthropic`SDKでMantleを直接呼び出し、seedのモデルIDが使えるかを確かめた。

```
OK  anthropic.claude-haiku-4-5: 'Hi there friend' usage=14/6
NG  anthropic.claude-sonnet-5: NotFoundError: Error code: 404 - {... 'not_found_error', 'message': "The model 'anthropic.claude-sonnet-5' doe...
```

✅ AWS側のモデルアクセス許可が下り、`anthropic.claude-haiku-4-5`が使えることを確認した
❌ seedに入れていた`anthropic.claude-sonnet-5`はMantle上に存在しないモデルIDだった
→ seedのモデルIDを`anthropic.claude-haiku-4-5`に修正した

#### 発見した不具合: `ai_models.max_tokens`が出力上限を超える

`POST /api/llm/chat`（`deployName: "anthropic.claude-haiku-4-5"`）を実行したところ、400エラーになった。

```
event: error
data: {"message": "Error code: 400 - {... 'invalid_request_error', 'message': 'max_tokens: 200000 > 64000, which is the maximum allowed number of output tokens for anthropic.claude-haiku-4-5'}}"}
```

リクエストで`maxTokens`を指定しない場合、`ai_models.max_tokens`が出力トークン上限として
使われる。移植元（`OpenAiLlmChatAdapter`の`maxOutputTokens = min(リクエスト値, max_tokens)`）でも
`ai_models.max_tokens`は出力上限の意味で使われており、コードの扱いは正しい。誤っていたのは
seedの値（コンテキスト長の200000を入れていた）のため、seedを64000に修正した。

#### 修正後の結果

```
event: text_delta
data: {"text": "富士山の高さは"}
...
event: text_delta
data: {"text": "されました。"}

event: message_stop
data: {"inputTokens": 28, "outputTokens": 47}
```

`token_usages`の記録:

```
 endpoint_type |           model            | input_tokens | output_tokens | total_tokens
---------------+----------------------------+--------------+---------------+--------------
 BEDROCK_CHAT  | anthropic.claude-haiku-4-5 |           28 |            47 |           75
```

✅ Bedrock経由で実際のテキスト応答がSSE（`text_delta`）でストリーミングされることを確認した
✅ `message_stop`イベントで入出力トークン数が返ることを確認した
✅ `token_usages`に`BEDROCK_CHAT`の利用量が記録されることを確認した

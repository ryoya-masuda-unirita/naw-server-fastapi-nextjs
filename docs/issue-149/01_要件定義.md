# 01_要件定義

## 背景

- 現状のチャットAPI呼び出しは、Azure OpenAIの`AIModelEndpointType.AZURE_OPENAI_CHAT`固定で
  AIモデル・テナントエンドポイントを検索しており、他プロバイダへの分岐が存在しない
- 一方で`ai_models`・`tenant_endpoints`のテーブル自体は元々マルチプロバイダを想定した設計
  （`EndpointType`に`CLAUDE_CHAT`等が既に定義済み、シードデータにも`claude-3-5-sonnet`の
  AIモデル行が存在する）だが、呼び出し側の分岐ロジックが未実装のため、Azure OpenAI以外は
  事実上使えない状態になっている
- AWS Bedrock経由でのClaude呼び出しは、Bedrockの新しい提供形態（`bedrock-mantle`エンドポイント）
  により、Anthropic公式APIと同一のリクエスト/レスポンス形式（Messages API）で呼び出せる。
  認証はBearerトークン（Bedrock API key）方式を用いれば、AWS SigV4署名や`boto3`を使わず、
  Anthropic公式SDKに`base_url`とAPIキーを指定するだけで利用できる
- モデルIDは`anthropic.claude-sonnet-5`のような単純な文字列（ARNではない）で指定する

## 機能要件

- `tenant_endpoints`の種別（`EndpointType`）に`BEDROCK_CHAT`を追加する
- テナントごとに、Bedrock Mantleのエンドポイント（リージョンを含むURL）とBedrock API key
  （Bearerトークン）を`tenant_endpoints`に登録できるようにする
- 登録した`BEDROCK_CHAT`エンドポイントと、モデルID（`assistants_endpoints.model`）を使い、
  既存のチャットAPI（ストリーミング応答）からBedrock経由でClaudeを呼び出せるようにする
- 呼び出し分岐ロジックを、現状の「Azure OpenAI固定」から「AIモデルに紐づくエンドポイント種別に
  応じて呼び出し先を切り替える」形に一般化する（Bedrock対応をきっかけに、元々マルチプロバイダ
  想定だったテーブル設計を実際に活かす）
- ストリーミング応答（SSE）に対応する
- 既存のトークン使用量記録（`token_usages`）にBedrock経由の呼び出しも記録されるようにする

## 非機能要件

- Bedrock API keyは他のテナントエンドポイントのAPIキーと同様、平文でDBに保存される
  （既存の`tenant_endpoints.api_key`と同じ扱い。暗号化は本Issueのスコープ外）
- Bedrock API keys機能はAWS側でも比較的新しい機能のため、対応リージョン・対応モデルの
  制約（サーバーサイドのweb検索・コード実行等は非対応、Files API非対応等）を踏まえた
  実装にする

## スコープ外

- Anthropic直接API（`CLAUDE_CHAT`）の実装（将来的に同じクライアント実装を流用できる設計には
  するが、今回は実装しない）
- AWS SigV4署名方式（`boto3`・IAMロールベース）でのBedrock呼び出し対応
- Bedrock以外の新規プロバイダ対応
- Bedrock経由でのembedding呼び出し対応（既存の`llm_embedding_service.py`はAzure OpenAI
  Embedding固定のままとする）

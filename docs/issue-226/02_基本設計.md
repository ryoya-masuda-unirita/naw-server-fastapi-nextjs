# 02_基本設計

## 変更対象

- 学習データのファイル更新 API（PATCH）
- 学習データのファイルダウンロード API（GET）
- チャットの RAG で、ベクトル検索の結果をファイルに解決する処理

## 画面 / API 変更概要

| API | 変更前 | 変更後 |
|---|---|---|
| ファイル更新（PATCH） | 削除済みのファイルでも 200 で更新し、状態を戻せる | 削除済みなら 400「削除済みのファイルは更新できません。」。何も保存しない |
| ファイルダウンロード（GET） | 削除済みのファイルは実体が無く 500 | 削除済みなら 400「削除済みのファイルはダウンロードできません。」 |
| メッセージ送信（RAG アシスタント） | 検索結果に削除済みのファイルが含まれると文脈・参照先に使う | 削除済みのファイルの検索結果は使わない |

画面の変更は無い。

## 影響範囲

- 学習中・停止中のファイルの更新・ダウンロード・RAG: 変更なし
- ファイル一覧・削除: 変更なし
- 画面: 一覧に削除済みは出ないため通常は影響しない。一覧を開いたまま別のタブで削除し、残った一覧で学習設定を切り替えた場合は、更新が 400 になり共通のエラー表示になる（移植元と同じ）

## 移植方針

### (1) 更新

移植元 NAW-1375 をそのまま移植する。取得したファイルが削除済みなら、どの更新経路（メタデータの変更・差し替え）でも 400 で拒否する。移植元は 404 にしない理由を「一覧は status=DELETED を指定すれば削除済みを返すので、存在しない扱いと食い違う」としており、これに従う。

### (2) ダウンロード

移植元は削除済みかを確かめず、消したストレージを読みに行く。ストレージの読み出し失敗には専用の例外処理が無く 500 相当になる。NAW-1375 の横展開調査でも「状態は戻らないため対応なし。実際の応答は未確認」とされている。

本 Issue はこの 500 を直すことが目的のため、移植元の 500 には合わせず、NAW-1375 と同じ考え方（削除済みのファイルを ID 指定で操作したら 400。存在しない扱いの 404 にはしない）で 400 を返す。

### (3) RAG

移植元は論理削除時にベクトルストア（Azure AI Search）からファイルのチャンクを消すため、削除済みのファイルは検索結果に出ない。検索結果からファイルを引くときは状態で絞っていない（存在しなければ捨てるだけ）。

このリポジトリはベクトルストアへの登録・削除が未移植で、論理削除してもチャンクが残る。検索結果のメタデータに入っているファイル ID をデータベースのファイルに解決し、見つからないものは捨てる作りなので、解決時に削除済みを除けば、移植元と同じく「削除済みのファイルは文脈・参照先に使われない」結果になる。

| 案 | 内容 | 判定 |
|---|---|---|
| A | 検索結果をファイルに解決する問い合わせで削除済みを除く | 採用。変更が小さく、チャンクが残っていても確実に除ける |
| B | 論理削除時にベクトルストアからチャンクを消す（移植元と同じ作り） | 不採用。チャンクを管理するテーブル・登録処理が未移植で、本 Issue だけでは実装できない |
| C | ベクトル検索のフィルタで削除済みを除く | 不採用。ファイルの状態はベクトルストアに入っておらず、メタデータは JSON 文字列のためフィルタできない |

案 A と移植元の差: 移植元は削除済みのチャンクが検索対象から消えるため上位 4 件が別のチャンクで埋まるが、案 A では上位 4 件に削除済みが含まれるとその分だけ文脈が減る。ベクトル登録・削除を移植した時点で解消する。

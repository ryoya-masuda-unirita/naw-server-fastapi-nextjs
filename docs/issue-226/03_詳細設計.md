## 実装内容

### `FileService.update_file`

- これまでは添付なし（メタデータ更新）の経路でだけファイルを取得し、差し替えの経路は `delete_file` の中で取得していた
- メソッドの先頭でファイルを取得し（無ければ 404「ファイルが存在しません。」）、削除済みなら 400 を返す。その後で添付の有無に応じて分岐する
  - 移植元 `FileService#updateFile` と同じく、`name` の必須チェック・インデックス取得・クレジット上限チェックより前に判定する（差し替え経路で旧ファイルを物理削除する前に止める）
- メッセージは定数 `DELETED_FILE_UPDATE_MESSAGE = "削除済みのファイルは更新できません。"`（移植元と同じ文言）
- 既存の「status=DELETED は PATCH では指定できません」の拒否はそのまま残す（学習中・停止中のファイルに DELETED を指定した場合）

### `FileService.get_file_for_download`

- 404 判定（存在しない・別インデックス・`storage_url` が無い）の後、ストレージを読む前に、削除済みなら 400「削除済みのファイルはダウンロードできません。」を返す
- 判定順を 404 判定の後にするのは、別インデックス配下のファイル ID を指定したときに、削除済みかどうかを漏らさないため

### `FileRepository.find_not_deleted_by_ids_and_tenant_id`

```python
stmt = select(File).where(
    File.id.in_(file_ids),
    File.tenant_id == tenant_id,
    File.status != FileStatus.DELETED,
)
```

- 呼び出し元は RAG の 1 か所だけのため、条件を追加して名前で意図が分かるよう改名する（旧名は残さない）
- `MessageService` 側は解決できなかった検索結果を既に読み飛ばしている（`file is None` なら `continue`）ため変更は呼び出し名だけ

## 移植元の根拠

- 更新: `server/src/main/java/com/example/naw/service/FileService.java` の `updateFile`（`existing.getStatus() == File.Status.DELETED` なら `ResponseStatusException(BAD_REQUEST, DELETED_FILE_UPDATE_MESSAGE)`）。コミット `061f0b7e`（NAW-1375）
- 移植元の文書: `documents/設計/NAW-1375/99_バグ修正.md`（404 にしない理由、ダウンロードは対応なしとした横展開の結果）
- ダウンロード: `FileController#downloadFile` → `FileService#downloadFile` → `AzureStorageService#downloadFile`。削除済みの判定は無く、読み出し失敗は `StorageException`（`APIControllerAdvice` に専用の処理なし）
- RAG: `MessageService` の RAG 処理（`vectorStore.similaritySearch` → `fileRepository.findByIdAndTenantId(...).ifPresent(...)`）。論理削除時のチャンク削除は `FileService#deleteFileWithAzureStorage`（`vectorStore.delete(ids)`）

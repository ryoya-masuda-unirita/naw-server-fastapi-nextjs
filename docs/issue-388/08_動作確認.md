## code-review 後の追加確認

- **インフラ用ロールを、既定では作らないようにした**（変数 `enable_github_actions_infra_role`、既定 false）。`plan` を 3 通りで確認した（上の No.2）
- デプロイ用のインラインポリシーに `s3:AbortMultipartUpload` を足した。ポリシーのシミュレーター（44 件。許可 20・拒否 24、不一致 0）は、この追加の前に実行した。追加は、既存の操作を広げず（同じバケットのオブジェクトの中断のみ）、拒否すべき 24 件のいずれにも関係しない
- 使われていない出力 `backend_task_family` を削除した
- README に、残るリスク（`RegisterTaskDefinition` と `PassRole` の組）、インフラ用ロールを使えるようにする必須の順序、最初の実デプロイでの `AccessDenied` を CloudTrail で確認すること、を書いた

## 未確認事項

- **実際のデプロイでの成否**: シミュレーターは、権限の判定だけで、実際のデプロイの成否は分からない。ECS のタスク定義へのタグ付けなど、実行して初めて分かる操作が漏れていると、デプロイが失敗する。`apply` と実デプロイをしていないため、確認できていない
- **信頼条件の動作**: ブランチ・Environment による引き受けの可否は、実際の OIDC トークンでの動作を確認していない（コードの読解のみ）。Environment を使うジョブの `sub` が `repo:<リポジトリ>:environment:infra` になること、は GitHub のドキュメントに基づく
- **Environment の作成コマンド**: README の `gh api` の例は、GitHub のドキュメントに基づくもので、実行して確認していない
- **インフラ用ロールは、広い権限のまま**: 絞っていない（実際に `apply` する機会に、別の変更で絞る）。既定では作らない
- **Environment の作成コマンド・有効にする順序**: 実行して確認していない（ロールを CI では作れないため、最初の有効化は、管理者権限でのローカルの `apply`）
- GitHub の GraphQL API の制限で、Issue へのブランチの紐づけと、プロジェクトボードの更新は、まだできていない

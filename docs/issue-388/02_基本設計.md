# 02_基本設計

## 変更対象

1. **GitHub Actions のロールのモジュール**
   - 既存のロール（デプロイ用）: 名前・出力・信頼条件（`develop` ブランチ）は変えない。広い管理ポリシー 2 つのアタッチを外し、インラインポリシーを、デプロイに必要な操作だけにする。tfstate へのアクセスは外す
   - 新しいロール（インフラ用）: **既定では作らない**（変数 `enable_github_actions_infra_role`、既定 false。true にしたときだけ作る）。信頼条件を、GitHub の Environment `infra` に限る。権限は、広い管理ポリシー 2 つと、tfstate へのアクセス（現行と同じ）
   - 入力: デプロイ用のポリシーが、リソースを限定するために、レジストリ・クラスタ・サービス・タスク定義・ロールの識別子を受け取る
2. **ecr・ecs モジュール**: ポリシーのリソース指定に必要な値（レジストリの ARN、クラスタの ARN、サービス名、タスク定義のファミリ名）を、出力に足す
3. **環境（dev）**: モジュールをつなぎ、新しいロールの ARN を出力に足す
4. **インフラのデプロイのワークフロー**: 新しいロール（新しい Secret）を使い、GitHub の Environment `infra` を指定する。backend・frontend のデプロイは、変えない
5. **手順書**: 新しい Secret の登録、Environment の作り方、2 つのロールの説明、残る広い権限の注意

## 画面 / API 変更概要

なし（インフラ・CI のみ）。

## 影響範囲

- **ふだんのデプロイ**: `develop` への push で動く backend・frontend のデプロイは、同じ Secret を使い、同じ操作を行う。権限は、その操作だけに絞られる。操作の漏れがあると、デプロイが失敗する（IAM のシミュレーターで、操作の一覧を確認する）
- **インフラのデプロイ**: 手動実行（`run_infra`）のときだけ、新しい Secret（`AWS_INFRA_ROLE_ARN`）と Environment `infra` を使う。Secret が未登録だと、失敗する（原因が分かる形で止める）
- **広い権限の残り**: インフラ用のロールは、作ったときは、現行と同じ広い権限のまま。ただし、ふだんの push では、引き受けられなくなる。手動実行で、Environment を使うジョブからだけ引き受けられる。**Environment に承認者・対象ブランチ（`develop`）の制限が付いていないと、どのブランチのワークフローも引き受けられてしまう**（Environment の識別子にブランチが含まれないため）。そのため、このロールは**既定では作らず**、Environment を保護してから有効にする
- **既存の環境**: 新アカウントへの新規構築が前提。既存の環境のロールには、適用しない
- **費用**: ロール・ポリシーに費用はかからない

## 移植方針

- 移植元の `github-actions-dev`（デプロイ専用ロール。ECR のプッシュ、ECS の更新、S3 の同期、CloudFront の無効化、ロールの引き渡し（ECS のタスク向けに限る）を、リソースを限定して許可）に揃える
- 移植元との違い
  - 移植元は、既存のロールに、ポリシーだけを付ける（信頼条件は、手動で管理）。このリポジトリは、OIDC プロバイダとロールを Terraform で作るので、信頼条件も管理する
  - 移植元のデプロイ用のポリシーに、マイグレーション用の一時タスクの起動（`ecs:RunTask`）はない（移植元の Java サーバーは、起動時にマイグレーションを行うため）。このリポジトリは、CI から一時タスクを起動するので、起動を、マイグレーション用のタスク定義とクラスタに限って許可する
  - 移植元の CI は、`terraform apply` を実行しない。このリポジトリは、手動実行で CI から `apply` できる構成なので、そのための専用ロールを別に持つ（権限は、確定できるまで、絞らない）
  - ECS のタスク定義の登録は、AWS の仕様上、リソースを限定できないため、移植元と同じく、リソースは全体を許可する

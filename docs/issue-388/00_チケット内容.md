# GitHub Actions ロールの権限を最小権限に絞る

## 概要

Issue #388（親: #380。#381〜#387 はマージ済み。親の最後の子 Issue）。GitHub Actions が AWS で使うロールの権限が広すぎる（`PowerUserAccess` + `IAMFullAccess`）ため、必要な権限だけに絞る。

## 説明

`github_oidc.tf`（現在は `secuaigent-infra/modules/github-actions/`）のロールは、`PowerUserAccess` と `IAMFullAccess` を持つ。移植元 `modules/github-actions-dev` のように、必要な権限だけのインラインポリシーに絞る。
絞ると、`deploy-infra.yml` の `terraform apply` が通らなくなる恐れがあるため、ほかの子 Issue が済んで、`apply` に必要な権限が確定してから着手する。

## その他

- 親 Issue: #380 / 前提: #381〜#387（すべて `develop` にマージ済み）。ディレクトリは `secuaigent-infra/`、アプリは `server/`・`client/`
- 移植元: `~/Documents/unirita-develop-pj/secuaigent-ref/secuaigent-infra/modules/github-actions-dev`（origin/develop 77249de3）
- AWS はローカル実行のときだけ `AWS_PROFILE=oic`（別アカウント・新規構築）。`apply` は人が実行する。**費用がかかるため、デプロイはしない**（ユーザーの指示）
- 調査で分かったこと
  - 現在は、**1 つのロール**を、3 つのワークフロー（backend のデプロイ、frontend のデプロイ、インフラの `terraform apply`）が共用している（すべて GitHub の Secret `AWS_ROLE_ARN`）。backend・frontend のデプロイは、`develop` への push のたびに動くので、**ふだんのデプロイが、ほぼ全能の権限を使っている**
  - 移植元の `github-actions-dev` は、**デプロイ専用**のロール（ECR へのプッシュ、ECS の更新、S3 への同期、CloudFront の無効化だけ）で、`terraform apply` の権限は持たない。移植元の CI は、`terraform apply` を実行していない
  - CI が実際に呼ぶ AWS の操作は、backend が 12 種（`ecr:GetAuthorizationToken`、プッシュ 5 種、`ecs:DescribeTaskDefinition`・`RegisterTaskDefinition`・`DescribeServices`・`RunTask`・`DescribeTasks`・`UpdateService`、`iam:PassRole`）、frontend が S3 の同期と CloudFront の無効化。いずれも、洗い出せる
  - `terraform apply` が必要とする権限は、VPC・RDS・ECS・IAM・CloudFront など多数で、実際に `apply` を試さないと、確定できない（費用がかかるため、今は試さない）
- この Issue 着手時に、GitHub の GraphQL API のレート制限で、`gh issue develop`（ブランチの作成と Issue への紐づけ）と、プロジェクトボードの更新ができなかった。ブランチは `git` で直接作った。紐づけとボードの更新は、制限の回復後にやり直す

# 01_要件定義

## 背景

- GitHub Actions が AWS を操作するためのロールは、`PowerUserAccess`（IAM 以外のほぼすべての操作）と `IAMFullAccess`（IAM のすべての操作）を持つ。つまり、アカウントのほぼすべてを操作できる
- このロールを、backend のデプロイ、frontend のデプロイ、インフラの `terraform apply` の 3 つのワークフローが共用している。前の 2 つは、`develop` への push のたびに自動で動く。したがって、**`develop` に入ったコードは、自動で、アカウント全体を操作できる権限で実行される**。ワークフローや、そこから呼ばれるスクリプト・依存パッケージに問題があると、被害がアカウント全体に及ぶ
- ふだんのデプロイに必要な操作は、限られている（イメージのプッシュ、ECS サービスの更新、マイグレーションの一時タスクの起動、静的ファイルの同期、CDN のキャッシュ無効化）。移植元も、デプロイ用のロールには、この範囲の権限だけを与えている
- 一方、`terraform apply` が必要とする権限は広く、実際に `apply` を試さないと、必要な権限を確定できない。今は費用がかかるため、`apply` はしない。確定できない権限を、推測で絞ると、実際の `apply` で、予期しない失敗が起きうる
- 現行のコードのコメントも、「本来は、必要な権限を洗い出して絞るべき」「簡易対応とした」と、後で絞る前提で書かれている

## 機能要件

1. ふだんのデプロイ（backend・frontend）に使うロールを、必要な操作だけに絞ること
   - 現行の 2 つの広い管理ポリシー（`PowerUserAccess`・`IAMFullAccess`）を外す
   - 次の操作を、可能な限りリソースを限定して許可する
     - コンテナレジストリへのログインとイメージのプッシュ（backend のレジストリに限る）
     - ECS のタスク定義の取得・登録、サービスの取得・更新（backend のサービスに限る）、マイグレーション用の一時タスクの起動（マイグレーション用のタスク定義と、backend のクラスタに限る）、タスクの取得（クラスタ内に限る）
     - タスク定義が使うロール（実行ロール・タスクロール）の引き渡し（ECS のタスクに渡す場合に限る）
     - 静的ファイル用のバケットの同期（そのバケットに限る）、CDN のキャッシュ無効化（その配信に限る）
   - 状態ファイル（tfstate）へのアクセスは、このロールには付けない
   - このロールの名前と出力は変えない（`develop` の push で動くワークフローが使う Secret `AWS_ROLE_ARN` を、登録し直さなくてよいように）
2. インフラの `terraform apply` 専用の、別のロールを用意すること。**既定では作らない**（変数で有効にしたときだけ作る）
   - 理由: このロールを引き受けられるのは Environment を使うジョブで、その識別子にはブランチが含まれず、AWS 側の信頼条件ではブランチを固定できない（`job_workflow_ref` などの追加の条件が使えるかは、確認できなかった）。Environment に承認者・対象ブランチの制限が付いていないと、どのブランチのワークフローも、広い権限のロールを引き受けられてしまい、旧ロール（`develop` に固定）より弱くなる。ロールが存在しなければ、引き受けられない
   - 有効にする順序（Environment の保護 → 管理者権限でのローカルの `apply` → Secret の登録）を、必須の手順として書く。ロールを使うワークフローが、そのロールを作ることはできないため、最初のロールは、ローカルで作る
   - `develop` への push では引き受けられないこと。手動実行（`run_infra`）で、GitHub の Environment（`infra`）を使うジョブからだけ、引き受けられること（OIDC の信頼条件を、Environment の識別子に限る）
   - 権限は、現行と同じ（`PowerUserAccess` + `IAMFullAccess` + tfstate へのアクセス）のままにする。**絞らない**。理由は、`apply` に必要な権限を、実際に `apply` を試さないと確定できないため（背景のとおり）。絞る作業は、実際に `apply` する機会に、別の変更として行う
3. インフラのデプロイのワークフローが、新しいロールと Environment を使うこと（ロールが用意されていなければ、原因と手順を示して止まること）。新しい GitHub の Secret（`AWS_INFRA_ROLE_ARN`）の登録手順を、手順書に書くこと
4. 絞った権限が、CI の実際の操作を許可し、不要な操作を拒否することを、IAM のポリシーシミュレーター（読み取りのみ）で確認すること
5. 手順書に、2 つのロールの役割・権限・信頼条件、Environment の作り方（承認者と、対象ブランチの制限の推奨）、残る広い権限の注意、絞る作業の今後を書くこと

## 非機能要件

- 変更は、設定・ワークフロー・手順書だけ。`apply` は実行しない（費用がかかるため）。`server/`・`client/` には触れない
- 既存の `AWS_ROLE_ARN` を使うデプロイ（backend・frontend）が、変更後も、同じ操作で動くこと（操作の漏れで、デプロイが失敗しないこと）
- `fmt`・`validate` が通ること。`plan` で、追加・変更されるリソースが想定どおりであること

## スコープ外

- インフラ用ロールの権限を、サービス・リソース単位で絞ること（実際の `apply` で確定してから、別の変更で行う）
- GitHub の Environment の作成と、承認者・対象ブランチの設定（リポジトリの設定の変更。手順は書くが、実行はしない）
- 既存の環境のロールの付け替え（新アカウントへの新規構築が前提）
- 実際の AWS への `apply` と、デプロイの実行（費用がかかるため）

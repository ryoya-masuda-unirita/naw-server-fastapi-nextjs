# 03_詳細設計

## 1. ecr・ecs の出力を足す

- `secuaigent-infra/modules/ecr/outputs.tf`: `repository_arn`（`aws_ecr_repository.backend.arn`）
- `secuaigent-infra/modules/ecs/outputs.tf`: `cluster_arn`、`cluster_name`、`service_arn`（`aws_ecs_service.backend.id` は ARN）、`backend_task_family`（`aws_ecs_task_definition.backend.family`）、`migrate_task_family`（`aws_ecs_task_definition.backend_migrate.family`）

## 2. github-actions モジュール（`secuaigent-infra/modules/github-actions/`）

入力を足す: `ecr_repository_arn`、`ecs_cluster_arn`、`ecs_cluster_name`、`ecs_service_arn`、`ecs_backend_task_family`、`ecs_migrate_task_family`。`data.aws_region.current` と `data.aws_caller_identity.current` を足す（タスク定義・タスクの ARN を組み立てるため）。

### 2-1. デプロイ用ロール（既存の `aws_iam_role.github_actions`）

- 名前（`<プロジェクト名>-github-actions-role`）、信頼条件（`repo:<リポジトリ>:ref:refs/heads/develop`）、出力 `role_arn` は変えない
- `aws_iam_role_policy_attachment.github_actions_power_user`・`github_actions_iam_full_access` を削除する
- インラインポリシー `aws_iam_role_policy.github_actions` を、次のステートメントにする（`TerraformStateAccess` は削除）

| Sid | 操作 | リソース |
|---|---|---|
| `EcrAuth` | `ecr:GetAuthorizationToken` | `*`（AWS の仕様上、リソースを限定できない） |
| `EcrPush` | `ecr:BatchCheckLayerAvailability`・`CompleteLayerUpload`・`InitiateLayerUpload`・`PutImage`・`UploadLayerPart` | `var.ecr_repository_arn` |
| `EcsTaskDefinition` | `ecs:DescribeTaskDefinition`・`ecs:RegisterTaskDefinition` | `*`（リソースを限定できない） |
| `EcsService` | `ecs:DescribeServices`・`ecs:UpdateService` | `var.ecs_service_arn` |
| `EcsRunMigration` | `ecs:RunTask` | `arn:aws:ecs:<リージョン>:<アカウント>:task-definition/<migrate ファミリ>:*`、条件 `ArnEquals ecs:cluster = var.ecs_cluster_arn` |
| `EcsDescribeTasks` | `ecs:DescribeTasks` | `arn:aws:ecs:<リージョン>:<アカウント>:task/<クラスタ名>/*` |
| `PassRoleForEcsTasks` | `iam:PassRole` | `var.ecs_task_execution_role_arn`・`var.backend_task_role_arn`、条件 `StringEquals iam:PassedToService = ecs-tasks.amazonaws.com` |
| `FrontendBucketList` | `s3:ListBucket` | `var.frontend_bucket_arn` |
| `FrontendObjects` | `s3:GetObject`・`PutObject`・`DeleteObject` | `${var.frontend_bucket_arn}/*` |
| `CloudFrontInvalidation` | `cloudfront:CreateInvalidation`・`GetInvalidation` | `var.cloudfront_distribution_arn` |

- backend のタスク定義の ARN（`ecs:DescribeTaskDefinition`・`RegisterTaskDefinition` の対象）は、AWS の仕様でリソースを限定できないため `*`。`ecs:RunTask` の条件に `ecs:cluster` を使い、起動先のクラスタも限定する

### 2-2. インフラ用ロール（新規 `aws_iam_role.github_actions_infra`。既定では作らない）

- 変数 `enable_infra_role`（bool、既定 false）。4 つのリソース（ロール、アタッチ 2 つ、インラインポリシー）は `count = var.enable_infra_role ? 1 : 0`。出力 `infra_role_arn` は、作らないときは null（`one(...[*].arn)`）
- 環境の変数 `enable_github_actions_infra_role`（既定 false）をモジュールに渡す

- 名前: `<プロジェクト名>-github-actions-infra-role`
- 信頼条件: `sts:AssumeRoleWithWebIdentity`、`aud = sts.amazonaws.com`、`sub` が `repo:<リポジトリ>:environment:infra` と等しい（`StringEquals`。Environment を使うジョブの `sub` は、ブランチではなく Environment になる）
- 権限: `PowerUserAccess`・`IAMFullAccess` のアタッチ（現行と同じ）と、tfstate へのアクセス（`s3:GetObject`・`PutObject`・`DeleteObject`・`ListBucket`。ロックファイルの削除に `DeleteObject` が必要なため。現行の `TerraformStateAccess` は `DeleteObject` を含まないが、`PowerUserAccess` が補っていた。明示的に足す）
- 出力 `infra_role_arn`
- コードのコメントに、「広い権限を、確定できるまで絞らない理由と、絞る時期」を書く

## 3. 環境（`secuaigent-infra/environments/dev`）

- `main.tf`: `module "github_actions"` に、新しい入力（`module.ecr.repository_arn`、`module.ecs.cluster_arn` など）を渡す
- `outputs.tf`: `github_actions_infra_role_arn`（`module.github_actions.infra_role_arn`）を足す。既存の `github_actions_role_arn` は、デプロイ用のまま。コメントを直す

## 4. ワークフロー（`.github/workflows/deploy-infra.yml`）

- ジョブ `terraform` に `environment: infra` を足す（Environment は、未作成なら、初回の実行で自動作成される。承認者・ブランチの制限は、README の手順で設定）
- `role-to-assume` を `${{ secrets.AWS_INFRA_ROLE_ARN }}` にする。未登録の場合に、原因を示して止まる検査を、`Check required variables` の前（`Configure AWS credentials` の前）に足す
- `deploy-backend.yml`・`deploy-frontend.yml` は、変更しない（`AWS_ROLE_ARN` のまま）

## 5. 手順書（`secuaigent-infra/README.md`）

- GitHub Secrets / Variables の登録の節: `AWS_INFRA_ROLE_ARN`（`terraform output -raw github_actions_infra_role_arn`）を足し、`AWS_ROLE_ARN` の説明を「デプロイ用（push で動く）」に直す
- 「GitHub Actions のロール」の節を足す: 2 つのロールの役割・権限・信頼条件、Environment `infra` の作り方（`gh api` のコマンド例。承認者と、対象ブランチを `develop` に限る設定）、インフラ用の広い権限が残ること、絞る作業の今後、確認方法（シミュレーター）と未確認のこと
- 手順 3 の説明などで、`AWS_ROLE_ARN` を使う箇所を確認し、必要なら直す

# 02_基本設計

## 変更対象

新規にフィードバックユーザー一覧取得APIを追加する（新規テーブルなし、既存テーブルの変更なし）。

## API 変更概要

| メソッド | パス | 概要 |
|---|---|---|
| GET | `/api/admin/feedbackUser` | フィードバックユーザー一覧取得（ページング・ソート・絞り込み対応、管理者限定） |

移植元は`{"feedbacks": Page<...>}`という共通ラッパーでSpringの`Page`をそのまま返すが、本リポジトリの既存API（アシスタント・グループ等の一覧API）は
`PagedXxxResponse`（`content`/`totalElements`/`number`/`size`）を直接返す方針のため、本issueもラッパーなしのその形式に変更する。

## 影響範囲

- 新規テーブルはなし。既存の `users` / `message_feedbacks` / `rooms` を集計するだけの読み取り専用API
- 既存テーブルへの変更はない

## 移植方針

- 認可は既存の `require_admin_or_group_admin`（`/api/admin/**` の一般的な認可方針）を使う
- 移植元の集計クエリ（`MessageFeedbackRepository.findFeedbackUsers`、users/message_feedbacks/roomsをLEFT JOINしCTEで集計したうえでresponseStatus/satisfactionによるHAVING相当のWHERE、ページングを行うネイティブSQL）は、SQLAlchemy CoreのCTE（`select(...).cte()`）で同等の集計クエリとして再現する。生SQL文字列は使わず、既存コードベースの流儀（SQLAlchemy Core / ORMクエリ）に合わせる
- `responseStatus`・`satisfaction`・`sortField`・`sortOrder`の値のバリデーション（許容値チェック）は`schemas/`のリクエストスキーマ（Query paramsを受けるPydanticモデル）に`field_validator`で実装する
- `sortField`の論理名（`updatedAt`/`name`/`count`/`review1`〜`review5`）から実カラムへのマッピング（移植元`toEntitySortField()`相当）はスキーマまたはサービス層のプライベート関数で行う
- ページングは既存の`PagedXxxResponse`パターン（`content`/`totalElements`/`number`/`size`、0始まり）に合わせる

# 02_基本設計

## 変更対象レイヤー

- `models`（`AssistantEndpoint`中間テーブルの新規追加）
- `schemas`（`AssistantGetResponse.endpoints`項目の型を`list[dict]`から専用スキーマに変更）
- `repositories`（`assistants_endpoints`・`tenant_endpoints`の結合取得）
- `services`（`AssistantService.get_assistants`のレスポンス構築ロジックを拡張）

## データモデル概要

### assistants_endpoints テーブル（中間テーブル）

- `assistant_id`：`assistants.id`への外部キー（`ON DELETE CASCADE`）
- `endpoint_id`：`tenant_endpoints.id`への外部キー（`ON DELETE CASCADE`）
- `tenant_id`：`tenants.id`への外部キー（`ON DELETE CASCADE`）
- `model`：AIモデル名
- 主キー：`(assistant_id, endpoint_id)`

`GroupUser`・`GroupAssistant`と異なり、`tenant_id`は主キーに含めない（移植元の最終スキーマに合わせる）。

## API変更概要

### `GET /api/assistants`

- 既存の実装（Group紐づけによるアシスタント取得）はそのまま維持し、各アシスタントに対して紐づく`assistants_endpoints`＋`tenant_endpoints`を結合取得してレスポンスの`endpoints`項目を構築する処理を追加する
- 複数アシスタント分のエンドポイント情報は、既存の`groups_by_assistant_id`と同様の「対象アシスタントID一覧に対して1クエリでまとめて取得しPython側で集約する」方式でN+1を回避する

## レスポンス形式

```json
{
  "id": "assistant-id",
  "endpoints": [
    {
      "id": "tenant-endpoint-id",
      "model": "gpt-4o",
      "type": "AZURE_OPENAI_CHAT",
      "url": "https://example.openai.azure.com"
    }
  ],
  "...": "..."
}
```

`label`は含めない。`apiKey`はそもそも`tenant_endpoints`から取得しないため露出しない。

## 影響範囲

- 新規テーブル追加のためAlembicマイグレーションが必要
- `AssistantGetResponse.endpoints`の型変更（`list[dict]` → 専用スキーマ）により、既存のissue-26テスト（`endpoints == []`を検証しているテスト）には影響しない（空リストのままなら型変更の影響を受けない）
- 既存の認証・ユーザー・グループ・テナントエンドポイント管理コードへの変更はなし
- `frontend-angular`のコード変更は不要（既存のchat機能側実装が`endpoints`の`model`/`type`を読む設計であることをissue-26で確認済み）

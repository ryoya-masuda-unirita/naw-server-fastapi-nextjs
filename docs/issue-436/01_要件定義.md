# 01_要件定義

## 背景

SECURE アシスタントは、質問や社内文書を社外に出さないための仕組みで、質問は顧客の社内（server-local → Waha! → アダプタ）で処理される。LLM を呼ぶのはアダプタだが、アダプタが直接呼べる LLM は OpenAI・Azure OpenAI だけで、Bedrock（Claude）は呼べない。

Bedrock を使うには今、SecuAiGent 経由（アダプタ → クラウドの server → Bedrock）にするしかなく、質問がクラウドを通る。社内で閉じたまま Bedrock を使うには、アダプタが Bedrock を直接呼べる必要がある。

移植元のアダプタにも、Bedrock も Anthropic も動く実装はない（Anthropic は「未対応」の失敗を返すスタブ）。そのため、この対応は移植ではなく、移植元にない新規の機能である。ただし、移植元のアダプタの設計（プロバイダごとのクライアント、設定の持ち方、失敗の分類）には沿わせる。

## 機能要件

| No | 要件 |
|---|---|
| F1 | 生成AIアダプタが、Bedrock（Claude）に質問を送り、回答を受け取れる |
| F2 | 通常のチャットと、RAG の回答（検索結果を引用資料にした回答と、その検証）の両方で使える |
| F3 | 接続先の URL・API キー・モデル名は、既存のプロバイダと同じ設定の項目（URL・API_KEY・MODEL_NAME）で渡せる |
| F4 | Waha! エミュレーターのワークフロー定義で、Bedrock をベンダーとして登録できる。既存のベンダーの設定は、そのまま動く |
| F5 | プロパティの保存時チェック（不正な設定の検出）で、Bedrock を使う設定が受け付けられ、未対応の理由で止められない |
| F6 | 失敗（認証エラー・モデル不明・通信エラーなど）は、既存のプロバイダと同じ分類の失敗として返り、API キーなどの秘密情報が出力に出ない |
| F7 | `onprem/` の compose と README だけで、ワークフロー定義の読み込みと Bedrock の API キーの設定ができる |

## 非機能要件

- 既存のプロバイダ（OpenAI・Azure・SecuAiGent・Echo）の挙動、既存のテストの結果が変わらない
- LLM の呼び出しは、他のプロバイダと同じく、ストリーミングなしの 1 回の呼び出しとする
- ネットワーク設定（プロキシなど）は、既存のプロバイダと同じ仕組みを使う
- 外部通信を行うテストは、モックで行い、本物の Bedrock には接続しない
- 追加・変更する関数・メソッド・クラスに、日本語の NumPy 形式の docstring を書く

## スコープ外

- 埋め込み（ベクトル化）の Bedrock 対応。別 Issue にする
- 通常のチャットでの tools（web 検索・MCP など）。Bedrock の Mantle が対応していないため、指定されたら既存の「通常 chat では扱えない」と同じ扱いにする
- クラウドの server 側の Bedrock 処理の変更
- 本物の Bedrock への接続確認（API キーが要るため、手順を残してユーザーが行う）
- Anthropic の公式 API（api.anthropic.com）への接続の確認。形式が同じなら動く可能性はあるが、保証しない
- Vertex AI・Google AI Studio の対応

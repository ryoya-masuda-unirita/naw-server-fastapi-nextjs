# 02_基本設計

## 変更対象

| 対象 | 変更内容 |
|---|---|
| generative-ai-core（プロバイダ） | Bedrock（Claude）を呼ぶチャットのクライアントを追加する。既存の OpenAI・Azure のクライアントと同じ作り（送信を担う部分と、失敗への変換を担う部分）にする |
| generative-ai-core（プロバイダの工場） | 設定のプロバイダに合わせて、新しいクライアントを選ぶ |
| 生成AIアダプタ（ベンダーの登録） | 新しいベンダーを、実行できるプロバイダの一覧に加える。プロパティの保存時チェックが通るようにする |
| Waha! エミュレーター | ワークフロー定義のベンダー名として、新しいベンダーを受け付ける |
| onprem | ワークフロー定義のファイルの読み込みと、Bedrock の API キーの受け渡しを、compose と README に足す |

## 画面 / API 変更概要

画面と HTTP の API の変更はない。変わるのは、ワークフロー定義で `VENDOR` に指定できる値が増えること。

通信の流れ（追加される部分）:

```
アダプタ → Bedrock Mantle の Anthropic 形式の入口 → Claude
```

- 送るもの: 会話（system・user・assistant）、モデル名、最大出力トークン数、温度
- 認証: Bedrock の API キー（Bearer 方式）
- 受け取るもの: 回答の本文。ストリーミングはしない

## 影響範囲

- 既存のプロバイダ: 変更しない。工場の選択に 1 つ分岐が増えるだけ
- 「未対応」として返していた Anthropic の扱い: 下の「決めること 1」で決める
- ベンダーの ID・名前の対応表: 新しいベンダーを使う場合は加える
- 既存のテスト: 影響しない想定。ただし、「Anthropic は未対応」を確かめているテストがあれば、決めたことに合わせて直す
- クラウドの server、server-local、client: 影響なし

## 移植方針

移植元に動く実装がないため、次の方針で作る。

1. プロバイダごとのクライアントの構成、設定の項目（URL・API_KEY・MODEL_NAME・TIMEOUT など）、失敗の分類は、移植元と既存の Python 版に揃える
2. 呼び出しの形式と認証は、クラウドの server が Bedrock を呼んでいる処理（Mantle の Anthropic 形式、Bearer の API キー）に合わせる
3. RAG の回答は、既存のプロバイダと同じ方針で、回答 1 回と検証 1 回の 2 回呼ぶ。プロンプトの組み立ては既存の共通部分を使い、プロバイダごとに書き直さない

## 決めること（第1承認の前に確認したい）

### 決めること 1: ベンダーの名前

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A（推奨） | 既存の `Anthropic`（ID 2）を動くようにする。接続先の URL を Bedrock Mantle にして使う | 移植元にすでにある ID と名前に沿う。Anthropic の公式 API にも流用できる余地がある | 名前から Bedrock と分かりにくい |
| B | 新しいベンダー `Bedrock` を追加する（新しい ID が要る） | 名前で用途が分かる | 移植元にない ID を作る。移植元の Waha! の設定とずれる |

推奨は A。呼び出しの形式が Anthropic の Messages API で、Bedrock は接続先が違うだけのため。

### 決めること 2: 認証のヘッダー

Bedrock Mantle が、Anthropic 標準のキー用ヘッダーと、Bearer のどちらを受け付けるかを、私は実際には確かめていない。クラウドの server は公式 SDK にキーを渡して動いており、その SDK がどちらを送っているかを、実装時に確認する。確認できなければ、両方のヘッダーを送る案にする。

### 決めること 3: 実機の確認

本物の Bedrock API キーでの接続は、私は行えない。手順（`08_動作確認.md` と `onprem/README.md`）を残し、あなたが確認する。この点に問題がなければ、このまま進める。

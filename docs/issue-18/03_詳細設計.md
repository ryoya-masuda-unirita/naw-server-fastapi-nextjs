## `backend/app/core/config.py`

```python
from functools import lru_cache
from typing import Annotated

from pydantic import Field, field_validator
from pydantic_settings import BaseSettings, NoDecode, SettingsConfigDict


class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_file=".env", env_file_encoding="utf-8", extra="ignore"
    )

    database_url: str
    secret_key: str


class CorsSettings(BaseSettings):
    """CORS関連の設定。

    `Settings` とは別クラスにする。`app.main` はモジュール読み込み時に
    CORSMiddleware を組み込む必要があるが、`database_url`・`secret_key` が
    必須の `Settings` と同じクラスにすると、DB接続情報を持たない環境
    （新規clone・CIでの単体テスト等）で `app.main` をインポートするだけで
    失敗してしまうため。
    """

    model_config = SettingsConfigDict(
        env_file=".env", env_file_encoding="utf-8", extra="ignore"
    )

    cors_allowed_origins: Annotated[list[str], NoDecode] = Field(
        default_factory=list, alias="CORS_ALLOWED_ORIGINS"
    )
    cors_allowed_origin_regex: str | None = Field(
        default=None, alias="CORS_ALLOWED_ORIGIN_REGEX"
    )

    @field_validator("cors_allowed_origins", mode="before")
    @classmethod
    def split_csv(cls, v: str | list[str]) -> list[str]:
        """カンマ区切りの環境変数を許可オリジンのリストに変換する。"""
        if isinstance(v, str):
            return [origin.strip() for origin in v.split(",") if origin.strip()]
        return v

    @field_validator("cors_allowed_origin_regex", mode="before")
    @classmethod
    def empty_str_to_none(cls, v: str | None) -> str | None:
        """空文字列をNoneに正規化する。"""
        return v or None


@lru_cache
def get_settings() -> Settings:
    return Settings()


@lru_cache
def get_cors_settings() -> CorsSettings:
    return CorsSettings()
```

### 設計変更のポイント（当初案からの修正）

- `Settings` に `cors_allowed_origins_raw`（str）+ `@property` を追加する当初案は、以下2点の問題が指摘されたため撤回した。
  1. **インポート時回帰**: `main.py` が `Settings`（`database_url`・`secret_key` 必須）を読み込むことになり、`.env` の無い環境で `import app.main` 自体が失敗するようになる（`develop` ブランチでは発生しなかった新規の回帰。回帰テストを追加済み）。
  2. **車輪の再発明**: pydantic-settings 2.14.2 には `Annotated[list[str], NoDecode]` + `field_validator` という複合型フィールドをカスタムデコードする標準的な手段があり、`_raw` フィールドと `@property` の二段構えは不要。
- そこで CORS 関連フィールドのみを持つ `CorsSettings` を新設し、`main.py` はこちらだけを読み込む。
- `cors_allowed_origin_regex` は空文字列 `""` を `None` に正規化するバリデータを追加（`.env` に `CORS_ALLOWED_ORIGIN_REGEX=`（値なし）と書くと pydantic-settings は `None` ではなく `""` として読み込むため）。

## `backend/app/main.py`

```python
from fastapi import FastAPI
from fastapi.middleware.cors import CORSMiddleware

from app.core.config import get_cors_settings
from app.routers import health, auth
from app.routers.users import admin_router, user_router

app = FastAPI(title="naw-server FastAPI", version="0.1.0")

cors_settings = get_cors_settings()
app.add_middleware(
    CORSMiddleware,
    allow_origins=cors_settings.cors_allowed_origins,
    allow_origin_regex=cors_settings.cors_allowed_origin_regex,
    # Cookie等の資格情報を伴うリクエスト（frontend/frontend-angular とも
    # credentials: 'include' / withCredentials: true を使用）を許可するため True にする。
    allow_credentials=True,
    # 移植元（Spring Boot）の CorsConfiguration も addAllowedMethod("*") /
    # addAllowedHeader("*") で全許可しており、新しいルーターやカスタムヘッダー
    # （例: X-Tenant-ID）が増えるたびに個別追加が必要にならないよう合わせる。
    allow_methods=["*"],
    allow_headers=["*"],
)

app.include_router(health.router)
app.include_router(auth.router)
app.include_router(auth.api_router)
app.include_router(admin_router)
app.include_router(user_router)
```

### 設計変更のポイント（当初案からの修正）

- `allow_methods`/`allow_headers` を個別列挙のハードコード（`["GET","POST","PATCH","DELETE"]` / `["Authorization","Content-Type"]`）から `["*"]` に変更した。
  - 当初案では `X-Tenant-ID`（`backend/app/routers/auth.py` が必須とするカスタムヘッダーで、`frontend/src/lib/api-client.ts` が全リクエストに付与する）が `allow_headers` から漏れており、テナントID判明後の全リクエストがプリフライトで拒否されていた（curlで再現・修正確認済み、`code-review.md` 参照）。
  - 個別列挙は「ヘッダー・メソッドが増えるたびに手動で追記が必要」という保守上の罠でもあるため、移植元Spring Bootの `"*"` 全許可方針に合わせて根本的に解消した。

## `frontend/src/lib/api-client.ts`

```typescript
const API_BASE_URL = import.meta.env.VITE_API_URL;
```

当初案は `API_PATHS.AUTH.SESSION` の値だけを `/api/auth` → `/auth` に修正するものだったが、これは対症療法だった。実際には `API_BASE_URL`（`${VITE_API_URL}/api`）が全パスに `/api` を自動付与する設計そのものが、バックエンドの実際のルーティング（`POST /auth/login` 等は `/api` 無し、`GET /api/auth` のみ `/api` 有り）と噛み合っていなかった。

`API_BASE_URL` から `/api` の自動付与をやめ、各パス定数に実際のバックエンドの完全なパスを持たせることで、4つのAUTHエンドポイント全てが正しく解決されるようにした。

## `frontend/src/lib/constants/api-paths.ts`

```typescript
export const API_PATHS = {
  AUTH: {
    LOGIN: '/auth/login',
    LOGOUT: '/auth/logout',
    SESSION: '/api/auth',
    PASSWORD_RESET: '/auth/password/reset',
  },
} as const;
```

`SESSION` のみバックエンド側で `/api` プレフィックスが付く（`backend/app/routers/auth.py` の `api_router`）ため `/api/auth` のまま。他の3つは元々 `/api` 無しの値だったため変更なし（`API_BASE_URL` 側の修正で自動的に正しく解決されるようになった）。

## `frontend/src/mocks/handlers/auth.ts`

MSWモックが `http://localhost:8001/api` を起点にハンドラーを登録していたが、実際の `.env` の `VITE_API_URL` は `http://localhost:8000` であり、かつ `/auth/login` 等は `/api` 無しが正しいパスだった。この不整合により `onUnhandledRequest: 'error'` 設定下でテストが失敗していたため、実際の構成に合わせて修正した。

## 前提条件

- `cd backend && uv run alembic upgrade head` を実行（適用済み）
- `cd backend && uv run uvicorn app.main:app --port 8001` でバックエンドを起動（`frontend-angular` の `proxy.conf.local.js` が `localhost:8001` を向いているため、慣例の8000ではなく8001で起動）

- 確認はヘッドレスブラウザ（Playwright）を用いてClaude Codeが実施。GUIのないサンドボックス環境のため、操作の様子は動画（webm）として記録した
- ログイン確認用アカウント: `test-tenant` テナントの `admin` / `admin@1234`（`backend/seed.sql` 記載のシードユーザー）
  - ローカルDBの `password_histories` に保存されていたシード済みハッシュがこの実行環境の bcrypt 実装では検証に失敗したため、動作確認のみを目的として同一パスワード（`admin@1234`）でハッシュを再生成しDBを更新した（コード・`seed.sql` は変更していない、ローカルDBの値のみの調整）

## 動作確認方針

今回の対応（バックエンド優先方針）に伴い、フロントエンドの実ブラウザ確認は `frontend/`（React、開発中）ではなく `frontend-angular/`（`secuaigent-client` を取り込んだもの、`http://<tenant>.localhost:4201`）を用いた。

`frontend-angular` は開発サーバーのproxy機能（`proxy.conf.local.js`）経由でバックエンドと通信するため、ブラウザから見ると同一オリジン通信になり、クロスオリジンのCORSプリフライトは発生しない。そのため、**CORSMiddleware自体の許可・拒否ロジックの検証は自動テスト（`tests/unit/test_cors.py`、3ケース）で行い**、ブラウザ確認では「CORSに関する既存の問題でログインがブロックされないこと」「バックエンドとの一連の通信が実際に成立すること」を確認する。

## 動作確認中に判明した問題（issue-18スコープ外・新規Issue化）

ダッシュボード遷移後、`GET /api/users/profile` が401、`GET /api/rooms` 等が404となり画面上に複数のエラートーストが表示された。また、ページをリロードすると `GET /api/auth` のセッション確認が401になり、ログイン画面に戻ってしまう現象を確認した。

調査の結果、原因はCORSやパス重複とは別の問題で、認証方式の設計不整合（移植元はCookieベースのセッション認証、FastAPI版はJWTをレスポンスボディで返すのみでCookie発行なし。両フロントエンドともAuthorizationヘッダーへのトークン再付与処理がない）であることを特定した。

issue-18の要件定義（CORS未設定・セッションAPIパス重複の2件）には含まれない別種の問題のため、今回は修正せず **Issue #20** として新規起票した。

## `/code-review` 対応後の再検証

`code-review.md` の指摘対応後、以下を実機で再検証した。

### curlによるCORSプリフライトの直接検証

```
$ curl -i -X OPTIONS http://localhost:8001/api/auth \
  -H "Origin: http://localhost:5173" \
  -H "Access-Control-Request-Method: GET" \
  -H "Access-Control-Request-Headers: content-type,x-tenant-id"

HTTP/1.1 200 OK
access-control-allow-headers: content-type,x-tenant-id
access-control-allow-origin: http://localhost:5173
access-control-allow-credentials: true
```

修正前は `400 Bad Request: Disallowed CORS headers` だったが、`allow_headers=["*"]` への変更により `X-Tenant-ID` を含むプリフライトが許可されるようになったことを確認。

許可外オリジン（`http://evil.example.com`）からのプリフライトは引き続き `400 Bad Request: Disallowed CORS origin` で拒否されることも確認した。

### git diff実験によるインポート時回帰の確認

```
$ mv .env /tmp/env-backup && .venv/bin/python -c "import app.main"
（修正前のmain.py: ValidationError で失敗）
（修正後のmain.py: 正常終了）
（develop の main.py: 正常終了）
```

`CorsSettings` を `Settings` から分離したことで、`.env` が無い環境でも `import app.main` が develop ブランチと同様に成功することを確認した（回帰テスト `test_app_main_importable_without_env_file` を追加）。

### Playwrightによる React フロントエンドの再検証

`frontend/`（React、`http://localhost:5173`）から `http://localhost:8000` への直接クロスオリジン通信で再検証した。

| # | 確認項目 | 修正前 | 修正後 |
|---|---|---|---|
| 1 | `POST /auth/login` | 404（`api-client.ts`が`/api/auth/login`にリクエストしていたため） | 200到達可能な正しいパス`/auth/login`に到達（後述の理由で422） |

`API_BASE_URL` から自動 `/api` 付与を除去したことで、パスの不整合自体は解消されたことを確認した。ただし、この検証の過程で本Issueのスコープ外の別バグ（Reactにはテナントサブドメインからのテナント ID 解決手段が無く、ログイン時に `X-Tenant-ID` を送信できず 422 になる）に気づいた。現在の開発方針（`frontend/` は当面不問）に基づき、Issueは起票せずここに記録のみ残す。

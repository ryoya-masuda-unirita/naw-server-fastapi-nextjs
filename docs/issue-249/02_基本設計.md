# 02_基本設計

## 変更対象

- アシスタントに紐づくチャット用エンドポイントの解決（Azure OpenAI 固定 → チャット用種別全般）
- メッセージ送信の AI モデル解決・LLM 呼び出し先の分岐・トークン使用量の記録種別
- LLM チャット API の出力トークン上限の算出、Bedrock のツール指定の事前検証
- LLM 呼び出しクライアント（Bedrock の事前検証と上限の受け取り方）
- チャット用の AI モデル種別とテナントエンドポイント種別の対応表（LLM チャット API・メッセージ送信で共有する）

## 画面 / API 変更概要

- API のリクエスト/レスポンス形式は変えない
- メッセージ送信: Bedrock のエンドポイントを紐づけたアシスタントで送信すると、400 ではなく Bedrock 経由で応答する
- LLM チャット API・メッセージ送信: Bedrock でツールを指定すると、SSE の `error` ではなく 400 を返す
- LLM チャット API: `maxTokens` がモデルの上限を超える場合、モデルの上限で呼び出す

## 影響範囲

- メッセージ送信（SAAS_CHAT・SAAS_RAG）のエンドポイント・AI モデル解決とトークン使用量の記録
- LLM チャット API の LLM 呼び出し引数
- アシスタントのチャット用エンドポイント解決を使う箇所（メッセージ送信のみ）

## 移植方針

### 1. メッセージ送信で Bedrock を使えるようにする（案A を採用）

| 案 | 内容 | 評価 |
|---|---|---|
| A. 送信でも Bedrock を使えるようにする | エンドポイント解決をチャット用種別全般に広げ、LLM チャット API と同じ分岐で Bedrock クライアントを呼ぶ | #149 の要件どおり。Bedrock クライアント・分岐は #149 で実装済みで、変更は解決条件・分岐・使用量の種別に限られ規模は小さい |
| B. 登録時に Bedrock を拒否する | アシスタント登録時のチャット用判定から Bedrock を除く | 変更は小さいが、#149 の要件（既存のチャット API から使える）を満たさず、Bedrock 対応が LLM チャット API だけに留まる |

案A を採用する。規模が小さく、#149 の要件を満たせるため。

- 移植元に Bedrock の実装はないため、エンドポイント解決・分岐は #149 の LLM チャット API と同じ設計にする
- チャット用の AI モデル種別とエンドポイント種別の対応表を、LLM チャット API・メッセージ送信・エンドポイント解決で
  共有し、プロバイダ追加時の更新漏れを防ぐ

### 2. 出力トークン上限の切り詰め

- 移植元 `OpenAiLlmChatAdapter.buildParams` は `reqMax != null ? min(reqMax, cap) : cap` で上限を決める
- リクエストで指定された場合のモデル上限での切り詰めは移植元どおりにする（Azure OpenAI・Bedrock の両方）
- 未指定時の扱いは移植元と異なり、Azure OpenAI は従来どおり上限を送らない（モデルの既定値に従う）。
  AI モデルの上限にはコンテキスト長相当の値（例: シードデータの gpt-4o は 128000）が入っており、未指定時に
  そのまま出力上限として送ると Azure OpenAI 側で上限超過のエラーになるおそれがあるため。Bedrock は上限が
  必須のため、従来どおりモデルの上限を使う
- メッセージ送信は移植元同様、リクエストに上限を持たないため未指定として扱う

### 3. Bedrock の非対応パラメータの事前検証

- Bedrock クライアントに、呼び出し前に使える検証処理を用意し、LLM チャット API・メッセージ送信の両方で
  ストリーミング開始前（AI モデル・エンドポイント解決の直後）に呼ぶ
- 検証に失敗した場合は 400 を返し、LLM 呼び出し・応答の保存・トークン使用量の記録を行わない
- メッセージ送信では RAG の検索（埋め込みの呼び出し）より前に検証し、無駄な埋め込み呼び出しをしない
- クライアント自身の呼び出し時の検証も防御的に残す

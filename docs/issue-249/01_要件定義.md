# 01_要件定義

## 背景

- #149 で LLM チャット API に Bedrock（Claude）経由の呼び出しを追加したが、メッセージ送信（アシスタントへの
  送信・SSE 応答）は Azure OpenAI のチャット用エンドポイント固定のままで、Bedrock のチャット用エンドポイントを
  紐づけたアシスタントに送信すると 400 になる
- アシスタント登録時は種別名が `CHAT` で終わるエンドポイントを受け付けるため、Bedrock のエンドポイントを
  登録できてしまい、「登録できるのに使えない」状態になっている
- #149 の要件定義は「既存のチャット API（ストリーミング応答）から Bedrock 経由で Claude を呼び出せるようにする」
  としており、メッセージ送信も対象に含まれる
- 移植元は出力トークン数の上限を `min(リクエストの上限, AI モデルの上限)` に切り詰めるが、このリポジトリでは
  リクエストの値をそのまま渡しており、Bedrock では応答開始後にエラーになる
- Bedrock はツール（web_search / mcp）に対応していないが、指定された場合のエラーがストリーミング開始後に
  SSE の `error` として返る。メッセージ送信ではエラー状態の応答が保存され、RAG の埋め込みトークンだけの
  使用量行も記録されうる

## 機能要件

1. メッセージ送信で、アシスタントに紐づく Bedrock のチャット用エンドポイントを使って応答を生成できること
   - アシスタントに紐づくチャット用エンドポイント（Azure OpenAI・Bedrock）のうち、従来どおり ID が最小のものを使う
   - AI モデルは、エンドポイント種別に対応する種別とモデル名で検索する
   - トークン使用量には、実際に呼び出したプロバイダの種別を記録する
   - SAAS_CHAT・SAAS_RAG の両方で使えること（RAG の埋め込みは従来どおり Azure OpenAI）
2. 出力トークン数の上限を、AI モデルの上限で切り詰めること（Azure OpenAI・Bedrock の両方）
   - リクエストで上限が指定され、モデルの上限を超える場合はモデルの上限にする
   - Bedrock は上限の指定が必須のため、未指定の場合はモデルの上限を使う（従来どおり）
3. Bedrock で非対応のパラメータ（ツール）が指定された場合、ストリーミング開始前に 400 で拒否すること
   - LLM チャット API・メッセージ送信の両方
   - 拒否した場合は LLM を呼び出さず、応答・トークン使用量を記録しない

## 非機能要件

- Bedrock の実呼び出しは自動テストで行わず、クライアントをモックして検証する
- 既存の Azure OpenAI 経路の挙動（未指定時の上限・ツール・応答形式）は、上限の切り詰め以外変えない

## スコープ外

- Anthropic 直接 API（`CLAUDE_CHAT`）など、Bedrock 以外の新規プロバイダ対応
- Bedrock でのツール（web_search / mcp）対応
- メッセージ送信リクエストへの `maxTokens`・`temperature` の追加
- アシスタント登録時のエンドポイント種別チェックの変更
- フロントエンドの変更

# 02_基本設計

## 変更対象

- バックエンドの共通ユーティリティに、並べ替え指定の解釈処理を新設する（Spring Data の Pageable の `sort` 相当）
  - クエリパラメータ `sort`（複数可）を「キーと方向の並び」に変換する
  - 各 API の「キー → 列」の対応表・未知キーの読み替え先・最終キーを受け取り、SQL の並び順を組み立てる
- 下表の一覧 API の並べ替えを、上記の共通処理に置き換える（ルーター・サービス・リポジトリ）
- ユーザー一覧の権限の絞り込みの検証（サービス）
- チーム所属ユーザー一覧の検索条件（リポジトリ）
- 利用クレジット順の判定（共通ユーティリティ）
- 対応する自動テスト

## 画面 / API 変更概要

### 適用しない API

| API | 理由 |
|---|---|
| ライブラリタグ一覧（管理者） | 移植元は Pageable だが、こちらは `sort` を受けておらず、受け付けるキーを増やすことになる。名前はテナント内で一意なので、最終キーも不要 |
| フィードバック系一覧 | 移植元も Pageable の `sort` を使わず、`sortField` / `sortOrder` で受ける（既に検証済み） |
| ルーム一覧・ライブラリ一覧・トークン使用量一覧 | 移植元が Pageable の `sort` を受けない（独自のパラメータ） |

### 並べ替え指定の解釈（全対象 API 共通）

- `sort` は複数指定できる。各値は「キー[,キー...][,方向]」。方向は `asc` / `desc`（大文字小文字は区別しない）で、省略時は昇順
- 最後の要素が方向でなければ、すべてキーとして昇順にする（Spring Data と同じ）
- 空の要素・前後の空白・末尾の `ignorecase` は無視する。キーが 1 つも残らなければ、その API の既定の並び順にする
- 未知のキーは読み飛ばす（移植元と同じ）。既知のキーが 1 つもなければ、先頭の指定の方向で、その API の読み替え先の列で並べる（従来どおり）
- 最後に最終キー（ID）を加える（上表）
- 利用クレジット順は、指定のいずれかに `totalCredits` があれば、利用クレジット順＋表示名昇順＋最終キーで並べる（移植元と同じ判定）

### 変更前後の挙動の差

既定の並び順と受け付けるキーは変わらない。変わるのは次の点だけ。

| 指定 | 変更前 | 変更後 |
|---|---|---|
| `sort=name,DESC`（大文字） | 一部の API（アシスタント・チーム系・インデックス）で昇順になる | 全 API で降順 |
| `sort=name,asc&sort=updatedAt,desc` | 2 つ目以降を無視 | 指定順に並べる |
| `sort=`（空） | API ごとに異なる（読み替え先の列の昇順など） | その API の既定の並び順 |
| `sort=a,b,desc` | `a` の昇順（`b` を方向として解釈できず昇順） | `a` 降順 → `b` 降順 |
| `sort=name,desc,ignorecase` | `name` の昇順（`desc` を方向として解釈しない） | `name` 降順 |
| `sort=foo,asc&sort=name,asc`（未知のキーが先頭） | 2 つ目以降を無視（読み替え先の列で並べる） | 未知のキーを読み飛ばして `name` 昇順 |
| 同じ値の行 | 最終キーがない API では並びが不定 | 最終キーで確定する |

### ユーザー一覧の権限の絞り込み

- `role` が `USER` / `ADMIN` / `SYSTEM` のいずれでもなければ 400 を返す。応答の形式は既存の 400（学習データファイル一覧の不正なステータスなど）と同じ
- 空文字・空白のみは、絞り込みなしとする

### チーム所属ユーザー一覧

- SYSTEM 権限のユーザーを、一覧と総件数から除外する

## 影響範囲

- 上表の一覧画面の並び順（同値の行の並び、大文字の方向指定、複数指定時）
- ユーザー管理一覧で、未知の権限を指定したときの応答（500 → 400）
- チーム詳細の所属ユーザー一覧に、SYSTEM 権限のユーザーが表示されなくなる（件数も減る）
- フロントエンドの変更は不要（送っている `sort` は単一の「キー,方向」で、解釈結果は変わらない）

## 移植方針

- 移植元は Spring Data の既定の Pageable 解釈をそのまま使っており、独自の設定はない（`@PageableDefault` もない）。共通処理はこの既定の解釈規則を再現する
- 移植元は、キーの読み替え（エイリアス）を Service ごとの対応表で行っている。こちらも API ごとの対応表を共通処理に渡す形にする
- 移植元は同値の行の並びを決めていない（DB 任せ）。こちらで最終キーを加えても、移植元で起こりうる並びの一つに確定させるだけなので、移植元の API 仕様からは外れない
- 未知のキーの扱いは、移植元でも API ごとにばらばら（DB エラー・無視が混在）。複数指定のときは移植元の「無視」に合わせて読み飛ばす。既知のキーが 1 つもないときは、既存の挙動を変えない指示に従い、従来どおり読み替え先の列で並べる
- 不正な権限の扱い: 移植元は権限文字列を列挙型に変換し、失敗すると 400 を返す（大文字小文字を区別する。空・空白のみは絞り込みなし）。これに合わせる
- チーム所属ユーザー一覧の SYSTEM 除外: 移植元はユーザーの権限が SYSTEM でないことを検索条件に加えている（NAW-1096）。同じ条件を加える

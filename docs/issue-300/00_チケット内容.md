# 埋め込みアダプタとcoreの埋め込み部分をPythonに移植しWaha!エミュレーターの学習・同期・削除に差し込む

Issue: #300（依存: #298）

## 概要

移植元 `generative-ai-adapter/embedding-adapter` と `generative-ai-core` の embedding・ファイル前処理（Text/Image/Word/Excel/PDF/PowerPoint）・vector の保存・更新・削除・Graph Candidate を移植し、エミュレーターの学習（登録）・削除・同期のワークフローに差し込む（#274 では未対応にしている）。出力は server-local が読む TSV（ファイル ID と部分 ID）。

- 同期（お客さんのサーバーから取り込む）の取り込み元は、移植元で根拠のある範囲（`filepath` で渡されたパス等）に限る

## 方針（Issue 本文）

- 移植元 `secuaigent-ref/generative-ai-adapter/`（Java。4 プロジェクト）を、同じ 4 つの分け方のまま Python に移植する（完璧なクローン）。置き場所はルートの `generative-ai-adapter/` 配下
- アダプタはサーバーではなくライブラリ。`waha-emulator/` のワークフローから import して呼ぶ。Waha! 固有の受け口（番号付きプロパティ・ColumnData・出力ファイル）は、エミュレーター側の設定・入出力に置き換える
- 本物の Waha! のワークフロー定義（どのサービス ID でどのアダプタをどの設定で動かすか）はどちらのリポジトリにもないため、移植元のコード・テスト・docs から読み取って決め、docs に根拠を書く
- チャット 1 回の流れをログ（INFO）で追えるようにする（#298）。学習・削除・同期でも同様にワークフローのログを出す

## 依頼時の追加条件

- #298 の作り方（`generative-ai-adapter/README.md`、`docs/issue-298/`、`waha-emulator/`）に揃える
- 移植元の `embedding-adapter/`（Waha! の入口・チャンク化・vector の保存・更新・削除・Graph Candidate・`adp/out/**/properties.xml` の設定項目）と `generative-ai-core` の embedding（Azure OpenAI・OpenAI の埋め込み）・vector の書き込み・ファイル前処理を移植元の構造のまま移植する
- `generative-ai-adapter/` のワークスペースに `embedding-adapter/` を追加する
- 学習（登録）・削除・同期のワークフローに差し込む。`server-local/` が読む出力は TSV（ファイル ID と部分 ID）。サービス ID → ワークフローの設定の持ち方は #298 のものに合わせる
- 実際の DB・Azure には接続しない自動テスト（DB・HTTP はモック）。可能なら `onprem/` の vector-db の Docker で PostgreSQL + pgvector の実書き込みを手元で確認し、結果を 08 に貼る。確認後はコンテナを片付ける
- 別エージェントが #299（検索アダプタ）を並行で進めるので、core の共通部分（プロバイダ・ネットワーク）は #298 のものを使い、embedding 固有の部分だけを足して衝突を減らす
- docstring は NumPy 形式（日本語。`Parameters`・`Returns`・`Raises`）。追加・変更したすべての関数・メソッド・クラスに書く

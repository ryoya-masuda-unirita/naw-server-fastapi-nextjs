## 変更対象

| 対象 | 内容 |
|---|---|
| `generative-ai-adapter/generative-ai-core/` | embedding・resource・vector・graphrag（ingestion・ingestion.llm・bootstrap）を新設。media に PDF・Word・Excel・PowerPoint を追加 |

| `waha-emulator/` | 埋め込みアダプタのワークフロー（学習・削除・同期）、設定ファイルの `adapter: "embedding"`、`SOURCE_ALLOWED_DIR`。Dockerfile にアダプタを含める |
| README・CLAUDE.md・AGENTS.md | 構成の表を更新 |

server-local・backend・frontend のコードは変更しない。

## 画面 / API 変更概要

画面・HTTP API の変更はない。エミュレーターの servicerun API（パス・パラメータ・応答）は #274 のまま。変わるのは、登録したサービス ID の execute で動くワークフロー（学習・削除・同期）の中身。

## 依存の向き（移植元と同じ）

```
embedding-adapter ─┐
generative-ai-adapter ─┼→ generative-ai-core（Waha! に依存しない）
（retrieval-adapter は #299）
waha-emulator → generative-ai-adapter・embedding-adapter（パス依存。core は一緒に入る）
```

## 埋め込みアダプタの呼ばれ方

生成AIアダプタと同じく Waha! の順序: `set_property` → `connect(出力モード)` → `set_column_information` → `set_view_name` → `before_execute` → `write(レコード)` → `after_execute`。出力モードは 0 テキスト出力、1 VDB追加登録、2 VDB削除、3 VDB新規登録。列は ID・入力ファイル・分割文字数の 3 つ。

## サービス ID とワークフローの対応

本物の Waha! の対応（管理コンソールで登録するサービス）はどちらのリポジトリにもない。#298 と同じく、エミュレーターの設定ファイル（JSON）の `services` に、サービス ID ごとの定義を書く。定義に `adapter: "embedding"` と `operation` を足した。

- 根拠: server-local は学習・削除・同期のサービス名を別々に持ち（`creation_service_name`・`deletion_service_name`・`sync_service_name`）、それぞれ違うパラメータ・入力スロットで呼ぶ。移植元のアダプタは出力モード（追加登録・新規登録・削除）とプロパティで動きを変える設計で、サービス = 出力モード + プロパティの組と読める点も #298 と同じ
- `operation`: `learn`（出力モード 3 が既定、1 も選べる）、`delete`（出力モード 2）、`sync`（アダプタは使わずベクトルDB の行を読む）
- プロパティは埋め込みアダプタの名前（`URL`・`VDB_URL` など）で書き、`${環境変数}` で秘密を参照できる。`OUTPUT_DIR` はジョブごとにエミュレーターが決める
- 不正な設定は起動時に失敗させる（アダプタの保存時チェック `validate_property` を通す）

## server-local が読む出力（根拠）

`server-local/app/services/file_service.py` を読んで決めた。

| 呼び出し | server-local の入出力 | エミュレーターの出力 |
|---|---|---|
| 学習 | `file` スロットにファイル、`execute?splitLength&filepath`、`outputfile` の各行を CRLF で分け、タブで分けて 1 列目=ファイル ID、2 列目=パート ID | アダプタの TSV（パス・本文・行 ID・ファイル ID）から、ファイル ID・パート ID だけを CRLF 区切りで出す |
| 削除 | `file` スロットにパート ID を 1 行ずつ、`execute`（パラメータなし）、出力は読まない | パート ID から行のファイル ID を引き、出力モード 2 で削除する |
| 同期 | `execute?start&end`、各行 1 列目=パス、2 列目=パート ID、3 列目=ファイル ID | ベクトルDB の行を `ファイル ID, 行 ID` 順に `start` から `end-start` 件読む |

## 同期の取り込み元

移植元には「ファイルサーバーを探索する」処理がない（アダプタは `write` で渡されたファイルを処理するだけ）。根拠のある範囲は次の 2 つに限る。

1. 学習時に `filepath` で渡されたパス: `file` スロットが空なら、そのパスのファイルを読んで学習する（`SOURCE_ALLOWED_DIR` の中だけ）。アップロードされたファイルは、ベクトルDB に書く「パス」を `<filepath>/<ファイル名>` にする
2. アダプタがベクトルDB に書いた行: 同期はこの行（パス・行 ID・ファイル ID）を返すだけ。server-local は「DB にないファイル」だけを取り込む

## Graph Candidate

Graph 書き込み（プロパティ 45）が有効なら、チャンクごとに LLM で候補を抽出し、GraphRAG のスキーマ（`graphrag_s02`）と AGE グラフに書く。拒否された候補の監査 TSV と、ジョブ結果マーカー（`graph-candidate-job-outcome.tsv`）も移植元どおり出す。エミュレーターの学習ワークフローは、定義に `GRAPH_WRITE_ENABLED` 等を書けば有効にできる。

## 影響範囲

- 登録していないサービス ID の学習・同期は従来どおり「未対応」の失敗
- 生成AIアダプタのワークフロー（チャット・RAG）は変わらない
- core のファイル前処理の既定の並びが移植元と同じ順（PDF・Word・PowerPoint・Excel・画像・テキスト）になり、PDF/Office が UNSUPPORTED_MIME でなくなる
- エミュレーターの依存に psycopg・python-docx・openpyxl・pypdf・pypdfium2・python-pptx・pillow が増える

## 移植方針

- #298 と同じ。移植元のクラス・メソッドの構造と挙動をそのまま移す。Java のライブラリ（Spring AI・Azure SDK・JDBC・POI・PDFBox・Tika・Gson）に依存する部分は、同じ入出力になるように Python の標準的な手段（httpx・psycopg 3・python-docx など）で書き換え、再現できなかった差は 03 に列挙する
- core はアダプタに依存させない。core の共通部分（プロバイダ・ネットワーク・失敗の伏せ字）は #298 のものを使い、#299 と衝突しないよう既存ファイルは変更せず、embedding 固有の部分だけをファイルとして足す

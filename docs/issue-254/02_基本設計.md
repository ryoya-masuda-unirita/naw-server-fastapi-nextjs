# 02_基本設計

## 変更対象

- メッセージ送信サービスの SSE 配信処理（保存部分の例外処理）
- 汎用チャットサービスの SSE 配信処理（保存部分の例外処理）
- 上記の単体テスト

## 画面 / API 変更概要

API の入出力（リクエスト・イベントの形）は変えない。保存失敗時のイベント列だけが次のように変わる。

### メッセージ送信 API（SSE）

| 状況 | 変更前 | 変更後 |
|---|---|---|
| 回答の保存が DB 障害等で失敗 | text_delta → message_stop のあと接続が異常終了 | text_delta → message_stop → error（固定文言） |
| ライブラリの保存が失敗 | 同上（トークン使用量も未保存） | text_delta 等 → message_stop → error。トークン使用量は保存する |
| トークン使用量の保存が失敗 | 同上 | text_delta → message_stop → error。message_content は送らない |
| LLM 呼び出しも保存も失敗 | error（LLM の例外文言）のあと異常終了 | error（LLM の例外文言）→ error（固定文言） |
| 再生成対象が保存時点で削除済み | text_delta → message_stop → error（変更なし） | 同左 |

### 汎用チャット API（SSE）

| 状況 | 変更前 | 変更後 |
|---|---|---|
| トークン使用量・ライブラリの保存が失敗 | message_stop のあと接続が異常終了 | message_stop のあとストリームを正常に閉じる（エラーはログのみ） |

## 影響範囲

- フロントエンドは error イベントを受け取ってもエラー扱いで表示を終えるだけのため、表示上の影響は「途中で切れる」が「エラーで終わる」に変わる点のみ
- 保存の成功時の挙動は変わらない

## 移植方針

- 移植元のメッセージ送信は、保存処理を含む処理全体を一番外側の catch で包み、`sendSseError` を送ってからストリームを閉じる。こちらは保存処理を個別に例外処理し、1 つでも失敗したら message_content の代わりに error を送ることで同じ結果にする。個別に処理するのは、回答の保存に失敗してもトークン使用量を記録するという既存の方針（移植元は回答とトークン使用量を同じトランザクションで保存するため、こちらでは別々に試みる必要がある）を保つため
- 移植元の一番外側の catch は例外メッセージをそのまま返すが、こちらは既存の「再生成対象削除」時と同じ固定文言「エラーが発生しました。」（移植元で例外メッセージがない場合の既定文言）を返し、DB の内部情報をクライアントへ出さない
- 移植元の汎用チャットは、`message_stop` 送信・`complete()` のあとに `finally` でトークン使用量を保存するため、保存失敗はクライアントへ通知されない。こちらも通知せず、ログに残してストリームを正常に閉じる

# 01_要件定義

## 背景

メッセージ送信 API の SSE は、LLM の応答を配信し終えたあと（またはクライアントが切断したあと）に、回答・ライブラリ・トークン使用量を保存する。現状は保存処理で起きた例外のうち「再生成対象が見つからない」ケースしか扱っておらず、DB 障害などそれ以外の例外が起きると、error イベントを送らないままストリームが異常終了する。クライアントからは応答が途中で切れたように見え、失敗を判別できない。

移植元（Spring Boot）は、保存処理を含むストリーミング処理全体を一番外側の catch で包み、例外が起きたら error イベントを送ってからストリームを閉じる。

## 機能要件

1. メッセージ送信の SSE で、回答・ライブラリ・トークン使用量のいずれかの保存に失敗した場合、message_content イベントを送らず、error イベントを送ってからストリームを閉じる（移植元の一番外側の catch と同じ）
2. error イベントの形は既存と同じ（`type` が `error`、`message` に文言）。文言は固定の「エラーが発生しました。」とし、内部の例外文字列はクライアントへ返さない（ログにのみ残す）
3. 回答の保存に失敗しても、LLM で消費済みのトークン使用量の保存は試みる（既存の方針を維持する）
4. クライアントが切断したあとの保存で例外が起きても、ストリームの終了処理で例外を送出しない（ログに残す）
5. 汎用チャット API（`/api/llm/chat`）の SSE についても同じ問題を確認し、保存の失敗でストリームが異常終了しないようにする。移植元の汎用チャットは応答の配信を終えてストリームを閉じたあとに保存するため、保存の失敗はクライアントへ通知しない（ログにのみ残す）

## 非機能要件

- 例外は握り潰さず、必ずスタックトレース付きでログに残す
- 並行作業（#245・#249）と衝突しにくいよう、メッセージ送信サービスの変更は保存処理の例外処理に限定する

## スコープ外

- LLM 呼び出し自体の失敗時の error イベントの文言（現状どおり例外メッセージを返す。移植元も同じ）
- イベントの送信順序の違い（移植元は保存の後に message_stop を送るが、こちらは message_stop の後に保存する。#220 の設計のまま変えない）
- 汎用チャット API でライブラリを保存するかどうか（調査の結果、移植元の最新版の汎用チャットはライブラリを保存しない（「local-server が登録するため二重登録になる」とのコメントあり）が、本 Issue の範囲外のため変更しない。必要なら別 Issue で扱う）

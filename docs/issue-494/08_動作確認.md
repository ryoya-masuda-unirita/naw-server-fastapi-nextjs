# 08_動作確認

実際に実行して確かめたことだけを書く。確かめていないことは「未確認」に分ける。

## 環境

- 移植元: Apache POI 5.5.1・PDFBox 3.0.7（`~/.m2` の jar。`spring-ai 1.1.7` → Tika 3.3.0 が引くもの）。各プロセッサのテキスト抽出の部分を写した `docs/issue-494/comparison/Extract.java` を Java 21 で実行
- 移植先: `generative-ai-core` のプロセッサ（`DISABLED` モード）
- サンプル: `docs/issue-494/comparison/` のスクリプトで作った 7 ファイル（Word 1・Excel 1・PowerPoint 1・PDF 4。日本語・表・結合セル・日付・数式・変更履歴・改行・2 段組みを含む）。実行時のタイムゾーンは JST

## 比較結果（修正前 → 修正後）

| ファイル | 修正前 | 修正後 | 差の中身 |
|---|---|---|---|
| Excel | 一致 | 一致 | 数値・日付・真偽・数式・結合セル・複数シートが同じ |
| Word | 差あり | 一致 | 変更履歴の挿入（`w:ins`）とコンテンツコントロール（`w:sdt`）の文字が、移植先で抜けていた |
| PowerPoint | 差あり | 一致 | 段落内の改行が、移植先では垂直タブ（`\x0b`）、移植元は `\n` |
| PDF（Chromium、日本語・表・2 段組み） | 差あり | 一致 | pypdf は、「方」「長」「行」「文」「目」を康熙部首（U+2F45 など）で返し、「第 1 条」のように文字の間に空白を入れていた |
| PDF（reportlab、日本語・表） | 差あり | 空白の数だけ差 | pypdf は、表の 1 行を 1 セルずつの行に分けていた |
| PDF（英語） | 一致 | 空白の数だけ差 | 修正後は、連続する半角空白が 1 つになる（下記） |
| PDF（空のページ） | 一致 | 一致 | |

- 差のあったものは、実害のある順に、PDF の康熙部首（検索・埋め込みで本来の文字と一致しない）、PDF の表の行の分かれ方、Word の抜け、PowerPoint の改行だった。
- 修正後も残る PDF の差は、**連続する半角空白が 1 つになる**ことだけ（PDFBox は `Col1      Col2` のまま、PDFium は `Col1 Col2`）。分割・埋め込みへの影響は小さいと見て、揃えていない。表の列の位置合わせに空白を使う PDF では、情報が減る。

## 未確認

- 比較は、こちらで作ったサンプル 7 ファイルだけ。実際のお客様の文書（スキャンした PDF、縦書き、フォントの埋め込みがない PDF、大きな PDF など）では、差が出る可能性がある
- PDF の抽出を pypdf から pypdfium2 にしたため、処理時間・メモリ・スレッドをまたいだ呼び出し（PDFium は並行実行に制限がある）の確認はしていない
- Word の本文のほか、表の中・テキストボックス・脚注・ヘッダー・フッターの文字は、移植元と同じ範囲（本文の段落だけ）で、サンプルでも一致した。それ以上の違いは未確認
- 移植元の Java は、`secuaigent-ref` をビルドせず、抽出部分を写して実行した。移植元のプロセッサ本体を通した結果とは、ファイル形式の判定やエラーの扱いが違う可能性がある
- PowerPoint の表・グループ内の文字は、移植元・移植先とも取り出さない（同じ）

# 02_基本設計

## 配置方針

Playwrightは`frontend-angular/`配下に導入する（`e2e/`独立ディレクトリではなく）。

理由：
- テスト対象はfrontend-angularの画面操作が中心
- `frontend-angular/package.json`に`test:e2e`スクリプトとして追加すれば、既存の`npm test`（vitest、単体テスト）と役割を分けたまま同一プロジェクト内で管理できる
- 独立ディレクトリにすると、frontend-angularの依存関係（型定義等）を別途参照する必要が生じ、モノレポ内で二重管理になる

```
frontend-angular/
├── e2e/                      # Playwrightのテストコード（新規）
│   ├── fixtures/
│   │   └── auth.fixture.ts   # ログイン共通化fixture
│   ├── login.spec.ts         # 03_ログイン.md 対応
│   └── README.md             # 実行手順
├── playwright.config.ts      # 新規
└── package.json              # devDependenciesにplaywrightを追加、scriptsにtest:e2eを追加
```

## テナント解決の方法

`tenant.helpers.ts`の`resolveTenantId()`は`window.location.hostname.split('.')`の先頭ラベルをテナントIDとして使う。ブラウザは`*.localhost`を自動でループバック解決するため、`http://test-tenant.localhost:4201`にアクセスするだけでホスト名が`test-tenant.localhost`（2ラベル）となり、テナントが正しく解決される。`environment.local.ts`のコメントにも同じ運用（`http://test-tenant.localhost:4201`でアクセスする）が明記されている。

**採用方針：`playwright.config.ts`の`baseURL`を`http://test-tenant.localhost:4201`にする**

```ts
// playwright.config.ts
export default defineConfig({
  use: {
    baseURL: 'http://test-tenant.localhost:4201',
  },
});
```

`sessionStorage`への注入やログインキー経由の回避は不要。実装済みの解決ロジックにそのまま乗るため、追加のfixtureコードなしでテナントが解決される。

## ログイン共通化（fixture設計）

Playwrightの[カスタムfixture](https://playwright.dev/docs/test-fixtures)として、認証済み状態を提供する`authenticatedPage`を用意する。

```ts
// e2e/fixtures/auth.fixture.ts
export const test = base.extend<{ authenticatedPage: Page }>({
  authenticatedPage: async ({ page }, use) => {
    await page.goto('/auth/login');
    await page.getByPlaceholder(/* ユーザーID placeholder */).fill('user01');
    await page.getByPlaceholder(/* パスワード placeholder */).fill('user01@1234');
    await page.getByRole('button', { name: /ログイン/ }).click();
    await page.waitForURL(/* ダッシュボード等 */);
    await use(page);
  },
});
```

- `baseURL`が`http://test-tenant.localhost:4201`のため、`page.goto('/auth/login')`は自動的に正しいテナントのホストでアクセスされる
- ログイン画面自体をテストする`03_ログイン.md`のテストも、素の`page`のまま（`baseURL`が効くため）ログイン操作を検証する
- 他カテゴリ（後続Issue）はこの`authenticatedPage`を使い、ログイン操作を毎回書かずに済む

## セレクタ戦略

`data-testid`が存在しないため、以下の優先順位でセレクタを構築する。

1. `getByRole`（アクセシビリティツリーベース、i18n変更に強い）
2. `getByPlaceholder`（i18nキーに依存するため、翻訳ファイルの変更に弱い点は許容する）
3. `getByLabel` / `getByText`

将来的に`data-testid`をログインフォームに追加する改善は、本Issueのスコープ外とし、必要になった時点で別Issue化する。

## テストデータ方針

- 既存の`backend/seed.sql`のユーザー（`admin`/`user01`/`user02`）で自動化できる項目を優先する
- 初回ログイン・パスワード期限切れのテスト項目（項番10・11）は、`seed.sql`に該当ユーザーを追加して対応する（既存ユーザーへの影響がないよう`ON CONFLICT DO NOTHING`で追記）
- ログイン試行回数上限（項番8）等、状態変化を伴うテストは、他のテストに影響しないよう専用ユーザーを用意する

## ローカル実行構成

```bash
# 1. DB/Redis/backendを起動
docker compose up -d

# 2. マイグレーション・シード投入（初回のみ、または更新時）
cd backend && alembic upgrade head
docker exec -i naw-fastapi-postgres psql -U root -d postgres < backend/seed.sql

# 3. frontend-angularを起動（モック無効、backend接続）
cd frontend-angular && npm run start:local

# 4. Playwright実行
cd frontend-angular && npx playwright test
```

`playwright.config.ts`の`baseURL`は`http://test-tenant.localhost:4201`固定とする（CI組み込みは本Issueのスコープ外のため、`webServer`による自動起動は行わず、手動起動を前提とする）。

## レポート・失敗時の証跡

- Playwright標準のHTMLレポーター（`playwright.config.ts`の`reporter: 'html'`）を使用
- 失敗時のスクリーンショット・トレースを自動保存（`screenshot: 'only-on-failure'`, `trace: 'on-first-retry'`）
- レポート出力先（`playwright-report/`, `test-results/`）は`.gitignore`に追加する

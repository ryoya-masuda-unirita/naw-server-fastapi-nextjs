# 01_要件定義

## 背景

`25DA61_結合テスト項目書_md/` に格納された旧システム（Spring Boot + Angular）の手動結合テスト項目書（全20カテゴリ、616〜627項目）を、ローカル環境（`frontend-angular` http://test-tenant.localhost:4201 + `backend` http://localhost:8001）で全自動実行できるE2Eテストとして整備する。

本Issueは基盤構築のみを対象とし、`03_ログイン.md`を試験実装の対象カテゴリとする。残り19カテゴリは後続Issueで対応する。

## 事前調査で判明した制約

- **テナント解決**：`frontend-angular`はhostnameのサブドメインからテナントIDを解決する（`tenant.helpers.ts`の`resolveTenantId()`。`window.location.hostname.split('.')`の先頭ラベルを使う）。ブラウザは`*.localhost`を自動でループバック解決するため、`http://test-tenant.localhost:4201`にアクセスすればホスト名が`test-tenant.localhost`（2ラベル）となり、追加の注入なしにテナントが正しく解決される。E2Eの`baseURL`はこの形式にする（`environment.local.ts`のコメントにも同じ運用が明記されている）
- **DOM特定手段**：ログインフォームに`data-testid`属性が存在しない。`placeholder`（i18nキー）・`autocomplete`属性・ボタンのテキスト内容でセレクタを構築する
- **認証状態の保持**：Cookie（`session_id`、HttpOnly）が実体。表示用に`sessionStorage['user']`も使われる。Playwrightの`storageState`は`localStorage`のみを対象とし`sessionStorage`は対象外のため、認証状態を再利用する場合は`cookies`の保存＋`addInitScript`での`sessionStorage`再注入を組み合わせる
- **既存シードユーザー**：`backend/seed.sql`に`admin`/`user01`/`user02`（すべて`is_required_password_reset=false`）が存在する。初回ログイン・パスワード期限切れユーザーは存在せず、該当テスト項目（`03_ログイン.md`の項番10・11）を自動化するにはseedへのユーザー追加が必要
- **ログインキー機能**：`?loginkey=xxx&tenantId=yyy`によるログインは実装済み（`login-key.initializer.ts`、`backend/app/routers/auth.py`の`/auth/login-key`）。テナントはURLで解決できるため、本Issueでは主にログインキー自体のテスト項目（項番20〜23）で使う

## スコープ

### 対象

- Playwrightの導入・実行環境構築
- ログイン共通化（fixture/ヘルパー）
- `03_ログイン.md`のうち自動化可能な項目の実装
- 失敗時のスクリーンショット等のレポート整備
- 実行手順のドキュメント化

### 対象外

- `04_ログアウト.md`〜`22_Waha!生成AI検索.md`の実装（後続Issueで対応）
- CI（GitHub Actions）への組み込み
- `03_ログイン.md`のうち、seedデータの追加なしには自動化できない項目（初回ログイン・パスワード期限切れ）は、seed追加を含めて本Issueで対応するか、後続Issueに送るかを基本設計で判断する

## 完了条件

- `frontend-angular/`（または独立ディレクトリ）にPlaywrightが導入され、`npx playwright test`等のコマンドでローカル環境に対して実行できる
- ログイン処理が共通のfixture/ヘルパーとして再利用可能な形になっている
- `03_ログイン.md`の自動化対象項目が実際にパスすることを確認する
- 実行手順・設計方針が`docs/issue-163/`にまとめられている

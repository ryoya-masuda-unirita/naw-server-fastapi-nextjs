# 画面操作を再帰的にたどってバグの疑いを検出するE2E探索ハーネスを作る

## 概要

このリポジトリのアプリ（React の `frontend/` + FastAPI の `backend/`）を対象に、E2E（ブラウザ操作）を基準として画面の操作を再帰的にたどり、バグと思われる箇所を自動であぶり出すハーネスを、新しいモジュールとして作る。

移植元にこの種のハーネスはない（2026-11-13 に移植元のスキル・ブランチを確認済み）。このリポジトリ独自の仕組み。

## 説明

### 作るもの

新しいモジュール `e2e-explorer/`。Playwright（TypeScript）で作る。

1. 巡回役（クローラー）
   - ログインしてから、画面にあるリンク・ボタン・入力欄・選択肢などの操作できる要素を洗い出し、1 つずつ操作して次の状態へ進む、を再帰的に繰り返す
   - 同じ状態（URL と画面の構造から作るキー）は二度たどらない。深さ・操作回数・時間に上限を付け、設定で変えられるようにする
   - 入力欄には境界値・異常値（空、最大文字数、最大+1、記号、絵文字、負の数、長い文字列など）を入れて送信する
   - 権限ごと（seed にあるユーザー）に巡回できるようにする
   - 同じ設定・同じ乱数の種なら、同じ順で巡回する
2. 判定役（オラクル）
   - API の 500 番台、想定外の 4xx（区別して出す）
   - コンソールのエラー、未処理の例外・Promise の reject
   - 真っ白な画面、操作しても何も起きない、エラー表示から戻れない
   - 表示崩れ（横スクロール・要素のはみ出し）、アクセシビリティの違反（axe）
   - 応答が極端に遅い（しきい値は設定）
3. レポート
   - 疑いごとに、再現手順・スクリーンショット・通信の記録（HAR または trace）・症状を出す
   - 同じ症状・同じ場所のものはまとめる
   - 人が読める形（Markdown または HTML）と機械が読める形（JSON）の両方で出す
4. 仕分け（Claude）: レポートを読み、本当にバグかをコードに照らして判断し、Issue の文案を作るスキル（起票は人が判断）
5. 実行環境: モジュールの docker compose で、専用の PostgreSQL・Redis・backend・frontend を既存と衝突しないポートで起動し、`backend/seed.sql` を入れてから巡回し、終わったら破棄する。dev や本番には向けない

### 追加要件（2026-11-13、コーディネーター経由・ユーザー承認済み）

巡回を並列で効率よく行えるようにする。

1. 並列のワーカーは同じ調査をしない。担当を「画面のまとまり（起点の URL・ルートのグループ）× 権限」で分け、重ならない担当範囲を割り当てる。担当外の画面へ遷移したら掘らずに戻る（担当外として記録だけする）
2. ヘッダー・ナビゲーションのような全画面に共通の要素は、全ワーカーで共有する「調査済みの一覧」（ファイルのロック付き、または専用環境の Redis など）に記録し、誰かが調べたものは他のワーカーが飛ばす
3. ワーカーどうしがデータを壊し合わないよう、ワーカーごとに専用のテナント（とそのユーザー）を用意して巡回する。DB はワーカー間で共有でよい
4. 並列数は設定で変えられるようにし、既定は手元のマシンで無理のない数（例: 4）。レポートはワーカーごとの結果を最後に 1 つにまとめ、重複をまとめる
5. 担当範囲の分け方は設定ファイルで見られ・変えられるようにし、README に書く
6. 各担当範囲を 1 コマンドで単独実行できる（例: `--shard users-admin`）。後で Claude のサブエージェント（探索・検証・まとめ）で分担する Issue の土台にする

- 専用環境で 1 コマンドで巡回 → レポート生成まで動く
- 実際に今の `frontend/` を巡回し、レポートが出る（疑いが 0 件でもよい。出た疑いは、この Issue では直さずに一覧を PR に載せる）

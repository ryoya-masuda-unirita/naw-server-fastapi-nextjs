# 02_基本設計

## 変更対象

| 対象 | 内容 |
|---|---|
| 新モジュール（E2E 探索ハーネス） | 巡回役・判定役・レポート・並列実行・専用環境の起動を持つ Node.js（TypeScript）のモジュール。Playwright でブラウザを動かす |
| Claude Code のスキル（仕分け） | レポートを読んでバグかどうかを判断し Issue の文案を作る手順 |

## 画面 / API 変更概要

画面・API の変更はない。

## 全体の流れ

```
1 コマンド（run）
  ├─ 専用環境の起動（別名・別ポートの PostgreSQL / Redis / backend / frontend）
  │    └─ マイグレーション → seed 投入 → 担当範囲ごとのテナント作成
  ├─ 担当範囲（シャード）を並列数ぶんのワーカーで巡回
  │    ├─ ワーカーは担当範囲の待ち行列から 1 つずつ取って巡回する
  │    ├─ 担当範囲ごとに専用テナントのユーザーでログイン（ログイン画面を通す）
  │    ├─ 巡回役が状態をたどり、判定役が操作ごとに疑いを記録する
  │    ├─ 共通領域の操作は「調査済みの一覧」（ファイルロック）で取り合う
  │    └─ 担当範囲ごとのレポート（JSON）を出す
  ├─ 担当範囲ごとのレポートを 1 つにまとめる（重複をまとめる）→ JSON / Markdown / HTML
  └─ 専用環境の破棄（データごと）
```

単独実行（`--shard <ID>`）では、指定した担当範囲だけを巡回する。環境を起動したまま（`env:up` → `explore --shard ...` を複数回 → `merge` → `env:down`）でも使える。

## 巡回の方式

- 状態に戻る方法として「起点から操作の列を再生する」方式をとる。SPA は前の状態に戻す一般的な方法がないため、操作のたびに新しいタブで起点を開き、そこまでの操作を再生してから次の操作をする。再生の手順がそのまま再現手順になる
- 探索は幅優先。待ち行列の順番と、1 つの状態の中での操作の順番は、乱数の種と状態のキーから決める（同じ種なら同じ順）
- 操作の単位
  - クリック（リンク・ボタン・役割がボタン/リンク/タブ/メニュー項目などの要素）
  - フォームへの入力と送信（フォーム内の入力欄すべてに同じ種類の値を入れて送信する。種類ごとに 1 操作。種類を混ぜた 1 操作も加える）
  - フォーム外の入力欄への入力と Enter
  - 選択肢の選択・チェックボックスの切り替え
- 要素は「タグ・役割・名前（aria-label・ラベル・文字など）・種類・共通領域」からなる署名と、同じ署名の中での順番で識別し、再生のたびに探し直す。見つからなければ「再生できなかった操作」として記録する（疑いではない）
- 状態のキーは、URL のパス（UUID・数字を `:id` に置き換える）と、操作できる要素の署名の集合のハッシュ。文言の数字などが変わっても同じ状態とみなす
- 担当範囲外の URL に遷移した操作は、その先を掘らずに「担当外」として記録する

## 判定の方式

| 判定 | 方法 |
|---|---|
| HTTP の異常 | ブラウザの通信を監視し、API への応答の状態コードを見る。4xx は設定で想定内とした組み合わせ（メソッド・パス・状態コード・異常値の送信直後かどうか）を除く |
| 通信の失敗 | 通信の失敗のイベント（中断は除く） |
| コンソール・例外 | コンソールの `error`、ページの未処理の例外、`unhandledrejection` |
| 真っ白 | 本文の文字がなく、画像・図形もない |
| 何も起きない | 操作の前後で、画面の変化（DOM の変更）・URL・通信・ダイアログ・新しいタブのどれもない。ブラウザの入力チェックで送信が止まった場合は除く |
| 戻れない | 操作できる要素が 1 つもない（エラー表示の有無を併記） |
| 表示崩れ | 設定した画面幅ごとに、横スクロール・右端からのはみ出し（はみ出しを隠す親がない要素）・枠からの文字のはみ出しを見る |
| アクセシビリティ | axe を状態ごとに 1 回実行する |
| 遅い | API ごとの応答時間、操作から落ち着くまでの時間をしきい値と比べる |

状態ごとの判定（表示崩れ・axe・真っ白）は、初めてその状態に来たときだけ行う。

## 担当範囲（シャード）

- 設定ファイルに「画面のまとまり」（ID・説明・起点の URL・範囲内とみなす URL のパターン・巡回する権限）を並べる。担当範囲の ID は `<まとまりの ID>-<権限>`
- `frontend/` の全画面のルート（`routes/index.tsx`。多くは「未移植」の仮画面）に合わせた既定の分け方（9 つのまとまり × 権限 = 15 の担当範囲）

| まとまり | 起点 | 権限 |
|---|---|---|
| `auth`（ログイン） | `/auth/login` | 未ログイン |
| `account`（パスワード再設定 `/auth/password/reset`） | 同左 | 未ログイン・管理者・一般 |
| `chat`（ダッシュボード・チャット・共有履歴・フィードバックのプレビュー。サイドバーもここで調べる） | `/dashboard` | 管理者・一般 |
| `library` | `/library` | 管理者・一般 |
| `legacy-admin`（`/users`・`/reports`・`/settings`） | `/users` | 管理者・一般 |
| `admin-people`（`/admin/users`・`/admin/groups`） | `/admin/users` | 管理者・一般（権限ガードの確認を兼ねる） |
| `admin-assistants`（アシスタント・テンプレート・学習データ） | `/admin/assistants` | 管理者 |
| `admin-history`（チャット履歴・フィードバック） | `/admin/chat-history` | 管理者 |
| `admin-tenant`（テナント設定・ホーム） | `/admin/tenant` | 管理者 |

- 画面が移植されたら、まとまりを足す（例: ユーザー管理なら `users` を足すと `users-admin` などができる）

## 調査済みの一覧（共通領域）

- 設定した共通領域（既定: `aside`・`header`・`nav`・`[role=navigation]`）の中の要素への操作は、「共通領域・要素の署名・操作」から作るキーで、出力先のファイルを取り合う。最初に取ったワーカーだけが操作し、他は飛ばして統計に数える
- 取り合いはロック用のディレクトリを作れたかどうかで排他する（同じマシンの別プロセスでも働く）
- 権限ごとに分けるか（既定: 分けない）は設定で変えられる

## 未移植の仮画面

- 移植が終わっていない画面は「未移植: 〇〇（#番号）」と出す仮画面。設定 `oracle.placeholderMarkers` の文字列が画面に含まれていたら仮画面として扱い、「何も起きない」「操作できる要素がない」・文字のはみ出しは疑いにしない
- 仮画面の表示崩れ・axe は、画面ごとに同じ枠が出るだけなので場所を `[未移植の仮画面]` に 1 つにまとめる。API のエラー・コンソールのエラー・例外は疑いにする
- 仮画面に着いた状態の数を担当範囲の統計（`placeholderStates`）に残す

## 専用テナント

- 担当範囲ごとに、テナント `e2e-<担当範囲の ID>`（32 文字を超えるときは短いハッシュ）を、seed のテナント（`test-tenant`）の設定を写して作る
- ユーザーは、権限の設定にある seed のユーザー（`admin`・`user01`）を、同じログイン ID・パスワードで写す
- 担当範囲ごとにテナントを分けるため、ワーカーの数や担当範囲の割り当てが変わっても、単独で実行しても、他の担当範囲のデータは壊れない（ワーカーごとに分けるより強い分離）
- テナントの中のデータ（アシスタント・グループなど）は写さない。データが要る画面の巡回は、写す範囲を広げる別 Issue で扱う

## 専用環境

- compose のプロジェクト名・コンテナ名・ポートを既存と分ける（ホストの `127.0.0.1` の 55432 / 56379 / 58000 / 55173）
- データは tmpfs に置き、破棄で消える
- backend は既存の本番用 Dockerfile でイメージを作る。frontend は今のソースから Vite の開発サーバーで動かす（React の開発時の警告もコンソールのエラーとして拾えるため）

## 安全策

- 対象のホストがローカル（`localhost`・`127.0.0.1`・`::1`）以外なら、明示の引数がない限り巡回を始めない
- 既定の設定は専用環境のポートだけを向く

## 影響範囲

- 既存のアプリのコード・テスト・CI には影響しない
- 既存のローカル環境（`docker-compose.yml` のコンテナ・ポート）には触れない

## 移植方針

移植元にこの仕組みはないため、移植ではない。移植元の E2E テスト（Playwright）の構成（設定・ログインの手順・ページ単位の整理）を参考にする。

# 01_要件定義

## 背景

- このリポジトリは、企業向け AI チャット管理 SaaS「SecuAiGent」を Spring Boot + Angular から FastAPI + React へ移植するプロジェクトである。画面は移植の途中で、移植済みの画面が日々増える
- 画面ごとの自動テスト（単体テスト・結合テスト）は、書いた人が想定した操作しか確かめない。想定外の操作の組み合わせ・異常な入力・権限の違いで起きる不具合（サーバーの 500、画面の例外、表示崩れなど）は、人が触るまで見つからない
- 移植元にも、画面を自動で巡回して不具合の疑いを探す仕組みはない。このリポジトリ独自に作る
- 巡回では削除・権限変更などの破壊的な操作も実行するため、開発者の手元環境や dev 環境とは切り離した使い捨ての環境で動かす必要がある
- 画面が増えると 1 本の巡回では時間がかかるため、並列で分担して巡回できる必要がある。後で Claude のサブエージェント（探索・検証・まとめ）に分担させる前提の土台にもする

## 機能要件

### 巡回

| No | 要件 |
|---|---|
| R1 | 起点の画面から、操作できる要素（リンク・ボタン・入力欄・選択肢・チェックボックスなど）を洗い出し、1 つずつ操作して次の状態へ進むことを再帰的に繰り返す |
| R2 | 状態は「正規化した URL」と「操作できる要素の構造」から作るキーで識別し、同じ状態は二度たどらない |
| R3 | 深さ・操作回数・1 状態あたりの操作数・時間に上限を付け、設定とコマンドの引数で変えられる |
| R4 | 入力欄には境界値・異常値（空、空白、最大文字数、最大+1、記号、HTML 断片、絵文字、負の数、長い文字列、種から決まる混合）を入れて送信する |
| R5 | 権限（seed のユーザー: テナント管理者 `ADMIN`・一般ユーザー `USER`、未ログイン）ごとに巡回できる。ログインは React のログイン画面（テナント ID 入力あり）を通す |
| R6 | 同じ設定・同じ乱数の種・同じデータなら、同じ順で巡回する |
| R7 | 確認ダイアログ（`confirm` など）は設定に従って承認または取り消しする |
| R8 | 別オリジンへのリンク・新しいタブを開くリンク・設定で除外した要素は操作しない |

### 判定

| No | 症状 | 扱い |
|---|---|---|
| O1 | API が 500 番台を返す | 重大度「高」 |
| O2 | API が 4xx を返す（設定で想定内とした応答を除く） | 500 番台と区別して「中」 |
| O3 | 通信自体の失敗（CORS・接続拒否など） | 「中」 |
| O4 | ブラウザのコンソールのエラー | 「中」 |
| O5 | 画面側の未処理の例外・Promise の reject | 「高」 |
| O6 | 画面が真っ白になる | 「高」 |
| O7 | 操作しても何も起きない（画面の変化・遷移・通信・ダイアログのどれもない） | 「低」 |
| O8 | 操作できる要素が 1 つもない画面に行き着く（エラー表示から戻れない） | 「中」 |
| O9 | 横スクロールが出る・要素が画面の右端からはみ出す・文字が枠からはみ出す（設定した画面幅ごと） | 「低」 |
| O10 | アクセシビリティの違反（axe。既定は重大度 critical・serious） | 「中」 |
| O11 | API の応答・操作後の落ち着くまでの時間がしきい値を超える | 「低」 |

### レポート

| No | 要件 |
|---|---|
| P1 | 疑いごとに、再現手順（権限・テナント・起点の画面から、どの要素に何をしたかの列）・スクリーンショット・Playwright の trace（通信の記録を含む）・症状を出す |
| P2 | 同じ症状・同じ場所のもの（症状の種類・場所・正規化したメッセージが同じもの）は 1 件にまとめ、発生回数・発生した担当範囲・権限を併記する |
| P3 | 一覧を Markdown・HTML（人が読む）と JSON（機械が読む）で出す |
| P4 | 担当範囲ごとの結果を最後に 1 つにまとめ、重複をまとめる。別々に実行した担当範囲の結果を後からまとめるコマンドもある |
| P5 | 巡回の統計（状態数・操作数・担当外への遷移・共有で飛ばした操作・再生できなかった操作）も出す |

### 並列・担当範囲

| No | 要件 |
|---|---|
| S1 | 担当範囲（シャード）を「画面のまとまり（起点の URL と、範囲内とみなす URL のパターン）× 権限」で定義する。定義は設定ファイルで見られ・変えられる |
| S2 | 各担当範囲は重ならない。巡回中に範囲外の URL へ遷移したら、そこは掘らずに「担当外」として記録だけする |
| S3 | 全画面に共通の要素（設定した領域。既定はサイドバー・ヘッダー・ナビゲーション）の操作は、全ワーカーで共有する「調査済みの一覧」（ファイルロック付き）に記録し、誰かが調べたものは他のワーカーが飛ばす。別々のプロセスで担当範囲を実行しても、同じ出力先を指定すれば一覧を共有できる |
| S4 | 担当範囲ごとに専用のテナントとユーザー（seed のユーザーを写したもの）を用意し、ワーカーどうしがデータを壊し合わないようにする。DB は共有する |
| S5 | 並列数は設定と引数で変えられる。既定は 4 |
| S6 | 担当範囲を 1 コマンドで単独実行できる（`--shard <ID>`。複数指定可） |

### 実行環境

| No | 要件 |
|---|---|
| E1 | モジュールの docker compose で、専用の PostgreSQL・Redis・backend・frontend を、既存のローカル環境（`naw-fastapi-*`・`naw-postgres` など）と名前・ポートが衝突しない形で起動する |
| E2 | 起動時に alembic でマイグレーションし、`backend/seed.sql` を入れ、担当範囲ごとのテナントを作る |
| E3 | 1 コマンドで「環境の起動 → 巡回 → レポート → 環境の破棄」まで行う。破棄はデータごと行う |
| E4 | 対象の URL は設定で変えられるが、既定は専用環境だけ。ローカル以外のホストは明示の引数がない限り拒否する |

### 仕分け

| No | 要件 |
|---|---|
| T1 | Claude Code のスキルとして、レポートを読み、コードに照らして本当にバグか（仕様どおりか、移植途中で未実装なだけか）を判断し、Issue の文案を作る手順を用意する。起票は人が判断する。起票先は `ryoya-masuda-unirita/naw-server-fastapi-nextjs` と明記する |

### 文書

| No | 要件 |
|---|---|
| D1 | モジュールの README の冒頭で、このリポジトリが何のプロジェクトか、このハーネスが何のためにあり、何を見つけられて何を見つけられないかを、初めて読む人に分かるように書く |
| D2 | README に仕組み・実行方法・設定・担当範囲の分け方・レポートの読み方・仕分けの手順を書く |
| D3 | ルートの README と CLAUDE.md のモノレポ構成にモジュールを追記する |

## 非機能要件

- lint・型チェック・単体テストのコマンドを用意し、すべて通る
- 判定役・巡回役の単体テストは、小さなテスト用ページ（Playwright の route で作る）で行い、専用環境を必要としない
- 既存のローカルのコンテナ・起動中のサーバーには触れない
- 依存パッケージのバージョンは固定する

## スコープ外

- 移植元（Angular + Spring）との比較
- 見つかったバグの修正（別 Issue）
- CI での定期実行（別 Issue）
- Claude のサブエージェントでの分担（別 Issue。この Issue はその土台まで）
- seed にない権限（`SYSTEM`）での巡回

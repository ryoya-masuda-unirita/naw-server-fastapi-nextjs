# 02_基本設計

## 変更対象

1. **リポジトリ（8 か所）**: 各一覧のクエリの `ORDER BY` の最後に、一意キーの昇順を足す。既存の並べ替え（列・向き）は、そのまま
   - 並べ替えが「列と向き」の組で決まる一覧は、その並びのあとに、一意キーの昇順を足す
   - 共通部品 `build_order_by(tie_breaker=...)` を使う一覧は、すでにある（対象外）。今回の 8 か所は、列を直接指定しているので、`ORDER BY` に 1 つ足す
2. **テスト**: 8 か所それぞれについて、同じ値の行がページ境界をまたぐデータで、ページをめくって重複・漏れがないことを確かめる

## 画面 / API 変更概要

- API の入出力は変えない。同じ値の行の返す順序が、決まる（以前は不定）。項目・形式・総件数・権限・ステータスコードは変えない
- 画面側（`client/`）の変更はない

## 影響範囲

- **一覧の返す順序**: 並べ替えのキーが異なる行どうしの順序は変わらない。同じ値の行どうしだけ、`id` の昇順に決まる。これまで、DB の返す順（実質、挿入順に近いが、保証はない）だった行の並びが、`id`（ランダムな UUID の文字列）の昇順に変わりうる。見た目の並びが変わって見える場合があるが、これは、同じ値の行の、以前は不定だった順序が、決まるだけ（作成順ではない）
- **既存のテスト**: 同じ値の行の順序に依存しているテストがあれば、影響を受ける（確認する）
- **性能**: `ORDER BY` に、主キーの列を 1 つ足すだけ。主キーには索引がある。影響は小さい見込み（計測はしない）
- **データベース**: SQLite・PostgreSQL の両方で動く
- **費用・インフラ**: なし
- **デプロイ**: `server/` を変更するので、マージすると、`Deploy` の `backend` ジョブが動く（通常のパイプライン）。AWS のロール（Secret `AWS_ROLE_ARN`）は、旧アカウントの環境を指していると見ており、マイグレーションの起動方法を Fargate 向けにした #384 のため、旧環境（EC2）に対しては、`Run DB migration task` で止まる（サービスの更新までは進まない）と推測しているが、確認していない

## 移植方針

- 移植元（`PageableSortUtil.withIdTieBreaker`、`Sort.by(...).and(Sort.by(ASC, "id"))` など）と同じく、最後のキーは、指定された並べ替えの向きにかかわらず、**昇順**
  - 共通部品 `build_order_by` の既定は、先頭の並べ替えと同じ向き（降順なら降順）。今回の 8 か所は、列を直接指定していて、`build_order_by` を使っていないので、移植元と同じ昇順にする
- フィードバック（ユーザー）は、移植元が `user_id` を足す（集計クエリで、ユーザーごとに 1 行になる列）。同じ列を、集計の副問い合わせ（CTE）の `user_id` で足す
- 移植元の変更のうち、`GroupService`・`FileService`・`IndexService`・`AssistantService` などは、移植済み

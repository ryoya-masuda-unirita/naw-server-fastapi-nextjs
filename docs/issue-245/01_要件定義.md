# 01_要件定義

## 背景

メッセージ送信 API は、過去の発話に付いていた添付ファイルの件数（履歴の各発話の添付件数の合計）と、履歴添付ファイルとして送られたファイルの件数が一致しないと 400 を返している。移植元ではこのチェックは定義だけされていて実行時には評価されず、さらに移植元のクライアントは履歴添付ファイルを送らない。そのため、画像を添付して送ったあとに同じルームで続けて送ると、移植先だけがエラーになる。

また、移植先は質問本文（userInput）に 1 文字以上を要求しているが、移植元は「項目があること（null でないこと）」だけを要求し、空文字を受け付ける。移植元のクライアントは本文が空でも添付ファイルがあれば送信できる。

### 移植元の確認結果

- リクエスト（textData）の受け取りクラスには、本文・履歴に関する制約がない
- Controller はリクエストから ViewModel を組み立てるだけで、Controller 側では ViewModel を検証しない
- ただし Service クラスには `@Validated` が付いており、コンテキスト解決メソッドの引数（ViewModel）に `@Valid` があるため、メソッドバリデーションは掛かる。このとき評価されるのは jakarta の制約（本文の `@NotNull`、アシスタントIDの `@NotEmpty` など）だけで、`javax.validation.constraints.AssertTrue` を付けた履歴添付件数のチェックは、実行時のバリデータ（spring-boot-starter-validation = Hibernate Validator、jakarta 名前空間）が認識しないため評価されない
- よって移植元の実際の挙動は「本文が null（項目なし）のときだけ 400、空文字は通る」「履歴添付件数が合わなくても通る」
- 空文字の本文は、そのまま LLM へのユーザー発話の本文（添付があれば画像と一緒）として送られ、質問文として保存される

Issue 本文の「ViewModel は `@Valid` なし」は Controller 側の話で、Service 側のメソッドバリデーションは効いている。ただし効くのは jakarta の制約だけなので、Issue の結論（件数チェックは効かない・空文字は通る）は変わらない。

## 機能要件

1. 履歴添付ファイルの件数が、履歴の添付件数の合計と一致しなくても、メッセージ送信を受け付ける（200 でストリーミング応答する）
2. 質問本文が空文字でもメッセージ送信を受け付ける
3. 質問本文の項目そのものがない場合は、これまでどおり 400 にする（移植元の `@NotNull` 相当）
4. 質問本文が空文字のとき、後続処理（LLM への送信・質問と回答の保存）が壊れない
   - 添付ファイルがある場合、LLM へは空の本文と添付ファイル（画像）を最後のユーザー発話として送る
   - 質問文は空文字のまま保存し、回答も保存される

## 非機能要件

- 既存の送信・再生成・添付ファイル送信の挙動を変えない

## スコープ外

- 履歴添付ファイルの内容を LLM に送ること（移植元も送らない。従来どおり受け取るだけ）
- 履歴の各発話の添付件数の値の制約（0 以上）の見直し
- React（frontend）のチャット履歴送信の移植

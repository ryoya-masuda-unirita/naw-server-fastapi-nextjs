# 02_基本設計

## 変更対象

- 新規ルーター: テナント本体の情報取得・部分更新（`tenant_endpoints.py`とは別ファイル）
- 新規サービス: テナント詳細取得・部分更新のビジネスロジック
- 新規スキーマ: `TenantDetailResponse`とその入れ子（リソース・サブスクリプション・プラン）、PATCHリクエスト
- 新規モデル・マイグレーション: テナントリソース（`TenantResource`相当）。FastAPI側に未移植のため新規追加する
- 既存リポジトリ拡張: テナントの取得に加え、名称・利用ベースクレジット上限の更新を行うメソッドを追加
- 新規リポジトリ: テナントリソースをテナントIDで取得するメソッド

## 画面 / API 変更概要

- `GET /api/admin/tenants`: `X-Tenant-ID`ヘッダーで指定したテナントの詳細情報を返す
- `PATCH /api/admin/tenants/{tenantId}`: テナント名・利用ベースクレジット上限を部分更新し、更新後の詳細情報を返す

## 影響範囲

- 新規追加のみで、既存エンドポイントの挙動は変更しない
- DBスキーマにテナントリソース用テーブルを追加する（既存テーブルへの影響なし）
- `app/main.py`に新規ルーターの登録を追加する

## 移植方針

- Spring Bootの`TenantController#getTenantDetails`/`patchAdminTenant`と`TenantService#getTenantDetailResponse`/`patchAdminTenant`のロジックをFastAPI/Pythonのイディオムで再実装する
- 「キーが送られたかどうか」の判定（Javaの`JsonNode.has()`相当）は、Pydantic v2の`model_fields_set`で表現する。PATCHリクエストのフィールドはすべて`default=None`にし、キーが送られたかどうかは`model_fields_set`の有無で判定し、値が`null`かどうかとは独立に扱う
- 請求期間内利用クレジットの上限チェックは、Issue #73で追加済みの`billing_cycle.py`・`SubscriptionRepository`・`TokenUsageRepository.summarize`をテナントサービス側から直接呼び出して実装する（`credit_usage_service.py`は経由しない）
- `TenantResource`はSpring側にEntityが存在するがFastAPI側は未移植のため、`models/tenant_resource.py`として新規追加し、マイグレーションで`tenant_resources`テーブルを作成する
